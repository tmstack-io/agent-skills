# decruft

指定された範囲のコードコメント・散文から、**成果物そのものには不要な「余計な記述」** を検出し、
確信度つきで dry-run で提示し、**承認された項目のみ**削除する — いきなりは消さない。
削除するのはコメントと散文のみ。

出力（レポート・提案）は、人間が一読で判断できる **正しく分かりやすい日本語** で書く。

**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨する選択肢を理由一言つきで明示し（推奨できる選択肢が無い場合は「推奨なし」とその理由を明示する）、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。

## 引数

- **対象パス（任意・複数可）**: ファイルパス、ディレクトリ、または glob。ディレクトリは再帰的に走査する。指定時はそのパスを対象とする（意図が明確なので対象確認は挟まない）。**リポジトリ全体を黙って走査しない。**
- **引数なし**: セッション生成物 — このセッションで作成・変更されたファイル（リポジトリ内外を問わない）— を候補として列挙し、フェーズ1の対象確認でユーザーが確定する。セッション生成物にはカテゴリ D と TODO 候補化（後述の「セッション生成物への追補」）が加わり、適用後の検証にテスト実行が加わる。

### 走査対象の絞り込み・除外

- `.gitignore` を尊重する（無視対象は走査しない）。
- 既定除外（パス）: `.git/`、`node_modules/`、`vendor/`、ビルド成果物（`dist/`、`build/`、`out/` 等）、バイナリ、各種 lock ファイル。
- **既定除外（文書種別）**: CHANGELOG・HISTORY・リリースノート・マイグレーションガイド・ADR 等、**変更の歴史を語ることが目的の文書**。これらでは B/C 該当の記述が本文そのものであり「余計」ではない。ファイル名と冒頭の見出しから判断し、除外したファイルはレポートの走査範囲に明記する。
- **明示指定の優先**: ファイルを直接指定された場合は、上記の既定除外より指定を優先する（除外はディレクトリ・glob の展開結果にのみ適用する）。

## 全体フロー

```
[1] 対象確定(パス指定はそのまま列挙 / 引数なしはセッション生成物を列挙→ユーザー確認) & git 前提チェック
        │
        ▼
[2] 種まき: grep で B/C の種語をコメント・散文ごと拾い、注意リストを作る
        │
        ▼
[3] 文脈判定: 対象ファイルを全読みし、
    全コメント・散文ブロックを判定 → JSON の候補リスト化
    → 後処理(行範囲の重なり統合・統計)
    (大規模時はサブエージェント並列バッチで加速可)
        │
        ▼
[4] dry-run レポート: 階層化して diff を提示、findings ファイルに永続化
        │
        ▼
[5] 承認 → 適用前の準備(複製・テストのベースライン) → 適用(置換・末尾側から) → 整形 → 検証(構文チェック・複製との diff) → 結果報告
```

最初に TODO リスト（[1]〜[5]）を作ってから着手する。

## フェーズ1: 対象確定 & git 前提チェック

1. 対象を確定する。
   - **パス指定時**: 引数のパスから、除外規則（`.gitignore`＋既定除外）を適用して対象ファイルを列挙し、「対象はこの N ファイル」と提示してから走査する。
   - **引数なし**: 会話履歴中のファイル作成・編集操作（Claude Code では Write / Edit / NotebookEdit）からセッション生成物を列挙する（会話に現れないファイルは加えない）。git リポジトリ内のファイルは `git status --short` と突合し、リポジトリ外（一時領域等）のファイルは「リポジトリ外」と注記して一覧に含める。番号付きの一覧と対象の指定方法を散文提示で確認する。指定方法は定型の選択肢なので一行に畳んでよい —「対象を返信してください: `全件` / 番号指定（例: `1,3`） / パス指定 / `中止`」— 推奨する対象を理由一言つきで添える。列挙が 0 件の場合、または返信から対象を確定できない場合は、対象を質問して回答を待つ（対象が不明確なまま走査を始めない）。
   - 確定した一覧の外のファイルはフェーズ5まで一切変更しない。
2. git 前提を確認する。
   - git リポジトリでなければ、その旨を伝え「適用前のバックアップ」を勧める（中断はしない）。
   - 作業ツリーの対象ファイルに未コミット変更があれば、decruft の変更が混ざる旨を伝え、commit / stash を勧める（中断はしない）。

## フェーズ2: 種まき（grep）

判定基準（後述の転記ブロック）に列挙された B/C の種語を `grep -n` で走査し、`ファイル:行番号:行内容` の一覧（注意リスト）を作る。**セッション生成物を対象とする場合は種語に `TODO`・`FIXME`・`HACK`・`XXX` を加える**（カテゴリ D / TODO 候補化の取りこぼし防止）。

grep の役割は次の 2 つに限る。**grep 結果を判定対象そのものにしてはならない。**

1. ヒット密度によるファイルの優先順位付け（バッチ割り当ての参考）。
2. フェーズ3への「取りこぼし防止の注意リスト」の提供。

理由: カテゴリ A の対象（ツール名・製品名など）は開いた集合で grep では網羅できず、逆に B/C の種語（`added`、`旧` 等）はコード本体の識別子や文字列にも大量にヒットする。よって検出の正体はフェーズ3の全読みであり、grep は補助に徹する。コード本体へのノイズヒットが混ざるのは許容してよい（フェーズ3で捨てられる）。

---

## フェーズ3: 文脈判定（全読み）

対象ファイルを 1 つずつ読み込み、下記「判定基準」（セッション生成物を対象とする場合は「セッション生成物への追補」も続けて適用）を**すべてのコメント・散文ブロック**へ適用し、判定基準末尾のフォーマットに従う JSON 配列として候補を作る。grep ヒット行だけに限定しない。フェーズ2の注意リストは取りこぼし防止用であり、各ヒット行を必ず検討する（候補にしない場合は黙って捨ててよい）。

### 判定後の後処理（実行経路によらず必ず）

- 同一ファイルで行範囲が重なる候補は確信度の高い方に統合する。
- 注意リストのヒット行のうち候補化された行数を数え、レポートの統計に「grep ヒット G 行中 K 行を候補化」として添える（検討漏れの目安として提示するのみで、再判定はしない）。

### 加速オプション: サブエージェント並列バッチ（大規模走査時）

並列サブエージェントが使える環境（Claude Code の `Agent` ツール等）では、対象が大規模な場合（目安: 10 ファイル超、または合計 2,000 行超）に限り、判定をサブエージェントの並列バッチへ委譲して加速してよい。判定基準・対象範囲・返却フォーマットは自己実行時と同一であり、この経路が変えるのは所要時間だけである。

- **バッチ分割**: 1 バッチ = 最大 10 ファイル、かつ合計 2,000 行程度を目安とする。目安を超える大ファイルは単独バッチにする。全バッチを 1 メッセージで並列起動する（Claude Code では `subagent_type: general-purpose`）。
- **サブエージェントへのプロンプト構成**: 判定基準の同一性を転記で確定させ、参照解決の失敗・解釈差を排除するため、各バッチのプロンプトには必ず次をすべて含める。
  1. 担当ファイルの絶対パス一覧。
  2. 下記「判定基準」の `BEGIN DECRUFT-JUDGE-SPEC` 〜 `END DECRUFT-JUDGE-SPEC` 間の本文を **一字一句そのままコピー** する。**セッション生成物を対象とする場合はさらに** `BEGIN DECRUFT-JUDGE-SPEC-SESSION` 〜 `END DECRUFT-JUDGE-SPEC-SESSION` 間の本文を続けてコピーする（それ以外では含めない）。
  3. フェーズ2の注意リストのうち担当ファイル分。添え書きとして、本フェーズ冒頭の「grep ヒット行だけに限定しない。フェーズ2の注意リストは取りこぼし防止用であり、各ヒット行を必ず検討する（候補にしない場合は黙って捨ててよい）」をそのまま転記する（正本は本フェーズ冒頭）。
  4. 指示: 「返却は判定基準末尾の JSON 配列のみ。前置き・後書き・説明文を書かない」。
- **親側**: 全バッチの返却 JSON を結合し、上記「判定後の後処理」を行う。バッチが失敗した、または返却が JSON 配列として解釈できない場合は、そのバッチの担当ファイルを自己実行（本フェーズ冒頭の手順）で判定し直し、その旨を結果報告に明記する。

## 判定基準

この節の `BEGIN`〜`END` 間が判定の正本である。フェーズ3の自己実行ではこのまま適用する（本文はサブエージェント宛の二人称で書かれているため、「担当ファイル」は対象ファイル、「返却」は候補リストの作成フォーマットとして読み替える）。加速オプション利用時はサブエージェントのプロンプトへ全文転記する。

<!-- BEGIN DECRUFT-JUDGE-SPEC -->
あなたはコードコメント・散文（Markdown 本文、docstring 等）のレビュアーである。担当ファイルを読み、すべてのコメント・散文ブロックについて「クリーンな成果物には不要な記述」を検出せよ。

判定の軸は「何が問題か」ではなく **「この記述は成果物に必要か」**。
コードの理解に役立つ rationale（なぜそうするか）は必要＝残す。
変更の経緯・開発時の道具立ての事情・歴史は不要＝消す。

### カテゴリ A: メタ環境依存

成果物を単体で見ると不要な、**開発時の道具立て**（AI エージェント、プラグイン、MCP、broker、他手段との比較、「この環境では」）への言及。

- 手がかりの例: `プラグイン`、`エージェント`、`broker`、`この環境`、`開発時`、`plugin`、`agent`、`in this environment`、特定の開発ツール名・製品名。
- **実行環境の制約（ブラウザ差異・OS・ランタイムのバージョン等）の説明は rationale であり対象外。** 削除するのは開発時の事情のみ。

### カテゴリ B: 後方互換・履歴ナラティブ

クリーンな現状では不要な、変更の歴史を語る記述。

- 日本語の種語: `元々`、`もともと`、`以前は`、`従来`、`旧`、`かつて`、`名残`、`後方互換`、`互換性のため`、`互換維持`、`代替として`、`〜の代わりに`、`削除された(ため|ので)`、`移行`、`レガシー`。
- 英語の種語: `originally`、`previously`、`used to`、`formerly`、`legacy`、`backward compat`、`for compatibility`、`replaced by`、`instead of the old`、`no longer`、`migration`。

### カテゴリ C: 変更ナラティブ・自己言及

diff / commit メッセージに属すべき変更経緯が、コメントや本文に書かれているもの。

- 日本語の種語: `修正しました`、`追加しました`、`変更しました`、`対応しました`、`変更点`、`修正点`、`今回`、`変更内容`。
- 英語の種語: `added`、`removed`、`changed`、`fixed`、`updated`（変更履歴の語り口）、`this was added`、`changed to`、`now uses`。

### 保護対象（候補に入れない。迷う場合のみ `protected: true` で候補に含め、理由を書く）

- ライセンス / 著作権ヘッダ（SPDX、Copyright、(c)、ライセンス表記）。
- 構造化ドキュメントタグ: `@param` `@return` `@throws` `@var` `@property` `@method` `@example` `@since` `@deprecated` 等（JSDoc / PHPDoc / docstring）。
- 仕様・設計として意図された互換レイヤ / フォールバックの説明。
- 現役の `TODO` / `FIXME` / `HACK` / `XXX` / `NOTE`。
- rationale（コードの意図・理由を説明する有用コメント）。特に次は必ず保護する: fail-fast の理由（なぜここで停止するか）、セキュリティ設計上の注意、isolation boundary の明示（例外を捕捉してよい境界の宣言）、複雑・保守上重要な処理に付けられた日本語のドキュメントコメント（PHPDoc / docstring 等）。
- `deprecated` / 互換の線引き: 正式な注記・仕様説明は保護する。削除するのは「元々〜が削除されたため代替として用意した」のような **冗長な変更ナラティブ** のみ。語の有無ではなく文脈で判別する。

### 確信度の較正（0–100）

75 以上 =「高確信: レビューなしで消してよい明白さ」、40–74 =「要確認: 削除して良さそうだが文脈確認が要る」、40 未満 = 返却しない（捨てる）。アンカー例:

- **95**: `// 元々 legacy_handler があったが削除されたため、代替として本関数を用意した` → B。純粋な変更経緯。
- **90**: `// バリデーション処理を追加しました` → C。コミットメッセージに属する内容。
- **85**: `// この環境では MCP が使えないため curl で代替した` → A。開発時の道具立ての事情。
- **60**: `// 従来方式との互換のため、戻り値は配列を維持している` → B に見えるが、仕様として意図された互換説明の可能性がある。要確認。
- **50**: README の「開発には Docker を使用します」 → A に見えるが、開発者向けセットアップ手順として正当な可能性がある。要確認。
- **20（返却しない）**: `// リトライ回数は API のレート制限に合わせて 3 回` → rationale。保護。

### 削除単位

`行` / `インライン`（コメント部分のみ）/ `ブロック` / `文` / `箇条書き項目` / `段落` / `節` のうち、**削除しても残りの意味が壊れない最小の整合単位** を選ぶ。散文では見出しと本文の対応・箇条書きの整合が崩れない単位にする。

### 返却フォーマット

JSON 配列のみを返す（候補 0 件なら `[]`）。前置き・後書き・説明文は書かない。

```json
[
  {
    "file": "絶対パス",
    "start_line": 42,
    "end_line": 43,
    "category": "A",
    "confidence": 90,
    "protected": false,
    "unit": "段落",
    "text": "削除対象の記述（原文そのまま）",
    "reason": "1文の判定理由"
  }
]
```

### セッション生成物への追補

この節の `BEGIN`〜`END` 間は、セッション生成物を対象とする場合に限り上記判定基準に**続けて**適用する（加速オプション利用時は判定基準に続けてプロンプトへ全文転記する）。

<!-- BEGIN DECRUFT-JUDGE-SPEC-SESSION -->
### セッション生成物への追補（書かれたばかりのコードへの追加基準。上記基準と矛盾する場合は本追補が優先）

担当ファイルはこのセッションで作成・変更されたばかりのコードである。次を追加で適用せよ。

**保護対象の変更**: 「現役の `TODO` / `FIXME` / `HACK` / `XXX`」の保護は適用しない。TODO 類は `category: "D"` の候補として返す。ただし confidence は **必ず 40–74（要確認）の範囲**とする（未実装の存在を示す TODO を無断で消させないため）。`NOTE` は引き続き保護。

### カテゴリ D: 自明・冗長コメント

直後のコードを読めば分かる内容をなぞるだけのコメント。書かれたばかりのコードでは AI 生成の癖として混入しやすい。

- **90**: `// カウンタをインクリメント` の直後が `count++;` → コードの逐語訳。
- **85**: `// ユーザーを取得する` の直後が `getUser()` 呼び出し → 関数名の反復。
- **50**: 処理ブロックの区切りコメント（`// --- バリデーション ---` 等）→ 冗長に見えるが可読性目的の可能性がある。要確認。
- **返却しない**: 「なぜ」を説明するコメント、非自明なアルゴリズム・単位・制約の説明 → rationale。保護。

## フェーズ4: dry-run レポート＋永続化

1. 結合済み候補から `protected: true` と、「確信度の較正」の返却下限を下回るものを除外する。除外した `protected: true` の件数は「保護扱いとした境界例」としてレポートの統計に載せる。
2. 残った候補の各エントリに、階層（`tier`: 高確信 / 要確認）とレポート上の番号（`report_no`）を付加し、JSON のまま、実行ごとに一意な名前のファイル（`decruft-findings-<日時>.json`。日時は `date +%Y%m%d-%H%M%S` で取得）としてセッションの一時領域（無ければ `/tmp`。以降「一時領域」と呼ぶ）へ保存し、レポートにそのパスを記す。承認〜適用の間にコンテキストが失われても、このファイルだけで番号指定の承認を候補に対応付けて再開できる。
3. 「確信度の較正」が定める2階層（高確信 / 要確認）で階層化し、削除 diff とともに提示する。**この時点では削除しない**。
4. サブエージェント（加速オプション）の返却はユーザーには一切表示されていない — レポートを本文へ出力するまで、提示は行われていない。レポートの末尾で適用範囲を散文提示で確認する。選択肢は定型なので一行に畳んでよい —「適用範囲を返信してください: `全件` / `高確信のみ` / 番号指定（例: `高確信 1,3` / `要確認 2`） / `適用しない`」— 推奨する適用範囲を理由一言つきで添える（例: 「推奨: 高確信のみ — 要確認2件は利用者向け説明の可能性」）。承認の確認を同一ターンで発行しない。完了条件: 保存した findings ファイルの候補件数と、本文レポートの番号付き項目数が一致している。

### レポート形式

```
## decruft: <対象パス>
   ```

## フェーズ5: 適用＆検証

### 承認と適用前の準備

1. フェーズ4へのユーザーの返信そのものを承認とする。返信を適用範囲（全件 / 高確信のみ / 番号の集合 / 適用しない）として解釈し、解釈できない場合のみ、フェーズ4のレポート末尾と同じ形式で選択肢を散文提示で再掲する。
2. 書き換えを始める前に、対象ファイルすべての複製を一時領域へ保存する（検証の基準点。リポジトリ内外を問わない。作業ツリーに混在するユーザーの未コミット変更もこの複製に保存される）。
3. セッション生成物を対象とした場合: プロジェクトのテスト / selftest コマンド（package.json・Makefile 等から特定）が存在すれば 1 回実行し、失敗を記録する（ベースライン）。テストが存在しない場合、または対象がリポジトリ外のファイルのみの場合はスキップし、その旨を結果報告に明記する。

### 適用

- 承認された項目のみ削除する。フェーズ4で保存した findings ファイルを正として適用する。
- 編集は文字列一致の置換で行う（Claude Code では Edit ツール）。置換対象の文字列（Edit の `old_string`）は周辺行を含めて **ファイル内で一意** になるようにする。同一ファイル内の複数候補は **行番号の大きい順（ファイル末尾側から）** に適用し、行ズレの影響を避ける。
- 置換に失敗した候補（承認までの間にユーザーの編集で対象文字列が変わった・周辺行を含めても一意化できない等）は削除せず見送りとし、結果報告の「見送り」にファイル・行番号・失敗理由を明記する。ファイルの書き直し等の独自の回復手段は使わない。
- 削除後の整形（最小限）:
  - インラインコメント（`code; // 余計`）はコメント部分だけ削除し、コードは残す。
  - 削除により生じた連続空行は1つにまとめ、ブロック先頭・末尾の余分な空行を除く。
  - 散文（Markdown 等）では、見出しと本文の対応や箇条書きの整合が崩れないよう、整合単位ごと削除する。
- **コードの振る舞いは変えない。** 変更はコメント・散文の削除に限る。
- **コミットしない**。削除は作業ツリー上の変更として残し、コミットはユーザーの指示があった場合のみ行う。

### 検証（適用後に必須）

1. 変更した各ファイルに、利用可能な軽量構文チェックを実行する:
   - PHP: `php -l` / Python: `python3 -m py_compile` / JavaScript: `node --check` / JSON: `jq .` / YAML: `python3 -c 'import yaml,sys; yaml.safe_load(open(sys.argv[1]))' <file>`
   - 該当コマンドが無い言語（TypeScript、CSS、Markdown 等）や、コマンドが実行環境にインストールされていない場合はスキップし、未検証である旨を結果報告に明記する。
2. 各対象ファイルについて、適用前の準備で保存した複製との diff を確認し、差分が **承認された項目のコメント・散文の削除と空行整理のみ** であることを確かめる（`git diff` は使わない — 作業ツリーにユーザーの未コミット変更が混在していると decruft 起因でない差分を含むため）。承認外の変化（コード行の変化を含む）があれば、該当ファイルを複製から復元して報告する。復元は複製ベースなので、ユーザーの未コミット変更は失われない。
3. **セッション生成物を対象とした場合**: テストを再実行し、適用前の準備で記録したベースラインに無い新たな失敗がないこと（NG 0 維持）を確認する。新たな失敗が出た場合は、原因となった削除だけを取り消して報告する。ベースラインをスキップした場合は再実行もスキップし、その旨を結果報告に明記する。
4. 結果を報告する: 適用 N 件 / 見送り M 件 / 構文チェックの実施ファイルと結果 / テスト実行結果（セッション生成物を対象とした場合）/ 未検証ファイル。

## 対応コメント構文（拡張子で判定）

- PHP: `//`、`#`、`/* */`、`/** */`（PHPDoc）
- JavaScript / TypeScript: `//`、`/* */`、`/** */`（JSDoc）
- CSS / SCSS: `/* */`
- HTML / XML: `<!-- -->`
- Python: `#`、`""" """` / `''' '''`（docstring）
- シェル / YAML / TOML / Ruby: `#`
- Markdown: 本文（散文）そのもの、および `<!-- -->`

未知の拡張子は、安全側に倒して候補化は控えめにし、フェーズ3の文脈判定に委ねる。
