`mattpocock/skills` の main flow（`ask-matt` が定義する idea → ship の流れ）を、grilling の結果から規模を判定して該当ルートへ振り分け、1セッションで完結する分は最後まで実行する。リポジトリに `/setup-matt-pocock-skills` が実施済みかどうかを問わず同じ手順で動く。

**用語**: **上流スキル**は `mattpocock/skills` 配布の各スキルを指す。**読み替え**は上流スキルの指示を本スキルの運用に合わせて置き換えることで、全件を「上流スキルの読み替え」節が持つ。**開始点**は起動時に記録する `HEAD` のコミットで、レビュー対象の差分の起点になる。**成果物言語**は spec・チケット・コミットメッセージ案に使う言語で、Step 0 で確定する。

## 起動形

本スキルを名指しで起動する（Claude Code では `/matt-flow …`）。

- 引数が説明文 — 新規案件。Step 0 → Step 1 → Step 2 の判定ルートへ進む。説明が無ければ、何を作るかの入力を求めて待つ。
- 引数が `--ticket <チケットのパスまたは番号>` — 大規模ルートで切ったチケット1枚を実装する。Step 0 の完了後に本スキル同フォルダの `ticket.md` を読み、その手順で進む。値が無ければ、チケットのパスまたは番号の入力を求めて待つ。

## git への態度

本スキルはコミット・push・ブランチ作成・stash を行わない。コミットは最終報告でメッセージ案を提示するまでとし、実行はユーザーに委ねる。git リポジトリでない場所での扱いは Step 0 の項目2が定める。

## 上流スキルの解決（前置きゲート）

上流スキルの SKILL.md は次の順で解決する: 自スキルの隣（`../<名前>/SKILL.md`）→ 実行ハーネス自身のスキルディレクトリのプロジェクト側 → グローバル側。実体は、Claude Code はプロジェクト側 `.claude/skills/`・グローバル側 `~/.claude/skills/`、Codex はプロジェクト側 `.agents/skills/`・グローバル側 `~/.agents/skills/`、その他のハーネスはそのハーネス自身の2箇所を同じ位置づけで使う。他ハーネス用のディレクトリは探さない。

作業開始前に次の全件が解決できることを確認する: `grill-with-docs`、`grilling`、`domain-modeling`、`codebase-design`、`to-spec`、`to-tickets`、`implement`、`tdd`、`code-review`。1件でも解決できなければ、何も作業せず解決できなかった名前を示して次を案内し中止する。途中で上流本文が新たに参照したスキルが解決できない場合も、その時点で同じ案内をして中止する。

> 依存する mattpocock/skills のスキルが見つからないため中止しました。`npx skills add mattpocock/skills` で導入してから再実行してください。

保留ルートと大規模ルートでユーザーに案内する `handoff`・`prototype`・`research`・`to-questionnaire`・`wayfinder`・`implement-spec` も `mattpocock/skills` 配布の上流スキルである。本スキルは実行せず案内だけするので前置きゲートの対象外とし、案内する直前に同じ順で解決を試み、解決できないものには「未導入（`npx skills add mattpocock/skills` で導入）」と添える。

## 上流スキルの読み替え

上流スキルの本文は SKILL.md を Read して同一コンテキストで適用する。適用時は次の読み替えをすべて行う。ここに無い指示は上流本文のとおりに従う。引用した文言は照合の目印であり、言い回しが違っても同じ意味の指示には同じ読み替えを適用する。上流の指示が「git への態度」や Step 0 で確定したトラッカー運用と食い違う場合は本スキルを優先する。上流のある指示が読み替えの対象かを判断できない場合は、該当箇所を引用して扱いを散文提示で確認する。

1. **スキル呼び出し**: 「Call the Skill tool with "X"」「Call the Skill tool for "X"」は、X を「上流スキルの解決」の順で解決して Read し、同一コンテキストで適用する、と読み替える。
2. **トラッカーの前提**: 「The issue tracker (and triage label vocabulary) should have been provided to you. If not, tell the user to run `/setup-matt-pocock-skills`.」は、Step 0 で確定したトラッカー運用に従う、と読み替える。setup の実行は促さない。
3. **リモートへの公開**: `to-spec`・`to-tickets` がリモートのトラッカー（GitHub・GitLab 等）へ公開する直前に、公開先と公開する件数を散文提示で確認し、承認された場合だけ公開する。承認されなければ、未 setup と同じ `.scratch/<feature-slug>/` 配下へローカル Markdown として書き出し、そのパスを公開先とする。spec の公開が承認されなかった場合は、チケットも確認なしで同じ `.scratch/<feature-slug>/` 配下へ書き出す。spec を公開した後でチケットの公開だけが承認されなかった場合は、公開した spec の本文も `.scratch/<feature-slug>/spec.md` へ書き出す（どちらも、`--ticket` がチケットの隣から親 spec を読めるよう置き場を揃えるため）。ローカル Markdown への書き出しは確認なしで行う。
4. **seam の合意**: `implement`・`tdd` の「pre-agreed seams」は、小規模ルートでは Step 3 で合意した seam、チケット実装では `ticket.md` の手順3で合意した seam を指す。`tdd` は検証方法が「自動テスト」の seam にだけ適用する。
5. **コミット**: `implement` の「Commit your work to the current branch.」は、最終報告でコミットメッセージ案を提示する、と読み替える。
6. **レビューの起点と差分**: `code-review` の固定点は開始点とし、ユーザーに尋ねない。差分コマンドは `git diff <開始点>`（作業ツリーとの比較）とし、加えて、Step 0 の項目4で定めた新規未追跡ファイルと、起動時の未追跡一覧のうちハッシュが記録時から変わったファイルを、ファイル全体として差分の一部に含めて各サブエージェントに渡す。コミット一覧は「コミット無し（作業ツリーの差分）」とする。`.scratch/` 配下は spec・チケットの置き場なのでコード差分から除く。差分も未追跡ファイルも無ければ、レビューせず「変更なし」と報告して終える。
7. **レビューの spec**: `code-review` の spec は、小規模ルートでは Step 3 で書いた spec ファイル、チケット実装ではチケットとその親 spec とし、探索や質問をしない。
8. **ユーザーへの確認**: 上流本文がユーザーに選択・承認・確認を求める場面は、選択式 UI ツールの使用を指示していても散文提示で確認する。

## Step 0: 前提確認

次の全項目を確認する。完了条件は全項目の確定。

1. **依存**: 「上流スキルの解決」の全件確認を通過している。
2. **git**: `git rev-parse --show-toplevel` が成功する。失敗したら「git リポジトリでないため中止しました」と伝えて中止する（上流の `code-review` が git の差分を前提とするため）。
3. **作業ツリー**: `git status --porcelain --untracked-files=no`（追跡済みファイルの変更だけ）の出力から `.scratch/` 配下を除いた結果が空でなければ（未追跡ファイルは項目4の記録で区別し、`.scratch/` は spec・チケットの置き場で読み替え6によりレビューの差分から除くため）、既存の未コミット変更がレビュー対象の差分に混ざることを示し、「中止して先にコミットか退避をしてから再実行する（推奨。レビューの差分が今回の変更だけになるため）／このまま続ける」を散文提示で確認する。
4. **開始点**: `git rev-parse HEAD` を記録する。コミットが1件も無いリポジトリでは `git hash-object -t tree /dev/null` の空ツリーを開始点にする。あわせて `git ls-files --others --exclude-standard` の出力を、各ファイルの `git hash-object <ファイル>` の値と組にして起動時の未追跡一覧として記録する。以後、同じコマンドの出力のうち起動時の未追跡一覧に無いものを**新規未追跡ファイル**と呼ぶ。
5. **トラッカー運用**: リポジトリ直下に `docs/agents/issue-tracker.md` があれば **setup 済み**とし、トラッカー・ラベル・ドメイン文書の扱いを `docs/agents/` 配下の各ファイルに従う。無ければ **未 setup** とし、次の運用を前提にする（`docs/agents/` の作成と CLAUDE.md・AGENTS.md の編集はしない）:
   - トラッカーはローカル Markdown。1機能1ディレクトリ `.scratch/<feature-slug>/`、spec は `spec.md`、チケットは `issues/<NN>-<slug>.md`（`01` から依存順に1ファイル1チケット）。
   - トリアージ状態はファイル冒頭近くの `Status:` 行に既定の役割名（`ready-for-agent` 等）で書く。
   - ドメイン文書は単一コンテキスト。リポジトリ直下に `GLOSSARY-MAP.md` があればそれが指す各 `GLOSSARY.md`、無ければ直下の `GLOSSARY.md` と `docs/adr/` を読む。無いファイルについては何も言わず進める。
   - `GLOSSARY.md`・`docs/adr/`・`.scratch/` は上流どおり必要になった時点で作成し、`.gitignore` は変更しない。
6. **成果物言語**: setup 済みなら `docs/agents/` と既存の spec・チケットの言語、未 setup なら既存の `.scratch/`・`GLOSSARY.md`・`docs/adr/` の言語に合わせる。判定材料が無ければ対話言語とする。コミットメッセージ案は `git log` の既存メッセージの言語に合わせる。

## Step 1: grilling（grill-with-docs 相当）

`grill-with-docs` を Read し、読み替えを適用して `grilling` と `domain-modeling` を適用し、起動時の説明を題材に grilling を行う。完了条件は `grilling` 自身の終了条件（frontier が空になり、共有理解に達したことをユーザーが確認した）を満たすこと。

grilling 中に、ユーザーが「今は決められない」と保留した決定は保留一覧として記録する（各項目に保留の理由を添える）。

## Step 2: 規模の判定

上から順に判定し、最初に当てはまったルートへ進む。判定結果と根拠を一文で示し、進むルートを散文提示で確認してから進む。選択肢は保留・大規模・小規模の各ルートを1項目ずつ、選ぶと何が起きるか（保留ルートは案内して終了、大規模ルートは spec とチケットの作成まで、小規模ルートは実装とレビューまで）を添えて並べ、判定したルートを推奨とする（理由: grilling で確定した決定事項に基づく判定のため）。保留一覧が空なら保留ルートは選択肢に出さない。保留一覧があるまま大規模ルートか小規模ルートが選ばれた場合は、各保留項目を理由つきで spec の Out of Scope（大規模ルートは `to-spec` が作る spec、小規模ルートは Step 3 の spec）に書き、最終報告の「未決事項」にも列挙する。完了条件は進むルートの確定。

1. **保留ルート**: 保留一覧が1件以上ある → 「保留ルート」へ。
2. **大規模ルート**: 確定した決定事項を `to-tickets` の縦スライス規則（1スライス＝新しいコンテキストウィンドウ1つに収まる、端から端まで貫く小さな機能）で切ると2枚以上になる → 「大規模ルート」へ。
3. **小規模ルート**: 上のどちらにも当たらない → Step 3 へ。

## 保留ルート

何も実装せず、保留一覧を理由ごとに次の案内付きで提示して終える。

- 動かして確かめないと決まらない（状態モデル・ロジック・UI の見た目）→ `handoff` で書き出し、新しいセッションで `prototype`、結果を `handoff` で持ち帰ってこのスレッドから参照する。
- 一次情報の調査が要る → `research`。
- 他人の回答が要る → `to-questionnaire`。
- 1セッションでは全体像を掴めない → `wayfinder`。

保留が解けたら、決まった内容を添えて本スキルを再起動するよう案内する。

## 大規模ルート

1. `to-spec` を Read して適用し、spec を作成・公開する（読み替えを適用）。完了条件は spec の公開先（ファイルパスまたは issue）の確定。
2. `to-tickets` を Read して適用し、チケットを作成・公開する（読み替えを適用）。完了条件はチケット一覧の公開先の確定。
3. 実装に入らずに終える。次を案内する（`ask-matt` のフローどおり、spec とチケットは grilling と同じコンテキストで作り、実装はチケットごとに新しいコンテキストで行うため）:
   - チケットごとに新しいコンテキスト（会話履歴を消した状態。Claude Code では `/clear`）で本スキルを `--ticket <チケットのパスまたは番号>` 付きで起動し（チケットを `.scratch/` へ書き出した場合はパスを渡す）、ブロッカーが解消済みのものから順に実装する（推奨。setup 有無を問わず動く）。各チケットの実装後は、最終報告のコミットメッセージ案でコミットしてから次のチケットへ進む（次のチケットのレビュー差分に前のチケットの変更を混ぜないため）。
   - setup 済みの場合に限り、`implement-spec` で spec 全体を一括実装する方法もある（上流どおり統合ブランチの作成・マージ・コミットを伴う）。

## Step 3: seam と検証方法の合意（小規模ルート）

最初に `tdd` と `to-spec` を「上流スキルの解決」の順で解決して Read し、`tdd` の「Seams: where tests go」節と `to-spec` の spec-template を特定する。どちらかを特定できなければ、探した場所を示して中止する。続けて、`tdd` の「Seams: where tests go」節の基準で、テストする seam（外から振る舞いを観測できる公開境界）を提案する。各 seam に、捉えるもの・捉えないものを一行で添え、検証方法を次の3つから1つ割り当てる。

- **自動テスト**: テストランナーで red → green を回せる。テスト基盤が無い場合は、導入する依存とテストファイルをリポジトリに残すかを提案に含める。
- **コマンド判定**: テスト基盤は使わず、1本のコマンド（`curl` と `grep`、ビルド、CLI 実行等）の結果で合否を判定できる。
- **手動確認**: 見た目・文言・設定値など自動で合否を判定できない。

一覧を散文提示で確認し、承認された内容で確定する。続けて、確定した内容を `.scratch/<feature-slug>/spec.md` に書く（同名ディレクトリが既にあれば別の slug にする）。構成は `to-spec` の spec-template のうち Problem Statement・Solution・Implementation Decisions・Testing Decisions・Out of Scope の5節とし、見出しはテンプレートのまま、本文は成果物言語で書き、Testing Decisions に seam ごとの検証方法を含める。完了条件は spec ファイルの作成。

## Step 4: 実装とレビュー（小規模ルート）

`implement` を Read し、読み替えを適用して実装とレビューを行う。検証方法ごとの扱いは次のとおり。

- **自動テスト**: `tdd` に従い red → green を回し、失敗した実行と成功した実行の両方を証跡として残す。Step 3 でテスト基盤をリポジトリに残さないと合意した場合は、証跡を残したうえで `code-review` の前に導入した依存とテストファイルを撤去し、撤去したものを最終報告の「検証」に明記する。
- **コマンド判定**: 変更前にコマンドを実行して期待どおり失敗（または期待値と異なる出力）を確認し、変更後に成功を確認する。両方の出力を証跡として残す。変更前に既に成功した場合は実装に進まず、その出力を示して「判定コマンドを変更前に失敗するものへ見直す（推奨。合否を見分けられない検証を避けるため）／その seam を手動確認に切り替える」を散文提示で確認する。
- **手動確認**: 確認手順と期待結果を書き出すだけにし、検証済みとは扱わない。

完了条件は `code-review` の集約結果が出ていること。Standards・Spec のどちらかに指摘がある場合は、指摘を散文提示で示し、「指摘を修正して再レビューする（推奨。報告前に解消できるため）／修正せず報告に進む」を確認する。修正した場合は Step 4 のレビューを再度行う。

## 最終報告

次の全項目を報告する。

- **ルート**: 進んだルートと判定の根拠。`--ticket` で起動した場合は「チケット実装」と対象チケットの題名。
- **変更**: 変更・作成したファイル。
- **検証**: seam ごとの検証方法と結果。自動テスト・コマンド判定は失敗時と成功時の証跡、手動確認は確認手順と「未検証」の明記。
- **レビュー**: `code-review` の Standards・Spec それぞれの結果と、未修正の指摘。
- **新規の未追跡ファイル**: Step 0 の項目4で定めた新規未追跡ファイル（`GLOSSARY.md`・`docs/adr/`・`.scratch/` 等）。コミットに含めるかはユーザーが判断する旨を添える。
- **未決事項**: Step 2 で保留一覧を残したまま大規模ルートか小規模ルートへ進んだ場合の各保留項目と理由（該当しなければ「なし」）。
- **コミットメッセージ案**: 成果物言語で、タイトルと必要なら本文。チケット実装ではチケットの状態更新が未実施であることも添える。

保留ルートでは、ルート・案内だけを報告する。大規模ルートでは、ルート・作成したファイル・案内・未決事項を報告する。
