# plainify 言語別規則: 日本語

plainify（`../SKILL.md`）の普遍規則に**加えて**適用する日本語固有の規則と較正例。
単独では使わない。大原則（意味厳守・直しすぎない）・保護対象・内部検証・出力の規定は
SKILL.md のものがそのまま適用される。

## 整形前の確認: 文体判定

文末表現（です・ます / だ・である）を走査する。

- 一貫していれば、**その文体を維持**する（敬体なら敬体、常体なら常体）。
- **文単位で常体と敬体が混在している場合のみ**、整形前に 1 回だけ、常体（だ・である）と
  敬体（です・ます）のどちらに統一するかを散文提示で確認してから整形する
  （定型の二択なので一行に畳んでよい）。
- 箇条書きの体言止め（「外部呼び出し元なし。」等）は list の慣習であり、混在に含めない。

## 語彙・語法（日本語固有の型）

- **サ変名詞の硬さを動詞表現へ** — 普遍規則「名詞化の硬さ」の日本語型。
  「〜の統一の範囲と判断します」のような漢語の塊を平易な動詞文へ。
- **英語動詞の生混入を自然な日本語へ** — 例「ハンドラが attach される」→「ハンドラが
  仕込まれます／登録されます」。
- **定着した訳語のあるカタカナ・翻訳調を置換** — 例「コンフィグレーション」→「設定」、
  「〜を考慮する必要がある」→「〜を考える必要がある／〜に注意する」。
- **英語直訳調の受動だけを直す** — 例「〜されることが可能です」→「〜できます」。
  技術文書として自然な受動（「フックが登録されます」等）はそのまま残す。

## 文（日本語固有の型）

- **係り受けを整理する** — 修飾語は被修飾語の近くへ置く。「〜という」「〜であるところの」
  で膨らんだ長い連体修飾（入れ子）は、独立した文に切り出してほどく。
- **間接構文の日本語型** — 普遍規則「間接構文の圧縮」の代表型。「〜という挙動により
  〜という状態が発生する」→「〜のため〜になる」。「こと」「もの」「状態」を経由した
  回りくどい言い回しを直接表現へ。

## 段落・構成（日本語固有の型）

- **概念の明示に「」を使ってよい** — 例「リクエスト限定リスナー」「リクエストで縛る方式」。

## 較正用 before / after（既定モード — 目標とする整形の強さ）

いずれも実務のコードレビュー出力を想定した例。最後の 1 例は段落・構成レベルの整形を示す。

**見出し＋超長文の分割 — before**

> 概要: user-import / csv-export / audit-log の3モジュールで、register_listeners() に
> 全リクエスト無条件登録されていたリクエスト限定リスナー（export/format/value 等）を、
> boot() の route_check() 通過時にのみ生成される Exporter/Importer クラスの
> コンストラクタへ移設し、notification と同じリクエスト縛りパターンへ統一する修正です。

**after**

> ## このPRがやっていること
> user-import / csv-export / audit-log の3モジュールで、register_listeners() が
> 全リクエストで無条件に登録していた「リクエスト限定リスナー」（export/format/value など）を
> 整理する修正です。これらを boot() の route_check() を通った場合だけ生成される
> Exporter / Importer クラスのコンストラクタへ移し、notification と同じ
> 「リクエストで縛る」方式に揃えています。

→ 見出しを平易化。1 文を複数文に分割。「リクエスト限定リスナー」「リクエストで縛る」を
「」で明示。識別子（`register_listeners()`, `export/format/value`, `route_check()` 等）は無改変。

**英語動詞＋因果連鎖 — before**

> #482 の修正は妥当: CSVエクスポートは export/table/screen（＝対象の一覧画面）で
> ハンドラが attach されるため、管理者一覧（/admins）では
> route_check(['/users'], [csv-export TYPE]) が false となり Exporter が生成されず、
> format_export_value が登録されません。

**after**

> - **#482 は確かに直る:** CSVエクスポートは一覧画面の export/table/screen で
>   ハンドラが仕込まれます。管理者一覧は /admins なので
>   route_check(['/users'], [csv-export TYPE]) が false になり、Exporter が生成されず
>   format_export_value も登録されません。

→ 「attach される」→「仕込まれます」。「（＝対象の一覧画面）」を語注「一覧画面の」へ
畳んで前置。因果連鎖（仕込まれる→ false →生成されない→登録されない）は保持。

**ツール採点タグの除去 — before**

> 検証を通過した act対象の不具合（CONFIRMED/PLAUSIBLE）はありませんでした。

**after**

> 修正が必要な不具合は見つかりませんでした。

→ 人間の判断に寄与しない内部タグ（`act対象`, `CONFIRMED/PLAUSIBLE`）を削除。
「不具合は無かった」という実体は保持。

**結論先出し＋間接構文の圧縮 — before**

> route_check() が false を返した場合に Exporter クラスが生成されないという挙動により、
> 管理者一覧画面においてエクスポート値の整形処理である format_export_value が
> 呼び出されないという状態が発生していることが確認できましたが、これは意図された挙動で
> あると考えられます。

**after**

> この挙動は意図されたものと考えられます。管理者一覧画面では route_check() が false を
> 返して Exporter クラスが生成されないため、エクスポート値を整形する
> format_export_value も呼び出されないことを確認しました。

→ 末尾に埋まっていた結論（意図された挙動）を先頭へ。「〜という挙動により〜という状態が
発生」の間接構文を「〜のため〜も呼び出されない」へ圧縮。評価の強度（「考えられます」）と
「確認できた」という事実は不変。

## 較正用 before / after（--for モード、読者 = 非技術者の場合）

読者適応の強さの較正例。読者が変わっても、同じ判定基準
（指定読者の判断・理解に必要か）を同じ強さで適用する。

**技術詳細の drop ＋ 一般知識の語注 ＋ keep-or-drop — before**

> route_check(['/users'], [csv-export TYPE]) が /admins では false を返すため
> Exporter が生成されず、format_export_value による出力値のサニタイズが行われない。
> XSS ペイロードが CSV 出力にそのまま残存する。

**after**

> 管理者一覧画面からの CSV 出力では、出力内容を無害化する処理（format_export_value）が
> 働いていない。そのため、悪意ある入力データが加工されないまま CSV に残る
> （XSS: 埋め込まれた不正な命令文が、閲覧者の画面で実行されてしまう攻撃の入り口になる）。

→ 内部の因果連鎖（route_check → Exporter 不生成）は読者の判断に不要なので丸ごと drop。
残した format_export_value は一字一句そのまま keep。「XSS」には一般知識の範囲の
一言説明を追加。「無害化されず残る」という事実と強度は不変。文体は原文の常体を維持。
