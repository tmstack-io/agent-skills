# publish-polish — 公開品質への整形

指定された範囲の散文（Markdown 本文等）とコードコメント・docstring を**初見の読者**——この成果物だけを手にし、作者の環境・歴史・社内事情を何も知らない読者——のレンズで走査し、成立しない記述を before→after の提案リストとして提示、**承認された項目のみ**書き換える。承認前にファイルへ触れない。

変更するのはコメント・散文のみで、コードの振る舞いは変えない。**コミットはしない**（書き換えは作業ツリーに残し、コミットはユーザーの指示があった場合のみ）。

## 引数

- **対象パス（必須・1個以上）**: ファイル、ディレクトリ（再帰）、または glob。引数が無ければ対象をユーザーに確認する。リポジトリ全体を黙って走査しない。
- **`--style`**: 判定に「磨き込み基準」（後述）を追加し、文体・体裁・構成の提案も行う。

### 走査対象の除外

- `.gitignore` を尊重する。既定除外: `.git/`、`node_modules/`、`vendor/`、ビルド成果物、バイナリ、lock ファイル。
- CHANGELOG・HISTORY・リリースノート・ADR 等、変更の歴史を語ることが目的の文書は、履歴・運用・視点の基準（カテゴリ 1〜3）を適用しない（歴史がコンテンツそのもの）。**要対応（漏えい）と磨き込み基準は適用する。**除外・縮退したファイルはレポートに明記する。

## フロー

### [1] 公開の姿の確認

走査前に必ずユーザーへ質問し、回答を待つ（Claude Code では AskUserQuestion。同等ツールが無い環境では散文で質問する）: **①想定読者は誰か ②配布形態は何か（OSS リポジトリ / パッケージ / 納品物 等）③この成果物は製品として何を約束するか**。同じ一文が公開の姿しだいで「名残」にも「仕様」にもなるため、この回答が以後の全判定の前提になる。

完了条件: ①〜③が各1文で確定し、判定の前提として宣言済み。

### [2] 対象列挙と git 前提チェック

除外規則を適用して対象ファイルを列挙し、「対象はこの N ファイル」と提示する。git リポジトリでなければ、適用前のバックアップを勧める（中断はしない）。作業ツリーの対象ファイルに未コミット変更があれば、書き換えが混ざる旨を伝え commit / stash を勧める（中断はしない）。

完了条件: 対象一覧の提示と git 状態の報告が済んでいる。一覧外のファイルは [5] まで変更しない。

### [3] 判定（全読み）

対象ファイルを 1 つずつ Read し、**すべての散文ブロック・コメント・docstring** に「判定基準」（`--style` 時は「磨き込み基準」も）を適用して候補リストを作る。

完了条件: 全対象ファイルの全散文・コメントブロックについて「候補あり」か「初見の読者に成立する」かを判定し終えている。

### [4] 提案レポート

候補を「レポート形式」に従って提示し、同じ内容を `publish-polish-findings.json` としてセッションの一時領域（無ければ `/tmp`）へ保存してパスを記す（承認までにコンテキストが失われても、このファイルを正として再開できる）。フィールドはレポートの提案項目と同一とする（file / line / category / before / after / reason。要対応は before・after を持たない警告項目として含める）。

完了条件: 要対応警告と全提案が本文に出力され、永続化パスが提示されている。**レポートを本文に出力し終えるまで [5] の承認質問を発行しない**（ユーザーは提案一覧を読んでから適用範囲を判断する。質問と同一の応答へのレポートの同居も避け、レポート出力→質問の順を守る）。

### [5] 承認 → 適用 → 検証

1. ユーザーに適用範囲を選択式で確認する（全件 / 番号指定 / 見送り。Claude Code では AskUserQuestion。同等ツールが無い環境では散文で選択肢を提示し回答を待つ）。質問文に件数（要対応 X / 提案 M）を、選択肢の説明に主要な提案の要旨を含め、レポートが画面に見えていない状態でも判断材料が残るようにする。要対応（漏えい）はこの承認の対象外で、ユーザーが対処方針を個別に指示する。
2. 承認された項目のみ適用する。編集は文字列一致の置換（Claude Code では Edit ツール）で行い、置換対象は周辺行を含めてファイル内で一意にする。同一ファイル内は行番号の大きい順（末尾側から）に適用する。
3. 検証: `git diff` で変更が**散文・コメントの書き換えのみ**であることを確認する（コード行に変化があれば即座に revert して報告）。非 git 環境では、適用の直前に対象ファイルの複製をセッションの一時領域へ保存しておき、適用後にその複製との diff で同じ確認を行う（代替検証であることを報告に明記する）。コードファイルには利用可能な軽量構文チェック（`php -l` / `python3 -m py_compile` / `node --check` / `jq .` 等）を実行し、無い言語は未検証と明記する。
4. 報告: 適用 N 件 / 見送り M 件 / 要対応の残件 / 検証結果と未検証ファイル。

完了条件: 承認された全項目が適用され、検証と報告が済んでいる。

## 判定基準

判定は一問に集約される: **「初見の読者に、この記述はこのまま成立するか」**。成立しない記述を以下のカテゴリで候補化し、それぞれの書き換え方針で案を作る。

書き換えの原則:

- 対象文書の言語で書く（英語文書は英語で）。
- 原文に無い機能・約束・事実を書き加えない。書き換えは視点の変換であり、内容の発明ではない。
- 削除を提案するのは「初見の読者に伝える価値がゼロ」の場合のみ。情報が残る余地があれば書き換えを選ぶ。
- 迷う場合は候補に含め、理由に迷いの内容を書く（取捨は承認時のユーザー判断）。

### 要対応: 漏えいの疑い

クライアント名・個人名・メールアドレス・内部 URL・非公開リポジトリ名・認証情報らしき文字列など、**公開してよいかの判断が表現の問題ではない**記述。書き換え案を作らず、レポート最上位に警告として提示し、対処（削除・一般化・公開可の確認）をユーザーに委ねる。参照先の公開状態を実確認できる環境では確認して結果を警告に添える（GitHub リポジトリなら `gh repo view <owner/name>` 等。公開と確認できた参照は要対応から外してよい）。確認できない環境では未確認である旨を警告に明記する。本スキルは secrets スキャナ（gitleaks 等）の代替ではなく、公開前には専用ツールの併用を勧める。

### カテゴリ 1: 履歴・経緯ナラティブ

変更の歴史・こうなった経緯を語る記述（「元々」「以前は」「〜が削除されたため」「移行した」等）。初見の読者は歴史を共有していない。→ **現在の仕様・現在の手順を語る現在形の記述に書き換える**か、経緯そのものにしか価値が無ければ削除。

### カテゴリ 2: ローカル・個人運用の名残

作者個人の環境・運用に依存し、初見の読者が再現できない記述（特定マシンのパス、個人的な symlink 運用、「私の環境では」等）。→ **公開された配布形態（[1] の回答）で成立する手順・説明に書き換える**。作者運用が公式手順を兼ねる場合は、読者が同じ手順を踏める一般形に直す。

### カテゴリ 3: 内部視点・自己言及

作者集団の内側からの語り（「自作」「正本」「本リポジトリに集約」等、読者を作者側に置く表現）や、文書内で定義されない内輪の略語・コードネーム。→ **製品を読者に向けて説明する視点に書き換える**。

### 保護対象（候補に入れない）

- 読者自身に向けた正当な開発者向け情報: セットアップ手順、動作要件、既知の制約。
- rationale（なぜこの設計・制約なのかの説明）。実行環境の制約（OS・ランタイム差異等）は rationale であり、開発時の事情ではない。
- ライセンス・著作権ヘッダ、構造化ドキュメントタグ（`@param` 等）、現役の TODO / FIXME / NOTE。

## 磨き込み基準（`--style` 時のみ追加）

- **表記ゆれ**: 同一概念に複数表記があれば、文書内の多数派に統一する。
- **文体**: です・ます / だ・である等の混在を文書内の多数派に統一する。
- **見出し**: 階層の飛ばし・同レベル間の粒度不整合を直す。
- **未定義用語**: 初見の読者に未知の専門用語・略語へ初出定義を添える。
- **構成**: 章立て・文の流れが読者の理解順に沿うよう再構成を提案する。提示単位は節または章の before→after とし、ファイル全文の置換はしない。

## レポート形式

```
## publish-polish: <対象パス>

公開の姿: <①②③の要約1〜2行>
対象ファイル: N 件（歴史文書として縮退: X 件） / 要対応: X 件 / 提案: M 件（--style 分: Y 件）
提案の永続化: <パス>

### 🚨 要対応（漏えいの疑い — 書き換え案なし、対処はユーザー判断）
1. `path/to/doc.md:12` 非公開リポジトリ名への言及: 「…」

### 提案
1. `path/to/doc.md:3`  [カテゴリ2 ローカル運用]
   before: 「~/.claude/skills/ の同名エントリはここへのシンボリックリンク。」
   after:  「各スキルはエージェントのスキルディレクトリに配置して利用する（配置手順は README を参照）。」
   理由: 作者個人の symlink 運用であり、初見の読者には再現できない。
```

候補 0 件なら「公開品質を損なう記述は検出されませんでした」と明記し、走査範囲（ファイル数・除外）を添える。
