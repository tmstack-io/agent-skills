# publish-polish — 公開品質への整形

指定された範囲の散文（Markdown 本文等）とコードコメント・docstring を**初見の読者**——この成果物だけを手にし、作者の環境・歴史・社内事情を何も知らない読者——のレンズで走査し、成立しない記述を before→after の提案リストとして提示し、承認後に書き換える。ファイルの変更は [5] のみで行う（承認と変更範囲の規則は [5] が正本）。

変更するのはコメント・散文のみで、コードの振る舞いは変えない。**コミットはしない**（書き換えは作業ツリーに残し、コミットはユーザーの指示があった場合のみ）。

<!-- BEGIN PROSE-PRESENTATION-CANONICAL -->
**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨する選択肢を理由一言つきで明示し（推奨できる選択肢が無い場合は「推奨なし」とその理由を明示する）、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。

## 引数

- **対象パス（必須・1個以上）**: ファイル、ディレクトリ（再帰）、または glob。引数が無ければ対象をユーザーに確認する。リポジトリ全体を黙って走査しない。
- **`--style`**: 判定に「磨き込み基準」（後述）を追加し、文体・体裁・構成の提案も行う。
- **`--auto [推奨|全件]`**（自動承認）: [1] の3問の確認と [4] の承認範囲の返信を、ユーザーの回答の代わりに規定の値で確定し、ターンを終えずに [5] まで進める。値を省略した `--auto` は `推奨` とみなす。採用値の意味・肩代わりする範囲・肩代わりしない範囲の正本は本スキル同フォルダの `auto-approval.md` で、`--auto` を含む起動では走査を始める前に読了する。以下の各工程にある「自動承認では〜」はこの規定を当該場面に当てはめた挙動。明示指定が無い起動（自然文の依頼を含む）では自動承認にしない。

開始時に承認方式（対話承認 / 自動承認＋採用値）を宣言する。

### 走査対象の除外

- `.gitignore` を尊重する。既定除外: `.git/`、`node_modules/`、`vendor/`、ビルド成果物、バイナリ、lock ファイル。
- CHANGELOG・HISTORY・リリースノート・ADR 等、変更の歴史を語ることが目的の文書は、履歴・運用・視点の基準（カテゴリ 1〜3）を適用しない（歴史がコンテンツそのもの）。**要対応（漏えい）と磨き込み基準は適用する。**除外・縮退したファイルはレポートに明記する。

## フロー

### [1] 公開の姿の確認

走査前に必ず次の3問を散文提示で確認する: **①想定読者は誰か ②配布形態は何か（OSS リポジトリ / パッケージ / 納品物 等）③この成果物は製品として何を約束するか**。同じ一文が公開の姿しだいで「名残」にも「仕様」にもなるため、この回答が以後の全判定の前提になる。ユーザーが判断を委ねた場合は、成果物の内容（README・package.json 等）から①〜③を推定して1文ずつ提示し、その確認をもって確定とする。自動承認では3問を確認せず、呼び出し側が①〜③を宣言して渡していればその宣言で、無ければ同じ推定で各1文を確定し、「呼び出し側の宣言により確定」または「推定により確定」と添えて宣言する（レポートの「公開の姿」にも同じ旨を書く）。

完了条件: ①〜③が各1文で確定し、判定の前提として宣言済み。

### [2] 対象列挙と git 前提チェック

除外規則を適用して対象ファイルを列挙し、「対象はこの N ファイル」と提示する。ファイル数が一度に読み切れない規模のときは、その旨を伝えて範囲の絞り込みか複数回に分けた実行を散文提示で提案する（自動承認では提案せず、読み切れる範囲を今回の対象として分割実行の1回目とし、未走査の残りを [3] の完了条件どおり明示する）。git リポジトリでなければ、適用前のバックアップを勧める（中断はしない。自動承認では勧めず、[5] の 3 で取る複製を戻す手段として適用し、複製の保存先パスを報告に載せる）。作業ツリーの対象ファイルに未コミット変更があれば、書き換えが混ざる旨を伝え commit / stash を勧める（中断はしない）。

完了条件: 対象一覧の提示と git 状態の報告が済んでいる。

### [3] 判定（全読み）

対象ファイルを 1 つずつ読み込み、**すべての散文ブロック・コメント・docstring** に「判定基準」（`--style` 時は「磨き込み基準」も）を適用して候補リストを作る。

完了条件: 全対象ファイルの全散文・コメントブロックについて「候補あり」か「初見の読者に成立する」かを判定し終えている。分割実行の場合は、今回の対象範囲と未走査の残りを明示している。

### [4] 提案レポート

候補を「レポート形式」に従って提示し、同じ内容を実行ごとに一意な名前のファイル `publish-polish-findings-<日時>.json`（日時は `date +%Y%m%d-%H%M%S` で取得。`date` が無い環境では実行環境の手段で同形式の日時文字列を得る）としてセッションの一時領域（Claude Code ではセッション用スクラッチパッドディレクトリ。無ければ OS の一時ディレクトリ — `TMPDIR` / `TEMP` 環境変数の指す場所。いずれも無ければ作業ディレクトリ直下）へ保存してパスを記す（承認までにコンテキストが失われても、このファイルを正として再開できる）。フィールドはレポートの提案項目と同一とする（file / line / category / tier / before / after / reason。要対応は before・after を持たない警告項目として含める）。

レポートの末尾で承認範囲（適用する提案の範囲）を散文提示で確認する。選択肢は定型なので一行に畳んでよい —「承認範囲を返信してください: `全件` / `高確信のみ` / 番号指定（例: `1,3,5`。番号は「提案」の番号） / `見送り`」— 推奨案は階層で決める: 要確認が 0 件なら `全件`、1 件以上なら `高確信のみ`（例: 「推奨: 高確信のみ — 要確認2件は公開の姿の確認が要る」）。要対応（漏えい）が1件以上あれば、あわせて各要対応の対処方針（削除 / 一般化 / 公開可の確認済み）を番号ごとに返信してもらう。自動承認では、推奨案を理由一言つきで示すところまでは同じに書き、返信案内の代わりに「自動承認（`<採用値>`）のため、承認範囲を `<確定した承認範囲>` として続行する」と一行で書いてターンを終えずに [5] へ進む。要対応の対処方針は求めない（[5] の規定どおり未対処として報告に残す）。

完了条件: 要対応警告と全提案が番号付き・階層付きで本文に出力され、永続化パスが提示され、保存した findings ファイルの提案件数と本文の番号付き提案数が一致している。

### [5] 承認 → 適用 → 検証

1. [4] へのユーザーの返信そのものを承認とする。返信を承認範囲（全件 / 高確信のみ / 番号の集合 / 見送り）として解釈し、解釈できない場合のみ、[4] と同じ形式で選択肢を散文提示で再掲する。要対応（漏えい）は承認範囲の対象外で、[4] で返信された対処方針に従う。対処方針が「削除」「一般化」であれば、その内容を before→after として散文提示で確認し、承認を得たうえで、通常の提案と同じ経路（適用 → 検証 → 報告）に載せる。「公開可の確認済み」であれば適用せず報告にのみ残す。自動承認では [4] で確定した承認範囲をそのまま承認とし（`推奨` は示した推奨案、`全件` は全提案）、返信は待たない。要対応は対処方針を判断せず、すべて「未対処（自動承認では判断しない）」として適用せず報告に残す。承認範囲が `見送り` なら 2〜3 を行わず 4 の報告へ進む。
2. 承認された項目のみ、[2] で提示した一覧内のファイルに限って適用する（一覧外のファイルは全工程を通じて変更しない）。編集は文字列一致の置換（Claude Code では Edit ツール）で行い、置換対象は周辺行を含めてファイル内で一意にする。一意化できない項目・置換に失敗した項目は適用せず、4 の報告に「未適用（理由）」として個別に列挙する。
3. 検証: 適用の直前に、変更対象ファイルの複製を [4] と同じ一時領域直下の `publish-polish-backup-<日時>/`（日時は findings ファイルと同じ値）に、作業ディレクトリからの相対パスの階層を保って保存する（git 環境でも同様。検証と復元はこの複製を基準にし、ユーザーの既存の未コミット変更を巻き込まない）。適用後にこの複製との diff で、変更が**散文・コメントの書き換えのみ**であることを確認する。コード行の変化を検出した場合は、当該ファイルを複製から復元し、そのファイルへの適用項目を「未適用（検証で差し戻し）」として報告する。コードファイルには利用可能な軽量構文チェック（`php -l` / `python3 -m py_compile` / `node --check` / `jq .` 等）を実行し、無い言語は未検証と明記する。
4. 報告: 承認方式（対話承認 / 自動承認＋採用値と確定した承認範囲） / 適用 N 件 / 未適用とその理由 / 見送り M 件 / 要対応の残件（自動承認では未対処の件数と、対処にはユーザーの判断が要る旨） / 検証結果と未検証ファイル。

完了条件: 承認された全項目が適用され、検証と報告が済んでいる。

## 判定基準

判定は一問に集約される: **「初見の読者に、この記述はこのまま成立するか」**。成立しない記述を以下のカテゴリで候補化し、それぞれの書き換え方針で案を作る。

書き換えの原則:

- 対象文書の言語で書く（英語文書は英語で）。
- 原文に無い機能・約束・事実を書き加えない。書き換えは視点の変換であり、内容の発明ではない。
- 削除を提案するのは「初見の読者に伝える価値がゼロ」の場合のみ。情報が残る余地があれば書き換えを選ぶ。
- 各提案に階層を付ける: **高確信**（初見の読者に成立しないことが明白で、書き換え案が原文の意味を保つ）/ **要確認**（成立しない可能性が高いが、公開の姿や作者の意図の確認が要る）。迷う場合は要確認として候補に含め、理由に迷いの内容を書く（取捨は承認時のユーザー判断）。

### 要対応: 漏えいの疑い

クライアント名・個人名・メールアドレス・内部 URL・非公開リポジトリ名・認証情報らしき文字列など、**公開してよいかの判断が表現の問題ではない**記述。書き換え案を作らず、レポート最上位に警告として提示し、対処（削除・一般化・公開可の確認）をユーザーに委ねる。参照先の公開状態を実確認できる環境では確認して結果を警告に添える（GitHub リポジトリなら `gh repo view <owner/name>` 等。公開と確認できた参照は要対応から外してよい）。確認できない環境では未確認である旨を警告に明記する。本スキルは secrets スキャナ（gitleaks 等）の代替ではなく、公開前には専用ツールの併用を勧める。

### カテゴリ 1: 履歴・経緯ナラティブ

変更の歴史・こうなった経緯を語る記述。手がかりの種語 — 日本語: 元々・もともと・以前は・従来・旧・かつて・名残・後方互換・互換性のため・代替として・〜の代わりに・削除された（ため／ので）・移行・レガシー。英語: originally・previously・used to・formerly・legacy・backward compat・for compatibility・replaced by・no longer・migration（種語の有無ではなく文脈で判別する）。初見の読者は歴史を共有していない。→ **現在の仕様・現在の手順を語る現在形の記述に書き換える**か、経緯そのものにしか価値が無ければ削除。

### カテゴリ 2: ローカル・個人運用の名残

作者個人の環境・運用や開発時の道具立てに依存し、初見の読者が再現できない記述（特定マシンのパス、個人的な symlink 運用、「私の環境では」、AI エージェント・サブエージェント・プラグイン・MCP 等の開発時の道具立てへの言及、「この環境では〜が使えないため」等）。→ **公開された配布形態（[1] の回答）で成立する手順・説明に書き換える**。作者運用が公式手順を兼ねる場合は、読者が同じ手順を踏める一般形に直す。

### カテゴリ 3: 内部視点・自己言及

作者集団の内側からの語り（「自作」「正本」「本リポジトリに集約」等、読者を作者側に置く表現）や、文書内で定義されない内輪の略語・コードネーム。→ **製品を読者に向けて説明する視点に書き換える**。

### 保護対象（候補に入れない）

- 読者自身に向けた正当な開発者向け情報: セットアップ手順、動作要件、既知の制約。
- rationale（なぜこの設計・制約なのかの説明）。実行環境の制約（OS・ランタイム差異等）は rationale であり、開発時の事情ではない。
- ライセンス・著作権ヘッダ、構造化ドキュメントタグ（`@param` 等）、現役の TODO / FIXME / NOTE。

## 磨き込み基準（`--style` 時のみ追加）

- **表記ゆれ**: 同一概念に複数表記があれば、文書内の多数派に統一する。
- **文体**: です・ます / だ・である等の混在を文書内の多数派に統一する。
- **見出し**: 階層の飛ばし・同レベル間の粒度不整合を直す。
- **未定義用語**: 初見の読者に未知の専門用語・略語へ初出定義を添える。
- **構成**: 章立て・文の流れが読者の理解順に沿うよう再構成を提案する。提示単位は節または章の before→after とし、ファイル全文の置換はしない。

## レポート形式

```
## publish-polish: <対象パス>

公開の姿: <①②③の要約1〜2行>
対象ファイル: N 件（歴史文書として縮退: X 件） / 要対応: X 件 / 提案: M 件（高確信 X / 要確認 Y。--style 分: Z 件）
提案の永続化: <パス>

### 🚨 要対応（漏えいの疑い — 書き換え案なし、対処はユーザー判断）
1. `path/to/doc.md:12` 非公開リポジトリ名への言及: 「…」

### 提案
1. `path/to/doc.md:3`  [カテゴリ2 ローカル運用 / 高確信]
   before: 「~/.claude/skills/ の同名エントリはここへのシンボリックリンク。」
   after:  「各スキルはハーネスのスキルディレクトリに配置して利用する（配置手順は README を参照）。」
   理由: 作者個人の symlink 運用であり、初見の読者には再現できない。
```

候補 0 件なら「公開品質を損なう記述は検出されませんでした」と明記し、走査範囲（ファイル数・除外）を添える。
