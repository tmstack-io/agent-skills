# clarify-ja と client-docs を plainify に一本化し読者を --for でパラメータ化する

client-docs の改名検討（名前が受託クライアント文脈に用途を限定しすぎる）から出発し、利用実態を確認した結果、client-docs の生成機能（対応報告書 / 意思決定資料のテンプレート生成）はほぼ使われておらず、価値の実体は「読者に合わせた平易化」にあると判明した。そこで client-docs を廃止し、clarify-ja を plainify へ改名したうえで、固定読者（非技術者）向けだった `--plain` を自由記述の `--for <読者>` に一般化した。client-docs の中核規律だった「納品物として書く」（開発の内側が読者に透けない）は、plainify の --for 規則に「指定読者の世界に存在しないものは drop 対象」という一般形で吸収した。読者適応の判定基準はすべて「指定読者の判断・理解に必要か」に統一し、旧 --plain の規則群は読者 = 非技術者の較正例として存続する。名前から `-ja` を外す代わりに、日本語専用であることは description 冒頭に明記する。

## Considered Options

- **client-docs を改名して存続させる案（stakeholder-docs / plain-docs 等）**: 生成機能がほぼ使われていない実態が判明し、使わない機能を名前問題ごと維持するコストの方が高いため却下。テンプレートが再び必要になれば git 履歴から別スキルとして再設計する。
- **plainify に生成機能も統合する案**: リライト（正しさの検証はしない・原文の誤りもそのまま磨く）と生成（検証済み事実のみ・捏造禁止・保存先確認ゲート）は契約が根本的に異なり、起動方式も逆（ユーザー起動専用 vs モデル起動型）のため、1 スキル内のモード分岐は出力の安定性を損なうと判断して却下。
- **--for を規定値の列挙にする案**: 読者の型を増やすたびにスキル改定が必要になる。旧 --plain の判定基準は元から「読者の判断・理解に必要か」という読者相対の形で書かれており、自由記述への一般化が自然なため却下。

## Consequences

- `--plain` / `--client` フラグと旧名 clarify-ja / client-docs はエイリアスなしで廃止（クリーンブレイク）。npx skills で旧名導入済みの環境は plainify の再導入が必要。
- 依存元の追随: impact-investigation は `--client` を `--for <読者>` に一般化し依存先が plainify 1 本になった。smart-commit は参照名のみ更新。
- 別リポジトリ claude-skills の deep-pr-review は clarify-ja を参照しているため、同リポジトリ側での更新が別途必要。
- グロッサリ（CONTEXT.md）の「納品物」エントリは削除。概念は plainify の「読者の世界に無いものは落とす」規則に吸収された。
