# 承認ゲートの前は指摘提示をターンの終端に置き、選択式確認を曖昧時のみに降格する

skill-refine は「一覧を出力し終えるまで承認の質問を発行しない」と明記していたにもかかわらず、指摘一覧が本文に出ないまま選択式確認（Claude Code の AskUserQuestion 等）が発行される失敗が頻発した。原因は2つ: サブエージェント委譲の返却はユーザーに表示されないのに「返却を見た＝提示済み」と混同されること、および選択式確認の選択肢説明への要旨記載が「提示した」という誤達成感の受け皿になること。

そこで、承認ゲートの手前を次のプロトコルに再設計した: 指摘に通し番号を振って本文へ全件出力し（完了条件は件数一致で二値化）、適用範囲の指定方法と推奨する適用範囲（理由一言つき）を添えて**ツールを呼ばずターンを終了**する。ユーザーの返信そのものを承認とし、選択式確認は返信が適用範囲として解釈できない場合のフォールバックに限る。提示と承認を「番号指定」で機能的に結合させ、提示なしでは承認が成立しない構造にしている。

## Considered Options

- **detect / exec の2スキルへの分離**: 承認・適用手順をコンテキストから消せるが、exec → detect →
  writing-great-skills の前置きゲート付き参照チェーンと配布単位の倍増という恒久コストを払う割に、
  転記の怠慢（今回の主故障）は防げないため却下。
- **選択式確認を維持したまま次ターンへ分割**: 破られた実績のある「順序・タイミング指示」への
  依存が残るため却下。

## Consequences

happy path に選択式確認が無いのは意図的な設計である。将来の査読で「承認が散文ベース＝不備」と映っても、選択式確認を承認の主経路へ戻さないこと（戻すと提示の擬似受け皿が復活する）。同型の構造（一覧提示→選択式承認、選択肢説明への要旨記載）を持っていた publish-polish と decruft にも同じプロトコルを適用済み。この型が実運用で有効と確認できたら、AGENTS.md のスキル設計規約へ昇格させる。

2026-08-19 追記: skill-refine に自動承認（`--auto`）を加えたが、これは承認ゲートの回答主体をユーザーの返信から起動時指定の承認範囲へ置き換えるだけで、指摘一覧・判定一覧・承認範囲の復唱の本文出力は省かない。「無人なら提示は不要」と巻き戻さないこと（提示は監査可能性と提示・承認の結合の担保であり、承認の入力手段とは独立）。
