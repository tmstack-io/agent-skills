# T3 Code 上では、別 provider への委譲を T3 Code の委譲ツールで行う経路を加える

Status: accepted

tui-harness は、指揮者自身が TUI マルチプレクサのペイン内で動いていることを前提にする。T3 Code（Claude Code や codex 等のハーネスを GUI から駆動するホスト）の上で動くエージェントはペインの中におらず、`mux.sh detect` が失敗する。そのため T3 Code 上では、deep-pr-review は TUI 専用ゲートで開始できず、maestro はハーネス指定を含む起動を中止していた。一方で T3 Code は、駆動するエージェントに子エージェントの委譲ツール（`delegate_task` 等）を渡しており、別 provider のモデルを指定して委譲できる。

**T3 Code 用の委譲基盤 t3-harness を、tui-harness と並ぶ別スキルとして新設し、deep-pr-review（外部レビュアー）と maestro（ハーネス指定のロール）に第2の経路として加える。** 経路は利用スキルが実行環境で選ぶ。判定は TUI 経路を先に行い、従来どおり `mux.sh detect` が検証済みバックエンドを返せば TUI 経路に入る。T3 経路を判定するのは、TUI 経路が成立せず従来は中止していた場合に限る。T3 経路は従来の中止を置き換えるだけで、TUI 経路が成立する環境の挙動は変えない。

あわせて次を定める。

- **T3 経路が受け持つのは別 provider への委譲に限る。** T3 Code がエージェントへ与える指示（以下、ホスト指示）は、同じ provider の子にはハーネス自身のサブエージェントを使い、別 provider のときに委譲ツールを使うよう定めている。
- **ホスト指示を t3-harness の規定より優先する。** tui-harness は自身の規定をセッション側の指示より優先するが、T3 経路では逆にする。ホスト指示は委譲ツールの仕様の一部であり（最初の委譲の前に能力一覧を取得する、実行中の委譲をポーリングしない、レビューと再確認は毎回新しい委譲で行う等）、逆らうと委譲が成立しないため。
- **裁定スコープを持たない。** T3 Code では、子の承認要求に答えられるのは人だけで、親エージェントは答えられない。権限は親から継承し、書き込み範囲はブリーフの規律と利用スキルの事後検査で守る。
- **sidebar と tandem は TUI 専用のままにする。** sidebar は T3 Code の画面で別 provider のスレッドを開けば代わりになる。tandem は、承認の裁定・相談役1体との文脈を保った往復・画面読みのいずれも T3 Code に対応する仕組みが無いか、ホスト指示と衝突する。
- **自己完結の規約に「ホストが提供するツール」を加える。** 存在チェックと、無いときに何もせず中止するゲートを SKILL.md 自身が備える場合に限り、依存してよいものとする。

判断の根拠は、T3 Code の公開ソースの調査と、2026-11-10 の実測（T3 Code Nightly 0.1.8-nightly.20261109、親 Claude Code、子 codex と Claude）である。実測で、codex への委譲とエフォート指定、codex を親にした委譲、完了済みの子への追送での文脈保持、子の質問への回答が成立することを確かめた。

## Considered Options

- **tui-harness のバックエンドに T3 Code を足す** — 却下。tui-harness の本文と `mux.sh` は、ペイン分割・キー送信・画面読み・承認ダイアログへの応答で成り立っており、T3 Code にはどれも対応する操作が無い。`transports/` の実測記録も使われない。
- **`t3 thread` CLI で委譲する** — 却下。CLI で作ったスレッドは親子関係を持たず、完了が親に通知されない。エフォートと実行モードも指定できない。
- **各利用スキルに T3 Code の手順を直接書く** — 却下。委譲ツールの存在確認、委譲先の検証、質問への答え方、止まった子への対処が2スキルに重複する。
- **T3 Code 専用の別リポジトリに置く** — 却下。経路を使う利用スキルが本リポジトリにある。また T3 Code は実行ハーネスではなくホストであり、Claude Code と codex のどちらが親でも同じ委譲ツールが使える（実測）ため、「実行ハーネス固有の機能に依存するスキルは専用リポジトリに置く」には当たらない。
- **sidebar と tandem も T3 経路に対応させる** — 却下（ユーザー判断）。
- **別スキル t3-harness を新設し、deep-pr-review と maestro に経路を加える（採用）**。

## Consequences

- T3 経路では委譲先に読み取り専用を強制できない。権限を狭めると子が人の承認待ちで止まり、止まったことは親に通知されなかった（実測）。deep-pr-review の外部レビュアーは親の権限のまま動かし、レビュー後に作業ツリーの差分を検査する。
- T3 Code の委譲ツールは変化が速い（現行方式は 2026-10-02 に導入され、10-27 にツールを統合する破壊的変更があった）。t3-harness が使うツールは最小限に絞り、作業開始前に存在を確かめ、無ければ中止する。ツールはシェルから呼べず自動の回帰検証にできないため、T3 Code の更新時に手で回す確認手順を `tests/t3-harness/` に置く。
- ADR 0016 の「TUI マルチプレクサが無い場合はハーネス指定を含む起動を中止する」は、T3 経路が成立する環境には適用しない。
- deep-pr-review の「TUI 専用」を外す。フェーズ0のゲートは経路の判定に変わり、TUI 経路も T3 経路も成立しない環境で中止する。
- モデル系統の正本は tui-harness の `catalog.sh family` のまま変えない（T3 Code のモデル ID でもそのまま系統を返す）。t3-harness は系統の規則を持たず、異系統を求める利用スキルが従来どおり tui-harness の規定を適用する。
- 委譲で作られた子スレッドは T3 Code に残る。スキルは削除せず、報告にスレッドへのリンクを添える。
- AGENTS.md の自己完結の条項に「ホストが提供するツール」の例外を加えた。異系統委譲の条項と、CONTEXT.md のペイン前提の用語（指揮者・裁定スコープ・成果物置き場等）への T3 経路での読み方の追加は、利用スキルへの経路追加とあわせて行う。
