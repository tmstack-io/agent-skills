# sidebar — 別席相談

> **明示起動の確認**: 次のいずれかの場合のみ実行する — (1) ユーザーがこのスキルを名指しで
> 起動した場合。(2) 実行中の他スキルの SKILL.md 本文が sidebar の使用を明示的に指示しており、
> その指示に従って本 SKILL.md を Read した場合（参照利用）。それ以外の文脈からの自動適用で
> 読み込まれた場合は、実行せずユーザーに起動意思を確認する（`disable-model-invocation` を
> 解釈しない実行環境での暴発防止）。

**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨する選択肢を理由一言つきで明示し（推奨できる選択肢が無い場合は「推奨なし」とその理由を明示する）、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。

本筋の傍らに席をひとつ立て、ユーザーがいま抱えた問いを実行中と別系統のモデルへ投げ、答えを**素通し**で持ち帰る。実行中のエージェントの答えに納得がいかないときの、その場の相談窓口である。

原則は3つ。

- **別席は軽い** — 合議しない。既定1席、ラウンド管理も収束判定も持たない。どの作業の途中からでも呼べ、工程には紐づかない。
- **素通し** — 別席の回答は全文のまま出す。統合・要約・並べ替えをしない。優劣は、ユーザーに求められたときだけ述べる。
- **無記名** — 手元の案は「すでに出ている案」として渡し、誰が出した案かは明かさない。出どころを知った別席は、遠慮するか、否定するために否定する。

**円卓（roundtable）との使い分け**: 円卓は「エージェントが作った案」を3席の合議で審査し、verdict へ統合する重い儀式である。別席は「ユーザーが抱えた問い」に独立の答えを1つ得る軽い相談で、統合しない。案の妥当性を問うなら円卓、別の発想が欲しいなら別席。

## tui-harness 参照

ペイン操作・委譲・裁定の共通手順は tui-harness を正本とする。作業を始める前に tui-harness の SKILL.md を次の順で探して Read し、このコンテキスト内で適用する — (1) `../tui-harness/SKILL.md`、(2) 実行ハーネス自身のスキルディレクトリをプロジェクト側 → グローバル側の順（Claude Code: `.claude/skills/` → `~/.claude/skills/`、Codex: `.agents/skills/` → `~/.codex/skills/`。他ハーネス用のディレクトリは探さない）。見つからない場合は相談を開始せず、復旧手順（`npx skills add tmstack-io/agent-skills --skill tui-harness`）を案内して中止する。

**呼び出しパラメータ**: 成果物置き場＝手順3で作る相談記録ディレクトリ、push ラベル＝席名（`seat1` / `seat2` …）、裁定スコープ＝相談記録ディレクトリへの書き込み＋通信規約の push（tui-harness の既定どおり）。候補の検証とモデル系統の確定には tui-harness の「異系統委譲」を適用する。同節手順3の同系統の扱いは、本スキルでは手順2の**同系統は起用しない**が定める。

失敗の上限も tui-harness の規定に従う。上限を超えた席の扱い（成功した席のみでの続行・全席失敗時の中止）は手順4が定める。

## 手順

1. **問いの受け取り** — 引数のうち `--` で始まらない自由文を問いとする。問いは**手を入れずそのまま**手順3のブリーフへ運ぶ（問いを整えると実行中のエージェントの枠組みが混ざり、別席の答えがその枠の中に閉じるため）。問いが空、または一語だけで何を聞きたいか判別できない場合に限り、散文提示で確認する。あわせて、相談前にどの作業のどこにいたかを1行で書き留める（手順7で使う）。完了条件：問いの本文が確定し、相談前の作業状況が1行で記録されている。

2. **環境と相手の確定** — tui-harness の `mux.sh detect` が検証済みバックエンドを返さなければ、TUI マルチプレクサが要る旨を案内して中止する。席数は `--cli` の出現数（無指定は1席）。各 `--cli` の値は tui-harness の「委譲先指定値の書式」（`<CLI名>[=<モデル>[@<エフォート>]]`）として解釈し、出現順に1出現を1席に対応させる（同一 CLI を複数席に指定してよい）。`--cli` で明示指定された席は新しく立てる。明示指定の無い席について、セッション内の対応表に生きている別席ペインがあれば、席ごとに続けて使うか新しく立てるかを散文提示で選んでもらう（続用する席は当該ペインの CLI・モデルをそのまま引き継ぎ、以下の確定を省く。生きているペインが複数ある場合や席数に足りない場合も同じ散文提示で席ごとの割り当てを決め、不足分だけ新しく立てる）。新しく立てる席の CLI・モデルは tui-harness の「異系統委譲」で確定する — 当該席の `--cli` 値があれば同節の検証に掛け（モデル未指定〔`=` 省略〕の席は `catalog.sh models` の結果を散文提示で選んでもらう）、`--cli` 自体が無い席は `catalog.sh probe` と `catalog.sh models` の結果を散文提示で選んでもらう。**同系統は起用しない**: `catalog.sh family` の結果が実行中のモデル系統と一致する候補は選ばない（実行中のエージェントの答えに納得がいかない場面のためのスキルであり、同系統は同じ癖の答えを返す）。異系統の候補が無ければ、除外理由と復旧方法を示して中止する（同系統への縮退はしない）。完了条件：席数ぶんの CLI・モデル・モデル系統が確定して全席が実行中と異系統である、または中止を報告している。

3. **ブリーフの作成** — 相談記録ディレクトリ `.sidebar/<連番3桁>-<問いの短い名前>/` を作り（`.sidebar/` の起点は「記録の扱い」の規定に従う。連番は既存ディレクトリの最大連番 +1。初回は `001`）、`question.md` に次の6項目を書く。

   - **問い** — 手順1の本文をそのまま。
   - **すでに出ている案** — 手元の案を全文で写す（要約すると、ユーザーが引っかかった細部が落ちる）。案の無い相談では「案なし」と明記する。案の出どころを示す記述は本文に置かない。
   - **決まったこと** — ユーザーとすでに合意済みの制約。
   - **却下したこと** — ユーザーが退けた案と、その理由。これが無いと、別席は退けられた案を自信をもって持ってくる。
   - **読むべきファイル** — この問いに答えるために要る資料のパスだけを列挙する。席ごとに読む範囲が変わると回答を比べられないため、範囲はここで固定する。
   - **答え方** — 「上の案に引きずられず自分の答えを出せ。結果的に同じ結論になるなら、そう言え」。回答の書き出し先 `answer-<席名>.md` のパス。

   末尾に tui-harness の通信規約ブロックを一字一句コピーする。完了条件：`question.md` に6項目が揃い、通信規約ブロックが末尾にあり、案の出どころを示す記述が本文に無い。

4. **委譲と回収** — tui-harness の「ペイン配置」「ペインの起動」「タスクの委譲」「応答の受け取り」「指揮者裁定」に従い、各席へブリーフを渡して回答を回収する。一部の席だけが失敗の上限に達した場合は、その席を打ち切り、成功した席の回答のみで手順5へ進む（失敗した席とその理由は手順5の提示に併記する）。全席が失敗した場合は中止して原因を報告する。完了条件：全席の回答ファイルを読み終えている、成功した席の回答と失敗した席の理由が揃っている、または中止を報告している。

5. **素通しの提示** — 回答を**全文のまま**提示する（席が複数なら席ごとに分けて、それぞれ全文で出す）。そのあとに**差分注記**を付ける — 手元の案と別席の答えがどこで食い違うかだけを書き、どちらが良いかは書かない（比較対象の案が無い相談では差分注記を省く）。優劣は、ユーザーが尋ねたときに理由を添えて答える。呼び出し元プロジェクトの規約（`CLAUDE.md` / `AGENTS.md` 等）に提示や文体の規定があれば、実行時にそれを読んでこの提示へ適用する。完了条件：成功した席の回答が全文で提示され、失敗した席があればその理由が併記され、差分注記が付いており（案の無い相談では省いており）、求められていない優劣の判断が本文に無い。

6. **追問** — ユーザーが続けて聞く場合、同じペインへ問いの一行だけを送る（ペインが文脈を持っているため、案・参照ファイルは再送しない）。複数席の場合は全席へ同じ問いを送り、ユーザーが席を指定したときはその席だけに送る。回答は同じディレクトリに `answer-<席名>-<連番>.md` として積み、そのつど手順5で提示する。問いが別件に変わったときは手順2へ戻って新しい相談として立て直す（ペインは使い回してよいが、記録ディレクトリは新しく作る）。完了条件：ユーザーが相談の終わりを告げるまで、追問のたびに手順5を通している。

7. **終わり方** — 相談を終えるとき、次の2つを散文提示で**別々に**聞く。(1) 手順1で書き留めた作業へ戻るか。(2) 別席のペインを閉じるか。閉じる場合は tui-harness の「クローズ」に従い、閉じない場合は対応表に残して手順2で選べるようにする。完了条件：2つの回答を得ており、ペインの実状態（閉じた／残した）が対応表と一致している。

## 記録の扱い

`.sidebar/` はプロジェクトルート（`.git` を持つ最も近い上位ディレクトリ。無ければ呼び出し時の作業ディレクトリ）直下に作る。commit しないローカルリソースであり、自動削除しない（後日「あのとき別席は何と言ったか」を引けるようにするため）。git リポジトリで `.sidebar/` が ignore されていなければ、**最初に作る相談で一度だけ** `.git/info/exclude`（ローカル・非コミット）への追記を散文提示で提案し、承認を得てから追記する（プロジェクトの `.gitignore` は編集しない。承認されなかった場合は追記せず、いずれの場合も以後の相談で繰り返さない）。非 git 環境でも同じ場所に作る。

記録に残す文（`question.md` と回答ファイル）の言語は、手元の案の言語に従う。案の無い相談では呼び出し元プロジェクトの既存文書の言語に従い、いずれも判定できなければ対話言語にする。ユーザーへの提示（手順5・7）は対話言語に従う。
