# sidebar — 別席相談

> **明示起動の確認**: 次のいずれかの場合のみ実行する — (1) ユーザーがこのスキルを名指しで
> 起動した場合。(2) 実行中の他スキルの SKILL.md 本文が sidebar の使用を明示的に指示しており、
> その指示に従って本 SKILL.md を Read した場合（参照利用）。それ以外の文脈からの自動適用で
> 読み込まれた場合は、実行せずユーザーに起動意思を確認する（`disable-model-invocation` を
> 解釈しない実行環境での暴発防止）。

**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨する選択肢を理由一言つきで明示し（推奨できる選択肢が無い場合は「推奨なし」とその理由を明示する）、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。
<!-- END PROSE-PRESENTATION-CANONICAL -->

本筋の傍らに席をひとつ立て、ユーザーがいま抱えた問いを、セッションの文脈を添えて実行中と別系統のモデルへ投げる。投げて受理を確認したら本スキルの仕事は終わりで、以後の壁打ちはユーザーがそのペインで直接行い、確定した答えを自分で持ち帰る。実行中のエージェントの答えに納得がいかないときの、その場の相談窓口である。

原則は3つ。

- **片道** — 回答を回収しない。ペインで受理を確認した時点で完了し、答えを読むのも、追い質問をするのも、ペインを閉じるのもユーザーである。
- **文脈を添える** — 問いだけでなく、手元の案・決まったこと・却下したこと・読むべきファイルを渡す。これが無いと、別席は退けられた案を自信をもって持ってくる。
- **無記名** — 手元の案は「すでに出ている案」として渡し、誰が出した案かは明かさない。出どころを知った別席は、遠慮するか、否定するために否定する。

**円卓（roundtable）との使い分け**: 円卓は「エージェントが作った案」を3席の合議で審査し、verdict へ統合する重い儀式である。別席は「ユーザーが抱えた問い」を別のモデルに渡して壁打ちの場を用意する軽い相談で、統合しない。案の妥当性を問うなら円卓、別の発想と対話したいなら別席。

## tui-harness 参照

ペイン操作・委譲の共通手順は tui-harness を正本とする。作業を始める前に tui-harness の SKILL.md を次の順で探して Read し、このコンテキスト内で適用する — (1) `../tui-harness/SKILL.md`、(2) 実行ハーネス自身のスキルディレクトリをプロジェクト側 → グローバル側の順（Claude Code: `.claude/skills/` → `~/.claude/skills/`、Codex: `.agents/skills/` → `~/.codex/skills/`。他ハーネス用のディレクトリは探さない）。見つからない場合は相談を開始せず、復旧手順（`npx skills add tmstack-io/agent-skills --skill tui-harness`）を案内して中止する。

本スキルは tui-harness の**片道委譲**を明示して適用する。呼び出しパラメータは成果物置き場（手順3で作る一時ディレクトリ）のみ。候補の検証とモデル系統の確定には tui-harness の「異系統委譲」を適用し、同節手順3の同系統の扱いは本スキルでは手順2の**同系統は起用しない**が定める。受理の再送上限は tui-harness の規定に従い、超えたら中止して原因を報告する。

## 手順

1. **問いの受け取り** — 引数のうち `--` で始まらない自由文を問いとする。問いは**手を入れずそのまま**手順3のブリーフへ運ぶ（問いを整えると実行中のエージェントの枠組みが混ざり、別席の答えがその枠の中に閉じるため）。問いが空、または一語だけで何を聞きたいか判別できない場合に限り、散文提示で確認する。`--cli` は最大1回で、値は tui-harness の「委譲先指定値の書式」（`<CLI名>[=<モデル>[@<エフォート>]]`）として解釈する。2回以上指定された場合は解釈せず、指定値を示して散文提示で再指定を求める。完了条件：問いの本文が確定している。

2. **環境と相手の確定** — tui-harness の `mux.sh detect` が検証済みバックエンドを返さなければ、TUI マルチプレクサが要る旨を案内して中止する。次に続用の判定を行う: セッション内の対応表に生きている別席ペインがあり、その CLI が `--cli` の指定（無指定なら任意）と一致するなら、続けて使うか新しく立てるかを散文提示で選んでもらう（起動時にユーザーが「前のペインに続けて」等と明示していれば確認を省く。指定モデルがペインの起動モデルと異なる場合は、その旨を示して続用か新設かを確認する）。一致するペインが無ければ新設と宣言する。新しく立てる席の CLI・モデルは tui-harness の「異系統委譲」で確定する — `--cli` の値があれば同節の検証に掛け（モデル未指定〔`=` 省略〕なら `catalog.sh models` の結果を散文提示で選んでもらう）、無ければ `catalog.sh probe` と `catalog.sh models` の結果を散文提示で選んでもらう。**同系統は起用しない**: `catalog.sh family` の結果が実行中のモデル系統と一致する候補は選ばない（実行中のエージェントの答えに納得がいかない場面のためのスキルであり、同系統は同じ癖の答えを返す）。続用する場合も系統を再チェックし、同系統になっていれば「前回は異系統でしたが今は同系統です」と示して続用せず、異系統の新設候補を散文提示する。異系統の候補が無ければ、除外理由と復旧方法を示して中止する（同系統への縮退はしない）。完了条件：続用するペイン、または新設する CLI・モデル・モデル系統（実行中と異系統）が確定している、または中止を報告している。

3. **ブリーフの作成** — 一時ディレクトリ `mktemp -d "${TMPDIR:-/tmp}/sidebar.XXXXXX"` を作り、`question.md` に次の項目を書く。

   - **問い** — 手順1の本文をそのまま。
   - **すでに出ている案** — 手元の案を全文で写す（要約すると、ユーザーが引っかかった細部が落ちる）。案の無い相談では「案なし」と明記する。案の出どころを示す記述は本文に置かない。
   - **決まったこと** — ユーザーとすでに合意済みの制約。
   - **却下したこと** — ユーザーが退けた案と、その理由。
   - **読むべきファイル** — この問いに答えるために要る資料のパス。
   - **引き渡し** — 「回答はこのペインで述べよ。以後の質問はこのペインで直接届く。ファイルへの書き出しと完了通知は不要」。

   **続用の場合**は、前回のブリーフ（対応表に記録した一時ディレクトリの `question.md`）を読み、上の項目のうち前回以降に変わったものだけを同じ項目名で書き、冒頭に「前回のブリーフからの差分」と明記する（問いは新しい問いを書く）。前回のブリーフが読めない（一時領域の掃除で消えた等）場合は全量を書き、その旨を手順5の報告に添える。通信規約ブロックは付けない（片道委譲のため回収先が無い）。完了条件：`question.md` に上記の項目（続用時は差分＋その旨）が揃い、案の出どころを示す記述が本文に無い。

4. **片道委譲** — tui-harness の「片道委譲」に従い、新設なら「ペイン配置」「ペインの起動」でペインを立て、「タスクの委譲」手順1〜3でブリーフを渡して受理を確認する（続用なら既存ペインへ同じ手順で送る）。ペイン ID・CLI・モデル・ブリーフの一時ディレクトリを対応表に記録する。受理の再送上限を超えたら中止して原因を報告する。完了条件：受理完了を確認し対応表に記録している、または中止を報告している。

5. **完了報告** — 「投げました。ペイン `<ID>`（`<CLI名>` / `<モデル>`）で続きをどうぞ」と報告し、本スキルを終える。以後のペインでの対話・承認ダイアログへの応答・ペインを閉じる判断はユーザーが行う（本スキルは関知しない）。相談前に進めていた作業があれば、その作業状況を1行添えて元の作業に戻る。完了条件：ペイン ID・CLI・モデルを報告している。

## 記録の扱い

ブリーフの一時ディレクトリは投げた後も削除しない（相手のモデルがブリーフを読み終える時点を本スキルは観測できないため。OS の一時領域の掃除に委ねる）。回答はペインの中にだけ残る。プロジェクト内にファイルは作らず、git 履歴にも触れない。

ブリーフ（`question.md`）の言語は、手元の案の言語に従う。案の無い相談では呼び出し元プロジェクトの既存文書の言語に従い、いずれも判定できなければ対話言語にする。ユーザーへの提示（手順1・2・5）は対話言語に従う。
