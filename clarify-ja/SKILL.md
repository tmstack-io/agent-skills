# clarify-ja — AI 生成日本語の明快化リライト

AI コーディングエージェント（Claude Code / Codex など）が出力するコードレビュー・
解析結果の「難解・冗長な日本語」を、**意味を 1 つも変えずに**、日本語話者が
すらすら読める平易で自然な日本語へ整形する。
これは **事後リライト専用**。生成時の予防（出力スタイル注入）はしない。

## このスキルの責務と割り切り

- **やること:** 分かりやすさ（明快さ・簡潔さ・自然さ）の改善だけ。
  「語彙・語法」「文」「段落・構成」「見出し・書式」の 4 つのレベルで整形する。
- **やらないこと:** 正しさの検証はしない。原文に技術的・事実的な誤りがあっても、
  指摘せず、意味厳守でそのまま整形する（＝誤った指摘を読みやすく磨いてしまう副作用は
  許容する。正しさの検証は別の責務）。
- **呼び出し方:** ユーザーが直接 `/clarify-ja` を実行するのが基本。加えて、他のスキルが
  本 SKILL.md を Read して**規則を同一コンテキストで適用する**用途も許容する
  （事後リライトは対象テキストが呼び出し元の手元にあるため、別プロセス化する必要がない）。
  Skill ツール経由でのモデル自動呼び出しは不可（`disable-model-invocation: true`）。

## 入力

1. ユーザーが `/clarify-ja` に続けて貼り付けたテキスト。
2. ファイルパス指定（`@path` や「ファイル: path」）。指定があればその内容を読む。
3. 入力が無ければ「整形したいテキストを貼ってください」とだけ尋ねて待つ。
   直前のセッション出力を勝手に対象にしない（自動傍受はしない方針）。

## 手順

### 1. 文体判定（整形前）

文末表現（です・ます / だ・である）を走査する。

- 一貫していれば、**その文体を維持**する（敬体なら敬体、常体なら常体）。
- **文単位で常体と敬体が混在している場合のみ**、整形前に 1 回だけ
  「常体（だ・である）と敬体（です・ます）どちらに統一しますか？」と確認してから整形する。
- 箇条書きの体言止め（「外部呼び出し元なし。」等）は list の慣習であり、混在に含めない。

### 2. リライト規則

**大原則 — 意味厳守:** 主張・指摘の数／強度／条件／例外／数値／評価語（妥当・適切・
望ましい 等の判断）、および文と文の論理関係（因果・逆接・並列・例示）を
1 つも増減しない・すり替えない。この範囲を守る限り、語順の変更・文の分割や統合・
段落内の並べ替えは行ってよい。

**もう 1 つの原則 — 直しすぎない:** 既に明快な箇所は変えない。改善の必要がなければ
そのまま通す（冗長な書き換えをしない）。迷ったら原文を残す。

規則は次の 4 グループ。番号順に「小さい単位 → 大きい単位」で見ていくと漏れがない。

#### 2-1. 語彙・語法 — 言葉を平易にする

- **表現の冗語のみ削除** — 重複、空虚な前置き、冗長な言い回し。情報は削らない。
- **名詞化・サ変名詞の硬さを動詞表現へ** — 「〜の統一の範囲と判断します」のような
  漢語の塊を平易な動詞文へ。
- **英語動詞の生混入を自然な日本語へ** — 例「ハンドラが attach される」→「ハンドラが
  仕込まれます／登録されます」。
- **定着した訳語のあるカタカナ・翻訳調を置換** — 例「コンフィグレーション」→「設定」、
  「〜を考慮する必要がある」→「〜を考える必要がある／〜に注意する」。
- **英語直訳調の受動だけを直す** — 例「〜されることが可能です」→「〜できます」。
  技術文書として自然な受動（「フックが登録されます」等）はそのまま残す。
- **語注（用語の和訳的補足）は、原文・識別子名から確実に導ける範囲のみ可** —
  例 `is_dirty` → 「未保存の変更があるか」。
  ⚠️ **原文に明示されていない事実・仕様の推測や追加は禁止**（ハルシネーション防止）。
  コードベースの知識で補いたくなっても、原文に無い事実は書かない。

#### 2-2. 文 — 一文を読みやすくする

- **長い一文は複数文に分割** — 一文一意に近づける。
- **係り受けを整理する** — 修飾語は被修飾語の近くへ置く。「〜という」「〜であるところの」
  で膨らんだ長い連体修飾（入れ子）は、独立した文に切り出してほどく。
- **間接構文を圧縮する** — 「〜という挙動により〜という状態が発生する」→
  「〜のため〜になる」。「こと」「もの」「状態」を経由した回りくどい言い回しを直接表現へ。
- **省略された主語を補う** — 読み手が主語を補えない文、文をまたいで主語がすり替わる
  箇所には、**原文から確実に導ける場合のみ**主語を明示する。導けなければそのまま残す。

#### 2-3. 段落・構成 — 流れを分かりやすくする

- **結論を先に出す** — 段落の中心となる主張が末尾に埋まっている場合、段落の先頭へ
  出してよい（根拠→結論 の並びを 結論→根拠 に並べ替える）。主張の数・強度・
  論理関係は変えない。
- **1 段落 1 トピック** — 複数の話題が 1 段落に詰まっていれば段落を分ける。
  同じ話題が細切れになっていれば統合してよい。
- **指示語を解消する** — 指示対象が遠い・曖昧な「これ」「その処理」は、指示対象が
  原文から一意に定まる場合のみ、具体的な語へ置き換える。
- **論理関係を明示する** — 文と文のつながりが読み取りにくい場合、原文の論理から
  確実に導ける接続表現（「そのため」「一方」「たとえば」）を補ってよい。
  ⚠️ 原文に無い論理関係を新しく作るのは禁止。
- **概念の明示に「」を使ってよい** — 例「リクエスト限定リスナー」「リクエストで縛る方式」。

#### 2-4. 見出し・ラベル・書式

- **見出し・ラベルの文言を平易化してよい**（セクション構造自体は保つ）— 例「概要」→
  「このPRがやっていること」、「総じて」→「まとめ」、「(情報) …」→「補足① …（短い説明見出し）」。
- **ツール固有の採点タグは削ってよい（ただし既定は保持）** — 削除してよいのは、文中に浮いた
  純粋なツール内部ラベル（`CONFIRMED` / `PLAUSIBLE`、「act対象」等、人間の判断に寄与しないもの）に限る。
  **構造化された重要度・確信度・出所ラベル**（例: 重要度見出し、`確信度: 80`、`出所: review/codex`）は
  読み手の判断材料なので**既定で保持する**。指摘の内容・重要度の実体は落とさない。迷ったら残す。
- **段落内でハードラップしない — 1 文 = 1 行、段落間は空行** — Markdown の表示環境には
  soft line break をそのまま改行として描画するものが多い。そこへ英文 `.md` の慣習で
  80 桁前後の物理折り返しを持ち込むと、句読点のない位置で改行される不自然な表示になる。
  段落内は 1 文 = 1 行を原則とし、段落と段落の間だけ空行で区切る。この形なら、改行を
  そのまま描画する環境でも、1 つの段落に連結する環境でも自然に読める。意図的な改行が
  必要な場合に限り、Markdown の hard break（行末の半角スペース 2 つ、または `<br>`）を
  明示的に置く。

### 3. 保護対象（一字一句保持・言い換え禁止）

- コード／識別子／関数名／フック名／クラス名・メソッド名
  （例 `export/format/value`, `route_check(['/users'], …)`, `Exporter::init()`）
- ファイルパス・`file:line`（例 `export-service.php:120,158`）
- 数値・PR / Issue 番号（例 `#482`, `#5`）
- コードブロック（```` ``` ````）とインラインコード（`` ` ``）の中身
- Markdown のセクション構造（見出しの階層、箇条書きの階層、コードブロック）
- 箇条書きの項目の並び順（重要度順・手順など、並び自体が意味を持つもの）
- 段落内の改行位置（原文が 1 文 = 1 行になっている場合はそれを維持する。可読性を理由に
  勝手に物理折り返しを追加しない）

### 4. 内部検証 — 主張の照合パス（出力前に必ず実行・出力には出さない）

1. 原文から「主張・指摘・条件・例外・数値・評価語・文と文の論理関係」を箇条書きで抽出する。
2. 整形後の文と 1 対 1 で突き合わせ、**情報の増減がゼロ**であることを確認する。
3. 並べ替え・分割・統合をした段落について、因果・逆接などの論理関係と、
   指摘と根拠の対応関係が原文どおりであることを確認する。
4. **整形で補った語注・主語・指示語の置き換え・接続表現・「」明示・平易化した見出し文言が、
   原文または識別子名から確実に導けることを確認する**。原文に無い事実・仕様・論理を
   足していたら削る（ハルシネーション防止）。
5. 不一致（落ちた条件・増えた事実・変わった強度・原文から導けない補足）があれば、
   整形後の文を直してから提示する。

この照合パスは内部処理であり、結果には出さない。

### 5. 出力

- **整形結果のみ**を返す。before/after や変更点リストは付けない。
- 文体確認が必要な場合のみ、整形前に 1 回だけ質問する。

## 較正用 before / after（目標とする整形の強さ）

いずれも実務のコードレビュー出力を想定した例。最後の 1 例は段落・構成レベルの整形を示す。

**見出し＋超長文の分割 — before**

> 概要: user-import / csv-export / audit-log の3モジュールで、register_listeners() に
> 全リクエスト無条件登録されていたリクエスト限定リスナー（export/format/value 等）を、
> boot() の route_check() 通過時にのみ生成される Exporter/Importer クラスの
> コンストラクタへ移設し、notification と同じリクエスト縛りパターンへ統一する修正です。

**after**

> ## このPRがやっていること
> user-import / csv-export / audit-log の3モジュールで、register_listeners() が
> 全リクエストで無条件に登録していた「リクエスト限定リスナー」（export/format/value など）を
> 整理する修正です。これらを boot() の route_check() を通った場合だけ生成される
> Exporter / Importer クラスのコンストラクタへ移し、notification と同じ
> 「リクエストで縛る」方式に揃えています。

→ 見出しを平易化。1 文を複数文に分割。「リクエスト限定リスナー」「リクエストで縛る」を
「」で明示。識別子（`register_listeners()`, `export/format/value`, `route_check()` 等）は無改変。

**英語動詞＋因果連鎖 — before**

> #482 の修正は妥当: CSVエクスポートは export/table/screen（＝対象の一覧画面）で
> ハンドラが attach されるため、管理者一覧（/admins）では
> route_check(['/users'], [csv-export TYPE]) が false となり Exporter が生成されず、
> format_export_value が登録されません。

**after**

> - **#482 は確かに直る:** CSVエクスポートは一覧画面の export/table/screen で
>   ハンドラが仕込まれます。管理者一覧は /admins なので
>   route_check(['/users'], [csv-export TYPE]) が false になり、Exporter が生成されず
>   format_export_value も登録されません。

→ 「attach される」→「仕込まれます」。「（＝対象の一覧画面）」を語注「一覧画面の」へ
畳んで前置。因果連鎖（仕込まれる→ false →生成されない→登録されない）は保持。

**ツール採点タグの除去 — before**

> 検証を通過した act対象の不具合（CONFIRMED/PLAUSIBLE）はありませんでした。

**after**

> 修正が必要な不具合は見つかりませんでした。

→ 人間の判断に寄与しない内部タグ（`act対象`, `CONFIRMED/PLAUSIBLE`）を削除。
「不具合は無かった」という実体は保持。

**結論先出し＋間接構文の圧縮 — before**

> route_check() が false を返した場合に Exporter クラスが生成されないという挙動により、
> 管理者一覧画面においてエクスポート値の整形処理である format_export_value が
> 呼び出されないという状態が発生していることが確認できましたが、これは意図された挙動で
> あると考えられます。

**after**

> この挙動は意図されたものと考えられます。管理者一覧画面では route_check() が false を
> 返して Exporter クラスが生成されないため、エクスポート値を整形する
> format_export_value も呼び出されないことを確認しました。

→ 末尾に埋まっていた結論（意図された挙動）を先頭へ。「〜という挙動により〜という状態が
発生」の間接構文を「〜のため〜も呼び出されない」へ圧縮。評価の強度（「考えられます」）と
「確認できた」という事実は不変。
