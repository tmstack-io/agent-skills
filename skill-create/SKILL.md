# skill-create — 新規スキルの固定工程での作成

> **明示起動の確認**: ユーザーがこのスキルを名指しで起動した場合のみ実行する。
> 文脈からの自動適用で読み込まれた場合は、実行せず、起動する・しないの二択を散文提示で確認する
> （散文提示の定義は下記の正準ブロック）
> （`disable-model-invocation` を解釈しない実行環境での暴発防止）。

<!-- BEGIN PROSE-PRESENTATION-CANONICAL -->
**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨する選択肢を理由一言つきで明示し（推奨できる選択肢が無い場合は「推奨なし」とその理由を明示する）、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。
<!-- END PROSE-PRESENTATION-CANONICAL -->

新規スキル1つを、Step 0 前提確認 → Step 1 設計 → Step 2 執筆 → Step 3 査読 → Step 4 照合 → 最終報告の順で作る。各 Step は完了条件を満たすまで次へ進まない。

**用語**: **適用範囲**は作るスキルが通用すべき範囲（汎用／ハーネス専用／プロジェクト専用）。**設計メモ**は Step 1 で決まった決定事項の一覧で、一時領域の `${TMPDIR:-/tmp}/skill-create-<スキル名>-design.md` に置く（POSIX シェルが無い環境では実行ハーネスが提供する一時ディレクトリを同じ命名で用いる。以下の一時領域のパスも同じ）。**読み替え**は依存スキルの指示を本スキルの運用に合わせて置き換えることで、全件を「依存スキルの読み替え」節が持つ。**成果物言語**は作るスキルの本文の言語で、Step 0 で確定する。

## 起動形

本スキルを名指しで起動する（Claude Code では `/skill-create …`）。

- **説明文**: 作りたいスキルの説明。無ければ、何を作るかの入力を求めて待つ。
- **`--myself` / `--project`**: 適用範囲の指定。`--myself` はハーネス専用（本スキルを実行しているハーネス専用）、`--project` はプロジェクト専用、無指定は汎用。
- **`--max N`**: Step 3 の査読の周回上限。

次のいずれかに該当する場合は、何も作業せず該当箇所と正しい形（上記の書式）を示して中止する: `--myself` と `--project` の同時指定、`--max` の値が1以上の整数でない、上記以外の `--` で始まる引数がある。

## git への態度

本スキルはコミット・push・ブランチ作成・stash を行わない（Step 3 の skill-refine も同じ）。コミットは最終報告でメッセージ案を提示するまでとし、実行はユーザーに委ねる。作成先が git 管理外でも同じ手順で進む（Step 3 の書き換え前の複製は skill-refine が行う）。

## 依存スキルの解決（前置きゲート）

依存スキルの SKILL.md は次の順で解決する: 自スキルの隣（`../<名前>/SKILL.md`）→ 実行ハーネス自身のスキルディレクトリのプロジェクト側 → グローバル側。実体は、Claude Code はプロジェクト側 `.claude/skills/`・グローバル側 `~/.claude/skills/`、Codex はプロジェクト側 `.agents/skills/`・グローバル側 `~/.agents/skills/`、その他のハーネスはそのハーネス自身の2箇所を同じ位置づけで使う。他ハーネス用のディレクトリは探さない。

作業開始前に次の全件が解決できることを確認する。1件でも解決できなければ、何も作業せず解決できなかった名前を示し、該当する案内を出して中止する。

- `mattpocock/skills` 配布: `grill-with-docs`、`grilling`、`domain-modeling`、`writing-for-agents`（SKILL.md と同フォルダの SKILL-MECHANICS.md の両方）
  > 依存する mattpocock/skills のスキルが見つからないため中止しました。`npx skills add mattpocock/skills` で導入してから再実行してください。
- `tmstack-io/agent-skills` 配布: `skill-refine`（SKILL.md と同フォルダの `review-spec.md`・`auto-approval.md`）
  > 依存する skill-refine が見つからないため中止しました。`npx skills add tmstack-io/agent-skills --skill skill-refine` で導入してから再実行してください。

## 依存スキルの読み替え

依存スキルの本文は SKILL.md を Read して同一コンテキストで適用する。適用時は次の読み替えをすべて行う。ここに無い指示は依存スキルの本文のとおりに従う。引用した文言は照合の目印であり、言い回しが違っても同じ意味の指示には同じ読み替えを適用する。依存スキルの指示が本スキルの「git への態度」と食い違う場合は本スキルを優先する。

1. **スキル呼び出し**: 「Call the Skill tool twice, for "X" and "Y"」等のスキル呼び出しは、各スキルを「依存スキルの解決」の順で解決して Read し、同一コンテキストで適用する、と読み替える。
2. **グロッサリーと ADR の書き出し**: `domain-modeling` がグロッサリー（`GLOSSARY.md`・`GLOSSARY-MAP.md`）や ADR（`docs/adr/`）を書く場面では、grilling の途中ではファイルに書かず、確定した用語と ADR にする判断を設計メモに記録する。Step 1 で作成先と作業先のルートを確定した後、作業先のルートがあり作成先がその配下にある場合に限り、記録した内容を作業先へ書き出す。書き出し先は、作業先の規約文書（Step 0 の項目3）がグロッサリーや ADR のファイル名・置き場を定めていればそれ、定めていなければ `domain-modeling` の既定どおりとする。
3. **ユーザーへの確認**: 依存スキルの本文がユーザーに選択・承認・確認を求める場面は、選択式 UI ツールの使用を指示していても散文提示で確認する。`grilling` のラウンド形式（番号付きの問いと推奨回答を本文に並べて回答を待つ形）は、各推奨回答に理由を一言添えたうえで散文提示として使う。
4. **事実の調査**: `grilling` の「dispatch a sub-agent」は、サブエージェント機構がある環境（Claude Code の Agent ツール等）ではそのとおりに、無い環境では自分で調べる、と読み替える。

## Step 0: 前提確認

次の全項目を確定する。完了条件は全項目の確定。

1. **依存**: 「依存スキルの解決」の全件確認を通過している。
2. **引数**: 「起動形」に従い、説明文・適用範囲・`--max` の値（または無指定）を確定し、本文で宣言する。
3. **作業先の規約文書**: 作業ディレクトリから上方向に最も近い `.git` を持つディレクトリ（無ければ作業ディレクトリ）を作業先のルートとし、そこにあるエージェント向け規約文書（Claude Code では CLAUDE.md・AGENTS.md・`.claude/rules/`、Codex では AGENTS.md、その他のハーネスでは当該ハーネスの規約文書。いずれも存在するものすべて）を読む。無ければ「規約文書なし」として進む。
4. **成果物言語**: 作業先の規約文書がスキル本文の言語を定めていればそれ、無ければ作業先の既存スキルの SKILL.md の言語、どちらも無ければ対話言語とする。コミットメッセージ案は、言語を `git log` の既存メッセージに合わせ（履歴が無ければ成果物言語）、規約文書がコミットメッセージの規則を定めていればそれに従う。

## Step 1: 設計（grill-with-docs）

`grill-with-docs` を Read し、読み替えを適用して `grilling` と `domain-modeling` を適用し、起動時の説明文を題材に grilling を行う。設計ツリーには次の枝を必ず含め、全枝の決定を得る（「該当なし」も決定として扱う）。

- スキル名（kebab-case）と目的
- 起動方式（モデル起動型か明示起動専用か）と description に載せるトリガー
- 引数
- 手順と、各手順の完了条件
- 成果物の形式・保存先・命名
- ユーザーに選択・承認・確認を求める場面
- 依存（他スキル・外部 CLI）と、見つからない場合の扱い
- git への態度（ループ・自動修正系のスキルの場合）と非 git 環境での挙動
- 出力言語（対話出力と成果物出力の別）

grilling が `grilling` 自身の終了条件（frontier が空になり、共有理解に達したことをユーザーが確認した）を満たしたら、設計メモを書く（同名の設計メモが残っていれば前回の残骸として置き換える）。書式は、冒頭に適用範囲・スキル名を置き、続けて決定事項を1件1ブロックで `D1` から番号を振って並べ、各ブロックに「内容」「目的（この決定で何を実現するか）」「対応箇所（Step 2 で記入）」の3行を持たせる。

続けて作成先を散文提示で確認する。候補と推奨は適用範囲に応じて次のとおりとし、どの候補にも当てはまらない場合は任意のパスを受け付ける。

- プロジェクト専用: 作業先のルート直下にある、実行ハーネスのプロジェクト側スキルディレクトリ（実体は「依存スキルの解決」の定義）の `<スキル名>/` を推奨とする（理由: プロジェクトの中で通用する置き場のため）。
- 汎用・ハーネス専用: 作業先のルート直下の `<スキル名>/` と、実行ハーネスのグローバル側スキルディレクトリの `<スキル名>/`。作業先のルート直下に `*/SKILL.md` があればルート直下を推奨とし（理由: 作業先がスキル集のため）、無ければグローバル側を推奨とする（理由: 作業先がスキル集ではないため）。

選ばれた場所に同名のディレクトリが既にある場合は、作成先に使わず、別のスキル名を散文提示で確認する（本スキルは新規作成専用のため）。改名した場合は設計メモのスキル名の決定事項とファイル名を新しい名前に直す。確定した作成先の絶対パスを設計メモの冒頭に書き足す。

作成先が作業先のルート配下に無い場合は、作成先から上方向に最も近い `.git` を持つディレクトリを作業先のルートとして決め直し、Step 0 の項目3と項目4をやり直す（`.git` が無ければ作業先のルートは無いものとし、規約文書なし・既存スキルなしとして判定する）（執筆で従う規約と、Step 3 の査読で照合される規約を同じものに揃えるため）。続けて、読み替えの項目2に従いグロッサリーと ADR を書き出す。

完了条件: 設計メモに必須の全枝が決定事項として書かれており、作成先の絶対パスが確定して設計メモに記されており、作業先のルートが作成先に合わせて確定している。

## Step 2: 執筆

次の全件を読了してから書く。

- `writing-for-agents` の SKILL.md と SKILL-MECHANICS.md
- `skill-refine` 同フォルダの `review-spec.md`。冒頭のモード別の適用表のうち、適用範囲に対応する列（汎用＝既定、ハーネス専用＝`--myself`、プロジェクト専用＝`--project`）が「適用」とする項目を執筆基準にする。散文提示の正準ブロックを転記する場合の正本は、解決した `skill-refine` の SKILL.md の `PROSE-PRESENTATION-CANONICAL` マーカー間の本文とする
- Step 0 の項目3で読んだ作業先の規約文書

作成先に SKILL.md と、設計メモが求める参照ファイルを、Step 0 で確定した成果物言語で作る。作成先が作業先のルート配下にあり、作業先の規約文書がスキル新設時の付随作業（収録一覧の更新・ハーネス別メタデータの作成・スキルディレクトリへのリンク作成等）を定めていれば、それもこの工程で行い、行った作業を記録しておく。

書き終えたら次の2つを確かめ、満たさない点を直して再度確かめる。

1. **設計メモとの対応**: 全決定事項について、その内容を実現している箇所（ファイル名と節名）を設計メモの「対応箇所」に書く。書けない決定事項があれば、スキル側に書き足す。
2. **自己点検**: 執筆基準の全項目を作ったスキルに適用し、指摘ゼロになっている。

両方を満たしたら、作成先ディレクトリを一時領域の `${TMPDIR:-/tmp}/skill-create-<スキル名>-written/` へ丸ごと複製する（Step 4 で査読前後の差分を取るため。同名の複製が残っていれば置き換える）。

完了条件: 設計メモの全決定事項に対応箇所が記入済み、自己点検が指摘ゼロ、執筆直後の複製が作成済み。

## Step 3: 査読（skill-refine の自動承認）

`skill-refine` を Read し、その Step 2 が定める査読台帳（判定済みの指摘の記録）が残っていてヘッダの対象絶対パスが作成先と一致すれば、新規作成の対象に属さない前回の残骸なので削除する（パスが異なる台帳は skill-refine 自身が作り直す）。続けて、次の引数で起動されたものとして同一コンテキストで適用する。

`<作成先の絶対パス> [--myself | --project] --auto 推奨 [--max N]`

適用範囲の引数は起動時の `--myself` / `--project` をそのまま付け、汎用なら付けない。`--max` は起動時に指定された場合だけ付け、無指定なら skill-refine の既定に従う。

skill-refine が自動承認でも散文提示で止まる場面（点検者の選択・取り違えガード等）は、skill-refine の規定どおりユーザーに確認する。skill-refine が中止した場合は Step 4 へ進まず、中止の理由を添えて最終報告を出して終える（照合と査読の項目は「中止のため未実施」と書く）。

完了条件: skill-refine の Step 6 の報告が出力されているか、中止が確定している。

## Step 4: 照合

執筆直後の複製と現在の作成先を比べ、設計メモの全決定事項を次の3区分のどれかに振り分ける。

- **一致**: 対応箇所の節の本文が執筆直後の複製と同一。
- **自動更新**: 対応箇所が変わったが、原因となる適用済みの指摘を査読台帳に辿れ、決定事項の目的は保たれている（言い回し・構成・実現手段だけの変更）。設計メモの内容と対応箇所を現在のスキルに合わせて直し、ユーザーには提示しない。
- **要判断**: 次のどちらかに当たる — (1) 変更の原因となる適用済みの指摘を査読台帳に辿れない。(2) 原因となる指摘はあるが、決定事項の目的が果たせなくなった（その機能が無くなった）。

あわせて、執筆直後の複製との差分のうち、どの決定事項の対応箇所にも属さない変更を全件洗い出し、原因となる適用済みの指摘を査読台帳に辿れないものを要判断に加える（項目名は決定事項の番号の代わりに変更箇所とする）。

要判断が1件以上あれば、各項目を「決定事項の番号と内容」「何がどう変わったか」「原因の指摘（辿れない場合はその旨）」の属性で並べた一覧として散文提示し、項目ごとに次のどちらかを選んでもらう。

- **戻す**: 決定事項をスキルに書き戻す（決定事項に属さない変更は、執筆直後の複製の記述に戻す）。Step 3 は回し直さず、最終報告に「査読の指摘を退けて戻した決定事項」として指摘の内容とともに載せる。
- **受け入れる**: 変更を受け入れ、設計メモの当該決定事項を現在のスキルに合わせて直す（決定事項に属さない変更は、そのまま残し設計メモは直さない）。

推奨は項目ごとに、決定事項の目的を果たす記述が現在のスキルのどこにも無ければ「戻す」、あれば「受け入れる」とし（決定事項に属さない変更は、どの決定事項の目的も損なっていなければ「受け入れる」、損なっていれば「戻す」）、理由を一言添える。

完了条件: 全決定事項が3区分のどれかに振り分け済みで、要判断の全項目が「戻す」か「受け入れる」のどちらかに決着し、戻す項目の書き戻しが済んでいる。

## 最終報告

次の全項目を報告する。

- **適用範囲と作成先**: 適用範囲と作成先の絶対パス。
- **作成・変更したファイル**: スキル本体、規約に従って行った付随作業、Step 1 で書き出したグロッサリーと ADR、Step 4 で書き戻したファイル。
- **査読**: 周回数、査読収束の判定（skill-refine の報告の表記のまま）、適用件数、査読台帳のパス、書き換え前の複製先（skill-refine が複製した場合）、skill-refine が実施せず持ち越した操作（あれば）。
- **照合**: 一致の件数、自動更新の件数、戻した決定事項（原因の指摘の内容とともに）、受け入れた決定事項。
- **設計メモ**: 設計メモのパス。
- **コミットメッセージ案**: 作成・変更したファイルが属する git リポジトリごとに、Step 0 の項目4の規則で書いたタイトルと必要なら本文。git 管理外のファイルは案に含めず、その旨を書く。
