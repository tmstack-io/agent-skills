# impact-investigation — 影響範囲調査レポート

外部起点の指摘（CVE / クライアント指摘 / バグ報告）を入力に、read-only の横断調査を行い、影響範囲・原因・修正が必要な箇所をレポートとして提示する。**調査と修正は分離する**: このスキルはコードを一切変更しない。修正はレポート提示後、ユーザーが承認した箇所のみ別途着手する。

**`--for` 指定時の前提チェック（調査開始前）**: 本スキルの `--for` は同梱スキル plainify に依存する。調査を始める前に、`plainify/SKILL.md` を次の順で探して読む — (1) 本スキルの隣（`../plainify/SKILL.md`）、(2) 実行エージェント自身のスキルディレクトリのプロジェクト側 → グローバル側（Claude Code: `.claude/skills/` → `~/.claude/skills/`、Codex: `.agents/skills/` → `~/.codex/skills/`。他のエージェントも自身の2箇所を同順。他エージェント用のディレクトリは探さない）。どこにも見つからなければ**調査に着手せず中止**し、復旧手順を案内する（agent-skills リポジトリ `tmstack-io/agent-skills` から plainify を導入して再実行。例: `npx skills add tmstack-io/agent-skills --skill plainify`）。通常レポート（`--for` なし）はこの依存を持たない。

<!-- BEGIN PROSE-PRESENTATION-CANONICAL -->
**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨できる選択肢がある場合は理由を一言添えて明示し、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。
<!-- END PROSE-PRESENTATION-CANONICAL -->

## Step 0: 保存先の確認

調査に入る前にレポートの保存先を確定する。まずプロジェクトに調査レポートの置き場（`.spec/`・`docs/` 等の慣例ディレクトリ）があるかを調べ、有無に応じた選択肢を散文提示で確認する:

- **置き場あり**: 「置き場に保存（推奨）」（既存ファイルの命名慣習に合わせた提案パスを添える）／「一時領域」／任意パスの入力
- **置き場なし**: 「一時領域（推奨）」／「`docs/investigation/YYYYMMDD-<slug>.md` を新設して保存」／任意パスの入力

一時領域はセッションの一時領域（Claude Code ではスクラッチパッドディレクトリ。無い環境では OS の一時ディレクトリ）で、報告後に削除する手間が要らない行き先。一時領域に置く場合のファイル名は `YYYYMMDD-<slug>.md` に従う。プロジェクト内へのファイル・ディレクトリの作成は、この確認で承認された場所に限る。ここで確定しておくことで、以降はレポート生成まで停止せずに走り切れる。

完了条件: 保存先パスが1つに確定している。

## Step 1: 論点整理

入力から以下を確定する:

- **問題の技術的実体**: 何が問題とされているか。CVE の場合は脆弱性の内容・影響バージョン・攻撃条件を、情報が手元に無ければ Web 検索で確認する（Claude Code では WebSearch / WebFetch。Web を参照できない環境では、確認できなかった項目を「判定不能・要確認」として情報不足を明記する）
- **調査観点**: どの API / 関数 / 設定 / 挙動が使われていると影響するか
- **検出すべき影響の種類**: エラー発生・セキュリティ露出・UX 障害 等、入力に応じて具体化する

完了条件: 「この調査で答えるべき問い」が箇条書きで列挙されている。入力が曖昧で問いを立てられない場合は散文提示で確認する。

## Step 2: 横断調査

コードベース全体を対象に、Step 1 の問いごとに順に調査する。並列サブエージェントが使える環境（Claude Code の Agent ツール等）では、独立した複数の問いをサブエージェント（プロンプトに読み取り専用・編集禁止を明記）へ 1 メッセージで並列起動して分担させてよい。その場合も判断と統合は本体で行う。

各問いは「候補箇所の列挙（テキスト検索・ファイル名パターン検索。Claude Code では Grep / Glob、無い環境では grep / find 等の CLI）→ 実際に影響するかの文脈確認（該当コードの読解）」の2段で調べる。検索ヒットをそのまま影響と断定しない。

完了条件: Step 1 の**全ての問い**に、次のいずれかの判定が付いている — 影響あり（根拠 file:line 付き）/ 影響なし（確認した根拠付き）/ 判定不能（理由と、判定に必要な追加情報）。

## Step 3: 重大度分類

検出した影響を分類する:

- **Critical**: セキュリティ露出・データ破損・サービス全面停止
- **High**: 機能停止・Fatal / 例外の発生
- **Medium**: UX 障害（404・表示崩れ・操作不能）・Warning 級のエラー
- **Low**: Notice・ログ汚染・軽微な劣化

## Step 4: レポート生成・保存

以下の構成で Markdown レポートを生成する:

```markdown
# 影響範囲調査: <タイトル>

## 調査起点
<CVE 番号・指摘文面・報告の要約>

## 調査範囲と方法
<対象コードベース・調査した問いの一覧・使った手段>

## 影響範囲
| 重大度 | 箇所 (file:line) | 影響内容 | 根拠 |
|---|---|---|---|

## 原因
<影響が生じる仕組みの説明>

## 修正が必要な箇所（提案）
<箇所ごとに修正方針を提示。このスキルでは実施しない>

## 判定不能・要確認
<判定できなかった問いと、判定に必要な条件>
```

**`--for <読者>` 指定時（読者適応レポート）**: 読者を指定読者（例: `--for クライアント` ならクライアント等の非エンジニア）とし、冒頭の前提チェックで読み込んだ plainify の **--for モードの規則**（読者の世界に無いものの drop を含む）を、生成時にこのコンテキストで適用する。レポート構成と保存先は本スキルの規定を維持する。適用の要点:

- 影響箇所の `file:line` は読者が修正範囲を確認する判断材料なので、keep-or-drop は常に keep（落とさない）
- 「修正が必要な箇所（提案）」は方針の平易な説明を主とし、技術的な詳細は補足に回す

保存先: Step 0 で確定したパス。

完了条件: Step 2 の全判定（影響なし・判定不能を含む）がレポートに現れている。

## Step 5: HTML ダッシュボード化（`--html` 指定時のみ）

レポートを単一 HTML ファイル（外部 CDN・スクリプト依存なし）として、レポートと同じディレクトリに併産する:

- 重大度で色分けした影響範囲テーブル。テーブルは `overflow-x: auto` のコンテナに入れ、ページ全体は `max-width` 固定
- 冒頭に重大度別件数のサマリー
- 生成過程・セッション由来のコメントを含まないクリーンな初版として出力する

## 報告

レポートの保存パスと要約（重大度別件数・最重要の指摘）を提示し、**修正候補の承認を求めて停止する**。承認された箇所のみ修正に着手する。`--for` なしで生成したレポートを後から特定読者向けに清書する場合は、同リポジトリの plainify（`--for <読者>`）を使う。
