# impact-investigation — 影響範囲調査レポート

外部起点の指摘（CVE / クライアント指摘 / バグ報告）を入力に、read-only の横断調査を行い、影響範囲・原因・修正が必要な箇所をレポートとして提示する。**調査と修正は分離する**: このスキルはコードを一切変更しない。修正はレポート提示後、ユーザーが承認した箇所のみ別途着手する。

## Step 1: 論点整理

入力から以下を確定する:

- **問題の技術的実体**: 何が問題とされているか。CVE の場合は脆弱性の内容・影響バージョン・攻撃条件を、情報が手元に無ければ WebSearch / WebFetch で確認する
- **調査観点**: どの API / 関数 / 設定 / 挙動が使われていると影響するか
- **検出すべき影響の種類**: エラー発生・セキュリティ露出・UX 障害 等、入力に応じて具体化する

完了条件: 「この調査で答えるべき問い」が箇条書きで列挙されている。入力が曖昧で問いを立てられない場合は AskUserQuestion で確認する。

## Step 2: 横断調査

コードベース全体を対象に、Step 1 の問いごとに調査する。問いが複数あり独立している場合は、サブエージェント（プロンプトに読み取り専用・編集禁止を明記）を 1 メッセージで並列起動して分担させ、判断と統合は本体で行う。

各問いは「候補箇所の列挙（grep / Glob）→ 実際に影響するかの文脈確認（該当コードの読解）」の2段で調べる。grep ヒットをそのまま影響と断定しない。

完了条件: Step 1 の**全ての問い**に、次のいずれかの判定が付いている — 影響あり（根拠 file:line 付き）/ 影響なし（確認した根拠付き）/ 判定不能（理由と、判定に必要な追加情報）。

## Step 3: 重大度分類

検出した影響を分類する:

- **Critical**: セキュリティ露出・データ破損・サービス全面停止
- **High**: 機能停止・Fatal / 例外の発生
- **Medium**: UX 障害（404・表示崩れ・操作不能）・Warning 級のエラー
- **Low**: Notice・ログ汚染・軽微な劣化

## Step 4: レポート生成・保存

以下の構成で Markdown レポートを生成する:

```markdown
# 影響範囲調査: <タイトル>

## 調査起点
<CVE 番号・指摘文面・報告の要約>

## 調査範囲と方法
<対象コードベース・調査した問いの一覧・使った手段>

## 影響範囲
| 重大度 | 箇所 (file:line) | 影響内容 | 根拠 |
|---|---|---|---|

## 原因
<影響が生じる仕組みの説明>

## 修正が必要な箇所（提案）
<箇所ごとに修正方針を提示。このスキルでは実施しない>

## 判定不能・要確認
<判定できなかった問いと、判定に必要な条件>
```

**`--client` 指定時（非エンジニア向けレポート）**: 読者をクライアント等の非エンジニアとし、同リポジトリの client-docs の共通仕様のうち**書き方の項目**（納品物として書く・捏造禁止・平易な日本語・最終整形）を読み込んでこのコンテキストで適用する。レポート構成と保存先は本スキルの規定を維持する。適用の要点:

- 「影響内容」「原因」は専門用語を言い換えた平易な日本語で書き、読者の判断に不要な技術詳細は落とす
- 影響箇所の `file:line` はクライアントのシステムに関する事実なので保持する
- 「修正が必要な箇所（提案）」は方針の平易な説明を主とし、技術的な詳細は補足に回す

保存先: プロジェクトの調査レポート置き場（`.spec/`・`docs/` 等の既存慣習）に従い、既存ファイルの命名慣習に合わせる。慣習がなければ `docs/investigation/YYYYMMDD-<slug>.md`。

完了条件: Step 2 の全判定（影響なし・判定不能を含む）がレポートに現れている。

## Step 5: HTML ダッシュボード化（`--html` 指定時のみ）

レポートを単一 HTML ファイル（外部 CDN・スクリプト依存なし）として併産する:

- 重大度で色分けした影響範囲テーブル。テーブルは `overflow-x: auto` のコンテナに入れ、ページ全体は `max-width` 固定
- 冒頭に重大度別件数のサマリー
- 生成過程・セッション由来のコメントを含まないクリーンな初版として出力する

## 報告

レポートの保存パスと要約（重大度別件数・最重要の指摘）を提示し、**修正候補の承認を求めて停止する**。承認された箇所のみ修正に着手する。`--client` なしで生成したレポートを後からクライアント提出用に清書する場合は、同リポジトリの client-docs（report モード）を使う。
