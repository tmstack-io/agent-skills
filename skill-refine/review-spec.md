# skill-refine 査読基準（正本）

skill-refine の点検で適用する査読基準と、指摘一覧の返却フォーマットの正本。点検者（委譲されたサブエージェント・ペインの委譲先、または自己実行する実行エージェント）は、点検を始める前にこのファイルを読了する。

## モード別の適用表

宣言されたモードに従い、適用する項目をこの表で確定する（行名は基準本文の見出しと対応する）。

| 基準・項目 | 既定（汎用） | `--myself` | `--project` |
|---|---|---|---|
| W. craft | 適用 | 適用 | 適用 |
| A. 公開品質 | 適用 | 適用 | 適用（「`--project` 時の読み替え」つき） |
| B-1 共通 | 適用 | 適用 | 適用（「`--project` 時の読み替え」つき） |
| B-2 汎用スキル基準 | 適用 | 適用しない | 適用しない |
| B-3 実行ハーネス専用基準 | 適用しない | 適用 | 適用しない |
| C. プロジェクト非依存 | 適用 | 適用 | 適用せず、代わりに「プロジェクト整合」を査読 |
| D. 運用の規定 | 適用 | 適用 | 適用 |
| E. 不足 | 適用 | 適用 | 適用 |
| F. コンテキスト負荷 | 適用 | 適用 | 適用 |

## 査読基準

適用表が定める項目を**全項目**適用する。完了条件: 各項目について「指摘あり（箇所と内容）」か「問題なし」かを判定し終えている。

**W. craft** — writing-for-agents 基準

- writing-for-agents の SKILL.md と SKILL-MECHANICS.md を読了してから、そこに定義される全観点（Invocation の選択 / context pointer〔description を含む〕の書き方 / 情報階層と progressive disclosure・co-location / 分割判断 / 完了条件と legwork / leading words と negation / Pruning〔single source of truth・environment を正本とみなす cache の扱い・relevance・no-op〕と、各レバーの隣に置かれた失敗モード）を対象スキルに適用する。基準の内容はここに再掲しない（正本は writing-for-agents 側）
- 指摘には writing-for-agents の術語（premature completion / duplication / no-op 等）をそのまま用いる（和訳で言い換えない）。指摘文面では各術語の初出に一言の日本語説明を添える
- description の書き方・progressive disclosure・sprawl・duplication のうち F の条項で二値判定できるものは F として挙げ、W では重ねて挙げない（W は F に条項が無い観点 — Invocation の選択・分割判断・leading words・no-op 等 — に使う）

**A. 公開品質** — 第三者がそのまま使えるか

- 前提知識・暗黙の文脈なしで手順を実行できるか
- frontmatter の整合（name / argument-hint がディレクトリ名・本文の引数仕様と一致しているか。起動方式の選択は W、description と argument-hint の内容は F で査読する）
- `--project` 時の読み替え: 「第三者」はチームメンバー（当該リポジトリの開発者）と読む。マシン固有パス・特定ユーザー名の禁止は維持する（リポジトリ相対パスは可）

**B. 環境非依存** — 実行環境を選ばないか

- **B-1 共通**:
  - 特定マシンの絶対パス・特定ユーザー名・ローカル固有の設定への依存
  - 他スキル・プラグイン・独自ツールへの参照（標準ツールと本体機能のみで完結させる）。例外: 対象スキルと同一の配布単位（同一リポジトリ）内のスキルを「SKILL.md を Read して同一コンテキストで適用する」形で参照するのは可。同一配布単位外の外部スキルへの依存も、対象スキル自身が前置きゲート（見つからない場合に黙って縮退せず、導入手順を案内して中止する規定）を明記していれば可
  - OS 依存コマンド（依存する場合は分岐か注記があるか）
  - `--project` 時の読み替え: 当該プロジェクト内の他スキル・現に存在するグローバルスキル・リポジトリ内の独自ツール（スクリプト・Makefile ターゲット等）への依存は可。査読の焦点を依存の排除から**依存の健全性**に反転する — 参照先が実在するか（dangling 参照の検出）、リポジトリ外依存（グローバルスキル等）が SKILL.md に前提として明記されているか
- **B-2 汎用スキル基準** — スキルディレクトリ単体のコピーで他ハーネスに配布されても成立するか:
  - 特定ハーネス固有のツール名の裸使用（例: WebSearch / Agent ツールを能力の説明なしに指示する）。能力主体の表現＋固有名の例示（「Web 検索できる環境では検索で確認し、できなければ情報不足と明記する（Claude Code では WebSearch）」の形）になっているか
  - 参照解決の手段としての絶対パス（`~/.claude/skills/...` 等を唯一の解決手段にした他スキル参照）。隣接優先（`../<名前>/SKILL.md`）→ 実行ハーネス自身のスキルディレクトリ（プロジェクト側 → グローバル側）の解決順になっているか。他ハーネス用ディレクトリの横断探索を書いていないか
  - 同梱スキルへの依存に前置きゲートが無い。作業の成立に必須の依存は、見つからない場合に「復旧手順を案内して中止する」規定があるか。代替経路にだけ使う依存は、見つからない場合に「縮退した事実と復旧手順を報告に載せる」規定があるか（いずれも黙って縮退しないことが要件）
  - 暴発防止などの安全機構を、実行環境によって解釈されない frontmatter フィールド（`disable-model-invocation` 等）だけに依存していないか。依存している場合、本文冒頭の明示起動ゲートのような frontmatter に依存しない代替が併記されているか
- **B-3 実行ハーネス専用基準** — モード宣言で自己申告した名称・固有ツール・配置を物差しに、実行ハーネスの専用スキルとして正しいか:
  - 実行ハーネス自身の固有ツール名・機能・配置パスへの依存は正当（能力主体への言い換えを要求しない）。実行ハーネス**以外**のハーネスの固有ツール名・配置パスに動作を依存していれば指摘する
  - 他スキル参照の解決順が実行ハーネスの配置（自スキルの隣 → プロジェクト側 → グローバル側）になっているか
  - 実行ハーネスが解釈しない frontmatter フィールドに安全機構（暴発防止等）を依存していないか（例: codex 上の `--myself` 査読で、対象が `disable-model-invocation` だけを暴発防止にしている → 本文への明示起動ゲート追加を指摘する）

**C. プロジェクト非依存** — 特定リポジトリの構成・命名・ドメイン知識が混入していないか。プロジェクト固有情報は「実行時に収集する手順」に置き換える。`--project` 時はこの項を適用せず、代わりに**プロジェクト整合**を査読する: プロジェクトのエージェント向け規約文書（Claude Code では CLAUDE.md と `.claude/rules/`、Codex では AGENTS.md、その他のハーネスでは当該ハーネスの規約文書）と矛盾していないか、それらが既に定める規則をスキルが再掲していないか（正本はプロジェクト文書側。スキルからは削る）。参照するプロジェクトルートは、対象 SKILL.md から上方向に最も近い `.git` を持つディレクトリを基本とし、`.git` が無ければハーネス規約ディレクトリ（`.claude/` 等）を持つ最も近いディレクトリとする（cwd ではなく対象スキルの所属で決める）。規約文書が見つからない場合は「規約文書なし」と判定し、その旨を返却の判定一覧に記す

**D. 運用の規定** — 成果物・ユーザー確認・git の扱いが定まっているか

- 成果物のフォーマット・保存先・命名が規定されているか
- ユーザーへの選択・承認・確認が散文提示になっているか — 選択式 UI ツール（AskUserQuestion 等）の使用を指示せず、`PROSE-PRESENTATION-CANONICAL` マーカーで区切られた正準ローカル定義ブロックが SKILL.md の冒頭付近に転記され、選択・確認の各場面がブロックの内容を再説明せず「散文提示で確認する」の形で参照しているか。各場面の固有指示（選択肢の中身・一行畳みの宣言・推奨案）が、対象 SKILL.md に転記された正準ブロックの規定（正本は skill-refine 自身の SKILL.md の同名マーカー間の本文で、点検者へは委譲プロンプトで渡される。ここに再掲しない）と矛盾していないか。対象にブロックが無い、または本文が正本と食い違う場合の修正案は、正本の本文を一字一句そのまま転記する形で書く
- サブエージェント委譲を持つスキルが、`SUBAGENT-RETURN-CANONICAL` マーカーで区切られた正準ローカル定義ブロックを転記し、各委譲場面が「サブエージェント返却規約に従う」の形で参照しているか（Claude Code 固有の手当て。委譲を持たないスキルには適用しない）
- ループ・自動修正系のスキルが git への態度を規定しているか（履歴に触れるか否か・非 git 環境での挙動。未規定だと実行側が履歴操作を発明する）

**E. 不足** — 分岐やエラー時の挙動が未定義の箇所、実行に必要なのに書かれていない前提

**F. コンテキスト負荷** — description・argument-hint・ルート SKILL.md が読み込み時に払う負荷を二値で判定する（W の観点のうち判断の余地が残るものを、多重点検で落ちないよう条項化したもの）

- **F-1 description の最短化**: `disable-model-invocation: true` の無いスキル（モデル起動型）は「何をするか」1文＋トリガー1分岐、有るスキル（ユーザー起動型）はヒト向け1行要約に収める。次のいずれかを含めば指摘あり — オプション（`--xxx`）の説明、本文を読めば分かる仕組み・工程・判定語彙の内訳、frontmatter や本文ゲートが既に担う制約の再掲（「ユーザー起動専用」等）、トリガー例の複数羅列。利用可否を左右する環境制約（TUI 専用等）と、起動した瞬間に何が起きるかの警告（「起動＝コミット実行の許可」等）は残してよい。指摘には現状の字数と最短案の全文を書く
- **F-2 argument-hint の書式限定**: 引数の書式（名前・値の形・省略可否・繰り返し可否）のみを書く。既定値・排他条件・値の意味の解説を含めば指摘あり（正本は本文のパラメータ節）
- **F-3 分岐の外出し**: 特定のオプション・実行環境・失敗時にしか通らない節が、1節あたり10行または1,000バイト以上ルート SKILL.md に同居していれば指摘あり（本流＝毎回の実行で通る手順は対象外）。修正案は「節見出し → 移動先ファイル名 → ルートに残すポインタ（いつ・何を読むか）」の形で書き、その節を名指しで参照している他スキル・スクリプトがあれば連動更新の対象として列挙する。次はルートに置くことが規約で決まっているため移動候補にしない: `PROSE-PRESENTATION-CANONICAL` / `SUBAGENT-RETURN-CANONICAL` の正準ブロック、他スキルの解決順と復旧手順の文言、明示起動の確認ゲート、各ステップの完了条件
- **F-4 ポインタと再掲**: 参照ファイルへのポインタが「いつ・どこを読むか」を含まなければ指摘あり。同一スキル内（SKILL.md 内、または SKILL.md と参照ファイルの間）で同じ意味が二箇所以上に書かれていれば指摘あり（片方が「正本は〜」と明示した参照になっていれば除く）

## 返却フォーマット

指摘一覧は「対象スキルの作者本人だが、査読の内部用語は知らない読者」を想定して書く。

- 各指摘は、違反している基準の条項（W/A〜F のどの項目のどの規定に反するか）を特定して本文段落に引用する。**条項違反と断定できない一般的な改善提案は指摘として返さない**（個体差で毎回異なる提案が湧き、査読が収束しなくなるため）
- 一覧の先頭に、対象スキルの目的と想定される起動のされ方を各一文で述べ、続けて description の字数・SKILL.md の行数とバイト数・参照ファイルの一覧（各行数）を1行ずつ書く（対象読了の証跡。F の判定根拠）
- 続けて、適用した基準項目とその判定（指摘あり / 問題なし）の一覧を置く（網羅の証跡。適用表で「適用しない」とされた項目は書かない）
- 指摘ごとに次の3ブロックを**空行で区切って**書く（指摘どうしの間も空行で区切る）:
  - **見出し行**: 通し番号と内容が一目で分かる短い見出しを太字の独立行で書き、末尾に重要度（【must】= 目的達成や公開を妨げる / 【should】= 品質向上）を付ける
  - **本文段落**: 基準（W/A〜F）と箇所、指摘内容（現状どうなっていて何が問題か）を完結した文で書く（体言止めの連結・記号連結で圧縮しない）
  - **修正案行**: 無装飾の「修正案:」で始まる独立した段落に、採用すると何がどう変わるかを完結した文で書く
- 雛形（架空の例。各指摘の形式をこれに合わせる）:

  ```
  **3. 保存先の確認手順が非 git 環境の分岐を欠く【should】**

  基準 E（不足 — 分岐やエラー時の挙動が未定義）。箇所は Step 4 の保存手順。git 管理下を前提に diff で変更を提示すると規定しているが、対象が git 管理外の場合の挙動が書かれておらず、実行側が確認なしの上書きへ進み得る。

  修正案: Step 4 に「git 管理外の場合は書き換え前に対象ファイルの複製を提示して承認を待つ」の一文を追加し、両環境で承認経路が揃う。
  ```
- 査読の術語・ラベルを文面に使う場合は、その場で一言の説明を添える
- スキルの切り分け・統合が妥当な場合は、その構成案を別枠で提示
- 指摘ゼロの場合は、判定一覧に加えてその旨を報告して終了
