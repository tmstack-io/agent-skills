# skill-refine 査読基準（正本）

skill-refine の点検で適用する査読基準と、指摘一覧の返却フォーマットの正本。点検者（委譲されたサブエージェント、または自己実行する実行エージェント）は、点検を始める前にこのファイルを読了する。

## モード別の適用表

宣言されたモードに従い、適用する項目をこの表で確定する（行名は基準本文の見出しと対応する）。

| 基準・項目 | 既定（汎用） | `--myself` | `--project` |
|---|---|---|---|
| W. craft | 適用 | 適用 | 適用 |
| A. 公開品質 | 適用 | 適用 | 適用（「`--project` 時の読み替え」つき） |
| B-1 共通 | 適用 | 適用 | 適用（「`--project` 時の読み替え」つき） |
| B-2 汎用スキル基準 | 適用 | 適用しない | 適用しない |
| B-3 実行エージェント専用基準 | 適用しない | 適用 | 適用しない |
| C. プロジェクト非依存 | 適用 | 適用 | 適用せず、代わりに「プロジェクト整合」を査読 |
| D. 運用の規定 | 適用 | 適用 | 適用 |
| E. 不足 | 適用 | 適用 | 適用 |

## 査読基準

適用表が定める項目を**全項目**適用する。完了条件: 各項目について「指摘あり（箇所と内容）」か「問題なし」かを判定し終えている。

**W. craft** — writing-great-skills 基準

- writing-great-skills の SKILL.md と GLOSSARY.md を読了してから、そこに定義される全観点（Invocation の選択 / description の書き方 / 情報階層と progressive disclosure / 分割判断 / Pruning / leading words / 失敗モード）を対象スキルに適用する。基準の内容はここに再掲しない（正本は writing-great-skills 側）
- 指摘には writing-great-skills の術語（premature completion / duplication / no-op 等）をそのまま用いる（和訳で言い換えない）。指摘文面では各術語の初出に一言の日本語説明を添える

**A. 公開品質** — 第三者がそのまま使えるか

- 前提知識・暗黙の文脈なしで手順を実行できるか
- frontmatter の整合（name / argument-hint がディレクトリ名・本文の引数仕様と一致しているか。起動方式の選択と description の書き方は W で査読する）
- `--project` 時の読み替え: 「第三者」はチームメンバー（当該リポジトリの開発者）と読む。マシン固有パス・特定ユーザー名の禁止は維持する（リポジトリ相対パスは可）

**B. 環境非依存** — 実行環境を選ばないか

- **B-1 共通**:
  - 特定マシンの絶対パス・特定ユーザー名・ローカル固有の設定への依存
  - 他スキル・プラグイン・独自ツールへの参照（標準ツールと本体機能のみで完結させる）。例外: 対象スキルと同一の配布単位（同一リポジトリ）内のスキルを「SKILL.md を Read して同一コンテキストで適用する」形で参照するのは可。同一配布単位外の外部スキルへの依存も、対象スキル自身が前置きゲート（見つからない場合に黙って縮退せず、導入手順を案内して中止する規定）を明記していれば可
  - OS 依存コマンド（依存する場合は分岐か注記があるか）
  - `--project` 時の読み替え: 当該プロジェクト内の他スキル・現に存在するグローバルスキル・リポジトリ内の独自ツール（スクリプト・Makefile ターゲット等）への依存は可。査読の焦点を依存の排除から**依存の健全性**に反転する — 参照先が実在するか（dangling 参照の検出）、リポジトリ外依存（グローバルスキル等）が SKILL.md に前提として明記されているか
- **B-2 汎用スキル基準** — スキルディレクトリ単体のコピーで他エージェントに配布されても成立するか:
  - 特定エージェント固有のツール名の裸使用（例: WebSearch / Agent ツールを能力の説明なしに指示する）。能力主体の表現＋固有名の例示（「Web 検索できる環境では検索で確認し、できなければ情報不足と明記する（Claude Code では WebSearch）」の形）になっているか
  - 参照解決の手段としての絶対パス（`~/.claude/skills/...` 等を唯一の解決手段にした他スキル参照）。隣接優先（`../<名前>/SKILL.md`）→ 実行エージェント自身のスキルディレクトリ（プロジェクト側 → グローバル側）の解決順になっているか。他エージェント用ディレクトリの横断探索を書いていないか
  - 同梱スキルへの依存に前置きゲートが無い（依存スキルが見つからない場合に、黙って縮退せず「復旧手順を案内して中止する」規定があるか）
- **B-3 実行エージェント専用基準** — モード宣言で自己申告した名称・固有ツール・配置を物差しに、実行エージェントの専用スキルとして正しいか:
  - 実行エージェント自身の固有ツール名・機能・配置パスへの依存は正当（能力主体への言い換えを要求しない）。実行エージェント**以外**のエージェントの固有ツール名・配置パスに動作を依存していれば指摘する
  - 他スキル参照の解決順が実行エージェントの配置（自スキルの隣 → プロジェクト側 → グローバル側）になっているか
  - 実行エージェントが解釈しない frontmatter フィールドに安全機構（暴発防止等）を依存していないか（例: codex 上の `--myself` 査読で、対象が `disable-model-invocation` だけを暴発防止にしている → 本文への明示起動ゲート追加を指摘する）

**C. プロジェクト非依存** — 特定リポジトリの構成・命名・ドメイン知識が混入していないか。プロジェクト固有情報は「実行時に収集する手順」に置き換える。`--project` 時はこの項を適用せず、代わりに**プロジェクト整合**を査読する: プロジェクトのエージェント向け規約文書（Claude Code では CLAUDE.md と `.claude/rules/`、Codex では AGENTS.md、その他のエージェントでは当該エージェントの規約文書）と矛盾していないか、それらが既に定める規則をスキルが再掲していないか（正本はプロジェクト文書側。スキルからは削る）。参照するプロジェクトルートは、対象 SKILL.md から上方向に最も近い `.git` を持つディレクトリを基本とし、`.git` が無ければエージェント規約ディレクトリ（`.claude/` 等）を持つ最も近いディレクトリとする（cwd ではなく対象スキルの所属で決める）。規約文書が見つからない場合は「規約文書なし」と判定し、その旨を返却の判定一覧に記す

**D. 運用の規定** — 成果物・ユーザー確認・git の扱いが定まっているか

- 成果物のフォーマット・保存先・命名が規定されているか
- ユーザーへの選択・承認・確認が散文提示になっているか — 選択式 UI ツール（AskUserQuestion 等）の使用を指示せず、`PROSE-PRESENTATION-CANONICAL` マーカーで区切られた正準ローカル定義ブロックが SKILL.md の冒頭付近に転記され、選択・確認の各場面がブロックの内容を再説明せず「散文提示で確認する」の形で参照しているか。各場面の固有指示（選択肢の中身・一行畳みの宣言・推奨案）がブロックの規定（空行区切り＋番号、完結した文、内部術語への一言説明、推奨案と理由の明示（推奨できない場合は「推奨なし」と理由の明示）、一覧は1行1属性）と矛盾していないか
- ループ・自動修正系のスキルが git への態度を規定しているか（履歴に触れるか否か・非 git 環境での挙動。未規定だと実行側が履歴操作を発明する）

**E. 不足** — 分岐やエラー時の挙動が未定義の箇所、実行に必要なのに書かれていない前提

## 返却フォーマット

指摘一覧は「対象スキルの作者本人だが、査読の内部用語は知らない読者」を想定して書く。

- 一覧の先頭に、対象スキルの目的と想定される起動のされ方を各一文で述べる（対象読了の証跡）
- 続けて、適用した基準項目とその判定（指摘あり / 問題なし）の一覧を置く（網羅の証跡。適用表で「適用しない」とされた項目は書かない）
- 指摘ごとに次の3ブロックを**空行で区切って**書く（指摘どうしの間も空行で区切る）:
  - **見出し行**: 通し番号と内容が一目で分かる短い見出しを太字の独立行で書き、末尾に重要度（【must】= 目的達成や公開を妨げる / 【should】= 品質向上）を付ける
  - **本文段落**: 基準（W/A〜E）と箇所、指摘内容（現状どうなっていて何が問題か）を完結した文で書く（体言止めの連結・記号連結で圧縮しない）
  - **修正案行**: 無装飾の「修正案:」で始まる独立した段落に、採用すると何がどう変わるかを完結した文で書く
- 雛形（架空の例。各指摘の形式をこれに合わせる）:

  ```
  **3. 保存先の確認手順が非 git 環境の分岐を欠く【should】**

  基準 E（不足 — 分岐やエラー時の挙動が未定義）。箇所は Step 4 の保存手順。git 管理下を前提に diff で変更を提示すると規定しているが、対象が git 管理外の場合の挙動が書かれておらず、実行側が確認なしの上書きへ進み得る。

  修正案: Step 4 に「git 管理外の場合は書き換え前に対象ファイルの複製を提示して承認を待つ」の一文を追加し、両環境で承認経路が揃う。
  ```
- 査読の術語・ラベルを文面に使う場合は、その場で一言の説明を添える
- スキルの切り分け・統合が妥当な場合は、その構成案を別枠で提示
- 指摘ゼロの場合は、判定一覧に加えてその旨を報告して終了
