# skill-refine — スキルの査読と洗練

指定されたスキルを査読基準で点検し、指摘と修正案を提示し、**承認された項目だけ**を修正する。点検フェーズでは対象スキルを一切書き換えない。査読基準と返却フォーマットの正本は、本スキル同フォルダの `review-spec.md`。

**用語**: **査読**は本スキルの実行全体（Step 1〜6）を指す。**点検**は対象を読み、査読基準を適用して指摘一覧を作る工程（Step 2）を指す。委譲時は親が査読全体を持ち、点検者（サブエージェント）は点検だけを担う。

<!-- BEGIN PROSE-PRESENTATION-CANONICAL -->
**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨できる選択肢がある場合は理由を一言添えて明示し、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。
<!-- END PROSE-PRESENTATION-CANONICAL -->

## モード

- **既定（汎用）**: 複数のコーディングエージェント（Claude Code / codex 等）への配布を前提として査読する。
- **`--myself`**: 対象を「本スキルを実行しているエージェント自身の専用スキル」とみなして査読する。専用スキルはその**当事者**——スキルを実際に解釈・実行できるエージェント——の上で査読する（例: codex 専用スキルは codex 上で `--myself`）。
- **`--project`**: 対象を特定プロジェクト専用のスキルとみなして査読する。

各モードで適用する査読項目は `review-spec.md` 冒頭の「モード別の適用表」が定める。モードはパスや内容からの自動判定をしない（symlink 構成で誤判定するため、常に引数で明示する。無指定は既定＝汎用）。`--myself` と `--project` は排他であり、同時に指定された場合は査読を始めず、「`--myself` として査読する」「`--project` として査読する」「査読を中止する」の三択を散文提示で確認する。点検開始時にモードを宣言する。`--myself` の宣言には、実行エージェント自身の名称・固有ツール・スキル配置（プロジェクト側 / グローバル側）の自己申告を含める（以降の専用基準はこの申告を物差しにする）。

## 前提 — writing-great-skills の解決（前置きゲート）

査読基準のうち craft 領域（基準 W）の正本は、外部配布スキル **writing-great-skills**（配布元: `mattpocock/skills`）である。一切の作業を始める前に、次の順で解決する: 自スキルの隣（`../writing-great-skills/`）→ 実行エージェント自身のスキルディレクトリのプロジェクト側 → グローバル側。

実行エージェント自身のスキルディレクトリの実体は次のとおりで、本スキル内の他の解決手順もこの定義を使う: Claude Code はプロジェクト側 `.claude/skills/`・グローバル側 `~/.claude/skills/`、Codex はプロジェクト側 `.agents/skills/`・グローバル側 `~/.codex/skills/`、その他のエージェントはそのエージェント自身のプロジェクト側とグローバル側のスキルディレクトリを同じ位置づけで使う。他エージェント用のディレクトリは探さない（実行エージェントに導入されていない依存は欠落として扱う）。

通過条件: 解決先に **SKILL.md と GLOSSARY.md の両方**が存在し読める。どちらかでも読めなければ、何も作業せず次を案内して中止する:

> writing-great-skills が見つからないため査読を中止しました。`npx skills add mattpocock/skills` で writing-great-skills を導入してから再実行してください。

## Step 1: 対象の特定

引数のスキル名またはパスから対象を特定する。引数が無い場合は、直前の会話から対象が特定できるならその絶対パスを散文提示で確認し、特定できなければ査読対象のスキル名またはパスの入力を求めて待つ。

名前で指定された場合は次の順で探索する:

- まず本スキルの隣（`../<名前>/SKILL.md`。スキルリポジトリの直読み時に成立）を見る
- 無ければ実行エージェント自身のスキルディレクトリ（実体は「前提」節の定義に従う）をモードに従う順で見る — 既定・`--myself` はグローバル側 → プロジェクト側（依存の解決順とは逆。導入済みスキルの査読が主用途のため）、`--project` はプロジェクト側 → グローバル側（同名スキルがグローバルにあっても誤解決しない）
- 同名のスキルが複数の場所に見つかった場合は、見つかった絶対パスのどれを査読するかを散文提示で確認する
- どこにも見つからなければ、探索した場所と近い名前の候補から査読対象を散文提示で確認する

完了条件: 解決した対象の絶対パスを本文で宣言済み。

## Step 2: 点検

点検は、対象スキルを書いた・議論した同一セッションの文脈から切り離したクリーンなコンテキストで行う。基準 A の核心「前提知識・暗黙の文脈なしで実行できるか」の判定精度は、査読者がどれだけ初見の読者を近似できるかで決まるためである。点検者は、対象スキルの SKILL.md とフォルダ内の全参照ファイルを読み、`review-spec.md` を読了し、冒頭のモード別の適用表に従って査読基準を全項目適用し、末尾の返却フォーマットで指摘一覧を作る。

- **サブエージェントが使える環境**（Claude Code の Agent ツール等）: 点検を読み取り専用のサブエージェント1体に**常に**委譲する（任意の加速ではなく必須の実行形態）。Step 1 の対象特定と Step 3 以降（一覧の提示・承認・修正・報告）は親が行う。
- **サブエージェントが無い環境**: 点検を自己実行する。その際、セッション中の議論や対象スキルの成り立ちに関する記憶を判定の根拠に使わず、SKILL.md とフォルダ内の参照ファイルに書かれている記述だけを根拠にする。書かれていない前提に気づいたら、それ自体を基準 A の指摘として挙げる。

<!-- BEGIN SKILL-REFINE-MYSELF-GUARD -->
**`--myself` の取り違えガード**: 対象の読了時に、対象が実行エージェントの専用スキルとして矛盾しないかを確かめる。対象の本文が別エージェント専用を明示している場合（別エージェントの専用宣言がある、実行エージェントに無い機能が中核手順に据えられている等）は、点検を進めずその根拠を示し、「このまま `--myself` として続行する」「査読を中止する」の二択を散文提示で確認する（モードの自動切替はしない）。
<!-- END SKILL-REFINE-MYSELF-GUARD -->

**サブエージェントへのプロンプト構成**: サブエージェントはこの SKILL.md を読めない。プロンプトには必ず次をすべて含める。

1. モード（既定 / `--myself` / `--project`）。`--myself` の場合はモード宣言で自己申告した名称・固有ツール・スキル配置の内容をそのまま転記する
2. Step 1 で解決した対象スキルディレクトリの絶対パスと、「SKILL.md とフォルダ内の全参照ファイルを読む。対象への書き込みは一切しない」という指示
3. 前置きゲートで解決した writing-great-skills の SKILL.md と GLOSSARY.md の絶対パス2つと、「点検を始める前に両方を読了する」という指示
4. 本スキル同フォルダの `review-spec.md` の絶対パスと、「点検を始める前に読了し、冒頭のモード別の適用表と末尾の返却フォーマットに従う」という指示
5. **`--myself` 時のみ**: 本 Step の `BEGIN SKILL-REFINE-MYSELF-GUARD` 〜 `END SKILL-REFINE-MYSELF-GUARD` 間の本文を続けてコピーし、「ガードに該当した場合は点検せず、その根拠のみを返す」と指示する（続行可否の確認は親が行い、承認を得たら「続行承認済み」と付して再委譲する）

返却が得られない場合、または返却に「適用した基準項目の判定一覧」と「通し番号・見出し・重要度つきの指摘本文」（指摘ゼロの場合は判定一覧とその旨の報告）の両方が含まれていない場合は、同一プロンプトで1回だけ再委譲する。それでも得られなければ点検を自己実行に切り替え、Step 6 の報告に「委譲に失敗し自己実行した」と明記する。

完了条件: 「指摘一覧」「指摘ゼロの報告」「`--myself` ガードの根拠」のいずれかが手元にある（委譲時はサブエージェントの返却として、自己実行時は自分の点検結果として）。ガードの根拠が返った場合は、続行可否の確認が「続行承認済みで再委譲」か「中止」のどちらかに決着している。

## Step 3: 指摘の提示

指摘を `review-spec.md` の返却フォーマットどおり、応答本文として出力する。委譲した場合、サブエージェントの返却はユーザーには一切表示されていない — 返却一覧（対象の目的・起動のされ方の各一文と、適用した基準項目の判定一覧を含む）を本文へ全件転記するまで、提示は行われていない。

**指摘ゼロの場合**: 適用した基準項目の判定一覧と指摘が無かった旨を本文に出力し、適用範囲の確認を出さずに完了する。Step 4 と Step 5 は実行せず、Step 6 の報告として「適用した指摘なし」を述べて終える。

指摘がある場合、一覧の末尾で適用範囲を散文提示で確認する。選択肢は定型の4択でどれも一行で意味が通るため、「適用範囲を返信してください: `全件` / `must のみ` / 番号指定（例: `1,3,5`） / `適用しない`」の一行に畳んでよい。承認の確認を同一ターンで発行しない。

完了条件: 判定された指摘の件数（委譲時はサブエージェントが返却した件数）と本文に番号付きで出力した指摘の件数が一致しており、適用した基準項目の判定一覧を本文に転記済み。

## Step 4: 承認

Step 3 へのユーザーの返信そのものを承認とする。返信を適用範囲（全件 / must のみ / 番号の集合 / 適用しない）として解釈し、解釈できない場合のみ、選択肢を散文提示で再掲する。

完了条件: 適用する指摘番号の集合が確定し、その解釈を本文で復唱済み（例: 「1・3 を適用し、5 は適用しません」）。

## Step 5: 修正

書き換えの前に、対象スキルが git 管理下にあるかを確認する。管理下でない場合は、変更前の状態に戻す手段が無いことを伝え、「このまま適用する」「中止する」の二択を散文提示で確認し、適用の回答を得てから進む。承認された指摘のみを適用し、承認されなかった指摘・スコープ外の改善は加えない。修正は対象スキルの SKILL.md と同フォルダの参照ファイルに及ぶ。ディレクトリの改名・ファイルの追加削除を伴う修正は実施せず、実行手順として Step 6 の報告に載せる。対象スキルが git 管理下にある場合もコミットはせず、修正を作業ツリーに残す（コミットはユーザーの指示があった場合のみ）。

**再点検**: 節の新設や手順の再構成など、初見の読者としての再判定が要る規模の書き換えを行った場合は、Step 2 と同じ形で再点検を委譲する。再点検の返却は今回の承認範囲に含めず、Step 6 の報告に「再点検の結果」として全件載せる（適用するかどうかは、次回の査読としてユーザーが決める）。

完了条件: 承認された全指摘が反映され、修正後の全文について文面上で確かめられる整合を確認済み — frontmatter（name / argument-hint）とディレクトリ名・引数仕様が一致し、同じ意味の二箇所書きが無く、各ステップの完了条件が残っており、参照（`review-spec.md` / writing-great-skills / 他スキル）の解決記述が壊れていない。

## Step 6: 報告

- 適用した指摘と、それによる変更内容の要約
- 適用しなかった指摘（承認されなかったもの）の一覧
- 点検の実行形態（サブエージェントへ委譲したか自己実行したか。フォールバックした場合はその理由）
- 実施せず持ち越した操作（ディレクトリ改名等）の実行手順（あれば）
- 再点検の結果（Step 5 の再点検を行った場合、その返却の全件）
- 修正後に残る既知の制約（あれば）

完了条件: 上記の各項目が、該当なしの場合はその旨も含めて報告に書かれている。
