# skill-refine — スキルの査読と洗練

指定されたスキルを査読基準で点検し、指摘と修正案を提示し、**承認された項目だけ**を修正する。点検フェーズでは対象スキルを一切書き換えない。

## モード

- **既定（汎用）**: 複数のコーディングエージェント（Claude Code / codex 等）への配布を前提とした査読基準を適用する。基準 B の「汎用スキル基準」を含む全項目を使う。
- **`--myself`**: 対象を「本スキルを実行しているエージェント自身の専用スキル」とみなし、基準 B の「汎用スキル基準」の代わりに「実行エージェント専用基準」（基準 B 内）を適用する。専用スキルはその**当事者**——スキルを実際に解釈・実行できるエージェント——の上で査読する（例: codex 専用スキルは codex 上で `--myself`）。
- **`--project`**: 対象を特定プロジェクト専用のスキルとみなし、査読基準 A〜C の「`--project` 時の読み替え」を適用する。

モードはパスや内容からの自動判定をしない（symlink 構成で誤判定するため、常に引数で明示する。無指定は既定＝汎用）。`--myself` と `--project` は排他であり、同時に指定された場合は査読を始めず、どちらのモードで査読するかをユーザーに確認する。点検開始時にモードを宣言する。`--myself` の宣言には、実行エージェント自身の名称・固有ツール・スキル配置（プロジェクト側 / グローバル側）の自己申告を含める（以降の専用基準はこの申告を物差しにする）。

## Step 1: 対象の読み込み

引数のスキル名またはパスから対象を特定する。名前の場合、まず本スキルの隣（`../<名前>/SKILL.md`。スキルリポジトリの直読み時に成立）を見て、無ければ**実行エージェント自身のスキルディレクトリ**（Claude Code: グローバル `~/.claude/skills/<名前>/`・プロジェクト `.claude/skills/<名前>/`、Codex: グローバル `~/.codex/skills/<名前>/`・プロジェクト `.agents/skills/<名前>/`。他エージェント用のディレクトリは探さない）をモードに従う順で探索する — 既定・`--myself`: グローバル側 → プロジェクト側、`--project` 時はその逆（プロジェクト側を優先。同名スキルがグローバルにあっても誤解決しない）。見つからなければ候補を挙げてユーザーに確認する。SKILL.md と、スキルフォルダ内の全参照ファイルを読む。

**`--myself` の取り違えガード**: 読了時に、対象が実行エージェントの専用スキルとして矛盾しないかを確かめる。対象の本文が別エージェント専用を明示している場合（別エージェントの専用宣言がある、実行エージェントに無い機能が中核手順に据えられている等）は、点検を始めずその根拠を示し、続行可否をユーザーに確認する（モードの自動切替はしない）。

完了条件: 全ファイルを読了し、「このスキルの目的」と「想定される起動のされ方」を各一文で言える。`--myself` では加えて、対象と実行エージェントの不一致が「なし」または「ユーザーが続行を承認済み」のどちらかである。

## Step 2: 点検

以下の査読基準を**全項目**適用する。完了条件: 各項目について「指摘あり（箇所と内容）」か「問題なし」かを判定し終えている。

### 査読基準

**A. 公開品質** — 第三者がそのまま使えるか

- 前提知識・暗黙の文脈なしで手順を実行できるか
- frontmatter が有効か（name / description / argument-hint の整合。起動方式の選択が用途に合っているか: 自然文で呼びたい・他スキルから参照される → モデル起動型、手動起動のみ → `disable-model-invocation: true`）
- description は「何をするか＋起動トリガー」に絞れているか。同義語の重複トリガーは1つに統合
- `--project` 時の読み替え: 「第三者」はチームメンバー（当該リポジトリの開発者）と読む。マシン固有パス・特定ユーザー名の禁止は維持する（リポジトリ相対パスは可）

**B. 環境非依存** — 実行環境を選ばないか

- 特定マシンの絶対パス・特定ユーザー名・ローカル固有の設定への依存
- 他スキル・プラグイン・独自ツールへの参照（標準ツールと本体機能のみで完結させる）。例外: 対象スキルと同一の配布単位（同一リポジトリ）内のスキルを「SKILL.md を Read して同一コンテキストで適用する」形で参照するのは可
- OS 依存コマンド（依存する場合は分岐か注記があるか）
- **汎用スキル基準**（既定モードのみ適用。`--myself`・`--project` 時は適用しない）— スキルディレクトリ単体のコピーで他エージェントに配布されても成立するか:
  - 特定エージェント固有のツール名の裸使用（例: AskUserQuestion / WebSearch / Agent ツールを能力の説明なしに指示する）。能力主体の表現＋固有名の例示（「ユーザーに選択式で確認する（Claude Code では AskUserQuestion。同等ツールが無い環境では散文で質問し回答を待つ）」の形）になっているか
  - 参照解決の手段としての絶対パス（`~/.claude/skills/...` 等を唯一の解決手段にした他スキル参照）。隣接優先（`../<名前>/SKILL.md`）→ 実行エージェント自身のスキルディレクトリ（プロジェクト側 → グローバル側）の解決順になっているか。他エージェント用ディレクトリの横断探索を書いていないか
  - 同梱スキルへの依存に前置きゲートが無い（依存スキルが見つからない場合に、黙って縮退せず「復旧手順を案内して中止する」規定があるか）
- **実行エージェント専用基準**（`--myself` のみ適用）— モード宣言で自己申告した名称・固有ツール・配置を物差しに、実行エージェントの専用スキルとして正しいか:
  - 実行エージェント自身の固有ツール名・機能・配置パスへの依存は正当（能力主体への言い換えを要求しない）。実行エージェント**以外**のエージェントの固有ツール名・配置パスに動作を依存していれば指摘する
  - 他スキル参照の解決順が実行エージェントの配置（自スキルの隣 → プロジェクト側 → グローバル側）になっているか
  - 実行エージェントが解釈しない frontmatter フィールドに安全機構（暴発防止等）を依存していないか（例: codex 上の `--myself` 査読で、対象が `disable-model-invocation` だけを暴発防止にしている → 本文への明示起動ゲート追加を指摘する）
- `--project` 時の読み替え: 当該プロジェクト内の他スキル・現に存在するグローバルスキル・リポジトリ内の独自ツール（スクリプト・Makefile ターゲット等）への依存は可。査読の焦点を依存の排除から**依存の健全性**に反転する — 参照先が実在するか（dangling 参照の検出）、リポジトリ外依存（グローバルスキル等）が SKILL.md に前提として明記されているか

**C. プロジェクト非依存** — 特定リポジトリの構成・命名・ドメイン知識が混入していないか。プロジェクト固有情報は「実行時に収集する手順」に置き換える。`--project` 時はこの項を適用せず、代わりに**プロジェクト整合**を査読する: プロジェクトの CLAUDE.md / `.claude/rules/` と矛盾していないか、それらが既に定める規則をスキルが再掲していないか（正本はプロジェクト文書側。スキルからは削る）。参照するプロジェクトルートは、対象 SKILL.md から上方向に最も近い `.claude/` または `.git` を持つディレクトリとする（cwd ではなく対象スキルの所属で決める）

**D. 出力の安定性** — 同じ入力で同じ品質の成果物が出るか

- 各ステップに検証可能な完了条件があるか（「〜を確認する」ではなく、done / not-done を判定できる形か）
- 曖昧な判断ゲートが残っていないか（二値化できるものは二値化: 例「問題がなければ」→「指摘ゼロなら」）
- 成果物のフォーマット・保存先・命名が規定されているか
- ループ・自動修正系のスキルが git への態度を規定しているか（履歴に触れるか否か・非 git 環境での挙動。未規定だと実行側が履歴操作を発明する）

**E. 記述の密度** — 不足・冗長・構造

- **不足**: 分岐やエラー時の挙動が未定義の箇所。実行に必要なのに書かれていない前提
- **冗長**: 同一の意味が複数箇所にある記述（正本を1つに）。モデルが指示なしでも既定で従う自明な指示（削除対象）。現在のスキルの目的に関係しない残骸
- **構造**: 一部の分岐でしか使わない長い参照は別ファイルへの分離を提案。逆に、分割されて読みにくいだけの断片は統合を提案。禁止形の指示は目標挙動の肯定形に書き換え

## Step 3: 指摘の提示

指摘を以下の形式で、応答本文として出力する:

- 指摘ごとに: `基準(A〜E) / 箇所 / 指摘内容 / 修正案`、重要度は must（目的達成や公開を妨げる）/ should（品質向上）の2段階
- スキルの切り分け・統合が妥当な場合は、その構成案を別枠で提示
- 指摘ゼロの場合はその旨を報告して終了

完了条件: 全指摘が上記形式で本文に出力されている。**一覧を出力し終えるまで Step 4 の質問を発行しない**（ユーザーは一覧を読んでから適用範囲を判断する）。

## Step 4: 承認

ユーザーに適用範囲を選択式で確認する（全指摘を適用 / must のみ適用 / 点検のみで終了。個別選択の回答も受ける。Claude Code では AskUserQuestion。同等ツールが無い環境では散文で選択肢を提示し、回答を待つ）。質問文に件数（must X / should Y）を、各選択肢の説明に主要な指摘の要旨を含め、一覧が画面に見えていない状態でも判断材料が残るようにする。

## Step 5: 修正

承認された指摘のみを対象スキルに適用する。承認されなかった指摘・スコープ外の改善は加えない。対象スキルが git 管理下にある場合もコミットはせず、修正を作業ツリーに残す（コミットはユーザーの指示があった場合のみ）。

完了条件: 承認された全指摘が反映され、修正後の全文を通読して Step 2 の査読基準に新たな違反を生んでいないことを確認済み。

## Step 6: 報告

- 適用した指摘と、それによる変更内容の要約
- 適用しなかった指摘（承認されなかったもの）の一覧
- 修正後に残る既知の制約（あれば）
