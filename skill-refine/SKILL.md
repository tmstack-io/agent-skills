# skill-refine — スキルの査読と洗練

指定されたスキルを査読基準で点検し、指摘と修正案を提示し、**承認された項目だけ**を修正する。点検フェーズでは対象スキルを一切書き換えない。査読基準と返却フォーマットの正本は、本スキル同フォルダの `review-spec.md`。

**用語**: **査読**は本スキルの実行全体（Step 1〜6）を指す。**点検**は対象を読み、査読基準を適用して指摘一覧を作る工程（Step 2）を指す。委譲時は親が査読全体を持ち、点検者（サブエージェントまたはペインの委譲先）は点検だけを担う。**多重点検**（とその集計区分である**過半数指摘**／**単独指摘**）は点検の既定形態を指し、定義・体制・受理規則は Step 2 が定める。**査読台帳**は判定済み指摘の再提示を防ぐ一時記録で、運用は Step 2 と Step 6 が定める。

<!-- BEGIN PROSE-PRESENTATION-CANONICAL -->
**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨する選択肢を理由一言つきで明示し（推奨できる選択肢が無い場合は「推奨なし」とその理由を明示する）、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。
<!-- END PROSE-PRESENTATION-CANONICAL -->

## モード

- **既定（汎用）**: 複数のコーディングエージェント（Claude Code / codex 等）への配布を前提として査読する。
- **`--myself`**: 対象を「本スキルを実行しているハーネス専用のスキル」とみなして査読する。専用スキルはその**当事者**——スキルを実際に解釈・実行できるハーネス——の上で査読する（例: codex 専用スキルは codex 上で `--myself`）。
- **`--project`**: 対象を特定プロジェクト専用のスキルとみなして査読する。

各モードで適用する査読項目は `review-spec.md` 冒頭の「モード別の適用表」が定める。モードはパスや内容からの自動判定をしない（symlink 構成で誤判定するため、常に引数で明示する。無指定は既定＝汎用）。`--myself` と `--project` は排他であり、同時に指定された場合は査読を始めず、「`--myself` として査読する」「`--project` として査読する」「査読を中止する」の三択を散文提示で確認する。点検開始時にモードを宣言する。`--myself` の宣言には、実行ハーネスの名称・固有ツール・スキル配置（プロジェクト側 / グローバル側）の自己申告を含める（以降の専用基準はこの申告を物差しにする）。

## 前提 — writing-great-skills の解決（前置きゲート）

査読基準のうち craft 領域（基準 W）の正本は、外部配布スキル **writing-great-skills**（配布元: `mattpocock/skills`）である。一切の作業を始める前に、次の順で解決する: 自スキルの隣（`../writing-great-skills/`）→ 実行ハーネス自身のスキルディレクトリのプロジェクト側 → グローバル側。

実行ハーネス自身のスキルディレクトリの実体は次のとおりで、本スキル内の他の解決手順もこの定義を使う: Claude Code はプロジェクト側 `.claude/skills/`・グローバル側 `~/.claude/skills/`、Codex はプロジェクト側 `.agents/skills/`・グローバル側 `~/.codex/skills/`、その他のハーネスはそのハーネス自身のプロジェクト側とグローバル側のスキルディレクトリを同じ位置づけで使う。他ハーネス用のディレクトリは探さない（実行ハーネスに導入されていない依存は欠落として扱う）。

通過条件: 解決先に **SKILL.md と GLOSSARY.md の両方**が存在し読める。どちらかでも読めなければ、何も作業せず次を案内して中止する:

> writing-great-skills が見つからないため査読を中止しました。`npx skills add mattpocock/skills` で writing-great-skills を導入してから再実行してください。

## Step 1: 対象の特定

引数のスキル名またはパスから対象を特定する。引数が無い場合は、直前の会話から対象が特定できるならその絶対パスを散文提示で確認し、特定できなければ査読対象のスキル名またはパスの入力を求めて待つ。

名前で指定された場合は次の順で探索する:

- まず本スキルの隣（`../<名前>/SKILL.md`。スキルリポジトリの直読み時に成立）を見る
- 無ければ実行ハーネス自身のスキルディレクトリ（実体は「前提」節の定義に従う）をモードに従う順で見る — 既定・`--myself` はグローバル側 → プロジェクト側（依存の解決順とは逆。導入済みスキルの査読が主用途のため）、`--project` はプロジェクト側 → グローバル側（同名スキルがグローバルにあっても誤解決しない）
- 同名のスキルが複数の場所に見つかった場合は、見つかった絶対パスのどれを査読するかを散文提示で確認する
- どこにも見つからなければ、探索した場所と近い名前の候補から査読対象を散文提示で確認する

完了条件: 解決した対象の絶対パスを本文で宣言済み。

## Step 2: 点検

点検は、対象スキルを書いた・議論した同一セッションの文脈から切り離したクリーンなコンテキストで行う。基準 A の核心「前提知識・暗黙の文脈なしで実行できるか」の判定精度は、査読者がどれだけ初見の読者を近似できるかで決まるためである。

<!-- BEGIN SKILL-REFINE-INSPECTION -->
点検者は、対象スキルの SKILL.md とフォルダ内の全参照ファイルを読み（対象への書き込みは一切しない）、`review-spec.md` を読了し、冒頭のモード別の適用表に従って査読基準を全項目適用し、末尾の返却フォーマットで指摘一覧を作る。
<!-- END SKILL-REFINE-INSPECTION -->

点検は**多重点検**を既定とする: 同一プロンプトの独立した点検者3体に点検させ、親が返却を突き合わせて「同じ箇所・同じ問題」を等価としてグルーピングし、2体以上が挙げた過半数指摘だけを正規の承認対象とする。単独指摘は、must なら「単独指摘（参考）」の別枠として残し、should なら破棄して件数のみ報告する（提示の体裁と承認範囲への入り方は Step 3 が定める）。個体差による指摘のばらつき（点検のたびに新規指摘が湧き、査読が収束しない）を多数決で除去する機構であり、点検者には互いの存在・返却を一切見せない（独立性が多数決の前提）。

**査読台帳**: `${TMPDIR:-/tmp}/skill-refine-ledger-<対象スキル名>.md` を台帳とする（固定パス・追記式。形態2の成果物置き場〔mktemp で作る削除対象のディレクトリ〕の外に置く）。点検の前に確認し、ヘッダの対象絶対パスが今回の対象と異なる残骸なら作り直す。セッションを跨ぐ保証は持たず、OS の一時領域の掃除に委ねる。

点検の実行形態は次の順で解決し、いずれの形態でも Step 1 の対象特定と Step 3 以降（一覧の提示・承認・修正・報告）は親が行う:

1. **サブエージェント**（Claude Code の Agent ツール等がある環境）: 点検を読み取り専用のサブエージェント3体へ**常に**委譲する（任意の加速ではなく必須の実行形態。並列起動できる環境では1メッセージで並列に、できなければ直列に立てる）。
2. **tui-harness ペイン**（サブエージェント機構が無い環境の代替）: tui-harness の SKILL.md を Read してこのコンテキスト内で適用する。解決順: `../tui-harness/SKILL.md` → 実行ハーネス自身のスキルディレクトリのプロジェクト側 → グローバル側（実体は「前提」節の定義に従う）。見つからない場合、または `mux.sh detect` が検証済みバックエンドを返さない場合は形態3へ縮退し、復旧手順（`npx skills add tmstack-io/agent-skills --skill tui-harness`）を Step 6 の報告に添える。成立する場合:
   - 点検者ハーネスは `catalog.sh probe` が ok の候補から散文提示で1つ選んでもらい（候補が1件ならそれを採用する旨を宣言して選択を省略する。候補が0件なら形態3へ縮退する）、選んだ CLI のペインを3面立てて多重点検を行う。モデルは tui-harness の委譲手順に従って確定する（明示指定が無ければ確定済みハーネスのモデル一覧を散文提示して選んでもらう）。**異系統委譲の系統ガードは適用しない** — 点検の要件は著者セッションから独立したクリーンな文脈であり異系統性ではなく、同系統の CLI でも別ペインなら成立するため（系統不問で立てた旨をブリーフに記す）。
   - 呼び出しパラメータ: 成果物置き場＝一時領域に作る本スキル専用ディレクトリ（`mktemp -d "${TMPDIR:-/tmp}/skill-refine.XXXXXX"`。ブリーフ・指摘一覧ファイルを置き、最終報告後に削除する）、push ラベル＝`sr-inspect-<1〜3>`（点検者ごとに一意）、裁定スコープ＝成果物置き場＋通信規約の push。起動 cwd はプロジェクトルート。
   - ブリーフには後述「サブエージェントへのプロンプト構成」の各項と同内容（`--myself` ガードの転記を含む）に加え、指摘一覧の書き出し先ファイルパス（成果物置き場内・点検者ごとに別名）を記載し、回収・集計した結果を Step 3 で本文へ転記する。
   - 再点検（Step 5 の周回）では前周回のペインを閉じ、新規ペインで行う（クリーンな文脈の維持が目的のため、文脈保持のための同一ペイン追送はしない）。Step 6 の報告を出力した後、本査読で開いた全ペインを tui-harness のクローズ手順で閉じる。
   - 受理の再送上限・pull 安全網の延長上限（いずれも tui-harness の規定）を消化した点検者は脱落として数える（扱いは後述の脱落時規定に従う）。
3. **自己実行**（上記いずれも成立しない場合の縮退）: 多重点検なしの1回の点検を自己実行する。その際、セッション中の議論や対象スキルの成り立ちに関する記憶を判定の根拠に使わず、SKILL.md とフォルダ内の参照ファイルに書かれている記述だけを根拠にする。書かれていない前提に気づいたら、それ自体を基準 A の指摘として挙げる。

<!-- BEGIN SUBAGENT-RETURN-CANONICAL -->
**サブエージェント返却規約（Claude Code 固有）**: Claude Code のバックグラウンドサブエージェントは、最終報告を親へ送らず待機通知だけで終わることがある。Claude Code でサブエージェントへ委譲するときは、委譲プロンプトに「完了したら、結果の全文を SendMessage で親へ1通で送る」ことを明示する。返却が届かず完了・待機の通知だけが来た場合は、継続対話で結果の再送を依頼する。再送依頼は同一委譲につき合計2回までとし、それでも届かなければ当該場面の失敗規律（再委譲・縮退・脱落・中止）に従う。Claude Code 以外のハーネスでは、サブエージェントの結果を当該ハーネスの通常の返却経路で受け取り、本規約の追加手順は適用しない。
<!-- END SUBAGENT-RETURN-CANONICAL -->

<!-- BEGIN SKILL-REFINE-MYSELF-GUARD -->
**`--myself` の取り違えガード**: 対象の読了時に、対象が実行ハーネスの専用スキルとして矛盾しないかを確かめる。対象の本文が別ハーネス専用を明示している場合（別ハーネスの専用宣言がある、実行ハーネスに無い機能が中核手順に据えられている等）は、点検を進めずその根拠を示し、「このまま `--myself` として続行する」「査読を中止する」の二択を散文提示で確認する（モードの自動切替はしない）。
<!-- END SKILL-REFINE-MYSELF-GUARD -->

**サブエージェントへのプロンプト構成**: サブエージェントはこの SKILL.md を読めない（ペイン委譲のブリーフも同じ前提）。3体には同一のプロンプトを与え、必ず次をすべて含める。

1. モード（既定 / `--myself` / `--project`）。`--myself` の場合はモード宣言で自己申告した名称・固有ツール・スキル配置の内容をそのまま転記する
2. Step 1 で解決した対象スキルディレクトリの絶対パスと、本 Step の `BEGIN SKILL-REFINE-INSPECTION` 〜 `END SKILL-REFINE-INSPECTION` 間の本文の一字一句そのままのコピー（点検の定義の正本。プロンプト側で再説明しない）
3. 前置きゲートで解決した writing-great-skills の SKILL.md と GLOSSARY.md の絶対パス2つと、「点検を始める前に両方を読了する」という指示
4. 本スキル同フォルダの `review-spec.md` の絶対パス
5. **`--myself` 時のみ**: 本 Step の `BEGIN SKILL-REFINE-MYSELF-GUARD` 〜 `END SKILL-REFINE-MYSELF-GUARD` 間の本文を続けてコピーし、「ガードに該当した場合は点検せず、その根拠のみを返す」と指示する（続行可否の確認は親が行い、承認を得たら「続行承認済み」と付して再委譲する）
6. **査読台帳が存在する時のみ**: 台帳の絶対パスと、「点検を始める前に読み、判定済み指摘と等価な指摘は再提示しない。ただし対象の該当記述が判定時から変わっている場合のみ、その旨を理由に添えて再提示してよい」という指示

委譲と回収はサブエージェント返却規約に従う。そのうえで返却が得られない、または返却に「適用した基準項目の判定一覧」と「通し番号・見出し・重要度つきの指摘本文」（指摘ゼロの場合は判定一覧とその旨の報告）の両方が含まれていない点検者には、同一プロンプトで1回だけ再委譲する。**脱落時規定**: それでも有効な返却が3体中2体に満たなければ、点検を自己実行（多重点検なし）へ切り替える。有効な返却が2体なら続行し、受理規則を「2体とも挙げた指摘を過半数指摘、1体のみを単独指摘」と読み替える。縮退・脱落の報告は Step 6 の報告項目（実行形態と多重点検の構成）が定める。いずれかの点検者が `--myself` ガードの根拠を返した場合は全点検者の結果を破棄して続行可否の確認へ進み、承認を得たら3体とも再委譲する。

完了条件: 2体以上の有効な返却を親が集計した「過半数指摘・単独指摘の一覧」「指摘ゼロの報告」「`--myself` ガードの根拠」のいずれかが手元にある（自己実行時は自分の点検結果1本をそのまま指摘一覧とする）。ガードの根拠が返った場合は、続行可否の確認が「続行承認済みで再委譲」か「中止」のどちらかに決着している。

## Step 3: 指摘の提示

指摘を `review-spec.md` の返却フォーマットどおり、応答本文として出力する。委譲した場合、点検者（サブエージェントまたはペイン）の返却はユーザーには一切表示されていない — 返却一覧（対象の目的・起動のされ方の各一文と、適用した基準項目の判定一覧を含む）を本文へ全件転記するまで、提示は行われていない。多重点検では集計後の一覧を提示する: 過半数指摘を通し番号で並べて各指摘に賛同数（例: 「3体中2体」）を付記し、続けて「単独指摘（参考）」の must を続き番号で並べ、破棄した単独 should の件数を一覧末尾に一行で記す。基準項目の判定一覧は各点検者の返却を突き合わせ、項目ごとに「指摘あり（n体）／問題なし」へ統合して転記する。

**指摘ゼロの場合**: 適用した基準項目の判定一覧と指摘が無かった旨を本文に出力し、承認範囲の確認を出さずに完了する。Step 4 と Step 5 は実行せず、Step 6 の報告として「適用した指摘なし」を述べて終える。

指摘がある場合、一覧の末尾で承認範囲（適用する指摘の範囲）を散文提示で確認する。選択肢は定型の4択でどれも一行で意味が通るため、「承認範囲を返信してください: `全件` / `must のみ` / 番号指定（例: `1,3,5`） / `適用しない`」の一行に畳んでよい — 推奨する承認範囲を理由一言つきで添える（例: 「推奨: must のみ — should 2件は文体の好みの範囲」）。`全件` と `must のみ` は過半数指摘のみを対象とし、単独指摘（参考）は番号指定でのみ承認範囲に入る。

完了条件: 集計後の指摘の件数（過半数指摘と単独指摘〔参考〕の must の合計。自己実行時は自分の点検結果の件数）と本文に番号付きで出力した件数が一致しており、統合した基準項目の判定一覧を本文に転記済み。

## Step 4: 承認

Step 3 へのユーザーの返信そのものを承認とする。返信を承認範囲（全件 / must のみ / 番号の集合 / 適用しない）として解釈し、解釈できない場合のみ、選択肢を散文提示で再掲する。

完了条件: 適用する指摘番号の集合が確定し、その解釈を本文で復唱済み（例: 「1・3 を適用し、5 は適用しません」）。

## Step 5: 修正

適用する指摘が一件も無い場合（承認範囲が `適用しない`）は、Step 5 を実行せず Step 6 へ進む。

書き換えの前に、対象スキルが git 管理下にあるかを確認する。管理下でない場合は、変更前の状態に戻す手段が無いことを伝え、「このまま適用する」「中止する」の二択を散文提示で確認し、適用の回答を得てから進む。承認された指摘のみを適用し、承認されなかった指摘・スコープ外の改善は加えない。修正は対象スキルの SKILL.md と同フォルダの参照ファイルに及ぶ。ディレクトリの改名・ファイルの追加削除を伴う修正は実施せず、実行手順として Step 6 の報告に載せる。対象スキルが git 管理下にある場合もコミットはせず、修正を作業ツリーに残す（コミットはユーザーの指示があった場合のみ）。

**再点検（周回）**: 節の新設や手順の再構成など、初見の読者としての再判定が要る規模の書き換えを行った場合は、Step 2 と同じ形で再点検を委譲する（この規模に満たない修正では再点検しない）。再点検は1回の査読で最大2回。1回目の再点検で指摘が出た場合は Step 3 に戻り、提示・承認・修正を同一の規定で繰り返す（指摘番号は周回ごとに1から振り直し、Step 4 の承認は直前に提示した一覧に対してのみ有効）。2回目の再点検で指摘が出た場合は Step 3 に戻らず、全件を Step 6 の報告に「持ち越した指摘」として載せる（適用するかどうかは、次回の査読としてユーザーが決める）。周回中にユーザーが `適用しない` を返信した場合は、その時点で修正を終えて Step 6 へ進む。

完了条件: 承認された全指摘が反映され、修正後の全文について文面上で確かめられる整合を確認済み — frontmatter（name / argument-hint）とディレクトリ名・引数仕様が一致し、同じ意味の二箇所書きが無く、各ステップの完了条件が残っており、参照（`review-spec.md` / writing-great-skills / 他スキル）の解決記述が壊れていない。

## Step 6: 報告

- 適用した指摘と、それによる変更内容の要約
- 適用しなかった指摘（承認されなかったもの）の一覧
- 点検の実行形態（サブエージェント委譲 / tui-harness ペイン委譲〔起用した CLI 名を含む〕 / 自己実行）と多重点検の構成（3体 / 脱落により2体 / 多重点検なし。縮退・脱落した場合はその理由と復旧手順）
- 収束判定（査読台帳の判定済みと等価な再提示が無く、かつ新規の指摘 — 多重点検時は過半数指摘、自己実行時は自分の点検結果 — に must がゼロなら「収束」と明記する。自己実行時は多重点検を経ていない旨を併記し、満たさない場合はその内訳を書く）
- 実施せず持ち越した操作（ディレクトリ改名等）の実行手順（あれば）
- 周回の記録（再点検を行った場合: 周回数と各周回の適用・持ち越しの件数、持ち越した指摘の全件）
- 修正後に残る既知の制約（あれば）

報告を出力した後、査読台帳へ今回提示した全指摘（過半数・単独参考とも）と判定（適用／見送り）・日時を追記する（台帳が無ければ対象の絶対パスをヘッダに記して新規作成する）。

完了条件: 上記の各項目が、該当なしの場合はその旨も含めて報告に書かれており、査読台帳への追記が済んでいる。
