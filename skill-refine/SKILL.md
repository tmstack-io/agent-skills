# skill-refine — スキルの査読と洗練

指定されたスキルを査読基準で点検し、指摘と修正案を提示し、**承認された項目だけ**を修正する。点検フェーズでは対象スキルを一切書き換えない。

## モード

- **既定（グローバル）**: 配布を前提とした査読基準をそのまま適用する。
- **`--project`**: 対象を特定プロジェクト専用のスキルとみなし、査読基準 A〜C の「`--project` 時の読み替え」を適用する。パスからの自動判定はしない（symlink 構成で誤判定するため、モードは常に引数で明示する）。

点検開始時に、どちらのモードで査読するかを宣言する。

## Step 1: 対象の読み込み

引数のスキル名またはパスから対象を特定する。名前の場合の探索順はモードに従う — 既定: `~/.claude/skills/<名前>/` → プロジェクトの `.claude/skills/<名前>/`、`--project` 時はその逆（プロジェクト側を優先。同名スキルがグローバルにあっても誤解決しない）。見つからなければ候補を挙げてユーザーに確認する。SKILL.md と、スキルフォルダ内の全参照ファイルを読む。

完了条件: 全ファイルを読了し、「このスキルの目的」と「想定される起動のされ方」を各一文で言える。

## Step 2: 点検

以下の査読基準を**全項目**適用する。完了条件: 各項目について「指摘あり（箇所と内容）」か「問題なし」かを判定し終えている。

### 査読基準

**A. 公開品質** — 第三者がそのまま使えるか

- 前提知識・暗黙の文脈なしで手順を実行できるか
- frontmatter が有効か（name / description / argument-hint の整合。起動方式の選択が用途に合っているか: 自然文で呼びたい・他スキルから参照される → モデル起動型、手動起動のみ → `disable-model-invocation: true`）
- description は「何をするか＋起動トリガー」に絞れているか。同義語の重複トリガーは1つに統合
- `--project` 時の読み替え: 「第三者」はチームメンバー（当該リポジトリの開発者）と読む。マシン固有パス・特定ユーザー名の禁止は維持する（リポジトリ相対パスは可）

**B. 環境非依存** — 実行環境を選ばないか

- 特定マシンの絶対パス・特定ユーザー名・ローカル固有の設定への依存
- 他スキル・プラグイン・独自ツールへの参照（標準ツールと本体機能のみで完結させる）。例外: 対象スキルと同一の配布単位（同一リポジトリ）内のスキルを「SKILL.md を Read して同一コンテキストで適用する」形で参照するのは可
- OS 依存コマンド（依存する場合は分岐か注記があるか）
- `--project` 時の読み替え: 当該プロジェクト内の他スキル・現に存在するグローバルスキル・リポジトリ内の独自ツール（スクリプト・Makefile ターゲット等）への依存は可。査読の焦点を依存の排除から**依存の健全性**に反転する — 参照先が実在するか（dangling 参照の検出）、リポジトリ外依存（グローバルスキル等）が SKILL.md に前提として明記されているか

**C. プロジェクト非依存**（グローバルスキルのみ）— 特定リポジトリの構成・命名・ドメイン知識が混入していないか。プロジェクト固有情報は「実行時に収集する手順」に置き換える。`--project` 時はこの項を適用せず、代わりに**プロジェクト整合**を査読する: プロジェクトの CLAUDE.md / `.claude/rules/` と矛盾していないか、それらが既に定める規則をスキルが再掲していないか（正本はプロジェクト文書側。スキルからは削る）。参照するプロジェクトルートは、対象 SKILL.md から上方向に最も近い `.claude/` または `.git` を持つディレクトリとする（cwd ではなく対象スキルの所属で決める）

**D. 出力の安定性** — 同じ入力で同じ品質の成果物が出るか

- 各ステップに検証可能な完了条件があるか（「〜を確認する」ではなく、done / not-done を判定できる形か）
- 曖昧な判断ゲートが残っていないか（二値化できるものは二値化: 例「問題がなければ」→「指摘ゼロなら」）
- 成果物のフォーマット・保存先・命名が規定されているか
- ループ・自動修正系のスキルが git への態度を規定しているか（履歴に触れるか否か・非 git 環境での挙動。未規定だと実行側が履歴操作を発明する）

**E. 記述の密度** — 不足・冗長・構造

- **不足**: 分岐やエラー時の挙動が未定義の箇所。実行に必要なのに書かれていない前提
- **冗長**: 同一の意味が複数箇所にある記述（正本を1つに）。モデルが指示なしでも既定で従う自明な指示（削除対象）。現在のスキルの目的に関係しない残骸
- **構造**: 一部の分岐でしか使わない長い参照は別ファイルへの分離を提案。逆に、分割されて読みにくいだけの断片は統合を提案。禁止形の指示は目標挙動の肯定形に書き換え

## Step 3: 指摘の提示

指摘を以下の形式で、応答本文として出力する:

- 指摘ごとに: `基準(A〜E) / 箇所 / 指摘内容 / 修正案`、重要度は must（目的達成や公開を妨げる）/ should（品質向上）の2段階
- スキルの切り分け・統合が妥当な場合は、その構成案を別枠で提示
- 指摘ゼロの場合はその旨を報告して終了

完了条件: 全指摘が上記形式で本文に出力されている。**一覧を出力し終えるまで Step 4 の質問を発行しない**（ユーザーは一覧を読んでから適用範囲を判断する）。

## Step 4: 承認

AskUserQuestion で適用範囲を確認する（全指摘を適用 / must のみ適用 / 点検のみで終了。個別選択の回答も受ける）。question 文に件数（must X / should Y）を、各選択肢の description に主要な指摘の要旨を含め、一覧が画面に見えていない状態でも判断材料が残るようにする。

## Step 5: 修正

承認された指摘のみを対象スキルに適用する。承認されなかった指摘・スコープ外の改善は加えない。対象スキルが git 管理下にある場合もコミットはせず、修正を作業ツリーに残す（コミットはユーザーの指示があった場合のみ）。

完了条件: 承認された全指摘が反映され、修正後の全文を通読して Step 2 の査読基準に新たな違反を生んでいないことを確認済み。

## Step 6: 報告

- 適用した指摘と、それによる変更内容の要約
- 適用しなかった指摘（承認されなかったもの）の一覧
- 修正後に残る既知の制約（あれば）
