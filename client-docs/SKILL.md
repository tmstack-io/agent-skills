# client-docs — クライアント提出資料の生成

クライアントにそのまま提出できる**納品物**を生成する。納品物とは、開発の内側（環境・道具・過程）が一切透けない、クライアントのシステムと案件の事実だけで書かれた文書である。

## モード判定

依頼内容から選ぶ。判定できない場合は AskUserQuestion で確認する。

- **report（対応報告書）**: 指摘・不具合・診断結果への対処を報告する依頼（「対応報告」「脆弱性診断の回答」「指摘事項への対処をまとめて」）
- **decision（意思決定資料）**: クライアントに選択・承認を求める依頼（「選択肢を提示したい」「費用が増える理由を説明したい」「方針を選んでもらいたい」）

## 共通仕様（両モード）

- **納品物として書く**: 記載してよいのは、クライアントのシステム・案件に関する検証済みの事実（コード・設定・実施した対応から確認できるもの）のみ。ローカル環境の情報・開発ツールや AI エージェントの名称・作業の試行錯誤・セッションの経緯は、成果物の読者には存在しない世界として書かない。
- **捏造禁止**: 実施していない対応・確認していない挙動を書かない。未実施・未確認の項目は「今後の対応」「要確認」として区別して記載する。
- **平易な日本語**: 読者は非エンジニアを想定する。結論を先に書く。一文一意で短く。同リポジトリの clarify-ja（`~/.claude/skills/clarify-ja/SKILL.md`）の **--plain モードの規則**（詳細の keep-or-drop・語注の限界・捏造禁止）を読み、**生成時に**このコンテキスト内で適用する。
- **保存先**: プロジェクトにクライアント資料の置き場（`docs/client/` 等）があればそれに従い、既存ファイルの命名慣習に合わせる。慣習がなければ `docs/client/YYYYMMDD-<内容のslug>.md`。保存前にパスを提示する。
- **最終整形**: 保存前に、clarify-ja の**既定モード（意味厳守）**の整形規則をこのコンテキスト内で適用し、文章を磨く。読者向けの取捨選択（--plain の担当）は上記「平易な日本語」で生成時に済んでいるため、整形段階は意味厳守で磨くだけにする（生成時に意図して残した詳細を事後に落とさない）。

## report モード（対応報告書）

まず元指摘の出所（クライアントの指摘文書のパス、無ければセッション内で対処した指摘の一覧）を確定する。特定できなければユーザーに確認する。

指摘項目ごとに次の対で構成する:

```markdown
## <指摘番号・タイトル>

**指摘内容**: <指摘の要約（クライアント側の指摘文書があれば、その番号・表現に対応させる）>

**対処内容**: <何をどう変更し、その結果どうなったか。対処済み/今後対応/対応不要（理由付き）の別を明示>
```

完了条件: 元の指摘事項の**全項目**が資料に現れ、それぞれに対処内容（または対応不要の理由）が対になっている。元指摘のリストと突き合わせて漏れゼロを確認する。

## decision モード（意思決定資料）

次の構成で書く:

```markdown
## 論点

<何を決めてもらいたいのか、なぜ今決める必要があるのかを冒頭に>

## 選択肢

### 案A: <名称>
- 内容: <非エンジニアが読める説明>
- コスト感: 軽 / 中 / 重（<根拠: 作業規模・期間・費用への影響>）
- 利点 / 欠点:

（案B・案C も同形式。選択肢は2〜4件）

## 推奨案

<推奨する案と、その理由。他案を採らない理由も一言ずつ>
```

完了条件: 全選択肢にコスト感とその根拠が付き、推奨案に理由（＋他案を採らない理由）が書かれている。

## 提出前チェック

- [ ] 開発の内側（環境・ツール名・過程・経緯）への言及がゼロか
- [ ] 書かれている対応・挙動はすべて実施・確認済みか（未実施は区別されているか）
- [ ] 非エンジニアが辞書なしで読み切れるか（専門用語の言い換え漏れがないか）
- [ ] report: 元指摘との対応漏れゼロ / decision: コスト感の根拠と推奨理由があるか
