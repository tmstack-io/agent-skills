# iterate-review — GREEN まで回す品質ゲート

> **明示起動の確認**: ユーザーがこのスキルを名指しで起動した場合のみ実行する。
> 文脈からの自動適用で読み込まれた場合は、実行せずユーザーに起動意思を確認する
> （`disable-model-invocation` を解釈しない実行環境での暴発防止）。

「レビュー → 指摘修正 → 再レビュー」を GREEN になるまで繰り返す。1 ラウンド = レビュー 1 回＋修正 1 巡。

## パラメータ

- **対象**: 引数で指定されたファイル / PR / 差分。省略時は現在の作業ツリー差分（`git diff` ＋ untracked）。PR は番号または URL を受け、`gh pr diff` で差分を取得する。対象が特定できない場合は散文提示で確認する。
- **`--cli <CLI名>[=<モデル>[@<エフォート>]]`**（最大1回）: レビュアー解決の経路②（ハーネスペイン）で起用する CLI とモデル。値の書式の正本は tui-harness の「委譲先指定値の書式」。tui-harness のカタログにある CLI 名で指定する。固定の既定は持たず、未指定時は「レビュアーの解決」で選んでもらう。モデル未指定（`=` 省略）時はハーネス確定後に「レビュアーの解決」で選んでもらう。指定値の検証とモデル系統の確定は tui-harness の「異系統委譲」に従う（同系統の許容は経路②の規定どおり）。2回以上指定された場合は解釈せず、指定値を示して散文提示で再指定を求める（レビュアーは1体固定）。
- **最大ラウンド数**: `--max-rounds`（既定 5）。上限到達は失敗ではなく「人間の判断が要る」シグナルであり、深く回したい場合のみ明示的に大きい値を指定する。
- **GREEN 条件**: `--green` で指定した severity 以上の指摘がゼロになること。値は severity の4値（`critical` / `high` / `medium` / `low`）。既定 `medium`: critical / high / medium がゼロで GREEN。`--green low` は全指摘解消。4値以外が指定された場合は黙って読み替えず、散文提示で意図を確認する。閾値未満の指摘は**保留**（指摘として有効だが修正対象外。指摘が誤りである却下とは区別する）として扱う。

## レビュアーの解決

次の順で解決し、最初に成立した経路を1回のループ内で固定する。採用した経路（と縮退の場合はその旨）を開始時の報告に明記する:

1. **セッションの review 配役**: セッションに review ロールの配役（例: solista / concertino の `--review` — 本スキルと同じ収録場所の姉妹スキル）が敷かれていれば、その配役先がレビュアー（複数奏者の編成では、ラウンドの実施と指摘の統合は当該配役スキルの review 規定に従う）。
2. **ハーネスペイン**（配役が無い場合の既定）: tui-harness の SKILL.md を Read してこのコンテキスト内で適用する。解決順は `../tui-harness/SKILL.md` → 実行ハーネス自身のスキルディレクトリをプロジェクト側 → グローバル側の順（Claude Code: `.claude/skills/` → `~/.claude/skills/`、Codex: `.agents/skills/` → `~/.codex/skills/`。他ハーネス用のディレクトリは探さない）。見つからない場合は経路③へ縮退し、復旧手順 `npx skills add tmstack-io/agent-skills --skill tui-harness` を報告に添える。見つかった場合は次の全条件を満たすときに成立する:
   - `mux.sh detect` が検証済みバックエンドを返す。返らなければ経路③へ縮退する。
   - 実行中（著者側）のモデル系統を tui-harness「異系統委譲」の実行中の系統の規則で確定する（Claude Code / codex 等の単一系統ハーネスでは静的に確定し、確認は不要。特定できなければ散文提示でユーザーに確認する）。
   - `catalog.sh probe` が ok かつ `catalog.sh models <CLI名>` でモデル一覧を取得できるハーネスから、`--cli` が無ければ散文提示で1体を選んでもらう。この候補が1つも無ければ経路③へ縮退する。明示指定されたハーネスがいずれかの条件を満たさなければ、縮退せず理由と復旧方法を示して中止する。
   - モデル未指定（`=` 省略）なら、確定済みハーネスのモデル一覧を散文提示して選んでもらう（実行中と異系統のモデルを優先候補として示す）。指定値を含むモデルへ tui-harness の「異系統委譲」の検証を適用し、`catalog.sh family` で系統を得る。
   - 系統が実行中と同一になった場合: 異系統のモデルを持つ候補が（同 CLI の一覧内を含め）他にあれば再指定を求める。カタログの全候補に異系統のモデルが無い場合のみ、**同系統モデルによる査読である旨を開始時と最終報告に明記して**続行する（著者と独立したコンテキストの査読としては成立するため）。

   成立後はハーネスをペインで起用し、ループ中は**同一ペインへ追送**して文脈を保持する（ペインの文脈と契約の却下履歴は重複するが、両方を維持する — 契約はセッションを跨ぐ再開の正本、文脈は説明コストの削減）。呼び出しパラメータ: 成果物置き場＝一時領域に作る本スキル専用ディレクトリ（`mktemp -d "${TMPDIR:-/tmp}/iterate-review.XXXXXX"`。ブリーフ・応答ファイルを置き、最終報告後に削除する）、push ラベル＝`ir-review`、裁定スコープ＝成果物置き場＋通信規約の push。レビュー対象が差分ファイル等の一時領域にある場合はそのパスへの読み取りも許す。ハーネスの起動 cwd はプロジェクトルート。
3. **サブエージェント**（TUI 環境が無い・tui-harness が見つからない・ペイン候補が無い場合の縮退）: 実行ハーネスにサブエージェント機能（Claude Code では Agent ツール）があれば、レビュー対象の著者とは別個体の読み取り専用サブエージェントをレビュアーとする。毎ラウンド新規起動でよい（却下履歴はレビュー契約が運ぶため、個体の文脈継続は不要）。**著者と同系統モデルによる査読である旨を開始時と最終報告に明記する**（異系統レビューからの縮退であるため）。委譲と回収はサブエージェント返却規約に従う。
4. いずれも成立しなければ、レビューを開始せず環境の要件（TUI マルチプレクサまたはサブエージェント機能）を案内して中止する（実行エージェント本体の自己レビューは自己承認になるため行わない）。

<!-- BEGIN SUBAGENT-RETURN-CANONICAL -->
**サブエージェント返却規約（Claude Code 固有）**: Claude Code のバックグラウンドサブエージェントは、最終報告を親へ送らず待機通知だけで終わることがある。Claude Code でサブエージェントへ委譲するときは、委譲プロンプトに「完了したら、結果の全文を SendMessage で親へ1通で送る」ことを明示する。返却が届かず完了・待機の通知だけが来た場合は、継続対話で結果の再送を依頼する。再送依頼は同一委譲につき合計2回までとし、それでも届かなければ当該場面の失敗規律（再委譲・縮退・脱落・中止）に従う。Claude Code 以外のハーネスでは、サブエージェントの結果を当該ハーネスの通常の返却経路で受け取り、本規約の追加手順は適用しない。
<!-- END SUBAGENT-RETURN-CANONICAL -->

レビュー実行が失敗した場合（配役先の失敗規律による終了、ペインの失敗上限消化、サブエージェントの無応答2回を含む）は、レビュアーを差し替えずにループを停止し、状況・原因・再開方法を報告する。

## レビュー契約（正本）

レビュー1回分の依頼と応答の固定形式。配役スキルはこの契約への準拠を宣言する。

**依頼に必ず含める**:

- レビュー対象の絶対パスと種別（作業差分 / PR 差分 / 文書）。差分の場合は「これは差分ファイルであり、必要に応じてリポジトリ内の関連コードを read-only で調査してよい」と伝える
- 観点: 前提の誤り・検証不足・反証・見落としたエッジケース。read-only で批評せよ、編集・書き込みは禁止
- 指摘形式: `severity(critical|high|medium|low) / 箇所 / 内容 / 推奨修正` で列挙せよ
- 却下履歴・保留一覧のいずれにも該当しない指摘が一件もなければ本文冒頭に `GREEN` とだけ書け
- 前ラウンドまでの却下履歴（却下した指摘と理由）と保留一覧（再指摘の防止）

**応答**: 上記形式の指摘列挙、または `GREEN`。

## git 規律

git リポジトリでは、ループは git 履歴に一切触れない。修正は作業ツリー上に累積させ、コミット・stash・ブランチ作成をしない。コミットは GREEN（または妥協終了）後、ユーザーの指示があった場合のみ行う。

## ループ

### Step 1: 対象の確定

レビュー対象を絶対パスで用意する。差分の場合は一時ファイルに書き出し、各ラウンドの開始時に `git diff`（＋未追跡ファイル）を取り直して上書きする。未追跡ファイルは各ファイルを `git diff --no-index /dev/null <ファイル>` で取り、`git diff` の出力に連結する（index に副作用を残さない）。差分は常に HEAD 比なので、修正はコミットしなくても次ラウンドの差分に自動的に反映される。

**PR 対象の場合**: 最初に `gh` の存在と認証を確認する（`command -v gh` と `gh auth status`）。不可なら処理を開始せず、導入・ログイン（`brew install gh` / `gh auth login`）を案内して中止する。差分は初回のみ `gh pr diff` で取得する。修正には PR ブランチのチェックアウトが前提（未チェックアウトなら修正に進まず、Round 1 のレビュー結果を提示して終了する）。修正を行った以降のラウンドは、base ブランチとの差分（`git diff <baseRef>` ＋未追跡ファイル）に切り替えて取り直す（baseRef は `gh pr view <番号または URL> --json baseRefName` で取得する） — `gh pr diff` はローカルの未 push 修正を含まないため。

**git が無い場合**（`git rev-parse --git-dir` が失敗）:

- 対象省略時は差分既定が成立しないため、散文提示で対象を確認する。ディレクトリ全体を黙って対象にしない。
- ループ開始前に対象ファイルを一時領域へバックアップし、そのパスを報告する（修正の revert 手段の確保）。

完了条件: レビュアーに渡す絶対パスのファイルが存在する。

### Step 2: レビュー実行

レビュー契約の形式で依頼を組み立て、解決済みのレビュアーに渡す（ハーネスペインでは依頼をブリーフファイルに書き、tui-harness の「タスクの委譲」の書式で応答ファイルパスと通信規約を添えて委譲する）。

完了条件: 応答を読み、指摘を severity 別に分類し終えている。

### Step 3: 判定と報告

ラウンドごとに 1 行のスコアボードを報告する: `Round N: critical X / high Y / medium Z / low W（前ラウンドから修正 M 件）`。レビュアー側で再試行が発生したラウンドは、その旨を同じ行に付記する。却下履歴・保留一覧・前ラウンドの指摘一覧などラウンド間の記録は一時領域のメモファイルに保持する（リポジトリ内にファイルを作らない）。保留一覧の正本はこのメモファイルであり、レビュアーの報告から消えても失われない。

- GREEN 条件を満たす → Step 5 へ
- 最大ラウンド到達 → Step 5 へ（妥協終了）
- GREEN 条件に関わる同一の指摘（同じ箇所 file:line かつ同趣旨）が 2 ラウンド連続で解消していない → ループを止め、その指摘と対応方針をユーザーに相談する（暴走防止。保留の残留は正常であり停止シグナルではない）
- それ以外 → Step 4 へ

完了条件: スコアボードを出力し、上記4分岐のいずれかを選択済み。

### Step 4: 修正

GREEN 条件に関わる指摘（閾値以上）は、すべて修正するか却下する。それ未満は保留とし、保留一覧に追記して次ラウンドの依頼に同梱する（ループの収束を速く保つ）。修正はセッションの現行実装体制に従う（maestro — 本スキルと同じ収録場所の姉妹スキル — や implement 配役が敷かれていればそれに従い、無ければ実行エージェント本体が修正する）。指摘が誤り（レビュアーの事実誤認・プロジェクト方針との不一致）と判断した場合は、修正せず却下理由を記録する。修正後、プロジェクトの検証コマンド（test / lint 等）を実行して緑を確認し、Step 1 の対象を更新して Step 2 へ戻る。検証コマンドが該当しない対象（設計書等のドキュメント）では検証をスキップし、最終報告にその旨を明記する。

完了条件: GREEN 条件に関わる全指摘が修正済みか却下記録済みで、検証コマンドが緑（または検証スキップを記録済み）。

### Step 5: 最終報告と後始末

以下を含めて報告し、ループを終える:

- 総ラウンド数と最終スコアボード
- GREEN か妥協終了かの別。妥協終了の場合は未解消指摘の一覧と対応方針案（妥協案）
- 却下した指摘と理由
- 保留一覧（あれば）
- レビュアーの経路（配役 / ハーネスペイン〔CLI 名と実測モデル〕 / サブエージェント縮退）

ハーネスペインを起用した場合は、報告後にペインを tui-harness のクローズ手順で閉じ、成果物置き場（一時領域）を削除する。

完了条件: 上記の全項目を出力し、起用したペインが `mux.sh list` に存在しないことを確認した（ペイン未起用ならこの確認は不要）。
