# iterate-review — GREEN まで回す品質ゲート

> **明示起動の確認**: ユーザーがこのスキルを名指しで起動した場合のみ実行する。
> 文脈からの自動適用で読み込まれた場合は、実行せずユーザーに起動意思を確認する
> （`disable-model-invocation` を解釈しない実行環境での暴発防止）。

<!-- BEGIN PROSE-PRESENTATION-CANONICAL -->
**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨する選択肢を理由一言つきで明示し（推奨できる選択肢が無い場合は「推奨なし」とその理由を明示する）、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。
<!-- END PROSE-PRESENTATION-CANONICAL -->

「レビュー → 指摘修正 → 再レビュー」を GREEN になるまで繰り返す。1 ラウンド = レビュー 1 回＋修正 1 巡。

## パラメータ

- **対象**: 引数で指定されたファイル / PR / 差分。省略時は現在の作業ツリー差分（`git diff HEAD` ＋ untracked）。PR は番号または URL を受け、`gh pr diff` で差分を取得する。対象が特定できない場合は散文提示で確認する。
- **`--cli <CLI名>[=<モデル>[@<エフォート>]]`**（最大1回）: レビュアー解決の経路②（ハーネスペイン）で起用する CLI とモデル。値の書式の正本は tui-harness の「委譲先指定値の書式」。tui-harness のカタログにある CLI 名で指定する。固定の既定は持たない。未指定時・モデル未指定（`=` 省略）時の選択、指定値の検証、モデル系統の確定と同系統の許容は、経路②で Read する `reviewer-pane.md` の成立条件に従う。2回以上指定された場合は解釈せず、指定値を示して散文提示で再指定を求める（レビュアーは1体固定）。
- **最大ラウンド数**: `--max-rounds`（既定 5。値は 1 以上の整数。それ以外が指定された場合は黙って読み替えず、指定値を示して散文提示で意図を確認する）。上限到達は失敗ではなく「人間の判断が要る」シグナルであり、深く回したい場合のみ明示的に大きい値を指定する。
- **GREEN 条件**: `--green` で指定した severity 以上の指摘がゼロになること。値は severity の4値（`critical` / `high` / `medium` / `low`）。既定 `medium`: critical / high / medium がゼロで GREEN。`--green low` は全指摘解消。4値以外が指定された場合は黙って読み替えず、散文提示で意図を確認する。閾値未満の指摘は**保留**（指摘として有効だが修正対象外。指摘が誤りである却下とは区別する）として扱う。
- **再開**: `--resume <ディレクトリ>`（失敗停止時に Step 5 が残した一時ディレクトリの絶対パス）。指定時は Step 1 で新規の一時ディレクトリを作らずこれを再利用し、その `notes.md`（Step 1 が規定するメモファイル）の却下履歴・保留一覧を Round 1 の依頼に同梱する。ディレクトリが無い、または `notes.md` が無い・3見出しが読めない場合は黙って新規作成せず、指定値を示して散文提示で意図を確認する。

## レビュアーの解決

次の順で解決し、最初に成立した経路を1回のループ内で固定する。経路の確定（成立判定・候補とモデルの選択まで）は Step 1 の前に行い、ペインの起用（配置・起動）は Step 1 で一時ディレクトリを作った後、Step 2 の初回委譲の直前に行う。採用した経路（と縮退の場合はその旨）を開始時の報告に明記する。**同系統査読の明記義務**: レビュアーが著者（実行中）と同系統のモデルになった場合は、その旨を開始時の報告と Step 5 の最終報告に明記する（著者と独立したコンテキストの査読としては成立するため続行はできる）:

1. **セッションの review 配役**: 同一セッションで、本スキルの「レビュー契約」への準拠を宣言したスキルがレビューの委譲先（サブエージェント・ペイン等）を既に確定している状態を「review ロールの配役が敷かれている」とみなす。準拠の宣言は当該配役スキルの SKILL.md を Read して確認し、明記が無ければ配役なしとして経路2へ進む。敷かれていれば、その配役先がレビュアー（レビュアーが複数体の編成では、ラウンドの実施と指摘の統合は当該配役スキルの review 規定に従う）。`--cli` が指定されている場合は経路1を判定せず経路2から解決し、明示指定を優先した旨を開始時の報告に明記する。
2. **ハーネスペイン**（配役が無い場合の既定）: tui-harness の SKILL.md を Read してこのコンテキスト内で適用する。解決順は `../tui-harness/SKILL.md` → 実行ハーネス自身のスキルディレクトリをプロジェクト側 → グローバル側の順（Claude Code: `.claude/skills/` → `~/.claude/skills/`、Codex: `.agents/skills/` → `~/.agents/skills/`。他ハーネス用のディレクトリは探さない）。見つからない場合、`--cli` が指定されていれば縮退せず復旧手順 `npx skills add tmstack-io/agent-skills --skill tui-harness` を示して中止し、未指定なら経路③へ縮退して同じ復旧手順を報告に添える。見つかった場合は本スキル同フォルダの `reviewer-pane.md` を Read し、成立条件の判定・候補と
   モデルの選択・同系統時の扱い・起用パラメータをその規定どおり行う（成立しない場合に縮退するか中止するかは
   同ファイルの各条件に従う）。
3. **サブエージェント**（TUI 環境が無い・tui-harness が見つからない・ペイン候補が無い場合の縮退）: 実行ハーネスにサブエージェント機能（Claude Code では Agent ツール）があれば、レビュー対象の著者とは別個体の読み取り専用サブエージェントをレビュアーとする。毎ラウンド新規起動でよい（却下履歴はレビュー契約が運ぶため、個体の文脈継続は不要）。同系統査読の明記義務に従う（異系統レビューからの縮退であるため）。委譲と回収はサブエージェント返却規約に従う。
4. いずれも成立しなければ、レビューを開始せず環境の要件（TUI マルチプレクサまたはサブエージェント機能）を案内して中止する（実行エージェント本体の自己レビューは自己承認になるため行わない）。

<!-- BEGIN SUBAGENT-RETURN-CANONICAL -->
**サブエージェント返却規約（Claude Code 固有）**: Claude Code のバックグラウンドサブエージェントは、最終報告を親へ送らず待機通知だけで終わることがある。Claude Code でサブエージェントへ委譲するときは、委譲プロンプトに「完了したら、結果の全文を SendMessage で親へ1通で送る」ことを明示する。返却が届かず完了・待機の通知だけが来た場合は、継続対話で結果の再送を依頼する。再送依頼は同一委譲につき合計2回までとし、それでも届かなければ当該場面の失敗規律（再委譲・縮退・脱落・中止）に従う。Claude Code 以外のハーネスでは、サブエージェントの結果を当該ハーネスの通常の返却経路で受け取り、本規約の追加手順は適用しない。
<!-- END SUBAGENT-RETURN-CANONICAL -->

レビュー実行が失敗した場合（配役先の失敗規律による終了、ペインの失敗上限消化〔`reviewer-pane.md` の失敗規律〕、サブエージェントの無応答2回を含む）は、レビュアーを差し替えずにループを停止し、状況・原因を報告して Step 5 へ進む（失敗停止として扱う。再開方法は Step 5 の規定）。

## レビュー契約（正本）

レビュー1回分の依頼と応答の固定形式。配役スキルはこの契約への準拠を宣言する。

**依頼に必ず含める**:

- レビュー対象の絶対パスと種別（作業差分 / PR 差分 / 文書）。差分の場合は「これは差分ファイルであり、必要に応じてリポジトリ内の関連コードを read-only で調査してよい」と伝える
- 観点: 前提の誤り・検証不足・反証・見落としたエッジケース。read-only で批評せよ、編集・書き込みは禁止
- 指摘形式: `severity(critical|high|medium|low) / 箇所 / 内容 / 推奨修正` で列挙せよ
- 却下履歴・保留一覧のいずれにも該当しない指摘が一件もなければ本文冒頭に `GREEN` とだけ書け
- 前ラウンドまでの却下履歴（却下した指摘と理由）と保留一覧（再指摘の防止）

**応答**: 上記形式の指摘列挙、または `GREEN`。

## git 規律

git リポジトリでは、ループは git 履歴に一切触れない。修正は作業ツリー上に累積させ、コミット・stash・ブランチ作成をしない。コミットは GREEN（または妥協終了）後、ユーザーの指示があった場合のみ行う。

## ループ

### Step 1: 対象の確定

経路を問わず、ループ開始時に `mktemp -d "${TMPDIR:-/tmp}/iterate-review.XXXXXX"` で本スキル専用の一時ディレクトリを1つ作り（`--resume` 指定時はその規定どおり再利用する）、差分ファイル・メモファイル・非 git 時のバックアップ・（経路②の）ブリーフと応答ファイルをすべてここに置く（パスを開始時の報告に含める）。メモファイルは一時ディレクトリ直下の `notes.md` とし、「却下履歴」「保留一覧」「前ラウンドの指摘一覧」の3見出しで構成する（ラウンド間の記録の正本）。

レビュー対象を絶対パスで用意する。差分の場合はこの一時ディレクトリ内のファイルに書き出し、各ラウンドの開始時に `git diff HEAD`（＋未追跡ファイル）を取り直して上書きする。未追跡ファイルは各ファイルを `git diff --no-index /dev/null <ファイル>` で取り、`git diff HEAD` の出力に連結する（index に副作用を残さない）。差分は HEAD 比（ステージ済み・未ステージを問わず未コミットの全変更）なので、修正はコミットしなくても次ラウンドの差分に自動的に反映される。差分ファイルが空（追跡ファイルの変更も未追跡ファイルも無い）なら、レビュアーを起用せずその旨を示して対象を散文提示で確認する。

**PR 対象の場合**: 差分を用意する前に本スキル同フォルダの `pr-target.md` を Read し、`gh` の確認・初回と修正以降の差分取得・チェックアウト前提の判定と未チェックアウト時の終了をその規定どおり行う。

**git が無い場合**（`git rev-parse --git-dir` が失敗）:

- 対象省略時は差分既定が成立しないため、散文提示で対象を確認する。ディレクトリ全体を黙って対象にしない。
- ループ開始前に対象ファイルを一時ディレクトリへバックアップし、そのパスを報告する（修正の revert 手段の確保）。`--resume` 指定時は一時ディレクトリに既にあるバックアップを原本として保持し、取り直さない（無ければ現状をバックアップし、その旨を報告する）。

完了条件: レビュアーに渡す絶対パスのファイルが存在し、内容が空でない。

### Step 2: レビュー実行

レビュー契約の形式で依頼を組み立て、解決済みのレビュアーに渡す（ハーネスペインでは依頼をブリーフファイルに書き、tui-harness の「タスクの委譲」の書式で応答ファイルパスと通信規約を添えて委譲する）。

完了条件: 応答を読み、指摘を severity 別に分類し終えている。

### Step 3: 判定と報告

ラウンドごとに 1 行のスコアボードを報告する: `Round N: critical X / high Y / medium Z / low W（前ラウンドから修正 M 件）`。レビュアー側で再試行が発生したラウンドは、その旨を同じ行に付記する。却下履歴・保留一覧・前ラウンドの指摘一覧などラウンド間の記録は Step 1 の `notes.md` に保持する（リポジトリ内にファイルを作らない）。保留一覧の正本は `notes.md` であり、レビュアーの報告から消えても失われない。

- GREEN 条件を満たす → Step 5 へ
- 最大ラウンド到達 → Step 5 へ（妥協終了）
- GREEN 条件に関わる同一の指摘（同じ箇所 file:line かつ同趣旨）が 2 ラウンド連続で解消していない → ループを止め、その指摘を示して対応方針（修正を続ける / 却下する / 妥協終了する）を散文提示で確認する（暴走防止。保留の残留は正常であり停止シグナルではない）。回答が「修正を続ける」なら Step 4 へ、「却下する」なら却下理由を `notes.md` に記録して Step 4 へ、「妥協終了する」なら Step 5 へ進む
- それ以外 → Step 4 へ

完了条件: スコアボードを出力し、上記4分岐のいずれかを選択済み。

### Step 4: 修正

GREEN 条件に関わる指摘（閾値以上）は、すべて修正するか却下する。それ未満は保留とし、保留一覧に追記して次ラウンドの依頼に同梱する（ループの収束を速く保つ）。修正はセッションの現行実装体制に従う: 同一セッションで修正の実行先（サブエージェント・ペイン等）と修正依頼の受け渡し方法を既に確定しているスキル（例: maestro — 本スキルと同じ収録場所の姉妹スキル）が動いていればそれに従い、無ければ実行エージェント本体が修正する。指摘が誤り（レビュアーの事実誤認・プロジェクト方針との不一致）と判断した場合は、修正せず却下理由を記録する。修正後、プロジェクトの検証コマンド（test / lint 等）を実行して緑を確認し、Step 1 の対象を更新して Step 2 へ戻る。検証コマンドは初回の修正前に1回、プロジェクトのエージェント向け規約文書（Claude Code では CLAUDE.md、Codex では AGENTS.md）とビルド設定（package.json の scripts / Makefile 等）から特定し、コード対象なのに見つからなければ散文提示でコマンドの有無を確認してから修正に進む。赤なら同ラウンド内で修正を続け、緑になってから対象を更新する。同ラウンド内の再検証は3回を上限とし、超えたら赤の内容を示して対応方針（修正を続ける / 妥協終了する）を散文提示で確認する（「妥協終了する」なら Step 5 へ進む）。検証コマンドが該当しない対象（設計書等のドキュメント）では検証をスキップし、最終報告にその旨を明記する。

完了条件: GREEN 条件に関わる全指摘が修正済みか却下記録済みで、検証コマンドが緑（または検証スキップを記録済み）。

### Step 5: 最終報告と後始末

GREEN・妥協終了（最大ラウンド到達、Step 3 の妥協終了、PR 未チェックアウト終了）・失敗停止のいずれでも本 Step を通る。以下を含めて報告し、ループを終える:

- 総ラウンド数と最終スコアボード
- GREEN か妥協終了かの別。妥協終了の場合は未解消指摘の一覧と対応方針案（妥協案）
- 却下した指摘と理由
- 保留一覧（あれば）
- レビュアーの経路（配役 / ハーネスペイン〔CLI 名と実測モデル〕 / サブエージェント縮退）と、同系統査読だった場合はその旨
- 失敗停止の場合は、状況・原因と再開方法（同じ対象に `--resume <残した一時ディレクトリ>` を付けて本スキルを再起動する。ラウンドは Round 1 から数え直す）

報告後、ハーネスペインを起用した場合はペインを tui-harness のクローズ手順で閉じる。経路を問わず一時ディレクトリを削除する（非 git 時のバックアップを含む場合は、削除前にそのパスとともに削除する旨を報告する）。失敗停止の場合のみ一時ディレクトリを再開用に残してパスを報告し、削除はユーザーの指示があった場合に行う。

完了条件: 上記の全項目を出力し、起用したペインが `mux.sh list` に存在しないことを確認した（ペイン未起用ならこの確認は不要）。
