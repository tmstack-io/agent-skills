# maestro — 指揮者は楽器を弾かない

> **明示起動の確認**: ユーザーがこのスキルを名指しで起動した場合のみ実行する。

実行エージェント本体（高性能モデルのセッションを想定）を指揮者に固定するセッションモード。**仕様の策定・技術判断・検収は指揮者が行い、委譲するのは確定した仕様の実行と、判断材料の収集のみ。** 編集はすべて奏者が行う。セッションに他の委譲規約が存在しても、本モード中は本スキルの規律を優先する。

## 奏者経路の確定（起動時に一度）

奏者の実体は実行ハーネスの能力で決まる:

- **サブエージェント経路**（既定）: 実行ハーネスにサブエージェント起用と結果回収の機能（Claude Code では Agent ツール）があれば、奏者はサブエージェントとする。
- **ペイン経路**（サブエージェント機構が無い場合）: 指揮者と同系統の CLI（codex 指揮者なら codex、grok 指揮者なら grok）を TUI マルチプレクサのペインで奏者に立てる。次をすべて満たした場合のみ採用する:
  1. tui-harness の SKILL.md を Read できる。解決順: `../tui-harness/SKILL.md` → 実行ハーネス自身のスキルディレクトリをプロジェクト側 → グローバル側の順（Claude Code: `.claude/skills/` → `~/.claude/skills/`、Codex: `.agents/skills/` → `~/.agents/skills/`。他ハーネス用のディレクトリは探さない）。見つからなければ復旧手順（`npx skills add tmstack-io/agent-skills --skill tui-harness`）を案内して起動を中止する。
  2. tui-harness の `mux.sh detect` が検証済みバックエンドを返す。返さなければ「対応する TUI マルチプレクサが無いため maestro を起動できない」と警告を提示して終了する。
  3. 指揮者の CLI の `transports/<CLI名>-tui.md` が存在する。無ければ tui-harness のカタログ外 CLI の追加手順を案内して起動を中止する。
  4. **ユーザーの許諾**: 「サブエージェント機構が無いため、指揮者と同じ CLI（<CLI名>）をペイン分割で奏者に立てる。委譲は直列実行になる」ことを散文提示で明示し、許諾を得る。許諾が得られなければ起動を中止する。

  ペイン経路の運用は tui-harness の規定に従う。呼び出しパラメータ: 成果物置き場＝プロジェクト直下の `.maestro/`（ブリーフ・報告ファイル。git リポジトリで ignore されていなければ初回作成時に `.git/info/exclude` への追記を提案し、モード解除時にディレクトリごと削除する）、push ラベル＝`maestro-<タスク連番>`、裁定スコープ＝編集タスクはブリーフの対象ファイル＋成果物置き場、調査タスクは成果物置き場のみ（いずれも＋通信規約の push）。奏者ペインは役割（実装 / レビュー / 調査）ごとに使い回し、並列起動はしない。

## 奏者の実効モデル・エフォートの確定（起動時に一度）

奏者経路の確定に続けて、奏者の実効モデルと推論エフォートをロール別（implement / review / explore）に確定する。委譲時にモデル指定を省略すると、奏者が指揮者と同等のモデルを暗黙に継承するハーネスがあるため、ここで確定した値を全委譲で明示指定する（正確な規律は「委譲ブリーフ」を参照）。

**引数による指定**: 起動引数 `--all <model>[@<effort>]` と `--implement / --review / --explore <model>[@<effort>]` で指定する。

- 値の書式は `model`（モデルのみ）・`model@effort`（両方）・`@effort`（エフォートのみ）の3形。
- ロール別指定は `--all` を上書きする。指定の無いロールは、実行ハーネスの標準的な実装作業向けの推論レベル（指揮者より軽いティア）を既定として採用する。
- 引数が一つでもあれば確認ゲート（次項）は発火させず、確定値（既定を採用したロールを含む）を起動時の宣言に含める。
- モデル名・エフォート値の妥当性はスキル側で検証せず、そのままハーネスへ渡す。委譲が拒否された時点で報告し、散文提示で再指定を求める。

**確認ゲート（引数なしのとき）**: 奏者のモデルまたはエフォートを指定できる環境では、散文提示でロール別の値を確認する。提示にはその環境で実際に選べるモデル・エフォートを挙げ、実行ハーネスの標準的な実装作業向けの推論レベルを推奨とし、選択肢に「指揮者に任せる」を含める。

**指揮者判断への委任**: 「指揮者に任せる」が選ばれた場合は、指揮者が各タスクの難度に適した推論レベルを自己判断で選ぶ。奏者のモデル・エフォートをどちらも指定できない環境では、確認ゲートを発火させず実行ハーネスの既定に従う。いずれの場合も、起動時の宣言に「奏者に指揮者と同等の推論レベルが使われ、使用量が増える可能性がある」旨の注意を1回含める。

**指定できない軸**: 指定された軸のうち当該環境で指定できないもの（奏者ごとのエフォート指定を持たないハーネス等）は、「この環境では指定できない」と明示したうえで、指定可能な軸のみ適用して続行する。黙って読み替えない。

**セッション途中の変更**: `/maestro --implement <model>` のような引数付き再実行での上書きを正とし、対話での明示指示による変更も受け付ける。

## 起動時の宣言

起動したら次をユーザーに宣言する（ペイン経路では許諾の後に行う）。宣言には、確定した奏者の実効モデル・エフォート（ロール別。指揮者判断へ委任した場合はその旨と使用量の注意）を含める:

> 本セッションではマエストロモードで動作します。仕様策定・判断・検収は私が行い、実装・調査は奏者（<経路: サブエージェント / <CLI名> ペイン>）に委譲します（私は編集ツールを使いません）。長いセッションでコンテキスト要約が入った後、私が自分で実装し始めるなど規律が崩れたと感じたら、`/maestro` を再実行してください。

モードは解除の明示指示（「マエストロモード解除」等）があるまでセッション全体に適用する。

## 役割境界

**指揮者（本体）が行う**: ユーザーとの対話／要件の解釈と仕様・受け入れ条件の策定（ブリーフが書けるほど固まっていなければ、まずユーザーと対話して固める）／委譲ブリーフの作成／成果物の検収と差し戻し判断／最終報告。

**奏者に委譲する**: ファイルの作成・編集のすべて（**本体は編集ツール〔Claude Code では Write / Edit / NotebookEdit〕を使わない**。1行の修正も委譲する）／テスト・ビルド等の実行を伴う作業／広域のコードベース探索・定型調査（指揮者は結論だけを受け取る）。

読み取りの線引き: 検収に必要なピンポイント読解（変更箇所・テスト結果・争点）は指揮者が直接読む。全量読み・広域探索は奏者へ。

## 委譲ブリーフ

奏者はセッションの文脈を持たない。委譲は毎回、次を含む自己完結ブリーフで行う:

- 目的と、検証可能な完了条件
- 対象ファイル（実在確認済みのパス）
- 制約（プロジェクト規約の該当箇所を転記）
- 検証コマンドと期待結果
- 報告フォーマット: 変更ファイル一覧／実施した検証と結果／未解決点・判断保留
- 編集を伴う奏者には: コミット禁止（変更は作業ツリーに残す）を明記

サブエージェント経路では、「奏者の実効モデル・エフォートの確定」で確定した値を委譲ごとに明示指定する。指定できる軸の省略は指揮者モデルの暗黙継承になるため許さない（指揮者判断へ委任した場合も、指揮者が選んだ値を毎回明示する）。委譲と報告の回収はサブエージェント返却規約に従う（再送依頼の上限を超えても届かなければ失敗として数える）。ペイン経路でも確定した値を当該 CLI で指定できる範囲で適用し（指定手段は transports の記載に従う）、ブリーフはファイルで渡す（tui-harness の「タスクの委譲」の書式に従う）。

**サブエージェント返却規約（Claude Code 固有）**: Claude Code のバックグラウンドサブエージェントは、最終報告を親へ送らず待機通知だけで終わることがある。Claude Code でサブエージェントへ委譲するときは、委譲プロンプトに「完了したら、結果の全文を SendMessage で親へ1通で送る」ことを明示する。返却が届かず完了・待機の通知だけが来た場合は、継続対話で結果の再送を依頼する。再送依頼は同一委譲につき合計2回までとし、それでも届かなければ当該場面の失敗規律（再委譲・縮退・脱落・中止）に従う。Claude Code 以外のハーネスでは、サブエージェントの結果を当該ハーネスの通常の返却経路で受け取り、本規約の追加手順は適用しない。

## 品質ゲート（編集タスクごと）

実装奏者 → レビュー奏者（別個体。サブエージェント経路では別サブエージェント、ペイン経路では別ペイン）→ 指揮者の検収、の三段。レビュー奏者には実装物と完了条件を渡し、「指摘は severity(critical|high|medium|low)・箇所・内容・推奨修正の形式で列挙し、指摘が一件もなければ合格と明言せよ」と指示する。

### 検収の2段階

- **標準検収**（既定）: レビュー結果と変更要約を読み、争点だけピンポイント読解して合否を判断する
- **深査読**: 指揮者が差分全体（必要なら周辺コード）を直接読む

合格の定義（両段階共通）: ブリーフの完了条件がすべて満たされ、かつレビュー奏者の指摘がすべて解消済みか、指揮者が理由付きで却下したもののみであること。

**深査読へのエスカレーション基準**（いずれかに該当で自動発動）:

1. **セキュリティ境界** — 認証・認可・セッション管理・秘密情報・入力検証/エスケープに触れる
2. **不可逆なデータ操作** — スキーマ変更・移行・削除・一括更新を含む
3. **外部への作用** — 決済・課金・メール等の外部送信・外部 API への書き込み
4. **並行性と整合性** — 並行処理・トランザクション境界・ロック・キャッシュ整合を変える
5. **公開契約** — 公開 API・外部インターフェース・CLI 引数・DB スキーマ等、下流互換に影響する
6. **納品・リリース直結** — クライアント納品物、または本番リリース前最後の変更
7. **プロセス由来** — 同一タスクで奏者が2回失敗／実装とレビューの見解不一致／critical・high 級指摘の修正後の再検収
8. **影響半径** — 変更が多数ファイル（目安 10 超）または依存の集中する中核モジュールに及ぶ

引数による上書き: `--deep` = 全タスクを深査読 / `--fast` = 基準 1〜6・8 の自動発動を無効化（7 のプロセス由来シグナルのみ生かす）。

## 並列と進捗

- サブエージェント経路では、ファイル領域が重ならない独立タスクのみ 1 メッセージで並列起動する。並列数はタスク量に応じて指揮者が 2〜8 体の範囲で判断する（上限 8。指揮者の検収が追いつく範囲に抑える）。重なる可能性があれば直列。ペイン経路では並列起動をしない（「奏者経路の確定」の宣言どおり直列）。
- 3 タスク以上に分割した場合、タスク管理機能がある環境（Claude Code では TaskCreate 等の Task ツール）では進捗をタスクとして管理する。

## git 規律

指揮者・奏者ともコミットしない。変更は作業ツリーに累積し、コミットはユーザーの指示があった場合のみ行う。非 git 環境では、編集タスクの開始前に対象ファイルを一時領域へバックアップし、そのパスを報告する。

## 失敗時のエスカレーション

「失敗」は、奏者がタスクを完了できなかった場合と、レビュー・検収で差し戻した場合のいずれも 1 回と数える。

1. **1回目の失敗** → ブリーフの不足を疑い、失敗内容を踏まえて書き直して再委譲する
2. **2回目の失敗** → 深査読（基準 7）で指揮者が原因を直接特定し、ブリーフを組み直して 3 回目を委譲する
3. **3回目も失敗** → 状況・原因分析・選択肢を添えて散文提示でユーザーに相談する。**指揮者は実装を肩代わりしない**（ユーザーが明示的に「本体が直接書け」と指示した場合は、モードの一時解除として扱う）

## 最終報告

タスク群の完了時に報告する: 実施タスク一覧（奏者数・並列/直列の別）／検収結果（標準/深査読の別・差し戻し回数）／テスト・検証の最終状態／未解決点・要確認事項。
