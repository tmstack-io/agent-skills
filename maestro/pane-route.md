# maestro ペイン経路

いずれかのロールの奏者経路がペイン経路（ハーネス指定のペイン経路、またはサブエージェント機構が無い環境の同系統のペイン経路）になった場合にのみ読む、ペイン経路固有の規定の正本。SKILL.md の「散文提示」「サブエージェント返却規約」等の定義を引き継いだ同一コンテキストで適用する。

## 採用条件

奏者に立てる CLI と満たすべき条件はペイン経路の種別で決まる:

- **同系統のペイン経路**: 奏者に立てる CLI は SKILL.md「奏者経路の確定」のとおり指揮者と同系統の CLI とする（codex 指揮者なら codex、grok 指揮者なら grok）。下記の条件1〜4をすべて満たした場合のみ採用する。
- **ハーネス指定のペイン経路**: 奏者に立てる CLI はロールの指定値の CLI名とする。ユーザーの明示指定であるため条件4は問わず、条件1〜3と条件5をすべて満たした場合のみ採用する。満たさなければ各条件の規定どおり maestro の起動自体を中止する（サブエージェント経路へ縮退しない）。

再起動時に採用条件を満たさない場合の扱いの正本は、本スキル同フォルダの `restart.md`。

1. tui-harness の SKILL.md を Read できる。解決順: `../tui-harness/SKILL.md` → 実行ハーネス自身のスキルディレクトリをプロジェクト側 → グローバル側の順（Claude Code: `.claude/skills/` → `~/.claude/skills/`、Codex: `.agents/skills/` → `~/.agents/skills/`。他ハーネス用のディレクトリは探さない）。見つからなければ復旧手順（`npx skills add tmstack-io/agent-skills --skill tui-harness`）を案内して起動を中止する。
2. tui-harness の `mux.sh detect` が検証済みバックエンドを返す。返さなければ「対応する TUI マルチプレクサが無いため maestro を起動できない」と警告を提示して終了する。
3. 奏者に立てる CLI の `transports/<CLI名>-tui.md` が存在する。無ければ tui-harness「カタログ（catalog.sh）」節のカタログに無い CLI の起用手順を案内して起動を中止する。
4. **ユーザーの許諾**（同系統のペイン経路のみ）: 「サブエージェント機構が無いため、指揮者と同じ CLI（<CLI名>）をペイン分割で奏者に立てる。委譲は直列実行になる」ことを散文提示で明示し、許諾を得る。許諾が得られなければ起動を中止する。
5. **起動時検証**（ハーネス指定のペイン経路のみ）: ロールの指定値に tui-harness「委譲先の確定と検証」の手順1・2（`catalog.sh probe` と `catalog.sh models <CLI名>` によるハーネスの検証、モデル一覧との照合、`catalog.sh validate`）を起動時に通す。手順が中止または散文提示での再指定となる場面（probe 不合格、モデル照合の不一致、validate 失敗、エフォート非対応の CLI への `@` 付き指定等）は、すべて理由と候補（得られれば）を示して maestro の起動を中止する（再指定は求めず、ユーザーが引数を直して再起動する）。

## 運用

ペイン経路の運用は tui-harness の規定に従い、本節の規定は同系統・ハーネス指定のどちらのペインにも共通に適用する。呼び出しパラメータ:

- 成果物置き場＝プロジェクト直下の `.maestro/`（ブリーフ・報告ファイル。git リポジトリで ignore されていなければ初回作成時に `.git/info/exclude` への追記可否を散文提示で確認し、承認を得た場合のみ追記する。モード解除時の扱いは SKILL.md「モード解除」に従う）
- push ラベル＝`maestro-<タスク連番>-<ロール>`（ロールは implement / review / explore。同一タスクの実装ペインとレビューペインを区別する）
- 裁定スコープ＝ロール別に定める。review 奏者は成果物置き場＋ブリーフに記載した検証コマンドの実行（その実行が書き込む生成物のパスがブリーフに明記されていればそのパスも）、implement 奏者は review 奏者の範囲＋ブリーフの対象ファイル、explore 奏者は成果物置き場のみ（いずれも＋通信規約の push）
- 失敗規律＝tui-harness が呼び出し側の失敗規律に従うと定める場面（受理の再送上限の超過・裁定スコープ外の承認要求の拒否・回答/報告の回収失敗）は、SKILL.md「失敗時のエスカレーション」の失敗1回として数え、同節の規定（`escalation.md`）に従う
- クローズ期限＝モード解除時（解除時に tui-harness「クローズ」の条件を満たしたペインから閉じる）

奏者ペインは役割（実装 / レビュー / 調査）ごとに1つを使い回し、ペイン経路のロールへの委譲は直列実行とする（並列起動はしない。ペイン経路の直列規定はこの一文が正本）。品質ゲートのレビュー奏者は、実装奏者と別のペインに立てる。ロールの経路・指定ハーネス・実効モデル・エフォートのいずれかが変わったとき（再起動・対話指示・指揮者判断による選択）は、当該ロールの既存ペインを tui-harness「クローズ」の条件を満たした時点で閉じ、次の委譲で新しい値により起動し直す（対応表も更新する。サブエージェント経路へ移ったロールはペインを閉じるだけで、ペインを起動し直さない）。

## 委譲の受け渡し

起動時に確定したロール別の値を、tui-harness「委譲先指定値の書式」の形（`<CLI名>=<model>[@<effort>]`）で明示指定値として渡す。ハーネス指定のペイン経路のロールはロールの指定値をそのまま渡し、同系統のペイン経路のロールは確定した実効モデル・エフォートを指揮者の CLI 名に連結して渡す。モデル・エフォートの照合と検証は同「委譲先の確定と検証」に委ねる（ハーネス指定のロールは採用条件5で起動時に検証済み。同系統のペイン経路のロールで照合・検証に失敗した場合は散文提示で再確定した値を渡し直す。tui-harness 側で改めてモデル選択の散文提示はさせない）。SKILL.md の確認ゲートで提示するモデル候補は tui-harness の `catalog.sh models <CLI名>` の出力から、エフォート候補は tui-harness「カタログ（catalog.sh）」節が `validate` の照合元とする当該 CLI の許容値一覧から取る（一覧を得られない CLI ではエフォート軸を SKILL.md「指定できない軸」として扱う）。ブリーフはファイルで渡す（tui-harness の「タスクの委譲」の書式に従う）。implement 奏者へのブリーフでは、通信規約ブロックを一字一句コピーした直後に「本委譲の書き込み範囲は、上記に加えて本ブリーフに列挙した対象ファイルを含む（通信規約の書き込み範囲より本行を優先する）」の一行を添える（review / explore 奏者へのブリーフでは添えない。裁定スコープと奏者への指示を一致させるため）。
