# tui-harness 直送委譲（正本）

SKILL.md「直送委譲」節のポインタから読まれる規定の正本（利用スキルが直送委譲を明示したときに適用する。加えて、cmux バックエンドでは直送委譲を適用せず、利用スキルはペインを立てる前に「直送委譲は cmux で未実測」と示して中止する — `backends/cmux.md` に直送委譲の読み替えは無い）。

往復委譲との差分だけを定める。初回はブリーフで文脈を渡し、2通目以降の指揮者の追問は**直送上限**以内ならペインへ直接送り、返答はペイン画面から読む。回収まで行う点は往復委譲と同じで、ペイロードは直送上限を超えるときだけファイルを通す。委譲先ペインは指揮者が専有し、専有中はユーザーがそのペインへ入力しない（採用ペインの専有規律と同じ）。

## 呼び出しパラメータ

往復委譲の3値（成果物置き場・push ラベル・裁定スコープ）に加えて、利用スキルは**直送上限**（1メッセージの上限文字数。改行を除いて数える）を定める。上限の既定値と指定手段は利用スキル側が持つ。上限は、送信の取り込み時間（ハーネスにより長さの2乗程度で伸びる）と、送信本文のエコーと返答が画面読みの上限（1000 行）に収まることの両方を満たす値にする（codex・agy は送信本文を全文エコーするため、長い本文はエコーの先頭が読み取り範囲の外へ出て返答を切り出せなくなる。実測は末尾）。

## 初回の委譲（ブリーフ）

「ペイン配置」「ペインの起動」（`--pane` なら `existing-pane.md`）、「タスクの委譲」手順1〜3 を適用する。ただし手順1の**回答/報告ファイルの絶対パス**は単一のパスとして記載せず、直送通信規約中の `<成果物置き場>/report-<n>.md`（委譲先が採番）がこれに代わる。また手順1のブリーフ末尾には往復委譲の通信規約ブロックの代わりに、次の**直送通信規約**を一字一句そのままコピーし、`<>` 内を実値に置換する（`<直送上限>` は呼び出しパラメータの値。`<n>` は委譲先が回答ごとに採番する枠としてそのまま残す）:

   BEGIN-直送通信規約（ブリーフ末尾へコピー）
   - 以後の追問は、このペインへ直接届くか、ファイルの絶対パスを添えた一行で届く（後者はそのファイルを読んでから答える）。
   - 回答はこのペインに書く。質問もこのペインに書く（別の通知手段は使わない）。
   - 回答が <直送上限> 文字（改行を除く。厳密に数えなくてよく、概算で超えそうなら超えるとみなす）を超えるときだけ、回答の全文を `<成果物置き場>/report-<n>.md`（n は 1 から順に採番）に書き、ペインには次の一行だけを書いてから、次を実行する:
     `<mux.sh> submit <指揮者ペインID> "[<push ラベル>] done <回答ファイルの絶対パス>"`
   - 上記コマンドが失敗した場合（Operation not permitted 等）: 回答ファイルはそのままに、同じ一行（`[<push ラベル>] done <回答ファイルの絶対パス>`）をペインに書いて終了する
   - 書き込みは <成果物置き場> の配下のみ。それ以外のファイルは作成・編集しない。
   - git のコミット・stash・ブランチ作成はしない。変更は作業ツリーに残す。
   END-直送通信規約

受理完了（手順2の条件）を確認したら、後述「返答の受け取り」で初回の返答を回収する（初回の返答も直送通信規約に従うため、往復委譲の「応答の受け取り」ではなく本書の手順を使う）。

## 追送（2通目以降）

1. **送信長の判定**: 送る本文の文字数（改行を除く）が直送上限以内なら直送する。超えるときは本文を `<成果物置き場>/note-<n>.md`（n は 1 から順に採番。既存と衝突すれば次の番号）に書き、ペインへ送る本文は `<note の絶対パス> を読んで答えよ` の一行に置き換える（直送通信規約の1項目目がこの形を委譲先に予告している）。黙って切り詰めない。
2. **送信と受理**: 「タスクの委譲」手順2 と同じ形で1回のシェル実行に束ねる。テキストは複数行でよい（改行は入力欄に改行として入り、送信は起こらない。`submit` の出現確認は本文の末尾で行い、長文の取り込みが遅い TUI では末尾が入力欄に現れるまで待ってから送信する。実測は末尾）:

   ```sh
   <mux.sh> submit "$PANE" "<本文>" \
     && <mux.sh> agent-wait "$PANE" --until working 15000
   ```

   受理完了の条件と、受理にならなかったときの手順3の二分・やり直し上限（合計2回）は「タスクの委譲」手順2〜3 と同じ。上限を超えたら呼び出し側の失敗規律に従う。
3. 受理完了ごとに「ペイン ID の揮発性」に従い、送信の直前に `mux.sh list` で ID を取り直す（往復委譲と同じ）。

完了条件: 送信した本文が受理完了し、直送上限を超えた本文は note ファイルに残っている。

## 返答の受け取り

受理完了のたびに、pull 安全網 `<mux.sh> agent-wait "$PANE" 1800000`（`--until` 無し）を**前面の同期実行**で待つ（直送委譲は会話のため、待っている間に指揮者が進める作業が無い。バックグラウンド実行は使わない）。発火したら、または安全網が状態到達なしに非0終了したら（扱いは SKILL.md「応答の受け取り」と同じ。時間切れは通常「まだ作業中」に相当する）、 `mux.sh read "$PANE" --scrollback --lines <L>` で画面を読み（`<L>` は SKILL.md「応答の受け取り」の画面読みの行数規則）、三分類する:

- **承認ダイアログで停止（blocked）** と **まだ作業中（working）** → SKILL.md「応答の受け取り」の同名分岐と同じ（安全網は前面同期実行で張り直す。working の2回目発火の確認は、利用スキルがこの確認に代わる規定を持つ場合はそれに従う）。
- **idle / done** → 次の順で返答を確定する:
  1. 指揮者ペインに `[<push ラベル>] done <パス>` の push が届いている、またはペイン画面の最後の非空行から 5 行以内にその一行がある → 回答ファイルを読む（読まずに次へ進まない）。回答ファイルが存在しない、または空なら 2 へ進む。
  2. 上記以外 → 画面テキストから**直前に送った本文の先頭行のエコー**を探す（note 経由なら `を読んで答えよ` の一行）。行数規則の上限まで広げても見つからなければ回収失敗として呼び出し側の失敗規律に従う。委譲先が直送上限の概算を外して長い返答をペインに書いた場合も、ここで画面から回収する（規約違反として失敗にしない）。
  3. エコーより後ろのテキストから、ハーネスの入力欄・ステータス行・空行を除いたものを返答とする（当該 transports に「直送委譲」節があれば、その画面マーカー — 送信エコー・返答の行頭記号 — で切り出す。無いハーネスでは指揮者が画面テキストを読んで返答部分を判別し、判別できなければ回収失敗として失敗規律に従う。黙って空の返答にしない）。

完了条件: 送信した本文ごとに、返答（画面から切り出した本文、または回答ファイルの内容）を読み終えている。

## 適用しない手順

往復委譲の「応答の受け取り」（`question:` push の処理を含む。直送委譲では委譲先の質問は返答として画面に現れる）、往復委譲の通信規約ブロックのコピー（直送通信規約で置き換える）、「タスクの委譲」手順4（pull 安全網のバックグラウンド起動。直送委譲では「返答の受け取り」の前面同期実行が代わる）。「指揮者裁定」「未知ダイアログの遭遇プロトコル」「ペイン ID の揮発性」「クローズ」（3条件と採用ペインの除外）はそのまま適用する。

## 実測記録

2026-09-15 実測（指揮者 = Claude Code、herdr バックエンド、委譲先 = Claude Code 2.1.270 / claude-haiku-4-5-20251001）:

- 4行の本文と、19行 1,037 文字（改行除く）の本文をそれぞれ `mux.sh send` で送信 → 入力欄に全行がそのまま入り（ペースト扱い）、改行による送信は起きない。1 秒後の `mux.sh key Enter` で送信され、working → idle に遷移。委譲先は行数を正しく 19 と答えた（欠落なし）。
- 返答は `mux.sh read --scrollback --lines 200` で読めた。画面バッファの末尾には表示行数（`viewport_rows` = 65）ぶんの空行が詰まるため、`--lines 40` では空行しか返らない（この実測が SKILL.md「応答の受け取り」の画面読みの行数規則の根拠）。
- Claude Code の画面マーカー: 送信エコーは `❯ ` で始まり、返答は `⏺ ` で始まる（正本は `transports/claude-tui.md` の「直送委譲」節）。
- 未実測: claude 以外の委譲先の画面マーカー、cmux バックエンド、直送上限を超える返答の report ファイル＋push 経路。

2026-10-14 実測（指揮者 = Claude Code、herdr 0.9.3 バックエンド、委譲先 = Claude Code 2.1.299 / claude-sonnet-5、codex-cli 0.162.1 / gpt-6.1-sol high、grok 1.0.52 / grok-4.7、agy / gemini-3.8-flash-high）。各行に乱数を埋め込んだ本文を `mux.sh submit` で送り、指定した3行の乱数と総行数を答えさせて照合した:

- 送信（submit の所要秒数。照合はすべて一致）: claude 3,000〜48,000 文字で 1〜3 秒 / codex 3,000〜48,000 文字で 2〜15 秒 / grok 6,000・12,000・24,000 文字で 3・10・31 秒 / agy 3,000・6,000・12,000 文字で 8・32・134 秒、24,000 文字は 490 秒以内に取り込みが終わらず失敗。grok は 48,000 文字の取り込み後に入力欄が Enter に反応しなくなった（CPU 約 100% のまま）。grok・agy は取り込み中に送った次の貼り付けを捨てる。
- 送信本文のエコー: claude は長い本文の途中を `(N lines hidden)` で畳み、先頭数十行と末尾を残す。grok は先頭3行に畳む。codex・agy は全文を表示する。
- 画面読み: `herdr pane read` は1回に最大 1000 行（`--source recent-unwrapped` では 999 行）しか返さず、それより前の行を読むオプションは無い（端末バッファには約 1700 行が残っていた）。
- グローバル設定で `tui = "fullscreen"`（Claude Code の代替画面描画）のとき、claude ペインには端末スクロールバックが残らず（`scroll.max_offset_from_bottom` = 0）、表示中の行しか読めない。
