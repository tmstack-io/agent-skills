対話型 LLM CLI（以下**ハーネス**。本書では委譲先ハーネスを指す。現行対応の一覧は「カタログ（catalog.sh）」節）を TUI マルチプレクサのペインで起用し、委譲・受理判定・pull 安全網・承認ダイアログの裁定・クローズまでを行う基盤。利用スキル（本書を Read して同一コンテキストで適用する上位スキル）または単発利用時の実行エージェント本体が、委譲のたびに次節の呼び出しパラメータを定めて本書を適用する。以下、本書を適用して委譲・裁定を行う実行エージェント本体を**指揮者**と呼ぶ。本書の適用中、セッション側から特定ハーネスの起用プロトコル（自動注入ルール等）が別途与えられていても、本書（および transports）を正本とし、食い違う点は本書に従う。

本スキルは主に利用スキルが SKILL.md を Read して適用する。単発利用（他ハーネスをペインで併走させたい等）では argument-hint の形式で直接起動できる。

原則は3つ。「**ペイロードはファイル、ペインは信号**」— 長文をペインに流し込まない。ブリーフ・回答/報告ファイルは受け渡しに使い、ペインには起動指示と通知だけを流す。「**待ちは確定待ち**」— 状態の完了を `sleep` で推測せず、`mux.sh wait-output` / `mux.sh agent-wait` による観測をもって次へ進む（入力ペーシングの短い `sleep` は状態待ちではない）。「**判断のない操作は束ねる**」— 指揮者の判断（出力の解釈・裁定・散文提示）を挟まない連続シェル操作は、1回のシェル実行に束ねてシェル実行の回数（＝指揮者の推論ターン数）を最小にし、判断が要る箇所でだけ実行を区切る（例: `catalog.sh` の probe→models、validate→family の連続実行。「ペイン配置」「ペインの起動」「タスクの委譲」「クローズ」の束ね形は各節が定める）。

ハーネス固有の差分（起動コマンド・trust / 承認ダイアログ・裁定基準・実測記録）は `transports/<CLI名>-tui.md` が持ち、本書と矛盾する記述があれば transports 側（実測）を優先する。実測記録には実測時の指揮者（実行エージェント）を明記する（指揮者の明記が無い既存記録は Claude Code 指揮者での実測である）。

本書中の `mux.sh` / `catalog.sh` / `transports/` / `models/` は、本 SKILL.md と同じディレクトリ配下の実体を指す。起用を始める前に `mux.sh` と `catalog.sh` の絶対パスを1回確定し（利用スキルから適用する場合は本書を Read したパスを基準にする）、以後の本書のコマンドはすべてその絶対パスで実行する（通信規約の `<mux.sh>` にも同じ値を使う）。

## 呼び出しパラメータ

利用スキル（または単発利用時の指揮者）は、ハーネスへの委譲を開始する前に次の3値を定める。以下、本書ではこれらを `<成果物置き場>` `<push ラベル>` `<裁定スコープ>` として参照する。

- **成果物置き場**: ハーネスが書いてよいディレクトリ。ブリーフ・回答/報告ファイルの置き場（例: 利用スキルが定める記録ディレクトリや委譲先ごとの作業ディレクトリ）。
- **push ラベル**: 通信規約の `[<push ラベル>]` に使う一意な識別子（例: 利用スキルが定める席名・委譲先ラベル）。呼び出し側が委譲先ごとに一意になるよう定める。
- **裁定スコープ**: 承認ダイアログを許可してよい書き込み先パス集合と許可コマンド。既定は「成果物置き場への書き込み＋通信規約の push コマンドのみ許可」。呼び出し側がこれより広い/狭いスコープを定めてもよい。

単発利用時は argument-hint の `--output-dir` / `--label` / `--scope` をそれぞれ成果物置き場・push ラベル・裁定スコープの指定に使い（`--label` は往復委譲では必須、`--oneway` 指定時は不要。利用スキル経由の呼び出しではフラグ名を利用スキル側が定める）、委譲先の指定（第1引数）を「委譲先の確定と検証」の手順で検証してから（`--pane` の場合は「既存ペインの起用」で採用ペインを確定してから）進み、`<委譲する作業>` をブリーフ本文の主要記述として使う。利用スキルの無い単発利用では、本書が「呼び出し側」「利用スキル側」に委ねる判断は指揮者自身が担い、失敗規律の既定は「失敗した委譲は中止し、原因（`mux.sh read` の内容を含む）と再試行の選択肢を散文提示で示して指示を待つ」とする。

完了条件: 委譲を開始する前に、往復委譲では3値が、片道委譲では成果物置き場が確定している。

## 片道委譲

本書の委譲は、回答/報告ファイルを回収するまでを1回の委譲とする**往復委譲**が既定である。利用スキルが「片道委譲」を明示した場合、または単発利用で `--oneway` が指定された場合に限り、次の縮約形を適用する — ペインへブリーフを送って受理を確認した時点で委譲を完了とし、以後のペインの対話はユーザーに引き渡す（指揮者は回答を回収も観測もしない）。

- **適用する手順**: 「ペイン配置」「ペインの起動」「タスクの委譲」の手順1〜3（ブリーフの作成・送信・受理確認と再送）。ただし「タスクの委譲」手順1の回答/報告ファイルの絶対パスは記載せず（回答は置かれない）、「ペインの起動」の対応表は push ラベルの代わりに CLI 名を見出しにして保持する。「委譲先の確定と検証」は適用し、「異系統委譲」は利用スキルの要求に従う。
- **適用しない手順**: 通信規約ブロックのコピー（回収先が無い）、「タスクの委譲」手順4の pull 安全網、「応答の受け取り」、「指揮者裁定」、「クローズ」の3条件（ペインの主はユーザーになり、閉じる判断もユーザーが行う）。
- **呼び出しパラメータ**: 3値のうち**成果物置き場のみ**を定める（ブリーフの置き場。回答は置かれない）。push ラベルと裁定スコープは定めない。
- **承認ダイアログ**: 受理確認後にペインで発生する承認ダイアログは、ユーザー自身がそのペインで応答する（指揮者は裁定しない。裁定スコープを持たないため）。
- **ペイン ID の伝達**: 受理確認後、利用スキル（単発利用では指揮者）はペイン ID と起動した CLI・モデルをユーザーに報告する（ユーザーがそのペインで続きを行うため）。「ペイン ID の揮発性」の規定はそのまま適用する（対応表に残す場合は増減操作のたびに `mux.sh list` で取り直す）。

完了条件: 受理完了（「タスクの委譲」手順2の条件）を確認し、ペイン ID・CLI・モデルをユーザーに報告した。

## 委譲先指定値の書式

利用スキルがフラグの値として、または単発利用が第1引数として委譲先を受け取るときの、値1つぶんの書式の正本:

`<CLI名>[=<モデル>[@<エフォート>]]`

- **CLI名**: カタログ（`catalog.sh`）上のハーネスの識別子。
- **`=<モデル>` 省略時**: モデルは「委譲先の確定と検証」手順2の散文提示で選ぶ。
- **`@<エフォート>` 省略時**: reasoning effort を指定しない（当該 CLI の既定に従う）。
- **エフォートの値**: 当該 CLI ネイティブの語彙をそのまま使う。許容値の正本は `catalog.sh validate`（CLI ごとの照合元は「カタログ（catalog.sh）」節に従う）。effort の設定手段を持たない CLI への `@` 付き指定は、黙って読み捨てず、非対応である旨を示して散文提示で再指定を求める。
- モデル・エフォートの検証は「委譲先の確定と検証」に、モデル系統の確定は「異系統委譲」に従う（エフォートは系統の照合に含めない）。

フラグ名・繰り返しの可否・席数や人数への対応づけは利用スキル側が定める（本書は値の書式だけを定める）。

## 委譲先の確定と検証

委譲先ハーネス・モデル・エフォートの確定と検証（下記手順1・2）は、異系統委譲の要否によらず、委譲先を指定値または散文提示で決めるすべての委譲で行う。

1. 委譲先ハーネスが未指定なら `catalog.sh probe` を実行し、ok かつ `catalog.sh models <CLI名>` でモデル一覧を取得できる候補を散文提示して選んでもらう。明示指定されたハーネスも同じ2条件で検証し、いずれかを満たさなければ中止する。候補が0件なら、除外理由と復旧方法を示して中止する。
2. 委譲先モデルが未指定なら、選択済みハーネスのモデル一覧から、`auto` 等の起動時まで実効モデルが決まらない値を除いて散文提示し、選んでもらう。明示指定されたモデルは同じ一覧と照合する。「委譲先指定値の書式」の `@<エフォート>` 付き指定は、モデル部（codex では slug 部）を一覧と照合し、エフォート部は `catalog.sh validate` の許容値照合に委ねる。claude は静的一覧と照合する（正本と更新規定は「カタログ（catalog.sh）」節）。それ以外は指定値全体を一覧と照合する。完全一致なら採用し、大文字小文字・区切り記号・部分一致のゆれで候補が1件なら一覧上の形へ是正して採用する。候補が0件または2件以上なら散文提示で再指定を求める。是正後の起動指定を `catalog.sh validate <CLI名> <model-spec>` で検証し、失敗したら理由と候補を散文提示で示して再指定を求める。

候補の優劣を判断できる根拠が無ければ、散文提示では推奨なしと理由を明記する。固定の候補順を推奨の代わりに使わない。

モデル一覧を取得できないハーネスを、未検証のモデル指定で起用する経路は持たない。

完了条件: 委譲先のハーネスとモデル指定（エフォート付き指定はエフォートを含む）が検証済みである。

## 異系統委譲

利用スキルが異系統委譲を要求する場合は、「委譲先の確定と検証」に加えて、実行中と委譲先の**モデル系統**を起動前に確定して比較する。モデル系統は、モデル名の先頭ファミリートークン（`claude` / `gpt` / `grok` / `gemini` 等）であり、`catalog.sh family <CLI名> <model-spec>` の出力を正本とする。バージョン・reasoning effort・thinking・fast・`[1m]`（1M トークンコンテキスト版を示すモデル名サフィックス）等は系統の照合に含めず、同系統の別バージョン・別ティアは同席（異系統性なし）として扱う（例: codex の `gpt-5.4@high` と cursor-agent の `gpt-5.6-luna-high` はともに `gpt`、agy の `claude-sonnet-4-6` と Claude Code の `Claude Opus 5` はともに `claude`）。

実行中の系統は次で確定する: 単一系統のモデルだけを提供するハーネス（Claude Code → `claude`、codex → `gpt`、grok → `grok`）では実効モデルによらず静的に確定し、確認は不要。複数系統のモデルを提供するハーネス（cursor-agent / agy / hermes 等）が実行中の場合は、実効モデルをセッション情報から特定して `catalog.sh family` で系統を得る。特定できなければ、散文提示でユーザーに確認し、回答を得るまで委譲を開始しない。カタログ外の実行ハーネスは、そのハーネスが示すモデル名の先頭ファミリートークンを同じ規則で使う。

委譲先の系統は次で確定・比較する: 検証済みの起動指定を `catalog.sh family` へ渡し、委譲先のモデル系統を得る。実行中の系統と同一なら起用せず、異なる系統の候補の再指定を散文提示で求める（再指定は「委譲先の確定と検証」の手順で検証する）。再指定が合計2回まで続いても異なる系統の候補が得られなければ、候補一覧と除外理由を示して中止する。同系統の許容可否と縮退（許容時の明記義務を含む）は利用スキルの規定が定め、本則に優先する。

完了条件: 実行中と委譲先のモデル系統がすべて確定し、利用スキル固有のガード（同系統の許容規定を含む）の全判定を通過している。

## ペイン配置

最初のハーネスペインを作る前に、対象と方向を次の規定で決める:

1. `<mux.sh> layout && <mux.sh> list` を1回のシェル実行で取り、layout の rect（width / height）から **width ≥ height × 2 なら横長、そうでなければ縦長**と判定し（端末セルの縦横比は約2:1のため、見た目の縦横は width/2 と height の比較に相当する）、list から**指揮者ペイン ID**（`focused` が真の自ペイン。以後、全ブリーフの通信規約に記載する）を得て対応表に記録する。
2. **1枚目のハーネスペイン**: 指揮者ペインを分割する。横長なら方向 `right`、縦長なら `down`。
3. **2枚目以降のハーネスペイン**: **直前に作ったハーネスペインを** `down` で分割する（指揮者ペインをそれ以上狭めず、ハーネスペインを1列に積み上げる）。
4. 分割のたびの ID 取り直しは、次節の起動シーケンス末尾に含めた `mux.sh list` が兼ねる（正本: 後述「ペイン ID の揮発性」）。

完了条件: 起用するハーネスの数だけペインが配置され、対応表に記録済み。

## ペインの起動（ハーネスごと・遅延）

あるハーネスへの最初の委譲が発生した時点で、そのハーネスのペインを起動する。分割から idle 確定待ちまでは指揮者の判断を挟まないため、次の**起動シーケンス**を1回のシェル実行に束ねる:

```sh
PANE=$(<mux.sh> split <対象ペインID> <方向>) \
  && <mux.sh> run "$PANE" "<起動コマンド>" \
  && { <初期ダイアログ手順>; } \
  && { <mux.sh> agent-wait "$PANE" --until idle 60000 \
       || { sleep 3; <mux.sh> agent-wait "$PANE" --until idle 60000; }; }
echo "pane=$PANE"; <mux.sh> list
```

- `<対象ペインID>` と `<方向>` は前節「ペイン配置」の規定で決める（ID は直近の `mux.sh list` の出力から取る）。
- `<起動コマンド>` は当該 transports の規定。**ハーネスの cwd はプロジェクトルートに固定する** — transports の起動コマンドにある `<プロジェクトルート>` は、呼び出し側セッションの作業対象プロジェクトの最上位ディレクトリ（`.git` / CLAUDE.md 等を持つルート）の絶対パスに展開する。ペインのシェル cwd は分割元を継承するが、それに依存せず起動コマンド側の cwd 指定（cwd オプションまたは `cd`）を正とする（ブリーフの書き込み規律「成果物置き場にのみ書く」の基準点を確定させるため）。
- `<初期ダイアログ手順>` には、trust 等の初期ダイアログを通過する当該 transports の規定（`mux.sh wait-output` によるパターンの確定待ち → `mux.sh send` / `mux.sh key` による固定の応答。確定待ちのタイムアウト＝ダイアログなしは正常分岐）を、ペイン ID を `"$PANE"` に置き換えて挟み込み、全体を `{ …; } || true` で括って正常分岐の非0が連鎖を止めないようにする。初期ダイアログの規定が無い transports ではこの行ごと省く。応答が固定手順で書けない規定を持つ transports に限り、`run` までで実行を区切り、ダイアログを個別に裁いてから idle 確定待ち以降を実行する。
- idle 確定待ちの再実行1回は、起動直後にエージェント検知が未登録で `agent_not_found` により即失敗する起動レース（実測）への手当てである（タイムアウト失敗でも同じ再実行が走るが、失敗経路だけの追加待ちとして受け入れる）。
- 実行後、agent-wait の出力で idle 到達を確認する。到達していなければ `mux.sh read "$PANE"` で画面を読み、原因（予期せぬダイアログ・起動失敗等）を特定してから対処する。
- 末尾の `mux.sh list` の出力で対応表を更新し、新ペインの ID（`pane=` の値）を**push ラベル→ペイン ID の対応表**（セッション内で保持）に記録する（分割で他ペインの ID が振り直されていれば併せて更新する。正本: 「ペイン ID の揮発性」）。

完了条件: 当該ハーネスが入力待ち（idle）に達し、対応表に記録済み。

## 既存ペインの起用

利用スキルが既存ペインの起用を明示した場合（単発利用では第1引数の代わりに `--pane [<ペイン指定>]` を受けた場合）、「ペイン配置」「ペインの起動」の代わりに、稼働中の既存ペインを委譲先として採用する。herdr のペイン操作はソケット API でタブ・ワークスペースを跨いで届くため、採用後の手順（「タスクの委譲」以降。受理判定・pull 安全網・応答の受け取り・指揮者裁定を含む）は新設ペインと同一である（タブ・ワークスペース跨ぎの send / key / read / wait-output / agent-wait は実測検証済み。指揮者: Claude Code）。

1. **解決**: `mux.sh list && mux.sh tabs` を1回のシェル実行で取り、指定値を各ペインの `pane_id` / `tab_id` / `terminal_title_stripped`（部分一致可）、および `tabs` の `label`（ユーザーが付けたタブ名。部分一致可。一致したタブの `tab_id` を持つペインへ展開する — ペイン一覧はタブ名を持たないため、タブ名指定はこの突き合わせでのみ解決できる）と照合する。ちょうど1件のペインに解決できれば手順2へ進む。0件・複数件・指定値なしの場合は、`agent` フィールドを持つペインの一覧（ペイン ID・CLI・タブ名・タイトル・cwd・`agent_status`）を散文提示して選んでもらう（明示指定が0件・複数件だった場合は、その照合結果も示す。同名タブが複数ワークスペースにありうるため、複数件はワークスペースを添えて提示する）。
2. **起用ゲート**: 解決したペインが次のすべてを満たさなければ採用せず、満たさない条件を示して呼び出し側の失敗規律に従い中止する（別候補への差し替え・新設への縮退は、呼び出し側が明示した場合のみ）:
   - `agent` フィールドが存在し、値がカタログ（`catalog.sh`）掲載の CLI 名と一致する（通信規約の送達と承認ダイアログの裁定基準は当該 transports の実測が正本であり、カタログ外エージェントには裁定根拠が無い）。
   - `agent_status` が idle である（作業中ペインへの割り込みをしない）。
3. **CLI・モデル・系統**: CLI は `agent` フィールドの値で確定する。ハーネスは起動済みのため、モデル・エフォートの指定・変更はできない（「委譲先の確定と検証」は適用しない。モデル・エフォート付きの指定値と `--pane` の併用は解釈せず、散文提示で再指定を求める）。利用スキルがモデル系統を要する場合は、「異系統委譲」の実行中の系統の規則を委譲先ペインに準用する — 単一系統 CLI は静的に確定し、複数系統 CLI はペインの画面・セッション情報から実効モデルを特定して `catalog.sh family` で系統を得る。特定できなければ散文提示でユーザーに確認する。
4. **採用の記録**: push ラベル→ペイン ID の対応表に記録し、**採用ペインである旨を併記する**（クローズ判定で参照するため）。

採用ペインの規律:

- **専有**: 委譲の開始から回収までの間、当該ペインは指揮者が専有する。ユーザーの直接入力が挟まると受理判定・回収が壊れるため、採用を宣言する際にその旨を伝える。
- **既存文脈**: ペインが保持する既存の会話文脈は消去できず、委譲はその文脈の上に乗る。それを予備知識という価値とみなすか汚染リスクとみなすかの判断・明記義務は利用スキル側の規定に従う。
- **cwd**: ペインの cwd は変更しない（「ペインの起動」の cwd 固定規定は適用されない）。ブリーフ・回答/報告ファイルのパスは常に絶対パスで受け渡す。
- **クローズ対象外**: 採用ペインは指揮者の所有物ではないため、「クローズ」の3条件が揃っても閉じない。委譲の終了時は、pull 安全網の停止（停止できる環境のみ）と対応表からの除去だけを行う。

完了条件: 採用ペインが1件に確定して起用ゲートを通過し、対応表に採用ペインとして記録済みである。または中止を報告している。

## タスクの委譲

1. ブリーフを成果物置き場にファイルとして書く（成果物置き場が存在しなければ作成してから書く）。ブリーフは `brief-<push ラベル>.md`、回答/報告ファイルは `report-<push ラベル>.md` を既定の名前とする（利用スキルが命名を定める場合はそれに従う。push ラベルを持たない片道委譲ではブリーフ名に CLI 名を使う）。同名の既存ファイルがあれば上書きせず、連番サフィックスを付けた別名で書く。ブリーフ本文には少なくとも、**委譲する作業の記述**と、**回答/報告ファイルの絶対パス**（成果物置き場の配下に定める。通信規約の「本ブリーフに定めた回答/報告ファイル」はこれを指す）を記載する。末尾に次のブロックを**一字一句そのままコピー**し、`<>` 内のうち `<一行の質問>` を除く箇所を実値に置換する（`<mux.sh>` は本スキルの `mux.sh` の絶対パス。`<一行の質問>` は委譲先が実行時に埋める枠としてそのまま残す）:

   BEGIN-通信規約（ブリーフ末尾へコピー）
   - 完了したら: 本ブリーフに定めた回答/報告ファイルを書き、次を実行する:
     `<mux.sh> send <指揮者ペインID> "[<push ラベル>] done <回答/報告ファイルパス>"` に続けて `<mux.sh> key <指揮者ペインID> Enter`
   - 不明点で作業を続けられないときは、作業を止めて次を実行する:
     `<mux.sh> send <指揮者ペインID> "[<push ラベル>] question: <一行の質問>"` に続けて `<mux.sh> key <指揮者ペインID> Enter`
   - 上記コマンドが失敗した場合（Operation not permitted 等）: 回答/報告ファイルはそのままに、同じ一行（`[<push ラベル>] done <回答/報告ファイルパス>` または `[<push ラベル>] question: <一行の質問>`）を最終メッセージとして出力して終了する
   - 書き込みは <成果物置き場> の配下のみ。それ以外のファイルは作成・編集しない。
   - git のコミット・stash・ブランチ作成はしない。変更は作業ツリーに残す。
   END-通信規約

2. 送信から受理の確定待ちまでを単一のシェル実行で回す。ペインへ送るのは起動指示の一行だけで、テキストと Enter は別コマンドに分けて間を置く（同一バーストで届いた Enter はペースト処理に吸収される）:

   ```sh
   <mux.sh> send "$PANE" "<ブリーフ絶対パス> を読んで実行せよ" \
     && sleep 1 && <mux.sh> key "$PANE" Enter \
     && <mux.sh> agent-wait "$PANE" --until working 15000
   ```

   受理完了の条件: working への遷移（終了コード 0）に加え、応答 JSON に `agent_session` が含まれていること。ただし **`agent_session` を報告しないハーネスがある**（当該 transports に明示。その場合は working 遷移のみで手順3へ）。working でも `agent_session` が期待されるのに無い場合は、TUI 初期化中の描画を working と誤検知した空振り（送ったテキストは破棄済み）とみなし、受理としない。
3. 受理完了にならなければ `mux.sh read "$PANE" --lines 40` で入力欄を見て二分する（TUI 初期化直後の Enter 吸収は全ハーネス共通の前提）:
   - 指示テキストが入力欄に残っている → Enter のみ再送する
   - 入力欄が空 → 手順 2 からやり直す（idle は入力受付可能より先に報告されることがあり、初期化中に送ったテキストは丸ごと捨てられる）

   再送・やり直しは当該ハーネスにつき合計 2 回まで。それでも受理完了にならなければ、呼び出し側の失敗規律に従い委譲を終了する（`mux.sh read` の内容を原因分析に添える）。
4. **pull 安全網**をハーネスごとに仕掛ける: `mux.sh agent-wait "$PANE" 1800000` を、バックグラウンド実行できる環境（Claude Code では Bash ツールの `run_in_background`）ではバックグラウンドで起動する（`--until` 無し = idle / done / blocked のいずれかで発火。ハーネスは完了後 idle に戻るだけで done を報告しないことがあり、`--until done` に絞ると完了を取り逃がす）。バックグラウンド実行が無い環境では、全委譲の受理完了後に同じコマンドを前面の同期実行で待つ（待ちが委譲ごとに直列化するが、コストとして受け入れる）。いずれの場合も安全網は手順 2 の受理完了の確認後に張る（エージェント状態は画面からの推定であり、受理前の無活動ペインは done と誤検知され即発火する）。

完了条件: 委譲した全ハーネスについて、受理完了の確認と安全網の起動が済んでいる。

## 応答の受け取り

push の `[<push ラベル>]` で発信元を特定してから処理する:

- **`[<push ラベル>] done <パス>`** が届いたら回答/報告ファイルを読む。読まずに次工程へ進まない。
- **`[<push ラベル>] question: ...`** が届いたら、回答を当該ペインへ `mux.sh send` ＋ `mux.sh key Enter` で送る。補足が長くなる場合はファイルに書いてパスを送る。回答を送ったら、当該ハーネスの pull 安全網を張り直す（question の push 時に idle で発火して消費されているため）。
- **安全網が先に発火**したら `mux.sh read "$PANE" --scrollback --lines 60` で画面を読み、**三分類**する:
  - **承認ダイアログで停止（blocked）** → 次節「指揮者裁定」に従い許可 / 拒否を送信し、安全網を張り直す（同一の委譲対応中に複数回発火しうる）。
  - **done / idle なのに push が無い** → 回答/報告ファイルの有無と画面内容から結果を直接回収する（push 漏れは回収漏れであり、呼び出し側の失敗規律の「失敗」に数えない。回答本文がペインにしかない場合は本文のみを回答/報告ファイルへ転記する）。回答/報告ファイルもペイン上の回答本文も無ければ、当該委譲を失敗として `mux.sh read --scrollback` の内容を原因分析に添え、呼び出し側の失敗規律へ進む（ただし直前に question へ回答して再開したペインは失敗とせず、安全網を張り直して待機する）。
  - **まだ作業中（working）** → 安全網を張り直して待機を延長する。延長はハーネスごとに1回まで。2回目の発火は散文提示でユーザーに確認する。

完了条件: 委譲した全ハーネスについて、回答/報告ファイル（または直接回収した結果）を読み終えている。

## 指揮者裁定

承認ダイアログは pull 安全網の blocked 発火で検知し、指揮者が裁定スコープとの照合で二値裁定する:

- 対象パス・コマンドが**裁定スコープ内** → 許可する。
- **範囲外** → 拒否し、呼び出し側の失敗規律へ進む。

対象パス・コマンドが表示で切れている場合は `mux.sh read --scrollback` で読み直して確認してから裁定する（対象不明のまま許可しない）。ダイアログの形式（文言・選択肢）と応答方法（キー送信 / テキスト送信）はハーネスごとに異なり、正本は当該 `transports/<CLI名>-tui.md` の裁定基準。

自動裁定機構を持たないハーネス（agy 等）への書き込み委譲は、承認ダイアログが頻発し指揮者裁定の回数が増える（起用の制限はしないが、コストとして受け入れる）。

完了条件: 発火した全 blocked について許可/拒否のいずれかを裁定し送信済み。

## 未知ダイアログの遭遇プロトコル

当該 transports に明示されていない形式のダイアログに遭遇したら:

- **(a) 文言から対象が読め、裁定スコープで判定できる** → 前節「指揮者裁定」の基準で裁定して続行し、文言・選択肢・応答・結果を実測ノートとして記録する。
- **(b) 判定不能** → 許可せず散文提示でユーザーに確認する。

いずれの場合も、セッション末尾に当該 transports への追記案（ダイアログ形式・応答方法・検証記録）を散文提示で示し、**承認を得てから**反映する（無承認の自己改定はしない）。

完了条件: 遭遇した未知ダイアログについて (a)/(b) いずれかで処理し、セッション末尾に追記案を提示済み（遭遇が無ければ提示不要）。

## ペイン ID の揮発性

ペイン ID はペインの増減で振り直される。増減操作（起動・クローズ）を行ったら、直後に `mux.sh list` を取って対応表を更新する（「ペインの起動」「クローズ」の束ね実行では、末尾に含めた `mux.sh list` がこれを兼ねる）。`mux.sh close` / `run` / `send`（`key` と一体の送信は一式で1回）の直前は `mux.sh list` で ID を取り直す — 複数ペインでは、古い ID への送信が**別のハーネス**を撃つ事故になる。取り直しで当該ハーネスのペインを特定できないときは、送信せず散文提示でユーザーに確認する。

## クローズ

ペインは**作業時のみの窓**である（採用した既存ペインは対象外 — 扱いの正本は「既存ペインの起用」）。次の3条件が当該ハーネスについて揃ったら閉じてよい: (1) 未回収の委譲・次ラウンドの委譲が無い (2) 未回収の push が無い (3) 当該ハーネスの pull 安全網が発火済み、または回答/報告ファイルを回収済みで以後の発火を待つ必要が無い（バックグラウンドの待ちは、停止できる環境では停止し、停止手段が無ければ放置してよい）。クローズ期限（いつ閉じるか）は利用スキルの規定に従う（利用スキルの無い単発利用では、指揮者自身が3条件の充足を判定し、充足後に閉じる）。`mux.sh list` で ID を取り直してから `<mux.sh> close <ペインID> && <mux.sh> list` を1回のシェル実行で行い、末尾の `list` の出力で消滅を確認して対応表から除く。複数ペインを閉じるときはこの実行を1ペインずつ繰り返し、次の対象 ID は直前の実行の `list` 出力から取る（クローズで残ペインの ID が振り直されるため）。次の委譲が確定している間は閉じずに同一ペインへ追送する（ペインの文脈保持が本ハーネス起用の価値であり、閉じれば失われる）。

完了条件: 閉じたペインが `mux.sh list` に存在しないことを確認した。

## カタログ（catalog.sh）

候補ハーネスの疎通確認とモデル一覧の**正本は同梱の `catalog.sh`**（現行カタログ: codex / cursor-agent / agy / claude / grok / hermes — いずれも対話 TUI 検証済みで `transports/<CLI名>-tui.md` を持つ）。サブコマンド（`probe` / `models` / `family` / `validate`）の仕様と出力形式の正本はスクリプトのヘッダコメント。本書で使う役割分担は、`probe` が候補の疎通確認、`models` がモデル指定の照合元、`validate` が起動前の指定値検証（エフォート部の許容値照合を含む）、`family` がモデル系統の確定である。`claude` のモデル一覧と effort 許容値は動的取得ではなく `models/claude.txt` / `models/claude-efforts.txt` の静的一覧を正本とする（この一覧は claude ペインの起動検証専用。未掲載モデルを使う場合は同ファイルを更新してから再実行する）。`hermes` のモデル一覧は hermes 自身のモデルキャッシュ（`~/.hermes/provider_models_cache.json`）を `<プロバイダ>:<モデル>` 形へ平坦化したものを正本とし、モデル指定なしの起用経路を持たない（hermes は特定モデルと結びつかないオープンハーネスのため、既定モデルに任せる委譲をしない）。`hermes` の TUI 起用では reasoning effort を指定できない（`@` 付き指定は非対応。正本は transports の実測）。

カタログに無い CLI の起用には (1) `catalog.sh` への probe / models / family / validate 分岐の追記と (2) 対話 TUI の実測検証に基づく `transports/<CLI名>-tui.md` の作成の両方が必要である。追記・作成の案を組み立てて散文提示で示し、承認を得てから反映して採用する（正本を更新する変更のため、承認なしに追記しない。検証なしに対話 TUI を使わない）。

`catalog.sh` は `timeout`（macOS では coreutils の `gtimeout`）を、codex / hermes のモデル一覧取得には `jq` を必要とする。前提コマンドの不足で `catalog.sh` 自体が非0終了した場合は、標準エラー出力の内容（導入手順を含む）を示して起用を中止する。

完了条件: 起用する全ハーネスが `catalog.sh probe` で ok と判定済み。

## マルチプレクサ（mux.sh）

ペイン操作はすべて同梱の **`mux.sh`**（マルチプレクサラッパー。サブコマンドの正本はスクリプトのヘッダ）を経由する。マルチプレクサの生コマンドを直接叩かない（バックエンド差の吸収とセッション毎のばらつき防止のため）。**現行バックエンドは herdr と cmux**（herdr の検出は環境変数 `HERDR_ENV=1`、cmux の検出は `CMUX_SOCKET_PATH` ＋ CLI ＋ `cmux ping` の疎通が前提。未検証のバックエンドは fail fast — `mux.sh detect` が検証済みバックエンドを返さなければ、呼び出し側（単発利用では指揮者自身）が起用を開始しない）。

**cmux バックエンドの差分**（対話 TUI で実測検証済み。指揮者: Claude Code）: ペイン ID は surface の UUID を正とする（`surface:N` 形式の ref は増減で振り直されるため使わない）。(1) エージェント状態 API が無いため、`agent-wait` は**画面静止推定**（既定 15 秒の静止で idle、サンプル間の画面変化で working。閾値は環境変数 `MUX_CMUX_QUIET_MS`）と**通知高速経路**（対象 surface 宛の新着通知で即 idle 発火。cmux のエージェント連携が効いているハーネスで発火し、効いていなくても静止推定で動作する）で代替する。blocked / done は個別状態としては報告されず idle に含まれる — 「応答の受け取り」の三分類が画面から裁く既存フローで吸収される。(2) `agent_session` は全ハーネスで報告されない — 受理判定は working 遷移のみで手順3へ進む。(3) `list` の各ペインは `agent` / `agent_status` を持たず、代わりに `commands`（surface 配下プロセスのコマンドライン一覧）を持つ。「既存ペインの起用」の起用ゲートは、`commands` のいずれかにカタログ CLI 名が現れること、および `agent-wait --until idle` の短時間実行（例: `MUX_CMUX_QUIET_MS=8000` で 20 秒）が idle を返すことで代替する。(4) `tabs` はワークスペース一覧（`label` = ワークスペース名）、`layout` は `list-panes` 形式（`columns` / `rows` をセル寸法の width / height として読む）。cmux での実測は mux.sh 全サブコマンドと codex / grok の委譲一巡（起動・trust 通過・受理・完了検知・回収・クローズ）まで。未実測: 委譲先自身による通信規約の push 送達、blocked（承認ダイアログ）場面の安全網検知と裁定、claude / cursor-agent / agy / hermes の各初期ダイアログ（transports の実測記録は herdr 指揮者のもの）。マルチプレクサ操作の一般知識（herdr スキル等）が文脈に読み込まれている場合も、本スキル実行中の操作は mux.sh 経由に統一する（診断時のみ読み取り参照可。診断後の操作は mux.sh に戻して行う）。

完了条件: `mux.sh detect` の結果（backend 名または中止理由）を確認済み。
