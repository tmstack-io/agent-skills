# tui-harness — TUI ペインで他ハーネスを起動・委譲・回収する

対話型 LLM CLI（以下**ハーネス**。本書では委譲先ハーネスを指す。現行対応: codex / cursor-agent / agy / claude / grok）を TUI マルチプレクサのペインで起用し、委譲・受理判定・pull 安全網・承認ダイアログの裁定・クローズまでを行う基盤。利用スキル（本書を Read して同一コンテキストで適用する上位スキル）または単発利用時の実行エージェント本体が、委譲のたびに次節の呼び出しパラメータを定めて本書を適用する。以下、本書を適用して委譲・裁定を行う実行エージェント本体を**指揮者**と呼ぶ。本書の適用中、セッション側から特定ハーネスの起用プロトコル（自動注入ルール等）が別途与えられていても、本書（および transports）を正本とし、食い違う点は本書に従う。

本スキルは主に利用スキルが SKILL.md を Read して適用する。単発利用（他ハーネスをペインで併走させたい等）では argument-hint の形式で直接起動できる。

原則は2つ。「**ペイロードはファイル、ペインは信号**」— 長文をペインに流し込まない。ブリーフ・回答/報告ファイルは受け渡しに使い、ペインには起動指示と通知だけを流す。「**待ちは確定待ち**」— 状態の完了を `sleep` で推測せず、`mux.sh wait-output` / `mux.sh agent-wait` による観測をもって次へ進む（入力ペーシングの短い `sleep` は状態待ちではない）。

ハーネス固有の差分（起動コマンド・trust / 承認ダイアログ・裁定基準・実測記録）は `transports/<CLI名>-tui.md` が持ち、本書と矛盾する記述があれば transports 側（実測）を優先する。実測記録には実測時の指揮者（実行エージェント）を明記する（指揮者の明記が無い既存記録は Claude Code 指揮者での実測である）。

## 呼び出しパラメータ

利用スキル（または単発利用時の指揮者）は、ハーネスへの委譲を開始する前に次の3値を定める。以下、本書ではこれらを `<成果物置き場>` `<push ラベル>` `<裁定スコープ>` として参照する。

- **成果物置き場**: ハーネスが書いてよいディレクトリ。ブリーフ・回答/報告ファイルの置き場（例: 利用スキルが定める記録ディレクトリや委譲先ごとの作業ディレクトリ）。
- **push ラベル**: 通信規約の `[<push ラベル>]` に使う一意な識別子（例: 利用スキルが定める席名・委譲先ラベル）。呼び出し側が委譲先ごとに一意になるよう定める。
- **裁定スコープ**: 承認ダイアログを許可してよい書き込み先パス集合と許可コマンド。既定は「成果物置き場への書き込み＋通信規約の push コマンドのみ許可」。呼び出し側がこれより広い/狭いスコープを定めてもよい。

単発利用時は `catalog.sh probe` で対象 CLI が ok であることを確認してから進み、`<委譲する作業>` をブリーフ本文の主要記述として使う。

完了条件: 委譲を開始する前に3値が確定している。

## 異系統委譲

利用スキルが異系統委譲を要求する場合は、前節の3値に加えて、実行中と委譲先の**モデル系統**を起動前に確定する。モデル系統は、モデル名の先頭ファミリートークン（`claude` / `gpt` / `grok` / `gemini` 等）であり、`catalog.sh family <CLI名> <model-spec>` の出力を正本とする。バージョン・reasoning effort・thinking・fast・`[1m]` 等は系統の照合に含めず、同系統の別バージョン・別ティアは同席（異系統性なし）として扱う（例: codex の `gpt-5.4@high` と cursor-agent の `gpt-5.6-luna-high` はともに `gpt`、agy の `claude-sonnet-4-6` と Claude Code の `Claude Opus 5` はともに `claude`）。

実行中の系統は次で確定する: 単一系統のモデルだけを提供するハーネス（Claude Code → `claude`、codex → `gpt`、grok → `grok`）では実効モデルによらず静的に確定し、確認は不要。複数系統のモデルを提供するハーネス（cursor-agent / agy 等）が実行中の場合は、実効モデルをセッション情報から特定して `catalog.sh family` で系統を得る。特定できなければ、利用スキルの散文提示でユーザーに確認し、回答を得るまで委譲を開始しない。カタログ外の実行ハーネスは、そのハーネスが示すモデル名の先頭ファミリートークンを同じ規則で使う。

委譲先の確定は次の順で行う:

1. 委譲先ハーネスが未指定なら `catalog.sh probe` を実行し、ok かつ `catalog.sh models <CLI名>` でモデル一覧を取得できる候補を散文提示して選んでもらう。明示指定されたハーネスも同じ2条件で検証し、いずれかを満たさなければ中止する。候補が0件なら、除外理由と復旧方法を示して中止する。
2. 委譲先モデルが未指定なら、選択済みハーネスのモデル一覧から、`auto` 等の起動時まで実効モデルが決まらない値を除いて散文提示し、選んでもらう。明示指定されたモデルは同じ一覧と照合する。codex の `<slug>@<effort>` は slug 部を一覧と照合する。claude は `models/claude.txt` の ID と照合する（この静的一覧は claude ペインの起動検証専用。未掲載モデルを使う場合は同ファイルを更新してから再実行する）。それ以外は指定値全体を一覧と照合する。完全一致なら採用し、大文字小文字・区切り記号・部分一致のゆれで候補が1件なら一覧上の形へ是正して採用する。候補が0件または2件以上なら再指定を求める。是正後の起動指定を `catalog.sh validate <CLI名> <model-spec>` で検証し、失敗したら理由と候補を示して再指定を求める。
3. 検証済みの起動指定を `catalog.sh family` へ渡し、委譲先のモデル系統を得る。実行中の系統と同一なら起用せず、異なる系統の候補の再指定を求める。同系統の許容可否と縮退（許容時の明記義務を含む)は利用スキルの規定が定め、本則に優先する。

候補の優劣を判断できる根拠が無ければ、散文提示では推奨なしと理由を明記する。固定の候補順を推奨の代わりに使わない。

モデル一覧を取得できないハーネスを、未検証のモデル指定で起用する経路は持たない。

完了条件: 実行中と委譲先のモデル系統がすべて確定し、利用スキル固有のガード（同系統の許容規定を含む）の全判定を通過している。

## ペイン配置

最初のハーネスペインを作る前に、対象と方向を次の規定で決める:

1. `mux.sh layout` で指揮者ペインの rect（width / height）を取り、**width ≥ height × 2 なら横長、そうでなければ縦長**と判定する（端末セルの縦横比は約2:1のため、見た目の縦横は width/2 と height の比較に相当する）。
2. **1枚目のハーネスペイン**: 指揮者ペインを分割する。横長なら方向 `right`、縦長なら `down`。
3. **2枚目以降のハーネスペイン**: **直前に作ったハーネスペインを** `down` で分割する（指揮者ペインをそれ以上狭めず、ハーネスペインを1列に積み上げる）。
4. 分割のたびに `mux.sh list` で ID を取り直して対応表を更新する（正本: 後述「ペイン ID の揮発性」）。

完了条件: 起用するハーネスの数だけペインが配置され、対応表に記録済み。

## ペインの起動（ハーネスごと・遅延）

あるハーネスへの最初の委譲が発生した時点で、そのハーネスのペインを起動する:

1. `mux.sh list` で**指揮者ペイン ID**（`focused` が真の自ペイン）を取得する。以後、全ブリーフの通信規約に記載する。
2. `mux.sh split <対象ペインID> <方向>`（対象と方向は前節「ペイン配置」）で新ペインを作り、出力されたペイン ID を得る。
3. `mux.sh run <ペインID> "<起動コマンド>"` でハーネスを起動する（起動コマンドは当該 transports の規定）。**ハーネスの cwd はプロジェクトルートに固定する** — transports の起動コマンドにある `<プロジェクトルート>` は、呼び出し側セッションの作業対象プロジェクトの最上位ディレクトリ（`.git` / CLAUDE.md 等を持つルート）の絶対パスに展開する。ペインのシェル cwd は分割元を継承するが、それに依存せず起動コマンド側の cwd 指定（cwd オプションまたは `cd`）を正とする（ブリーフの書き込み規律「成果物置き場にのみ書く」の基準点を確定させるため）。
4. trust 等の初期ダイアログは当該 transports の規定で通過する（`mux.sh wait-output` で確定待ちし、`mux.sh send` / `mux.sh key` で応答する。確定待ちのタイムアウト＝ダイアログなしは正常分岐）。
5. `mux.sh agent-wait <ペインID> --until idle 60000` で入力待ちへの到達を確認する。
   - 起動直後はエージェント検知が未登録で `agent_not_found` により即失敗することがある（起動レース・実測）。失敗したら数秒おいて同じ確定待ちを1回だけ再実行する。
   - タイムアウトしたら `mux.sh read <ペインID>` で画面を読み、原因（予期せぬダイアログ・起動失敗等）を特定してから対処する。
6. ペイン ID を**push ラベル→ペイン ID の対応表**（セッション内で保持）に記録する。

完了条件: 当該ハーネスが入力待ち（idle）に達し、対応表に記録済み。

## タスクの委譲

1. ブリーフを成果物置き場にファイルとして書く（成果物置き場が存在しなければ作成してから書く。既存ファイルを上書きしない）。末尾に次のブロックを**一字一句そのままコピー**し、`<>` 内だけ実値に置換する（`<mux.sh>` は本スキルの `mux.sh` の絶対パス）:

   BEGIN-通信規約（ブリーフ末尾へコピー）
   - 完了したら: 本ブリーフに定めた回答/報告ファイルを書き、次を実行する:
     `<mux.sh> send <指揮者ペインID> "[<push ラベル>] done <回答/報告ファイルパス>"` に続けて `<mux.sh> key <指揮者ペインID> Enter`
   - 不明点で作業を続けられないときは、作業を止めて次を実行する:
     `<mux.sh> send <指揮者ペインID> "[<push ラベル>] question: <一行の質問>"` に続けて `<mux.sh> key <指揮者ペインID> Enter`
   - 上記コマンドが失敗した場合（Operation not permitted 等）: 回答/報告ファイルはそのままに、同じ一行（`[<push ラベル>] done <回答/報告ファイルパス>` または `[<push ラベル>] question: <一行の質問>`）を最終メッセージとして出力して終了する
   - git のコミット・stash・ブランチ作成はしない。変更は作業ツリーに残す。
   END-通信規約

2. 送信から受理の確定待ちまでを単一のシェル実行で回す。ペインへ送るのは起動指示の一行だけで、テキストと Enter は別コマンドに分けて間を置く（同一バーストで届いた Enter はペースト処理に吸収される）:

   ```sh
   <mux.sh> send "$PANE" "<ブリーフ絶対パス> を読んで実行せよ" \
     && sleep 1 && <mux.sh> key "$PANE" Enter \
     && <mux.sh> agent-wait "$PANE" --until working 15000
   ```

   受理完了の条件: working への遷移（終了コード 0）に加え、応答 JSON に `agent_session` が含まれていること。ただし **`agent_session` を報告しないハーネスがある**（当該 transports に明示。その場合は working 遷移のみで手順3へ）。working でも `agent_session` が期待されるのに無い場合は、TUI 初期化中の描画を working と誤検知した空振り（送ったテキストは破棄済み）とみなし、受理としない。
3. 受理完了にならなければ `mux.sh read "$PANE" --lines 40` で入力欄を見て二分する（TUI 初期化直後の Enter 吸収は全ハーネス共通の前提）:
   - 指示テキストが入力欄に残っている → Enter のみ再送する
   - 入力欄が空 → 手順 2 からやり直す（idle は入力受付可能より先に報告されることがあり、初期化中に送ったテキストは丸ごと捨てられる）

   再送・やり直しは当該ハーネスにつき合計 2 回まで。それでも受理完了にならなければ、呼び出し側の失敗規律に従い委譲を終了する（`mux.sh read` の内容を原因分析に添える）。
4. **pull 安全網**をハーネスごとに仕掛ける: `mux.sh agent-wait "$PANE" 1800000` を、バックグラウンド実行できる環境（Claude Code では Bash ツールの `run_in_background`）ではバックグラウンドで起動する（`--until` 無し = idle / done / blocked のいずれかで発火。ハーネスは完了後 idle に戻るだけで done を報告しないことがあり、`--until done` に絞ると完了を取り逃がす）。バックグラウンド実行が無い環境では、全委譲の受理完了後に同じコマンドを前面の同期実行で待つ（待ちが委譲ごとに直列化するが、コストとして受け入れる）。いずれの場合も安全網は手順 2 の受理完了の確認後に張る（エージェント状態は画面からの推定であり、受理前の無活動ペインは done と誤検知され即発火する）。

完了条件: 委譲した全ハーネスについて、受理完了の確認と安全網の起動が済んでいる。

## 応答の受け取り

push の `[<push ラベル>]` で発信元を特定してから処理する:

- **`[<push ラベル>] done <パス>`** が届いたら回答/報告ファイルを読む。読まずに次工程へ進まない。
- **`[<push ラベル>] question: ...`** が届いたら、回答を当該ペインへ `mux.sh send` ＋ `mux.sh key Enter` で送る。補足が長くなる場合はファイルに書いてパスを送る。
- **安全網が先に発火**したら `mux.sh read "$PANE" --scrollback --lines 60` で画面を読み、**三分類**する:
  - **承認ダイアログで停止（blocked）** → 次節「指揮者裁定」に従い許可 / 拒否を送信し、安全網を張り直す（同一の委譲対応中に複数回発火しうる）。
  - **done / idle なのに push が無い** → 回答/報告ファイルの有無と画面内容から結果を直接回収する（push 漏れは回収漏れであり、呼び出し側の失敗規律の「失敗」に数えない。回答本文がペインにしかない場合は本文のみを回答/報告ファイルへ転記する）。
  - **まだ作業中（working）** → 安全網を張り直して待機を延長する。延長はハーネスごとに1回まで。2回目の発火はユーザーに相談する。

完了条件: 委譲した全ハーネスについて、回答/報告ファイル（または直接回収した結果）を読み終えている。

## 指揮者裁定

承認ダイアログは pull 安全網の blocked 発火で検知し、指揮者が裁定スコープとの照合で二値裁定する:

- 対象パス・コマンドが**裁定スコープ内** → 許可する。
- **範囲外** → 拒否し、呼び出し側の失敗規律へ進む。

対象パス・コマンドが表示で切れている場合は `mux.sh read --scrollback` で読み直して確認してから裁定する（対象不明のまま許可しない）。ダイアログの形式（文言・選択肢）と応答方法（キー送信 / テキスト送信）はハーネスごとに異なり、正本は当該 `transports/<CLI名>-tui.md` の裁定基準。

自動裁定機構を持たないハーネス（agy 等）への書き込み委譲は、承認ダイアログが頻発し指揮者裁定の回数が増える（起用の制限はしないが、コストとして受け入れる）。

完了条件: 発火した全 blocked について許可/拒否のいずれかを裁定し送信済み。

## 未知ダイアログの遭遇プロトコル

当該 transports に明示されていない形式のダイアログに遭遇したら:

- **(a) 文言から対象が読め、裁定スコープで判定できる** → 前節「指揮者裁定」の基準で裁定して続行し、文言・選択肢・応答・結果を実測ノートとして記録する。
- **(b) 判定不能** → 許可せずユーザーに確認する。

いずれの場合も、セッション末尾に当該 transports への追記案（ダイアログ形式・応答方法・検証記録）を提示し、**承認を得てから**反映する（無承認の自己改定はしない）。

完了条件: 遭遇した未知ダイアログについて (a)/(b) いずれかで処理し、セッション末尾に追記案を提示済み（遭遇が無ければ提示不要）。

## ペイン ID の揮発性

ペイン ID はペインの増減で振り直される。増減操作（起動・クローズ）を行ったら、直後に `mux.sh list` を取って対応表を更新する。`mux.sh close` / `run` / `send`（`key` と一体の送信は一式で1回）の直前は `mux.sh list` で ID を取り直す — 複数ペインでは、古い ID への送信が**別のハーネス**を撃つ事故になる。取り直しで当該ハーネスのペインを特定できないときは、送信せずユーザーに確認する。

## クローズ

ペインは**作業時のみの窓**である。次の3条件が当該ハーネスについて揃ったら閉じてよい: (1) 未回収の委譲・次ラウンドの委譲が無い (2) 未回収の push が無い (3) 当該ハーネスの pull 安全網が発火済みまたは停止済み。クローズ期限（いつ閉じるか）は利用スキルの規定に従う。`mux.sh list` で ID を取り直してから `mux.sh close` し、対応表から除く。次の委譲が確定している間は閉じずに同一ペインへ追送する（ペインの文脈保持が本ハーネス起用の価値であり、閉じれば失われる）。

完了条件: 閉じたペインが `mux.sh list` に存在しないことを確認した。

## カタログ（catalog.sh）

候補ハーネスの疎通確認とモデル一覧の**正本は同梱の `catalog.sh`**（現行カタログ: codex / cursor-agent / agy / claude / grok — いずれも対話 TUI 検証済みで `transports/<CLI名>-tui.md` を持つ）。

- `catalog.sh probe` — 候補の検出・疎通確認。1候補1行の `名前 <TAB> ok|excluded <TAB> 詳細`（ok の詳細にはモデル一覧等の補足が入る。excluded は未導入・認証切れ等の理由）。
- `catalog.sh models <cli>` — 当該 CLI の指定可能モデルを1行1件で出力する（モデル指定の検証に使う）。`claude` は動的取得ではなく `models/claude.txt` の ID を返す。
- `catalog.sh family <cli> <model-spec>` — モデル指定からモデル系統（先頭ファミリートークン）を出力する。`auto` 等の起動前に実効モデルを確定できない指定は非0で終了する。`claude` は提供モデルが Anthropic のみのため指定値によらず `claude` を返す。
- `catalog.sh validate <cli> <model-spec>` — モデル指定を現在のモデル一覧・CLI 固有設定の許容値と照合する。委譲先の起動前検証に使い、系統の確定は `family` で行う。

カタログに無い CLI の起用には (1) `catalog.sh` への probe / models / family / validate 分岐の追記と (2) 対話 TUI の実測検証に基づく `transports/<CLI名>-tui.md` の作成の両方が必要である。追記・作成の案を組み立ててユーザーに提示し、承認を得てから反映して採用する（正本を更新する変更のため、承認なしに追記しない。検証なしに対話 TUI を使わない）。

完了条件: 起用する全ハーネスが `catalog.sh probe` で ok と判定済み。

## マルチプレクサ（mux.sh）

ペイン操作はすべて同梱の **`mux.sh`**（マルチプレクサラッパー。サブコマンドの正本はスクリプトのヘッダ）を経由する。マルチプレクサの生コマンドを直接叩かない（バックエンド差の吸収とセッション毎のばらつき防止のため）。**現行バックエンドは herdr のみ**（未検証のバックエンドは fail fast — `mux.sh detect` が検証済みバックエンドを返さなければ、利用スキル側が起用を開始しない）。マルチプレクサ操作の一般知識（herdr スキル等）が文脈に読み込まれている場合も、本スキル実行中の操作は mux.sh 経由に統一する（診断時のみ読み取り参照可。診断後の操作は mux.sh に戻して行う）。

完了条件: `mux.sh detect` の結果（backend 名または中止理由）を確認済み。
