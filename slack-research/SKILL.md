# slack-research — Slack ワークスペース調査

プロジェクト直下の `.slack-research-env` に保存された Slack User Token (xoxp) を使い、`curl` で Slack Web API を直接呼んでワークスペースの中身を調査し、質問に答える。MCP サーバーは使わない。POSIX シェル（bash 等）と `curl` が使える環境を前提とする。

**完全読み取り専用**: 使ってよいのは検索・履歴・スレッド・チャンネル情報・ユーザー情報の取得系 API のみ。メッセージ投稿・リアクション・ファイルアップロード等の書き込み系 API はこのスキルの範囲外であり、依頼されても実行せず範囲外である旨を伝える。プロジェクトのファイルも書かない（Step 3 の保存依頼時に承認されたパスへの出力のみ例外）。git 履歴には一切触れない。

## Step 0: 前提チェック

調査に入る前に、次を上から順に確認する。いずれかで失敗したら**その時点で調査に着手せず中止**し、対応する案内だけを行う。

1. **トークンファイルの発見**: git リポジトリ内なら `git rev-parse --show-toplevel` の直下、非 git 環境ならカレントディレクトリで `.slack-research-env` を探す。以降の手順はすべてここで解決した絶対パス（下記の `$env_file`）を使い、cwd 相対では参照しない。無ければ中止し、本スキルと同じディレクトリの `SETUP.md` を Read してセットアップ手順を案内する。

   ```sh
   root=$(git rev-parse --show-toplevel 2>/dev/null || pwd)   # 非 git 環境ではカレント
   env_file="$root/.slack-research-env"
   ```

2. **git 漏洩ガード**: git リポジトリ内では `git -C "$root" check-ignore -q .slack-research-env` で ignore 済みかを確認する。ignore されていなければ中止し、`.gitignore` に `.slack-research-env` の1行を追加するよう案内する（スキル側では書き換えない）。非 git 環境ではこのチェックをスキップして続行する。
3. **トークンの読み込み**: `token=$(sed -n 's/^SLACK_TOKEN=//p' "$env_file")` で値を読み込む。
4. **トークン検証**: `auth.test` を1回呼ぶ。`ok: false` なら中止し、エラー内容（`invalid_auth`＝失効等）と、Slack アプリの OAuth ページからトークンを再発行して `.slack-research-env` を更新する手順を案内する。`ok: true` の応答に含まれるワークスペース名・ユーザー名を「どこを誰として調査するか」として報告に使う。

完了条件: 4項目すべてが通過し、ワークスペース名が特定できている。

## API 呼び出しの共通規定（Step 1・Step 2 のすべての呼び出しに適用）

- **呼び出しの型**: トークンの秘匿と HTTP ステータス・ヘッダの取得を両立する形で呼ぶ。トークン値そのものは会話・レポート・コマンド出力に一切表示せず、読み込みと使用は同一シェル呼び出し内の変数展開で行う:

  ```sh
  hdr=$(mktemp)
  resp=$(curl -s -D "$hdr" -H "Authorization: Bearer $token" "https://slack.com/api/<method>" ...)
  ```

- **ページネーション**: `response_metadata.next_cursor` が空でない限り、必要な範囲まで `cursor` を付けて辿る（`conversations.list` / `users.list` / 履歴・検索のいずれも同様。1ページ目だけ見て「無い」と判定しない）。
- **レート制限**: HTTP 429 が返ったら、`$hdr` に記録された `Retry-After` ヘッダの秒数を待って同じ呼び出しを再試行する。
- **API エラー**: `ok: false` の応答は握りつぶさない。`missing_scope`・`channel_not_found` 等は対象の問いを「確認不能」とし、エラー名と必要な対処（スコープ追加・チャンネル参加等）を報告に載せる。

## Step 1: 調査スコープの解決

`.slack-research-env` の任意行 `SLACK_CHANNELS` を解釈する:

```sh
# 例
SLACK_TOKEN=xoxp-1234-...
SLACK_CHANNELS=#general,#proj-x,@yamada
```

- **未指定**: トークンで見える範囲すべて（公開・プライベートチャンネル・DM・グループDM）を対象にする。
- **指定あり**: カンマ区切りの各項目を既定スコープにする。`#名前` はチャンネル（`conversations.list` の `types=public_channel,private_channel` で名前→ID 解決）、`@名前` は 1対1 DM の相手（`users.list` で表示名・実名から user ID を特定し、`conversations.list` の `types=im` の `user` フィールドで DM チャンネル ID に解決）。**1件でも解決できない名前があれば中止**し、どの名前が解決できなかったかを報告する（黙って除外して続行しない）。
- **グループDM は指定記法の対象外**: `SLACK_CHANNELS` を指定した場合、グループDM は既定スコープに含まれない。グループDM を調べたいときは依頼の中で明示する（下記の明示指定として扱う）。
- **ユーザーの明示指定が優先**: 依頼の中でユーザーがスコープ外のチャンネル・相手を名指ししたら、そちらを調査対象に含め、既定スコープ外を調べた旨を報告に明記する。

完了条件: 調査対象が「全可視範囲」か「解決済み ID のリスト」のどちらかに確定している。

## Step 2: 調査

依頼内容を「Slack 上で確認すべき問い」に分解し、問いごとに次の道具立てで調べる:

- **横断検索**: `search.messages`。キーワードに `in:#チャンネル名` `in:@相手` `from:@発言者` `before:` `after:` の修飾子を組み合わせる。既定スコープが指定されているときは対象チャンネルごとに `in:` 付きで検索して結果を統合する。
- **文脈確認**: 検索ヒットだけで断定せず、`conversations.history`（`oldest`/`latest` で期間指定）で前後の流れを、`conversations.replies` でスレッド全体を読む。
- **名前解決**: 発言者 ID は `users.list` の結果で表示名に引き当てる（結果は調査中キャッシュして再利用する）。
- **出典リンク**: 引用するメッセージは `chat.getPermalink` で permalink を取得する。

完了条件: 分解した**すべての問い**に、次のいずれかが付いている — 回答あり（出典メッセージ付き）/ 該当なし（検索条件と探索範囲を添えて）/ 確認不能（エラー名と対処付き）。ゼロ件や権限不足を推測で埋めない。

## Step 3: 提示

会話内で次の構成で答える:

1. **結論**: 依頼への直接の答え。
2. **根拠**: 経緯・やりとりの要約。時系列が重要なら時系列で。
3. **出典**: 引用ごとに チャンネル名・発言者・日時・permalink。
4. **注記**: 既定スコープ外を調べた場合はその旨、確認不能だった問いはエラー名と対処。

ファイルとして保存する依頼があったときのみ、書き出す前に保存先をユーザーに選択式で確認する（Claude Code では AskUserQuestion。同等ツールが無い環境では散文で質問し回答を待つ）: プロジェクトに調査資料の置き場（`docs/` 等の慣例ディレクトリ）があればそこ（推奨）、なければセッションの一時領域（Claude Code ではスクラッチパッドディレクトリ。無い環境では OS の一時ディレクトリ）を推奨とし、任意パスの入力も受け付ける。承認された場所以外にファイル・ディレクトリを作らない。

完了条件: Step 2 の全判定が提示に現れている。
