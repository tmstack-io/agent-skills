# figma-to-code — Figma デザインの 1:1 実装

Figma MCP サーバー（get_metadata / get_design_context / get_screenshot / download_assets / get_variable_defs / whoami）が接続された環境で、デザインを実装先の Web フロントエンド（HTML/CSS）コードベースの規約に沿って 1:1 で再現する（Web 以外の媒体の依頼では、検証手順が HTML/CSS の計測を前提としている旨を伝え、適用可否を散文提示で確認してから進む。推奨: 対象外として中止する — 数値照合の合否判定が成立しないため）。柱は3つ:

- **対応表が背骨** — 実装前に、確定した画面種ぶんのセクション対応表（node-id 付き）を作り、以後の全作業がこれを参照する
- **キャッシュが正** — 取得と参照の規律は Step 1「一括キャッシュ」に定める（根拠は「レート予算」の節）
- **数値と目視が正** — 合否判定の規律は Step 3「検証の規律」に定める

## レート予算（Figma MCP のツールコール制限）

Figma MCP のツールコールには分単位と日/月単位の二段構えの上限がある（2026-08 時点の公式値。上限は変わりうるため、制限に当たったら出典を確認する。出典: https://developers.figma.com/docs/figma-mcp-server/rate-limits-access/ ）:

| シート種別 | 分あたり | 日/月あたり |
|---|---|---|
| View / Collab 席（全プラン） | — | 月 6 回 |
| Dev / Full 席・Starter | 10 回/分 | 200 回/日 |
| Dev / Full 席・Professional | 15 回/分 | 200 回/日 |
| Dev / Full 席・Organization | 20 回/分 | 600 回/日 |
| Dev / Full 席・Enterprise | 未確認（Organization と同水準と推定） | 600 回/日 |

- `whoami` はカウント対象外のため、プラン・シート種別の確認に自由に使える
- Starter プランのチームに属するファイルへの呼び出しは、呼び出し側が他プランの有償席でも月 6 回に制限される
- 残量を事前確認する手段は無く、日次リセットの正確な時刻は非公開（枯渇したら実務上は日付が変わるのを待つ）
- `get_design_context` は応答が最も重く、実行ハーネスのツール出力上限を超えることがある（上限を拡げられるハーネスもある。Claude Code では環境変数 MAX_MCP_OUTPUT_TOKENS）

**予算の立て方**（正本はこの節。Step 0 の手順 3 から参照される）: `whoami` でシート種別を確認し、概算コール数（ルートの metadata 取得とルート全体スクリーンショット〔いずれも画面種ぶん〕＋ デザイントークン取得 ＋ セクション数 ×〔design context + スクリーンショット〕× 画面種 + アセット書き出し + 予備 2〜3 割）を上限と突き合わせる。着手前はデザインの全体像から見込んだセクション数で概算し、Step 1 の列挙で確定したら再計算する。200 回/日の席では 1 ページ規模の実装で使い切りうる。この予算が、一括取得とキャッシュ参照（Step 1）を必須にしている。

**枯渇時の対処**: 「try again tomorrow」系のエラーは日次/月次の枯渇 — Figma への呼び出しを止め、キャッシュで作業を継続し、取得の残りは翌日以降に回す。即時エラーが分単位の制限なら 1 分程度待って再開し、以後は呼び出し間隔を空ける。並行するエージェント・セッションは同一アカウントのクォータを共有するため、並行作業がある場合もキャッシュを参照させ、同じノードの再取得を発生させない。Step 1 の一括取得・Step 2 のアセット書き出しの途中で枯渇した場合は、未取得のセクション・アセットを対応表に「取得待ち」として記録し、取得済み分に限って先の Step へ進んでよい — 取得を再開できたら当該 Step に戻って残りを取得し、合流させる（取得待ちのアセットを使うセクションは、仮のプレースホルダで進めるか保留するかを対応表に記録する）。取得待ちのまま残った項目は Step 5 の報告に含める。セクション列挙・デザイントークン・ルート全体スクリーンショットといったルート単位の取得の途中で枯渇した場合は、対応表を作成して確定済みの画面種・ルート node-id・取得できた範囲を記録し、未取得のルート単位項目を「取得待ち」として残して実装には着手せず、枯渇の事実と再開見込みを報告して中断する。

## Step 0: 入力と前提の確定

1. **Figma MCP の接続確認（前置きゲート）**: 最初に `whoami`（レート計上外）を呼び出して Figma MCP の接続を確認する。呼び出せない場合は黙って別の手段で代替せず、何も作業せずに、Figma MCP サーバーの接続設定が必要である旨と公式の設定手順（ https://developers.figma.com/docs/figma-mcp-server/ ）を案内して中止する
2. **フレームの URL を揃える**: 実装対象（PC/SP、対象ページごと）の node-id 付き URL を確定する。対象ページが複数の場合は、ページごとに識別子（実装上のページ名）を確定する。ページ一覧の取得（nodeId 無しの `get_metadata`）は一部のページしか返さないことがあり、PC 版と SP 版が別ファイルに分かれていることもある — 見つからないフレームは探索でコールを消費せず、ユーザーに URL の提供を求める。PC/SP の一方しか存在しない場合や 1 フレームでレスポンシブを表現しているデザインの場合は、無い側の扱い（実装対象外とするか、存在する側から導出するか。推奨: 存在する側から導出する — 実装対象外にすると実機でその画面種の表示が未定義のまま残るため）を散文提示で確認し、確定した画面種と無い側の扱いを控えて Step 1 で対応表を作成する際に先頭へ転記する — 以後の記録・キャッシュ・検証は確定した画面種のみで行う。導出を選んだ場合、導出側は確定した画面種に含めず、導出方針（元にする画面種と、幅・余白・折り返しの変換規則）と検証に用いる代表幅を、その場で Step 4 の不変条件として散文提示で承認を得て控え、Step 1 で対応表を作成する際に先頭へ転記する — 導出側の合否は数値照合の対象外とし、承認済みの不変条件への適合と目視・実効ビューポートの確認で判定し、Step 5 手順 3 の検証幅に導出側の代表幅を加える。補足指示が渡されている場合は、実装範囲・優先順・既知の制約として控え、同じく Step 1 で対応表の先頭へ転記して以後の工程に反映する
3. **レート予算**: 「レート予算」節の「予算の立て方」に従って見込み概算を上限と突き合わせる。予算が厳しい場合はその旨をユーザーに一言共有する
4. **実装先の規約収集**: CSS 命名規則・ブレークポイント・ビルド手順・使用ライブラリ・既存共通部品・アセット（画像・アイコン）の配置ディレクトリを、プロジェクトの規約文書と既存コードから収集する（本スキルは特定の値を持ち込まない）
5. **成果物言語**: 対応表・報告に使う言語を確定する（プロジェクトの既存文書の言語に追従し、判定材料が無ければ対話言語）
6. **git への態度**: 本スキルはコミットしない（求められた場合もコミット案の提示まで）。編集対象が git 管理外の場合は、編集前に対象の複製を OS の一時ディレクトリへ保存する

完了条件: 実装対象の全フレームの node-id・レート見積り・実装先規約・成果物言語が確定し、実装対象の画面種（PC/SP の別。片側しか無い場合は無い側の扱いの承認を含む）が確定し、補足指示があればその内容が控えられている。

## Step 1: 対応表の作成と一括キャッシュ

**セクションの列挙**: 対応表のセクションは、確定した画面種それぞれのルート node-id に対する `get_metadata` で子ノードを列挙して洗い出し、実装順にセクション表へ転記する。取得した metadata はキャッシュ置き場へ保存する。セクション内部の要素の実測値はキャッシュした design context を正とし、ルートの metadata はセクションの列挙と外形寸法に用いる — 健全性確認・数値照合に必要な粒度がキャッシュに無いセクションに限り、当該セクションの `get_metadata` を1回だけ追加取得してキャッシュへ保存する（それ以外のセクション単位の再呼び出しはしない）。

**対応表**（既定はプロジェクト直下の `design-nodes.md`。置き場所の規約があればそれに従う）に次を記録する（対象ページが複数の場合は、ページ識別子ごとにルートの記録とセクション表を分ける）:

- ファイルキーと、確定した画面種ごとのルート node-id・ルートサイズ（デザイン幅・高さ。「セクションの列挙」でキャッシュした metadata から転記）、デザイントークン（`get_variable_defs`）、ブレークポイント方針
- セクション表（実装順）: 実装上の名前 / 確定した画面種ごとの node-id・サイズ / 実装メモ（レイアウト変換の要点・共通部品化の候補）
- アセット一覧: 書き出し元 node-id、実データとプレースホルダ（透かし入り素材等）の別
- **未確定要素リスト**: ダミーテキスト、透かし入り素材、誤字の疑い、欠落しているデザイン（例: メニュー開閉の開状態が無い）、PC/SP 間の食い違い。発見のたびにここへ追記する

**一括キャッシュ**: 表の全セクションについて `get_design_context` と基準スクリーンショット（`get_screenshot`、確定した画面種ぶん）をこの段階でまとめて取得し、キャッシュ置き場へ保存する。置き場の既定はプロジェクト直下の `design-cache/`（置き場所の規約があればそれに従う）とし、実際に使ったパスを対応表に記録する。ファイル名はセクション名と画面種が分かる形（例: `<セクション名>-<pc|sp>.context.md` / `<セクション名>-<pc|sp>.base.png`。複数ページ案件ではページ識別子を前置し、全キャッシュ物で同じ規則を使う）とする。`get_design_context` が切り詰め・出力上限に当たるセクションは子ノード単位に分割して取得する。以後の工程はキャッシュを参照し、Figma への追加問い合わせはキャッシュに無い情報が必要になった箇所に限る。キャッシュ直後に基準スクリーンショットの**健全性**を確認する: 当該ノードの design context / metadata に列挙される子要素が全て写っているか照合する。非表示レイヤーのまま書き出された部分キャプチャや、背景と同色で写っていても視認できない要素は、ここで検出しない限り以後の全目視比較が誤った正解に収束する。写っていない・見えない要素は metadata の座標・寸法値を正として扱い、その旨を対応表に記録し、あわせて未確定要素リストへ「基準画像に写らない要素」として追記する（方針確認を経たうえで、Step 3 では当該要素の数値照合の一致を根拠に既知差異として扱う）。あわせて、確定した画面種それぞれのルートノードの全体スクリーンショットも `<pc|sp>.root.png` としてキャッシュする（Step 5 の境界検証で使う）。キャッシュした design context から画像・アイコン・ベクター素材のノードを洗い出し、書き出し元 node-id と実データ・プレースホルダの別を対応表のアセット一覧へ記入する。

**未確定要素の方針確認**: リストの各項目の扱い（推奨: デザイン通りに仮実装して差し替えをリストで管理する。実装を止めずに進められ、差し替え漏れもリストで追跡できるため）を散文提示で確認する。

完了条件: 表の全セクションに、対応表で確定した画面種ぶんの node-id が入り、全セクションが「取得済み」か「取得待ち」（レート枯渇時のみ）のいずれかに分類され、取得済みセクションの design context と基準スクリーンショットがキャッシュ置き場に保存され、そのパスが対応表に記録され、全基準スクリーンショットの健全性確認が済み（写っていない・見えない要素は対応表に記録済み）、確定した画面種のルートノードの全体スクリーンショットがキャッシュ置き場に保存され、全セクションについてアセット一覧への記入が済み、未確定要素の方針が承認済み。ルート単位の取得物が未取得のまま枯渇した場合は、確定済みの画面種・ルート node-id と「取得待ち」の旨が対応表に記録されていれば本 Step を閉じてよい（取得再開まで以後の Step へ進まない）。

## Step 2: アセット書き出し

- 書き出し先は Step 0 で収集したアセット配置ディレクトリに従い、実際に使ったパスを対応表のアセット一覧に記録する（規約から判別できない場合は候補を散文提示で確認する。推奨: 既存の同種アセットが最も多く置かれているディレクトリ — 既存の参照パスの書き方をそのまま流用できるため）
- アイコン・罫線・マスク等のベクター素材は**レイヤー単体のベクター書き出し**（`download_assets` の svgAssets 相当）で取得する。ノードのレンダリング書き出し（export 相当）は親フレーム全体や背景付きで出力されることがあるため、写真などラスタ素材に使う。トリミング前の元画像が要る場合は rawImages 相当を使う
- 書き出し直後に全ファイルを検証する: 空でない・形式が正しい・**画像として開いて目視**する（背景の混入・向きの反転・欠けは、この段階でしか安く見つからない）
- 透かし入りのプレースホルダ素材は「仮実装用」と命名・記録で区別し、未確定要素リストと対応付ける
- 命名は実装先の規約に従う。同名の既存ファイルがある場合は上書きせず、新規側に区別できる接尾辞を付けて保存し、旧名と新名の対応をアセット一覧に記録する。書き出し先の無関係な既存ファイルも残す（どちらを参照に残すかの整理は Step 5 の手順 4 で参照確認の上で行う）

完了条件: アセット一覧の全項目が「検証済み」か「取得待ち」（レート枯渇時のみ）のいずれかに分類され、検証済みの項目がローカルに揃っている。

## Step 3: セクション単位の実装ループ

最初に基盤（デザイントークンの定義・ページ骨格・共通部品の置き場）を実装し、以後は対応表の順に（複数ページ案件では対象ページごとに）セクション単位で回し、各セクションでは確定した画面種すべてについて手順 1〜4 を実施する（対応表で「取得待ち」または保留のセクションは飛ばし、取得を再開できたら戻って合流させる）:

1. キャッシュから当該セクションの design context と基準スクリーンショットを読む
2. 実装する（実装先の命名規則・トークン・既存部品の再利用。色や寸法の直書きはトークンが無い場合に限る）。デザインに描かれていない状態へ実装を広げる必要が生じたら、その場で Step 4 の承認ゲートを実施し、不変条件の承認を得てから続ける
3. 対応表に記録した当該画面種のルートサイズと同じビューポート幅・等倍で実機スクリーンショットを撮り、あわせて照合対象要素の座標・寸法・computed style を計測する — ブラウザ自動化ができる環境では撮影と計測の両方をそれで行い（Claude Code では Chrome DevTools MCP 等）、できない環境ではユーザーに撮影条件を指定して該当箇所のスクリーンショット提供を依頼する
4. 「数値と目視の二本柱」に従って数値照合と目視比較を行う。差異（配置・余白・フォント・色）を修正して 3 へ戻り、数値照合に許容差（「数値と目視の二本柱」）を超える残差が無く、残る目視差異が「拡大表示でも判別できない」または「未確定要素リストに記録済みで方針が承認済みの既知差異」のみになったら、合格時点の実機スクリーンショットをキャッシュ置き場へ `<セクション名>-<pc|sp>.final.png` として保存して次のセクションへ。ループ中に未確定要素リストへ追記した項目は、Step 1 と同じ方針確認を散文提示で行ってから既知差異として扱う

**検証の規律**（ループ全体の正）:

- **数値と目視の二本柱**: 寸法・余白・整列・色は、design context / metadata の実測値とレンダリング結果の計測値（座標・computed style）の**数値照合を一次判定**とする（目視は数 px の差や重なり量の不足を安定に検出できない）。許容差は実装先の規約に規定があればそれに従い、無ければ座標・寸法は 1px 未満の差を一致とみなし、色はトークン値または 16 進値の一致を求める。許容差を超える差が技術的に解消できない場合は、未確定要素リストに記録して方針確認に回す。照合対象要素は、当該セクションの design context に実測値が記載されている全ての可視要素とする（テキストは座標・フォントサイズ・行送り・色、図形・画像は外形の座標と寸法、コンテナは余白と整列）。レンダリング済みスクリーンショットの目視は、数値化しにくい判定 — 視認性・形状・質感・重なり順 — の正とする。テキストは「読める」ことを画像で確認する — 白文字が明るい背景に重なるなど、DOM 上は正常のまま視認不能になる失敗があり、必要なら高解像度で切り出して確認する。レンダリング結果を計測できない環境（手順 3 の縮退でユーザー提供のスクリーンショットに依る場合）では、依頼時に撮影条件（ビューポート幅・拡大率・撮影範囲）を指定し、数値照合の代わりに design context / metadata の実測値を明記した目視判定で代替する — 数値照合を実施できなかった範囲は実施済みと扱わず、Step 5 の報告に明記する
- **実効ビューポートの確認**: レスポンシブ検証の前に、描画された実効幅（document.body 等）が指定幅（対応表に記録した当該画面種のルートサイズに由来するデザイン幅）と一致することを確かめる。既存 CSS（body への min-width 等）や自動化ツールの制約で指定が効かないまま検証を積むと、全て無効になる
- **変形背景上の文字**: 背景が矩形でないシェイプのときは、全ての表示状態でテキストがシェイプの上に乗っていることを画像で確認する
- **動きは状態ごと**: スクロール連動・アニメーションを含むセクションは、開始・中間・終端の代表状態それぞれでスクリーンショット比較する。「固定される」「追従する」という挙動の主張は、位置の時系列サンプリングで裏取りする。タブ・アコーディオン等の状態切替 UI は、状態ごとの一致に加えて、**切替の前後で共通要素（ラベル・周辺レイアウト）の座標が意図せず動かない**ことを数値で確認する（状態別の静止画比較では切替時のレイアウトシフトが写らない）。自動再生カルーセル等は停止し、アニメーションは完了させてから撮影する（過渡状態の撮影は偽の差分を生む）
- **スタイルの真偽はベクターデータ**: 線種・形状の印象が資料間で割れたら、design context のベクター実データ（パス・stroke 指定）で確定する
- **検証の独立性**: 実装者の自己申告と実装時に撮った証跡だけを合格根拠にしない。少なくとも統合検証（Step 5）は、実装した主体とは別の独立したコンテキスト（サブエージェント等の独立した実行コンテキストを起用できる環境ではそれ。Claude Code では Agent ツール）が、実装時の証跡を再利用せず自ら撮影・計測して行う。委譲と結果の回収はサブエージェント返却規約に従う（返却が得られなければ、次の縮退に合流する）。独立コンテキストを用意できない環境では、検証専用のパスとして証跡を取り直し、数値照合の結果を添える

**既存コードベースの扱い**:

- 新実装のクラス名・識別子は既存と衝突しない名を選ぶ
- 置き換えで到達不能になった旧コード（CSS・スクリプト）は、その場では削除せず削除候補として対応表に記録する（整理と削除は Step 5 の手順 4）
- 他ページと共有される部品（ヘッダー・フッター・共通 CTA 等）は共有範囲を確認してから触り、デザイン対象外の現役部品は温存して報告する

完了条件: 取得済みかつ保留でない全セクションについて、確定した全画面種が手順 4 の「次のセクションへ進む条件」を満たし（計測できない環境での代替判定は「数値と目視の二本柱」の規定による）、取得待ち・保留のセクションはその旨が対応表に記録され、実装済みの各セクションの最終スクリーンショットが手順 4 の命名でキャッシュ置き場（Step 1）に保存済み。

## Step 4: 一般化の承認ゲート

本ゲートは Step 3 のループ中に該当が生じた時点で実施する（手順 2 から参照される。本 Step の位置は残った該当分の確認と記録の場である）。デザインに描かれていない状態へ実装を広げる必要が生じたとき（要素数の増減への対応、文言量の変化、デザインが無い中間幅・**デザイン幅を超える広幅**・開閉状態など）は、**何を固定し何を可変にするか（不変条件）を散文提示で確認してから**実装する（不変条件は案件ごとに正解が異なるため推奨なしとし、その旨と各選択肢の帰結を添えて提示する）。特にデザイン幅超は必ず不変条件を確定する。ビューポートがデザイン幅と一致している間は「中央寄せ」と「左右いずれかへの固定配置」が見た目で完全に同一になり、スクリーンショット比較では正誤を判定できないため、観察ではなく仕様として決める必要がある。デザインの見た目と可変要件が両立しない技術的制約があるときは、制約と選択肢を散文提示で示して判断を仰ぐ（優先順は案件ごとに正解が異なるため推奨なしとし、その旨と各選択肢の帰結を添える）。

完了条件: 一般化を含む全セクションで不変条件が承認済み（該当が無い場合はその旨を報告に記す）。

## Step 5: 統合検証と報告

本 Step の手順 1〜3 の実施主体は Step 3「検証の独立性」に従い、手順 4 の削除と手順 5 の報告はユーザーと対話する主体が自ら行う（削除は、削除候補と参照検索の結果を散文提示で示して承認を得てから実行する。推奨: 参照ゼロと確認できた候補は削除する — 到達不能な旧コードを残すと以後の改修で誤参照の元になるため）。手順 1〜3 の合否は Step 3「数値と目視の二本柱」の許容差を準用する（導出側の画面種は数値照合の対象外とし、Step 0 手順 2 の承認済み不変条件への適合と目視で判定する）— 許容差を超える差異・意図しない横スクロール・レイアウト崩れを検出したら、原因セクションを対応表に記録して Step 3 のループへ差し戻し、修正後に当該手順を再実施する（技術的に解消できない差異は未確定要素リストへ記録して方針確認に回す）。

1. ページ全体を通しで確認する（確定した画面種ごとに、複数ページ案件では対象ページごとに実施する）: まず Step 3 手順 3 と同じ撮影条件で実装ページ全体のキャプチャを撮り、`<pc|sp>.page.png` としてキャッシュ置き場へ保存する。隣接セクションの**全ペア**について境界をまたぐ帯（目安: 境界±100px）をこのキャプチャから切り出し、ルートノードの全体キャプチャ（Step 1）の対応する領域（両者のセクション境界の座標を基準に対応づける）と突合する。セクション単体のキャプチャには隣のセクションからはみ出す要素（重なり・食い込み）が写らないため、セクション別比較だけでは境界の差分を検出できない。あわせて意図しない横スクロールの有無を確認する
2. 共有部品・グローバル CSS を触った場合は、変更した部品名・セレクタを全テンプレート・全スクリプトへの検索で引き当てて影響ページを列挙し、各ページを表示して意図しないレイアウト崩れ・横スクロールが無いことを確認する（起動できないページは制約として報告に記す）。列挙したページと確認結果は手順 5 の報告に含める
3. 複数幅で確認する: デザイン幅・中間幅（リキッド帯）・確定した画面種ぶんの幅（SP を実装対象としている場合は SP 幅。導出側の画面種があれば対応表に記録されたその代表幅も含める）に加え、**デザイン幅を超える広幅**（目安: デザイン幅の 1.5〜2 倍。プロジェクトに上限幅の規定があればその幅）と、**各メディアクエリ帯の下端・上端の幅**（帯の代表幅だけでは端で破綻する固定寸法を検出できない）。いずれも実効ビューポートの確認を含む
4. Step 2 で保留した既存アセットと Step 3 で記録した旧コードの削除候補を整理する: 全テンプレート・全スクリプトへの参照が検索でゼロと確認できたものだけ削除する
5. 報告する（報告項目の正本）: 実装したセクション一覧 / 残存する既知差異（理由付き）/ 未確定要素リスト（差し替え待ち項目）/ 取得待ち・保留のまま残った項目 / 数値照合を実施できなかった範囲とその制約 / 温存したデザイン対象外の現役部品 / 不変条件の承認状況（該当なしを含む）/ 影響ページの列挙と確認結果（該当なしを含む）/ 統合検証の実施主体 / Figma コール数の概算と残り予算感

完了条件: 1〜5 がすべて実施され、差し戻しが生じた場合は再実施で許容差内に収まり（残る差異は方針確認を経た既知差異のみ）、報告を提示済みで、統合検証の実施主体（独立したコンテキストか、縮退して検証専用パスで取り直したか）が報告に明記されている。未実施が許されるのは、実行側の裁量では解消できない外的制約（ブラウザ自動化が無い・レート枯渇・影響ページを起動できない等）がある項目のみで、その制約と代替に行った確認を報告に明記する。
