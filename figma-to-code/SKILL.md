# figma-to-code — Figma デザインの 1:1 実装

Figma MCP サーバー（get_metadata / get_design_context / get_screenshot / download_assets / get_variable_defs / whoami）が接続された環境で、デザインを実装先コードベースの規約に沿って 1:1 で再現する。柱は3つ:

- **対応表が背骨** — 実装前に PC/SP のセクション対応表（node-id 付き）を作り、以後の全作業がこれを参照する
- **キャッシュが正** — Figma からの取得は前半に一括して行い、ローカルへ保存する。実装・検証・レビューの反復はキャッシュを読む（根拠は「レート予算」の節）
- **目視が正** — 合否判定はレンダリング済みスクリーンショットの目視で行う。DOM 計測は補助

## レート予算（Figma MCP のツールコール制限）

Figma MCP のツールコールには分単位と日/月単位の二段構えの上限がある（2026-08 時点の公式値。上限は変わりうるため、制限に当たったら出典を確認する。出典: https://developers.figma.com/docs/figma-mcp-server/rate-limits-access/ ）:

| シート種別 | 分あたり | 日/月あたり |
|---|---|---|
| View / Collab 席（全プラン） | — | 月 6 回 |
| Dev / Full 席・Starter | 10 回/分 | 200 回/日 |
| Dev / Full 席・Professional | 15 回/分 | 200 回/日 |
| Dev / Full 席・Organization | 20 回/分 | 600 回/日 |
| Dev / Full 席・Enterprise | 未確認（Organization と同水準と推定） | 600 回/日 |

- `whoami` / `create_new_file` / `add_code_connect_map` はカウント対象外。プラン・シート種別の確認に `whoami` を自由に使える
- Starter プランのチームに属するファイルへの呼び出しは、呼び出し側が他プランの有償席でも月 6 回に制限される
- 残量を事前確認する手段は無く、日次リセットの正確な時刻は非公開（枯渇したら実務上は日付が変わるのを待つ）
- `get_design_context` は応答が最も重く、実行ハーネスのツール出力上限を超えることがある（上限を拡げられるハーネスもある。Claude Code では環境変数 MAX_MCP_OUTPUT_TOKENS）

**予算の立て方**: Step 0 で `whoami` によりシート種別を確認し、概算コール数（セクション数 ×〔design context + スクリーンショット〕× 画面種 + アセット書き出し + 予備 2〜3 割）を上限と突き合わせる。200 回/日の席では 1 ページ規模の実装で使い切りうる。この予算が、一括取得とキャッシュ参照（Step 1）を必須にしている。

**枯渇時の対処**: 「try again tomorrow」系のエラーは日次/月次の枯渇 — Figma への呼び出しを止め、キャッシュで作業を継続し、取得の残りは翌日以降に回す。即時エラーが分単位の制限なら 1 分程度待って再開し、以後は呼び出し間隔を空ける。並行するエージェント・セッションは同一アカウントのクォータを共有するため、検証・レビューの担当にもキャッシュを参照させ、同じノードの再取得を発生させない。

## Step 0: 入力と前提の確定

1. **フレームの URL を揃える**: 実装対象（PC/SP、対象ページごと）の node-id 付き URL を確定する。ページ一覧の取得（nodeId 無しの `get_metadata`）は一部のページしか返さないことがあり、PC 版と SP 版が別ファイルに分かれていることもある — 見つからないフレームは探索でコールを消費せず、ユーザーに URL の提供を求める
2. **レート予算**: `whoami` でシート種別を確認し、概算コール数と突き合わせる。予算が厳しい場合はその旨をユーザーに一言共有する
3. **実装先の規約収集**: CSS 命名規則・ブレークポイント・ビルド手順・使用ライブラリ・既存共通部品を、プロジェクトの規約文書と既存コードから収集する（本スキルは特定の値を持ち込まない）
4. **成果物言語**: 対応表・報告に使う言語を確定する（プロジェクトの既存文書の言語に追従し、判定材料が無ければ対話言語）
5. **git への態度**: 本スキルはコミットしない（求められた場合もコミット案の提示まで）。編集対象が git 管理外の場合は、編集前に対象の複製を OS の一時ディレクトリへ保存する

完了条件: 実装対象の全フレームの node-id・レート見積り・実装先規約・成果物言語が確定している。

## Step 1: 対応表の作成と一括キャッシュ

**対応表**（既定はプロジェクト直下の `design-nodes.md`。置き場所の規約があればそれに従う）に次を記録する:

- ファイルキーと PC/SP のルート node-id、デザイントークン（`get_variable_defs`）、ブレークポイント方針
- セクション表（実装順）: 実装上の名前 / PC node-id・サイズ / SP node-id・サイズ / 実装メモ（レイアウト変換の要点・共通部品化の候補）
- アセット一覧: 書き出し元 node-id、実データとプレースホルダ（透かし入り素材等）の別
- **未確定要素リスト**: ダミーテキスト、透かし入り素材、誤字の疑い、欠落しているデザイン（例: メニュー開閉の開状態が無い）、PC/SP 間の食い違い。発見のたびにここへ追記する

**一括キャッシュ**: 表の全セクションについて `get_design_context` と基準スクリーンショット（`get_screenshot`、PC/SP）をこの段階でまとめて取得し、作業用の一時領域へ保存する。`get_design_context` が切り詰め・出力上限に当たるセクションは子ノード単位に分割して取得する。以後の工程はキャッシュを参照し、Figma への追加問い合わせはキャッシュに無い情報が必要になった箇所に限る。

**未確定要素の方針確認**: リストの各項目の扱い（推奨: デザイン通りに仮実装して差し替えをリストで管理）を散文提示で確認する。

完了条件: 表の全セクションに PC/SP の node-id が入り、全セクションの design context と基準スクリーンショットがローカルに保存され、未確定要素の方針が承認済み。

## Step 2: アセット書き出し

- アイコン・罫線・マスク等のベクター素材は**レイヤー単体のベクター書き出し**（`download_assets` の svgAssets 相当）で取得する。ノードのレンダリング書き出し（export 相当）は親フレーム全体や背景付きで出力されることがあるため、写真などラスタ素材に使う。トリミング前の元画像が要る場合は rawImages 相当を使う
- 書き出し直後に全ファイルを検証する: 空でない・形式が正しい・**画像として開いて目視**する（背景の混入・向きの反転・欠けは、この段階でしか安く見つからない）
- 透かし入りのプレースホルダ素材は「仮実装用」と命名・記録で区別し、未確定要素リストと対応付ける
- 命名は実装先の規約に従う。書き出し先に既存ファイルがある場合、既存側は残す（整理は Step 5 で参照確認の上で行う）

完了条件: アセット一覧の全項目が検証済みでローカルに揃っている。

## Step 3: セクション単位の実装ループ

最初に基盤（デザイントークンの定義・ページ骨格・共通部品の置き場）を実装し、以後は対応表の順にセクションごとに回す:

1. キャッシュから当該セクションの design context と基準スクリーンショットを読む
2. 実装する（実装先の命名規則・トークン・既存部品の再利用。色や寸法の直書きはトークンが無い場合に限る）
3. 実機スクリーンショットを撮る — ブラウザ自動化ができる環境ではそれを使い（Claude Code では Chrome DevTools MCP 等）、できない環境ではユーザーに該当箇所のスクリーンショット提供を依頼する
4. 基準と並べて目視比較し、差異（配置・余白・フォント・色）を修正して 3 へ戻る。差異が「拡大表示でも判別できない」または「未確定要素リストに記録済みの既知差異」のみになったら次のセクションへ

**検証の規律**（ループ全体の正）:

- **目視が正**: 合否はレンダリング済みスクリーンショットで判定する。DOM 計測（座標取得・要素存在確認）は補助に使う。テキストは「読める」ことを画像で確認する — 白文字が明るい背景に重なるなど、DOM 上は正常のまま視認不能になる失敗があり、必要なら高解像度で切り出して確認する
- **実効ビューポートの確認**: レスポンシブ検証の前に、描画された実効幅（document.body 等）が指定幅と一致することを確かめる。既存 CSS（body への min-width 等）や自動化ツールの制約で指定が効かないまま検証を積むと、全て無効になる
- **変形背景上の文字**: 背景が矩形でないシェイプのときは、全ての表示状態でテキストがシェイプの上に乗っていることを画像で確認する
- **動きは状態ごと**: スクロール連動・アニメーションを含むセクションは、開始・中間・終端の代表状態それぞれでスクリーンショット比較する。「固定される」「追従する」という挙動の主張は、位置の時系列サンプリングで裏取りする
- **スタイルの真偽はベクターデータ**: 線種・形状の印象が資料間で割れたら、design context のベクター実データ（パス・stroke 指定）で確定する

**既存コードベースの扱い**:

- 新実装のクラス名・識別子は既存と衝突しない名を選ぶ
- 置き換えで到達不能になった旧コード（CSS・スクリプト）は、全テンプレート・全スクリプトへの参照が検索でゼロと確認できたものだけ削除する
- 他ページと共有される部品（ヘッダー・フッター・共通 CTA 等）は共有範囲を確認してから触り、デザイン対象外の現役部品は温存して報告する

完了条件: 全セクションが基準スクリーンショットと目視一致し、各セクションの最終スクリーンショットが保存済み。

## Step 4: 一般化の承認ゲート

デザインに描かれていない状態へ実装を広げる必要が生じたとき（要素数の増減への対応、文言量の変化、デザインが無い中間幅・開閉状態など）は、**何を固定し何を可変にするか（不変条件）を散文提示で確認してから**実装する。デザインの見た目と可変要件が両立しない技術的制約があるときは、制約と選択肢を散文提示で示して判断を仰ぐ。

完了条件: 一般化を含む全セクションで不変条件が承認済み（該当が無い場合はその旨を報告に記す）。

## Step 5: 統合検証と報告

1. ページ全体を通しで確認する: セクション間の余白と重なり、意図しない横スクロールの有無
2. 共有部品・グローバル CSS を触った場合は、影響しうる既存ページの回帰確認を行う
3. 複数幅で確認する: デザイン幅・中間幅（リキッド帯）・SP 幅（実効ビューポートの確認を含む）
4. Step 2 で保留した既存アセット・旧コードを整理する（参照ゼロ確認の上で削除）
5. 報告する: 実装したセクション一覧 / 残存する既知差異（理由付き）/ 未確定要素リスト（差し替え待ち項目）/ Figma コール数の概算と残り予算感

完了条件: 1〜5 がすべて実施され報告を提示済み（未実施の項目がある場合は理由とともに報告に明記）。
