# pr-respond

> **明示起動の確認**: ユーザーがこのスキルを名指しで起動した場合のみ実行する。
> 文脈からの自動適用で読み込まれた場合は、実行せずユーザーに起動意思を確認する
> （`disable-model-invocation` を解釈しない実行環境での暴発防止。起動＝コードの push と
> 公開返信につながるため、確認なしの発火は実害が出る）。

レビュアー側の連鎖（deep-pr-review: 生成 / pr-comment: 投稿 / pr-recheck: 修正検証）の鏡像にあたる
**著者側**のスキル。自分が著者の PR に付いた**レビュー指摘**（レビュアーが著者へ向けて残した個々の
コメント。人間・bot を問わない）を集め、1件ずつ**対処判定**（妥当 / 不当 / 要判断）を付けて
ユーザーの承認を得てから、妥当分を修正 → レビュー指摘ごとに atomic コミット → push し、
妥当分には修正内容とコミット SHA を、不当分には現状維持の理由を、それぞれ返信として投稿する。
要判断分は返信せずユーザーへ報告する。

**セッションを跨ぐ前提で設計している** — 入力は PR 上のレビュー指摘とそのメタデータのみに依り、
同一セッションの他スキルの出力を前提にしない。

**git への態度**: 本スキルは PR の head ブランチをチェックアウトした clean な作業ツリー上で修正し、
レビュー指摘ごとにコミットを作り、承認後に 1 回だけ通常の push を行う。rebase・force push・
stash による退避（検証 NG の修正を残す目的の 1 件を除く）・ブランチ作成は行わない。
スレッドの resolve は行わない（閉じる判断はレビュアーに残す）。

<!-- BEGIN PROSE-PRESENTATION-CANONICAL -->
**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨する選択肢を理由一言つきで明示し（推奨できる選択肢が無い場合は「推奨なし」とその理由を明示する）、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。

## フロー概観

前提と中止条件 → レビュー指摘の収集 → 対処判定 → **第1段承認（判定と修正方針）** → 修正・検証・
コミット（レビュー指摘ごと）→ 返信の整形 → **第2段承認（差分要約と返信文面）** → push → 返信の
投稿 → 報告

不変条件: **返信は push が成功して SHA が確定した後にのみ投稿する**。復唱と承認を経ない push・
投稿は禁止。

---

## 入力（引数）

- **PR番号|URL**（任意）: 対象 PR の指定。URL が渡された場合は `<owner>/<repo>` も URL から取る。
  PR 番号のみ・省略の場合、リポジトリは cwd から決め、省略時の PR は現在のブランチに紐づくものを
  使う。特定できなければユーザーに対象 PR を確認して中止する（推測で別 PR を対象にしない）。

以降の全 `gh` コマンドには `--repo <owner>/<repo>`（API 形式は `repos/<owner>/<repo>/...`）を
明示する。

---

## 前提と中止条件（前置きゲート）

順に確認し、満たせなければ**何も変更せずに中止**する。

1. **gh の確認**: `command -v gh` と `gh auth status`。不可なら導入・ログインを案内して中止する。
2. **公開整形契約と整形スキルの解決**（必須依存）: 次の順で
   `pr-comment/partial-application-contract.md`（公開整形契約の正本）を探して Read する —
   (1) 本スキルの隣（`../pr-comment/partial-application-contract.md`）、(2) 実行ハーネスの
   スキルディレクトリのプロジェクト側 → グローバル側（Claude Code: `.claude/skills/` →
   `~/.claude/skills/`、Codex: `.agents/skills/` → `~/.codex/skills/`。他ハーネス用の
   ディレクトリは探さない）。どこにも無ければ、導入手順
   （`npx skills add tmstack-io/agent-skills --skill pr-comment`）を案内して中止する。
   続けて、同ファイルの「整形スキルの解決手順」に従って `publish-polish/SKILL.md` と
   `plainify/SKILL.md` を解決する（解決できなければ同手順の規定どおり中止する）。
3. **PR の特定と状態確認**: 「入力（引数）」の規則で PR 番号と `<owner>/<repo>` を確定し
   （省略時の PR は `gh pr view --json number,url`、リポジトリは
   `gh repo view --json nameWithOwner`）、`gh pr view <PR番号> --repo <owner>/<repo> --json
   number,url,title,body,state,headRefName,headRefOid,headRepositoryOwner,headRepository,
   author` を取得する。`state` が closed / merged なら、その事実を示して「続行する」
   「中止する」の二択を散文提示で確認する（推奨は「中止する」— 閉じた PR への修正 push は
   意味を成さないため。マージ後の申し送り返信が目的の場合のみ続行する）。続行した場合は以降を
   **返信のみモード**で進める: 対処判定では妥当（修正済み）・不当・要判断のみを付け（修正を
   要する指摘は要判断にして報告に回す）、「修正・検証・コミット」節と push は実行せず、
   前提ゲート5は `git status --porcelain` が空であることだけを要求する（ブランチ・head・
   upstream の一致は要求しない）。
4. **著者の一致**: `author.login` と `gh api user --jq .login` を突合する。不一致なら
   「本スキルは著者としての返信を投稿し、PR ブランチへ push する」旨を示し、「続行する」
   「中止する」の二択を散文提示で確認する（推奨なし — 代理対応か PR の誤指定かは状況によるため。
   他人名義の PR に著者面をした返信を投稿する事故を防ぎつつ、代理対応の正当な用途は残す）。
5. **作業ツリーの状態**: 次のすべてを満たすこと（返信のみモードでは3番目の条件のみ）。満たさなければ、満たすための手順（該当ブランチの
   checkout・pull・コミットや退避）を案内して中止する（本スキルは stash・checkout・worktree
   作成を代行しない）:
   - `git rev-parse --abbrev-ref HEAD` が `headRefName` と一致する。
   - `git rev-parse HEAD` が `headRefOid` と一致する（ローカルが PR の head と同一。先行・遅延
     どちらも不可）。
   - `git status --porcelain` が空（未コミット変更・未追跡ファイルなし）。
   - 現在のブランチに upstream（`git rev-parse --abbrev-ref --symbolic-full-name @{u}`）があり、
     その remote の URL が `headRepositoryOwner.login/headRepository.name` を指す（フォーク PR
     ではフォーク側）。以降この remote を `<remote>`、`@{u}` のブランチ名を push 先とする。
6. **レビュー指摘の収集**: 「レビュー指摘の収集」節に従って収集し、対象が 0 件なら
   「未対応のレビュー指摘が無い」と報告して中止する。

完了条件: 上記 6 項がすべて通過し、`<owner>/<repo>`・PR 番号・`<remote>`・push 先ブランチが
確定し（返信のみモードでは `<remote>`・push 先ブランチの確定を求めない）、対象のレビュー指摘が
1 件以上ある。

## レビュー指摘の収集

3 種の入力を `--paginate` で**全件**取得する（既定のページサイズで打ち切らせない）。認証ユーザー
（`gh api user --jq .login`。以下「自分」）の発言は対象から除外し、返信関係の判定材料としてのみ
使う。

- **行アンカーのスレッド**: `gh api --paginate "repos/<owner>/<repo>/pulls/<PR番号>/comments"`
  （`id` / `path` / `line` / `original_line` / `body` / `in_reply_to_id` / `user.login` /
  `user.type` / `created_at` / `html_url`）。`in_reply_to_id` の無いものがスレッド先頭で、
  先頭 `id` にぶら下がる返信を `created_at` 順に並べたものが 1 スレッド。`パス:行` は
  `path` と `line` から作り、`line` が null（差分の更新で行アンカーが陳腐化した場合）なら
  `original_line` を用いて、一覧に「行アンカー陳腐化」と注記する。resolve 状態は
  GraphQL で引く（`hasNextPage` が true の間 `endCursor` を `-f cursor=<値>` で渡して繰り返す。
  初回は cursor を渡さない）:

  ```sh
  gh api graphql -f query='query($owner:String!,$repo:String!,$pr:Int!,$cursor:String){
    repository(owner:$owner,name:$repo){pullRequest(number:$pr){
      reviewThreads(first:100, after:$cursor){pageInfo{hasNextPage endCursor}
        nodes{id isResolved comments(first:1){nodes{databaseId}}}}}}}' \
    -f owner=<owner> -f repo=<repo> -F pr=<PR番号>
  ```

  対象＝ `isResolved` が false かつ**スレッドの最後の発言者が自分以外**のスレッド。1 スレッド＝
  1 レビュー指摘とし、判定材料は先頭コメントとスレッド内の全発言（自分の過去の返信を含む）。
- **レビュー本文**: `gh api --paginate "repos/<owner>/<repo>/pulls/<PR番号>/reviews"`
  （`id` / `body` / `state` / `user.login` / `user.type` / `submitted_at` / `html_url`）。
  `body` が空でなく自分以外のもの。本文に複数の指摘が混ざる場合は 1 件ずつに**分解**し、
  それぞれを別のレビュー指摘とする（分解の根拠となる引用範囲を保持する）。「Approve」の
  挨拶だけ等、著者への要求を含まない本文は対象にしない（判断に迷う本文は対象に含めて
  一覧に出し、ユーザーに除外させる）。
- **会話コメント**: `gh api --paginate "repos/<owner>/<repo>/issues/<PR番号>/comments"`
  （`id` / `body` / `user.login` / `user.type` / `created_at` / `html_url`）。自分以外のもの。
  レビュー本文と会話コメントには resolve が無いので、**未対応**＝当該コメントより後に、
  同じ内容（引用・permalink・同一 `パス:行`）に言及する自分の会話コメントが無いこと。

**発信元**は `user.type`（`Bot` / `User`）と `user.login` で記録し、一覧に明示する（bot の
レビュー指摘も除外せず、判定は人間と同じ基準で行う）。

完了条件: 未対応のレビュー指摘の全件に **C1〜Cn の連番**が付き、それぞれに種別（スレッド /
レビュー本文 / 会話）・発信元・`パス:行`（行アンカーのみ）・本文（分解した場合は該当引用）・
`html_url`・返信先の識別子（スレッドは先頭コメントの `id`、他は permalink）が記録されている。

## 対処判定

実行エージェント自身が、レビュー指摘ごとに次の材料を読んで三値の判定と根拠を付ける
（並列サブエージェントが使える環境（Claude Code の Agent ツール等）では、コードの読み取り調査に
限って委譲してよい。委譲と回収はサブエージェント返却規約に従う。判定そのものと根拠の記述は
本体が行う）:

<!-- BEGIN SUBAGENT-RETURN-CANONICAL -->
**サブエージェント返却規約（Claude Code 固有）**: Claude Code のバックグラウンドサブエージェントは、最終報告を親へ送らず待機通知だけで終わることがある。Claude Code でサブエージェントへ委譲するときは、委譲プロンプトに「完了したら、結果の全文を SendMessage で親へ1通で送る」ことを明示する。返却が届かず完了・待機の通知だけが来た場合は、継続対話で結果の再送を依頼する。再送依頼は同一委譲につき合計2回までとし、それでも届かなければ当該場面の失敗規律（再委譲・縮退・脱落・中止）に従う。Claude Code 以外のハーネスでは、サブエージェントの結果を当該ハーネスの通常の返却経路で受け取り、本規約の追加手順は適用しない。
<!-- END SUBAGENT-RETURN-CANONICAL -->

委譲した調査の返却が再送依頼の上限を超えても届かない場合は、その調査を本体が自分で行う
（判定を保留したまま第1段承認へ進まない）。

- PR の `title` / `body`（目的範囲の根拠）と、本文からリンクされた issue（`gh issue view`）
- レビュー指摘が指す `パス:行` の現在のコードと周辺実装（`git diff <base>...HEAD` の差分内外を問わず）
- プロジェクトの規約（CLAUDE.md / AGENTS.md / rules 等、実行時に検出できるもの）
- スレッド内の過去の往復（自分の返信を含む）

判定の定義（三値）:

- **妥当**: レビュー指摘の事実認識が正しく（コードは指摘どおりに振る舞う／欠けている）、修正が
  **PR の目的範囲内で局所的**（設計方針の変更・広範なリファクタ・新機能の追加を要しない）。
  → 修正して返信する。下位区分 **妥当（修正済み）**: 指摘は正しいが、現在の head で既に
  修正されている（修正したコミットを `git log` で示せる。スキル起動前に自分で直した場合や、
  push 拒否後の再実行がこれにあたる）。→ 修正せず、そのコミット SHA を添えて返信する。
- **不当**: 事実誤認（コードは指摘どおりには動かない — 根拠となる `パス:行` を示せる）、PR の
  目的範囲外の要求、または既存規約・PR 本文で明示済みの意図に反する要求。→ 理由を返信する。
- **要判断**: 事実は正しいがトレードオフの選択が要る／修正が PR の目的範囲を超える規模になる／
  レビュアーへの質問が要る。→ 返信せずユーザーへ報告する。

判定に迷う場合は妥当・不当へ丸めず要判断にする（PR を膨らませない・誤った反論を公開しない
ための歯止め）。返信のみモード（前提ゲート3）では、修正を要する指摘に妥当を付けず要判断にする。妥当には**修正方針**（何をどう変えるか。1〜3 行）を、不当には**理由**（根拠の
`パス:行` つき）を、要判断には**論点**（ユーザーまたはレビュアーが決めるべき事柄）を必ず付ける。

完了条件: 全 C に三値の判定・根拠・（判定に応じた）修正方針 / 理由 / 論点が付いている。

## 第1段承認（判定と修正方針）

全 C を散文提示で一覧提示し、承認範囲のテキスト回答を待つ。各項目のブロック形式:

```
- **C<n>** [妥当|妥当（修正済み）|不当|要判断] `<パス:行>`（<種別> / <発信元 login>[bot]）
  - 指摘: <一行要旨>
  - 根拠: <判定の根拠。不当は事実の根拠となる パス:行 を、修正済みは該当コミットの短 SHA を含む>
  - 方針: <妥当: 修正方針 / 修正済み: 返信で示すコミット / 不当: 返信で述べる理由 / 要判断: 論点>
```

前置きに、対象 PR・push 先（`<remote>/<ブランチ>`）・「承認された妥当分のみ修正・コミットし、
push と返信は第2段で改めて承認を得る」ことを含める（返信のみモードでは push 先の代わりに
「返信のみモード（修正・push なし）」と書く）。承認範囲の値は次の 4 種で、組み合わせて
よい（定型なので一行に畳んでよい）:

- **全件承認**: 一覧の判定どおりに進める。
- **番号指定**: 指定した C だけを進め、他は今回の対象から外す（外した C は最終報告に「未対応
  のまま」と残す）。
- **判定の上書き**: 例「C3 は不当」「C5 は妥当。方針は〜」。上書きされた判定と（妥当なら）
  ユーザーの方針で進め、上書きの事実を最終報告に残す。上書き後に妥当となった C の方針が
  無ければ、その C について方針を提案して再確認する。不当・要判断への上書きで理由・論点が
  示されなければ、対処判定と同じ基準（不当は `パス:行` つきの理由、要判断は論点）で提案して
  再確認する。
- **中止**: 何も変更せず終了する。

推奨は「全件承認」— 判定と根拠が一覧で揃っているため。上書きしたい判定があれば番号指定・
上書きと併用する旨を添える。

承認後、妥当が 0 件で不当も 0 件なら、修正・push を行わず報告のみで終了する。

完了条件: 全 C について「進める（判定と方針つき）」「今回は外す」のいずれかが、ユーザーの
テキスト回答で確定している。

## 修正・検証・コミット（レビュー指摘ごと）

承認された**妥当**の C（修正済みを除く — 修正済みはコードに触れず、既存コミットの SHA を
控えるだけ）を 1 件ずつ順に処理する。返信のみモードでは本節を実行しない（該当する C は
存在しない）。1 件の処理が完了する（コミット済みまたは退避
済み）まで次の C に着手しない（作業ツリーは各 C の開始時点で clean）。

1. **修正**: 承認された方針どおりに変更する。方針の範囲を超える変更（ついでのリファクタ・
   無関係な整形）は行わない。**同一ファイルの同一関数／ブロック**を指す複数の C に限り、1 回の
   修正・1 コミットにまとめてよい（まとめた C を後述のコミット本文と返信の双方に列挙する）。
2. **軽量検証**: 型チェック＋Lint に相当する検証コマンドをリポジトリから**検出**して実行する
   （`package.json` の `typecheck` / `lint`、`tsc --noEmit`、`eslint`、`ruff` / `mypy`、
   `phpstan` / `php -l`、`go vet` 等、エコシステムに合わせる。CLAUDE.md / AGENTS.md に指定が
   あればそれを優先する。**自動修正モード（`--fix` 等）は使わない**）。検出できなければ
   「検証コマンド未検出」として実行せず、その旨を最終報告に記す（返信には検証の有無を書かない）。
   検証の前後で `git status --porcelain` を比較し、検証コマンドが作業ツリーを汚した場合は
   NG と同じ扱いにする。
3. **検証 NG の扱い**: コミットせず、その C の変更を `git stash push -u -m "pr-respond C<n>: <一行要旨>"`
   で退避して作業ツリーを clean に戻し、当該 C を**検証失敗**（修正未確定・返信しない）として
   記録する（診断出力の要約と stash の名前・復元手順 `git stash pop` を最終報告に書く）。
   次の C へ進む。
4. **コミット**: 当該 C の変更だけをステージしてコミットする。メッセージは直近のコミット群
   （`git log -20 --format=%s`）から言語・prefix・粒度の慣習を読み取って揃え、本文の末尾に対象
   レビュー指摘の `html_url` を 1 行入れる（`Ref: <html_url>`。まとめた場合は複数行）。
   pre-commit / commit-msg フックはプロジェクトの意思として尊重する — フックがファイルを
   書き換えた場合は当該 C のファイル内なら軽量検証を再実行して OK なら
   `git commit --amend --no-edit` で 1 回だけ取り込み、NG または範囲外のファイルなら
   `git reset --soft HEAD~1` で取り消して手順 3 の退避へ回す。フックが非ゼロで終了して
   コミットが作成されなかった場合も、検証 NG と同じ扱い（手順 3 の退避）とし、フックの出力を
   最終報告に記す。コミット後に
   `git rev-parse HEAD` を当該 C の SHA として控える。

不当・要判断の C ではコードに触れない。

完了条件: 承認された妥当の全 C が「コミット済み（SHA あり）」「検証失敗（退避済み）」の
いずれかで、`git status --porcelain` が空である。

## 返信の整形（publish-polish → plainify）

投稿候補＝コミット済みの妥当の C、妥当（修正済み）の C、承認された不当の C。それぞれ**1 件 = 1 返信**でドラフトを
書き、前提ゲート2で Read した公開整形契約にそのまま従って整形する（本節では再掲しない）。

**成果物言語**: 返信の言語は返信先のレビュー指摘の本文の言語に追従する（判定材料が無ければ
対話言語）。コミットメッセージの言語は既存コミット履歴に従う（前節）。

ドラフトの骨子:

- **妥当**: 「何をどう直したか」を 1〜3 文で述べ、末尾に修正コミットの短 SHA（7 桁以上）を
  添える。まとめて修正した C には、対象を列挙する。修正済みの C も同形で、示すのは既存の
  コミットの短 SHA。
- **不当**: 「現状維持とする理由」を、事実の根拠となる `パス:行` を添えて述べ、末尾に
  「異論があれば教えてほしい」旨の 1 文を置く。
- レビュー本文・会話コメントへの返信（スレッド返信ができないもの）は、冒頭に元コメントの
  permalink と該当箇所の引用（`> `）を置き、対応関係が第三者にも分かるようにする。
- @メンションは付けない（スレッド返信・会話コメントで通知は届く）。

本スキルでの三点宣言（契約が求める想定読者・配布形態・約束するもの）:

- **想定読者**: レビュー指摘を書いたレビュアーと、後からこのスレッドを読む第三者。
- **配布形態**: 対象リポジトリの PR レビュースレッドまたは会話タブに残る著者の返信。
- **約束するもの**: 妥当分では何がどのコミットで変わったかを、不当分では現状維持の根拠となる
  `パス:行` を示し、レビュアーがスレッドを閉じるか再指摘するかを判断できる材料を提供すること。

本スキル固有の適用要点:

- **内部語を落とす**: C 番号・対処判定の三値の名称・スキルの工程への言及は読者の判断に寄与しない
  ため、すべて落とす。
- **保護対象**: `パス:行`、識別子、数値、コミット SHA、引用した元コメントの文言、permalink。
- **実体を変えない**の対象は、修正内容の記述・現状維持の理由・根拠。

完了条件: 投稿候補の全 C の返信文面が整形済みで、漏えい保留分はユーザーの判断
（修正して投稿 / 見送り）が確定している。

## 第2段承認（差分要約と返信文面）

投稿候補の全 C を散文提示で一覧提示し、push と投稿の承認を待つ。各項目のブロック形式:

```
- **C<n>** [妥当|妥当（修正済み）|不当] `<パス:行>`
  - 変更: <妥当のみ。`git show --stat <SHA>` の要約と短 SHA。修正済みは既存コミットの短 SHA>
  - 検証: <実行した検証コマンドと結果 / 検証コマンド未検出>
  - 返信（整形済み・投稿する文面そのまま）:
    <文面>
```

前置きに、push 先（`<remote>/<ブランチ>`）と push するコミット数、投稿先の PR 番号、
「返信は push 成功後にのみ投稿する」「スレッドは resolve しない」ことを含める（返信のみモードでは
push 先とコミット数の代わりに「返信のみモード（push なし）」と書く）。承認範囲の値は
次の 4 種で、組み合わせてよい（定型なので一行に畳んでよい）:

- **全件承認**: push し、全候補を投稿する。
- **番号指定**: 指定した C の返信だけを投稿する（push はコミット済みの全件を対象に 1 回行う。
  投稿しない妥当分は最終報告に「push 済み・返信なし」と残す）。
- **文面の差し替え**: 例「C2 の返信は次の文で」。差し替え文面はユーザーが最終文面を確定した
  ものとして整形せずそのまま投稿する。
- **中止**: push も投稿も行わず終了する（コミットはローカルに残る。最終報告に SHA と
  「未 push」を書く）。

推奨は「全件承認」— 文面は整形済みで、変更は第1段で承認した方針どおりのため。文面を
直したい C があれば差し替えと併用する旨を添える。

完了条件: push の実行可否と、投稿する C（文面確定）がユーザーのテキスト回答で確定している。

## push

コミットが 1 件以上あれば `git push <remote> HEAD:<push 先ブランチ>` を 1 回実行する
（`--force` 系は使わない）。

- **拒否（non-fast-forward 等。remote が先に進んでいる）**: rebase・force を発明せず中止する。
  コミットはローカルに残し、返信は 1 件も投稿しない（SHA が確定しないため）。remote の状態と
  再開手順（`git pull --rebase` と push はユーザーの操作。ローカルが PR head と一致した状態で
  本スキルを再実行すれば、当該スレッドは未対応のまま再び候補に出て、対処判定で
  妥当（修正済み）となり返信のみを行える）を報告する。
- **成功**: `gh pr view <PR番号> --repo <owner>/<repo> --json headRefOid` を取り直し、
  `git rev-parse HEAD` と一致することを確認する。不一致（push の直後に他者が push した等）なら
  投稿を開始せず中止し、再実行を案内する。

コミットが 0 件（不当・修正済みのみ、または返信のみモード）の場合は push を行わず、上の head
一致確認だけを行って投稿へ進む（返信のみモードでは head 一致確認も省略する — ローカルの
head との一致を要求していないため）。

完了条件: push が成功して PR の `headRefOid` がローカル HEAD と一致している（または push 不要が
確定している）。

## 返信の投稿

**1 件 = 1 返信**で投稿する。複数の C を 1 本にまとめない（同一コミットにまとめた C も、返信先の
スレッドが異なれば別々に返信する）。

行アンカーのスレッドへの返信（返信先は先頭コメントの `id`）:

```sh
gh api "repos/<owner>/<repo>/pulls/<PR番号>/comments/<先頭コメントID>/replies" \
  -f body="$(cat <<'EOF'
<整形済み本文>
EOF
)" --jq '.html_url'
```

レビュー本文・会話コメント由来の C への返信は、同じ heredoc 形式で
`gh pr comment <PR番号> --repo <owner>/<repo> --body "$(cat <<'EOF' … EOF
)"` を使う（デリミタのクォートで `$` や backtick のシェル展開を防ぐ）。

失敗時: 投稿に失敗（権限不足・認証切れ・レート制限・ネットワーク断など）したら残りの投稿を止め、
投稿できた `html_url` と未投稿の C を並べて報告し、原因と再開方法（解消後に本スキルを再実行する —
投稿済み分は「最後の発言者が自分」となり自動的に候補から外れる）を添える。

完了条件: 投稿対象の全 C について返信の `html_url`、または中断による未投稿の理由が記録されている。
