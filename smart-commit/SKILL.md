役割は **コミット／ブランチルールの「番人」ではなく「補完役」**（規約の検出元と優先順位の正本は [1]。
規約が触れていない側面だけを本スキルの既定で埋める）。

> ⚠️ **起動 = コミット実行の許可。** `/smart-commit` を打った時点で、検証を通った変更は
> そのまま `git commit` される（毎回の「コミットしてよいか」確認はしない）。
> 即実行を止める安全策は全体フローの各節が定める。
>
> **明示起動の確認**: ユーザーがこのスキルを名指しで起動した場合のみ実行する。
> 文脈からの自動適用で読み込まれた場合は、実行せず起動意思を散文提示で確認する（選択肢は「実行してコミットする」「実行しない」の二択。推奨は「実行しない」— 上記のとおり起動が実行許可のため）。
> `disable-model-invocation` を解釈しない実行環境では、この確認が唯一の暴発防止となる。

引数は取らない。対象は常に「現在のリポジトリの未コミット変更」の全部
（範囲は `git add -A` 相当 = 未追跡を含む・`.gitignore` は尊重。ただし実際のステージは
[7] で単位ごとに行う）。

> ⚠️ **既存のステージ状態は保持しない。** 実行開始時点でユーザーが作っていた
> ステージ状態（部分ステージ含む）は上書きされ、中断時も復元しない
> （ステージ境界・hunk 境界の復元手段もない）。
> 意図的な部分ステージを守りたい場合は本スキルを使わないこと。

## 全体フロー

```
[0] 前提チェック → [1] ルール検出 → [2] ブランチ規約チェック → [3] 安全スキャン
→ [4] 分割プラン作成 ＋ 低信頼判定 → [5] コミットメッセージ生成 → [6] 分割プランのログ表示
→ [7] 順次コミット → [8] 最終フル検証 → [9] 結果報告
```

## [0] 前提チェック（機械的）

以下のいずれかなら、コミットを一切作らず状況を報告して終了する。
（ルール検出に依存しない機械的な判定のみ。ブランチ規約の判定は [2] で行う。）

- **git リポジトリでない**: `git rev-parse --git-dir` が失敗。
- **作業進行中**: `$(git rev-parse --git-dir)` 配下に `MERGE_HEAD` / `rebase-merge` /
  `rebase-apply` / `CHERRY_PICK_HEAD` / `REVERT_HEAD` のいずれかが存在 →
  「○○ 進行中のため中断」。基準パスは必ず `git rev-parse --git-dir` の結果を使う
  （linked worktree ではこれらが `.git/` 直下に無く、固定パス判定では素通りするため）。
- **detached HEAD**: `git symbolic-ref -q HEAD` が失敗。
- **コミットが1つも無い**: `git rev-parse --verify -q HEAD` が失敗 → 初回コミットは本スキルの
  対象外（[3]〜[7] が HEAD 基準の差分と stash に依存する）。最初のコミットを手動で作ってから
  再実行するよう案内して中断。
- **submodule 内部に未コミット変更がある**（`git status --porcelain=v2
  --ignore-submodules=none` の submodule 行の `S<c><m><u>` 欄で m〔追跡変更〕または u〔未追跡〕が
  立っている）→ submodule 内部の変更は本スキルの対象外のため中断して報告。c〔コミット前進〕だけ
  （ポインタ更新のみ）なら通常の変更として続行してよい。
- **変更なし**: ステージ・未ステージ・未追跡のいずれにも対象が無い →
  「コミット対象なし」とだけ報告。
- **前提スキル plainify が見つからない**: 本スキルは [5] の本文整形で
  同梱スキル plainify に依存する。次の順で `plainify/SKILL.md` を探す —
  (1) 本スキルの隣（`../plainify/SKILL.md`）、(2) 実行ハーネス自身の
  スキルディレクトリのプロジェクト側 → グローバル側（Claude Code: `.claude/skills/` →
  `~/.claude/skills/`、Codex: `.agents/skills/` → `~/.agents/skills/`。他のハーネスも
  自身の2箇所を同順。他ハーネス用のディレクトリは探さない）。解決したディレクトリに
  `SKILL.md` と `auto-approval.md`（[5] が依存する `--auto` の規定の正本）の両方があることを
  通過条件とし、どこにも無い・どちらか一方でも欠ける場合はコミットを一切作らず中断し、
  復旧手順を案内する（agent-skills リポジトリ
  `tmstack-io/agent-skills` から plainify を導入して再実行。
  例: `npx skills add tmstack-io/agent-skills --skill plainify`）。

## [1] ルール検出（優先順位で統合）

以下を上から順に調べ、見つかった規定を集めて **「有効ルールセット」** を組み立てる。
**上位で決まった側面は上書きしない。下位は、上位が触れていない側面だけを埋める。**

1. **リポジトリ内の CLAUDE.md / AGENTS.md / `.claude/rules/*.md`**（最優先）
   - コミット関連記述とブランチ関連記述を両方読む。例: 使用言語、prefix 規約、
     署名の可否、本文の書き方、コミット実行ポリシー、ブランチ運用（命名規約・
     base ブランチ・直コミット禁止など）。
2. **実行環境のユーザーグローバル設定**（Claude Code: `~/.claude/CLAUDE.md`、
   Codex: `~/.codex/AGENTS.md` 等、実行環境が読み込むグローバル指示ファイル）の同種記述。
   - 同一側面で 1 と矛盾する場合は **リポジトリ側が勝つ**（より局所的なルール優先）。
3. **設定ファイル**: `.gitmessage`、`commitlint.config.*` / `.commitlintrc*`、
   `package.json` の commitlint 設定、Conventional Commits 系設定。あれば**厳密に**従う。
4. **既存 git log のスタイル**: 直近 20〜30 件から言語・prefix 傾向・件名の語調を推定して踏襲。
5. **既定**: 上位のいずれでもスタイルが決まらない側面（既存ログが少ない等）は、無難な既定
   （Conventional Commits + 変更が一目で分かる具体的な件名）にフォールバック。

**運用上の解釈 2 点:**

- **「指示が無い限りコミットしない」系ポリシーとの関係**: `/smart-commit` の起動自体が
  「コミット実行の明示指示」に当たる。この種のポリシーは起動によって満たされたものと
  して扱い、スキルの実行を止める根拠にはしない（それ以外のコミット規約・ブランチ規約は
  通常どおり最優先で適用する）。
- **規約が外部情報を要求する場合**（Issue 番号・チケット ID 等、変更内容から導けない
  情報が件名・本文に必須のとき）: まず現在のブランチ名から推定する
  （例: `feature/123-...` / `issue-123` / `PROJ-123`）。確実に導けなければ
  **捏造せず**、低信頼扱い（[4] の基準 4）としてユーザーに確認する。

**有効ルールセットに必ず含める要素**: 言語 / prefix 方式 / 件名の語調・長さ / 本文の方針 /
署名の可否 / 分割粒度の指針 / メッセージに必須の外部情報の有無とその値。

## [2] ブランチ規約チェック

[1] で検出したブランチ規約（例: 「main 直編集禁止」「新規作業は `feature/` `bugfix/`
`hotfix/` から作る」「特定ブランチへの直コミット禁止」）に **現在の状態が違反している**
場合は、コミットを一切作らず、違反内容と該当ルール箇所を提示して中断する。
ユーザーが明示的に例外を許可（例: 「main で作業」と指示済み）している証跡がある場合のみ
続行してよい。

ブランチ規約が無いリポジトリでは、既定として main / master への直コミットも止めない
（即実行を優先する意図的な割り切り）。

## [3] 安全スキャン（分割の前に必ず）

分割やステージを始める前に、コミット対象になり得る全変更を一括でスキャンする。
分割後に 1 コミットだけ止めても手遅れになるため、この順序は必須。

**スキャン範囲**（ファイル全体を無差別に走査しない — 過去コミット済みの内容に反応して
無関係な変更まで毎回止まるのを防ぐため）:

- **追跡済みファイル**: `git diff HEAD` の **追加行のみ** を内容スキャン。加えて、
  新規追加・rename・copy されたパス（`git diff HEAD --name-status` の A / R / C）には
  ファイル名パターン検出も適用する（危険な名前への rename を見逃さないため）。
- **未追跡ファイル**（一覧は [4] 手順 1 と同じ `--untracked-files=all` の列挙を使う）: ファイル全体の
  内容スキャン + ファイル名パターン検出。

**検出対象:**

- **secret**: `.env*`（`.env.example` 等の明示的サンプルは除外）、秘密鍵
  （`*.pem` / `id_rsa` / `*.key` / `*.p12` 等）、`credentials.json` / `*serviceaccount*`、
  API キー・トークンらしき高エントロピー文字列やよく知られた鍵プレフィックス。
- **大容量**: 目安 5MB 超、またはバイナリで明らかに成果物（ビルド出力・メディア・
  アーカイブ）と判断できるもの。

**ヒットしたら【全体を中断して報告】する。** 自動で除外して続行しない・自動でコミット
しない。何が検出されたか（パスと理由）を一覧にし、散文提示で判断を求める。選択肢は
「検出されたパスをコミット対象から外して [4] へ進む（`.gitignore` 等の変更はユーザーの操作に
委ね、本スキルは行わない）」「対象から外さず終了する（ユーザーが対処してから再実行する）」の
二択とし、推奨は後者（誤検出か否かをスキル側では判定できないため）。誤検出と回答された項目は
対象に戻して [4] へ進む。外した結果コミット対象が残らなければ、[4] へ進まず「コミット対象なし・
中止」とだけ報告して終了する。

## [4] 分割プラン作成と低信頼判定

1. `git status --porcelain --untracked-files=all` で変更・削除・未追跡（`.gitignore` 適用済み）を
   ファイル単位で列挙する（未追跡ディレクトリを 1 行に畳んだ出力は使わない）。
2. 追跡済みは `git diff HEAD`、未追跡は内容を読む。
3. **論理単位へグルーピング**して atomic 分割プランを作る:
   - 1 つの関心事（機能追加 / バグ修正 / リファクタ / ドキュメント / 設定 / 依存更新
     など）＝ 1 コミット。
   - 相互依存するものは同じコミットか、**依存元が先** になる順序へ。
   - テストとその対象実装は原則同じコミットにまとめてよい。
   - 同一ファイル内に無関係な変更が混在する場合のみ、hunk 単位の分割を検討する
     （未追跡ファイルは hunk 分割不可・常にファイル単位）。
4. 各単位に「対象パス / hunk・含める理由・依存関係・コミット種別」を持たせる。

**低信頼判定** — プランが次の **いずれか** に当たる場合、即実行を止めて分割プランを
**散文提示で人間に確認** する:

1. 同一ファイル内の hunk を複数コミットに分けている（部分ステージ）。
2. 無関係に見える変更を同一コミットにまとめている（グルーピングの自信が低い）。
3. 大量ファイル（目安 20 ファイル超）、または rename / move を含む（意図推定が難しい）。
4. コミットメッセージの推定が曖昧（「何を・なぜ」が読み取れない）、または規約必須の
   外部情報（Issue 番号等）がブランチ名等から推定できない。

提示する選択肢は「このプランで進める」「プランを修正する（修正内容を回答してもらい、更新後に
再提示する）」「コミットせず終了する」の3つとし、推奨は「このプランで進める」（低信頼の理由を
併記する）。終了を選んだ場合は、この時点で index・作業ツリーとも変更していないので「コミット
対象なし・中止」とだけ報告して終える。該当が無ければ確認せず（[6] の表示を経て）そのまま
コミットする。

## [5] コミットメッセージ生成

- **有効ルールセット（[1]）に従う**。prefix・言語・件名語調・必須外部情報はルール最優先。
- **本文は Markdown を使わない。** 箇条書き記法・コードフェンス・見出し記法を入れない
  プレーンテキスト。
- **全変更を網羅列挙しない。** 「何を・なぜ」が伝わる概要のみ。ファイルを 1 つずつ
  並べ立てる本文にはしない。
- **署名は既定で付けない**（Co-Authored-By / Generated with 等）。ルールが明示的に要求
  する場合のみ付ける。
- **本文の整形**: [0] で解決した `plainify/SKILL.md` の**既定モード（意味厳守）**を
  **`--auto`** で読み込み、その「言語の扱い」に従って対象言語の言語別規則ファイルも解決した
  うえで、**このコンテキスト内で適用**する（別プロセス・別呼び出しにはしない。`--auto` の規定は
  plainify 同梱の `auto-approval.md` が正本。`--for` モードの節は適用しない — 読者適応の詳細 drop で
  コミット本文の情報が落ちるため）。ただし:
  - **整形対象は本文のみ。件名は整形しない**（prefix・形式・長さ・1 行制約を崩さない
    ため）。
  - 整形前の確認の値（日本語の文体等）は、有効ルールセット（無ければ既存ログ）の語調を
    宣言して渡す。自動確定した確認事項の一言はコミット本文に含めず、報告に載せる。

メッセージは [4] でプラン確定後に生成する。[7] でコミットが統合された場合は、統合後の
単位のメッセージを生成し直し、同じ規則で整形する。

## [6] 分割プランのログ表示（コミット直前）

実際に `git commit` を始める直前に、これから作る各コミットの一覧
（順序 / 件名 / 含めるパス・hunk の要約）をログ表示する。取り消し・見直しの判断材料を
残すため。低信頼（[4]）に該当しない高信頼ケースでは、表示後そのまま [7] へ進む
（待ちのゲートにはしない）。

## [7] 順次コミット（単位ごとに退避 → 検証 → コミット）

### 検証コマンドの検出

検証コマンドはリポジトリごとに**検出**する（このスキルは特定プロジェクトに依存しない）:

- **軽量（コミットごと）**: 型チェック + Lint。
  - 検出例: `package.json` の `typecheck` / `lint` スクリプト、`tsc --noEmit`、`eslint`、
    `ruff` / `mypy`、`phpstan` / `php -l`、`go vet` など、リポジトリのエコシステムに
    合わせる。**自動修正モード（`--fix` 等）は使わない**（検証中に作業ツリーを変えない）。
- **フル（最終 1 回・[8]）**: テスト + ビルド。
  - 検出例: `test` / `build` スクリプト、`vitest` / `jest` / `pytest` / `phpunit`、
    ビルドコマンド等。
- 該当する検証手段が**無い**場合は、その検証を省略し、**省略した旨を報告に明記**する
  （黙って飛ばさない）。

### 検証もフックも「HEAD + この単位」だけを見る

軽量検証と pre-commit フックには、**「HEAD + この単位」だけを含む作業ツリー** を見せる
（退避の時点とコマンドはコミットループ手順 2 が正本）。そうしないと、型チェック・Lint・フックが
ディスク上の「後のコミット分を含む全変更」を読んでしまい、コミット単位の検証に
ならない（依存漏れを検出できず、フックが未来の変更を巻き込む）。

### コミットループ

ループ開始前に `git reset`（mixed・パス指定なし）で index を HEAD に揃える
（作業ツリーは変更しない。ユーザーの既存ステージ状態はここで失われる — 冒頭の警告
どおり）。

プラン順（依存元が先）に、各単位について:

```
1. ステージ（この単位だけ・パスは常に "--" 区切りで渡す）:
   - ファイル丸ごと → git add -- <path>（未追跡もこれで含める）
   - rename / move → git add -A -- <旧パス> <新パス>（旧パスの削除を含め損ねない）
   - hunk 分割     → この時点の git diff（index ↔ 作業ツリー）から対象 hunk の
                     パッチを生成し git apply --cached <patch>
                     ※ プラン時に作ったパッチを使い回さない（先行コミットで行位置が
                       ずれるため、ステージの直前に最新差分から生成し直す）。
                     ※ 適用に失敗したら 1 回だけ差分を取り直して再試行。なお失敗
                       したら中断して報告。
2. 残りの未コミット変更を退避:
   git stash push --keep-index --include-untracked -m "smart-commit: <単位名>"
   直後に git rev-parse stash@{0} でこの stash のハッシュを記録する（手順 6 の照合用）。
   → 作業ツリーは「HEAD + この単位」だけになる
   （ステージ後に未ステージ差分も未追跡も無い＝残りが無い場合、2 はスキップする。復帰の要否は手順 6 の規定に従う）
   ※ --keep-index でも stash 自体にはステージ済みの単位も記録される。pop 時には
     HEAD 側に単位が既に入っているため three-way マージで既適用として吸収され、
     実際に戻るのは残りの変更だけ。
3. 軽量検証（型チェック + Lint）を実行
   - 検証前後で git status --porcelain を比較し、検証コマンドが作業ツリーを汚して
     いたら（新たな差分・未追跡の出現。gitignore 済みキャッシュは現れない）中断する。
     このとき pop はしない（汚れた状態への自動 pop は衝突リスクがあるため）。
     現在の状態（HEAD + 単位 + 検証生成差分）を報告して中断する（stash の残りの報告は [9] に従う）。
4. 検証 NG の場合（まだ何もコミットしていない）: 本スキル同フォルダの verify-fail.md を Read し、
   その規定で退避の復帰・依存統合の再試行・中断を決める（対処はそのファイルの規定に限る）
5. 検証 OK → git commit（[5] のメッセージ）
   - コミット直前に git write-tree で index のツリー ID を記録しておく
     （フックによる index 書き換えの検出用）。
   - --no-verify / --no-gpg-sign での回避は禁止。
   - commit 自体が失敗した場合（pre-commit / commit-msg フックの拒否、GPG 署名設定の
     不備等）→ 手順 6 の「退避の復帰」を行ってからブロックし、原因を報告して中断。勝手に直さない。
   - コミット後、`git rev-parse HEAD^{tree}` が記録したツリー ID と一致しない、または新たな
     未ステージ差分・未追跡が現れた場合のみ、本スキル同フォルダの `hook-rewrite.md` を Read し、
     その規定で続行・取り消し・amend を決める（対処はそのファイルの規定に限る）。それ以外は
     手順 6 へ進む。
   - commit-msg フックがメッセージを書き換えた場合は続行し、結果報告に記録する
     （フックはプロジェクトの意思なので尊重する）。
6. **退避の復帰**: 手順 2 を実行した場合のみ、git stash pop で残りの変更を戻す（実行して
   いなければ何もしない。手順 4・5 から「退避の復帰」として参照される場合も同じ規定）
   - pop の前に git rev-parse stash@{0} が手順 2 で記録したハッシュと一致することを
     確認する（メッセージ一致より確実）。一致しなければ操作せず中断して報告
     （別プロセスが stash を作っている）。
   - pop がコンフリクトした場合（フックの書き換えが退避中の hunk と重なった等）は
     それ以上操作せず中断。コンフリクト状態にあることと stash が保持されたままであることを
     [9] の規定で報告する。
```

- 処理がどこで中断しても、[9] の報告項目（特に stash の残り）を必ず出す。

---

## [8] 最終ツリーでフル検証

全コミット後、最終ツリーに対して **テスト + ビルド** を 1 回実行する。

- 通れば成功。
- **落ちてもコミットは取り消さない**（履歴はそのまま残す）。失敗内容、どのコミット以降が
  疑わしいかの手がかり、対処の選択肢（追いコミットで修正する / `git reset --soft` で
  戻してやり直す）を [9] の未対応・要確認事項に併記して終了する（本スキル内では選択を待たず、
  どちらの対処も実行しない。対処はユーザーの次の指示に委ねる）。
- コミットごとの検証は軽量のみのため、中間コミットが単体でテスト・ビルドを通る保証は
  ない点も報告に明記する。

---

## [9] 結果報告

最後に以下を対話言語（ユーザーとの対話で使っている言語）で報告する:

- 作成したコミット一覧（短縮ハッシュ / 件名）。
- コミットごとの軽量検証・最終フル検証の結果（省略した検証があればその旨と理由）。
- 統合した単位・低信頼で確認した事項・中断した事項など、判断の記録。
- stash に退避が残っている場合はその旨と復旧手順（`git stash list` で確認・`git stash pop` で復旧。手順 6 のコンフリクト時は解消後に `git stash drop`）。中断時も必ず含める。
- 未対応・要確認事項（フル検証が落ちた、署名要否が曖昧だった 等）。
