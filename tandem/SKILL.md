# tandem — 相談役と二人三脚で完遂する

> **明示起動の確認**: ユーザーがこのスキルを名指しで起動した場合のみ実行する。
> 文脈からの自動適用で読み込まれた場合は、実行せずユーザーに起動意思を確認する
> （`disable-model-invocation` を解釈しない実行環境での暴発防止）。

実行エージェント（以下**著者**）が依頼された課題（設計書の作成・コードの変更・意見の統合など）を進めながら、ハーネス1ペイン（以下**相談役**）に各段階のドラフトや問いを投げ、返ってきた指摘・意見の反映までを著者が中継する。

原則は3つ。

- **著者は一人** — 成果物への書き込みはすべて著者が行う。相談役は読み取り調査と応答ファイルへの回答のみ（書かせない）。
- **相手は1ペイン固定** — ループ全体を通して同一ペインへ追送し、相談役側の文脈を保持する。相手を替えたいときはループを終了して起動し直す。
- **新設時は異系統必須** — 新しくペインを立てる相談役は実行中と異なるモデル系統に限る（`--pane` の特例を含む運用は手順 [2] が定める）。

往復の形は2つ。**ラウンド型**（既定。手順 [3]）は毎回ブリーフと応答ファイルで往復し、ラウンドごとに集計・判定する。**直送モード**（`--direct`。手順 [3-D]）は初回だけブリーフで文脈を渡し、以後は著者の追問をペインへ直接送って返答を画面から読む会話で進める。

## tui-harness 参照

ペイン操作・委譲・回収の共通手順は tui-harness を正本とする。作業を始める前に tui-harness の SKILL.md を次の順で探して Read し、このコンテキスト内で適用する — (1) `../tui-harness/SKILL.md`、(2) 実行ハーネス自身のスキルディレクトリをプロジェクト側 → グローバル側の順（Claude Code: `.claude/skills/` → `~/.claude/skills/`、Codex: `.agents/skills/` → `~/.agents/skills/`。他ハーネス用のディレクトリは探さない）。見つからない場合はループを開始せず、復旧手順（`npx skills add tmstack-io/agent-skills --skill tui-harness`）を案内して中止する。

呼び出しパラメータ: 成果物置き場＝一時領域に作る本スキル専用ディレクトリ（作成の時点は手順 [1] 冒頭、後始末は手順 [4] が定める。ブリーフ・応答ファイル・ラウンド間の記録を置く）、push ラベル＝`tandem`、裁定スコープ＝書き込みは成果物置き場のうち当該ラウンドの回答ファイル（ラウンド型は `report-r<k>.md`、直送モードは `report-<n>.md`）のみ＋通信規約の push、読み取りは手順 [3] の2の観点項がブリーフで相談役に許した範囲と同一（正本は同項。`decisions.md`・`rejected.md`・`dialog.md`・ブリーフ・note は著者の一次記録であり、相談役の**書き込み**はスコープ外＝拒否）。直送モードでは tui-harness の「直送委譲」（`direct.md`）を適用し、直送上限＝`--max-text` の値とする。新設ペインの候補検証とモデル系統の確定には tui-harness の「異系統委譲」を適用し、同節の同系統の扱いは本スキルの手順 [2] が定める。既存ペインの採用は tui-harness の「既存ペインの起用」を適用する。

## パラメータ

- **依頼文**: 引数のうち `--` で始まらない自由文。空なら散文提示で依頼内容を確認する。
- **`--cli <CLI名>[=<モデル>[@<エフォート>]]`**（最大1回）: 新設する相談役ペインの CLI とモデル。値の書式の正本は tui-harness の「委譲先指定値の書式」。未指定時は手順 [2] で選んでもらう。2回以上指定された場合は解釈せず、指定値を示して散文提示で再指定を求める（相談役は1体固定）。
- **`--pane [<ペイン指定>]`**: 稼働中の既存ペインを相談役として採用する。ペイン指定は `--pane` の直後の1語（次の空白まで）とし、その語が `--` で始まるか引数末尾なら値省略とみなす（値を省略して依頼文を続ける場合は `--pane` を他のオプションの直前または引数末尾に置く）。指定値の解決・起用ゲート・採用の規律は tui-harness の「既存ペインの起用」に従う。`--cli` との併用は解釈せず、散文提示で再指定を求める（既存ペインのモデル・エフォートは変更できない）。
- **`--direct`**: 直送モード。初回ブリーフの後はラウンド構造を持たず、著者の追問を相談役ペインへ直接送り、返答を画面から読む（規定は手順 [3-D]）。`--cli` / `--pane` のどちらとも併用できる。
- **`--max-text N`**（既定 1000。`--direct` 時のみ有効）: 直送する1メッセージの上限文字数（改行を除く）。超える本文はファイルに書いてパスだけ送る（手順 [3-D]）。正の整数以外が指定された場合、または `--direct` 無しで指定された場合は黙って読み捨てず、散文提示で再指定を求める。
- **`--max-rounds N`**（既定はラウンド型 5・直送モード 10）: ラウンド型では最大ラウンド数、直送モードでは著者の送信回数（初回ブリーフを含む）の上限。正の整数以外が指定された場合は黙って読み替えず、散文提示で再指定を求める。上限到達は失敗ではなく「人間の判断が要る」シグナルとして扱う。

## git への態度

git リポジトリでは、ループは git 履歴に一切触れない。成果物への修正は作業ツリー上に累積させ、コミット・stash・ブランチ作成をしない。コミットは完遂（または妥協終了）後、ユーザーの指示があった場合のみ行う。git が無い環境（`git rev-parse --git-dir` が失敗）で成果物が既存ファイルの変更である場合は、ループ開始前に対象ファイルを同じディレクトリへ `<ファイル名>.tandem-backup` の名前でバックアップし、そのパスを報告する（修正の revert 手段の確保。一時領域に置くと OS の掃除で消えるため成果物と同じ場所に残す）。

## 手順

### [1] 依頼の確定

まず成果物置き場を確定する。依頼文に既存の成果物置き場のパス（`tandem.` で始まる一時ディレクトリで `decisions.md` を含むもの）が含まれる場合は**再開**とし、新規作成せずそのディレクトリを成果物置き場に採用して `decisions.md`（と、あれば `rejected.md`）を読み込み、以下の確定項目とモード（ラウンド型か直送モードか・`--max-rounds` の実効値・`--max-text`）は `decisions.md` の記録を引き継ぎ（依頼文で変更が指示された項目だけ更新する。起動フラグと記録が食い違う場合は記録を優先し、その旨を宣言する）、再開位置は既存のファイルで決める。ラウンド型では `brief-r<k>.md` の最大 k について、対応する `report-r<k>.md` が無ければラウンド k の手順 [3] の3（委譲と回収）から同じブリーフを書き直して上書き送付し、あってもその内容が成果物・`decisions.md`・`rejected.md` に反映済みと確認できなければラウンド k の手順 [3] の4（反映）から、反映済みなら k+1 の手順1から続ける。直送モードでは `dialog.md` を読み、最後の見出し行が `## 送信 1` なら手順 [3-D] の1から（同じ `brief-1.md` を書き直して再送）、`## 送信 <i>`（i ≥ 2）ならその送信を手順 [3-D] の3から再送し、`## 返答 <i>` ならその返答の反映（手順 [3-D] の4）から続ける。`--max-rounds` は継続後の回数に対して適用する（再開前を含めた累計）（再開時の相談役は手順 [2] で `--pane` により残したペインを採用する。`--pane` 無しの再開は新設扱いとなり、相談役側の文脈は引き継がれない。直送モードの新設再開では初回ブリーフの参照資料に `dialog.md` の絶対パスを加え、会話の経緯を読ませる）。含まれなければ `mktemp -d "${TMPDIR:-/tmp}/tandem.XXXXXX"` で新規作成し、パスを控える。次に依頼文から以下を確定する。すべて一意に読み取れれば「この成果物・この完遂条件で進めます」と宣言だけして次へ進み、読み取れない点がある場合のみ散文提示で確認する。

- **成果物と要件**: 成果物はプロジェクト内のファイル（コード・設計書等）か、チャット上の報告のみか。あわせて**成果物の要件**（成果物として満たすべき内容上の条件。対象パスと新規/変更の別を含む）を箇条書きで書き出す。
- **完遂条件の型**: 次の2型のどちらか。
  - **LGTM 収束型**（作成・変更を伴う依頼の既定）: 著者が成果物の要件をすべて成果物に反映し終えており、かつ相談役の指摘（却下済みを除く）がゼロ＝LGTM で完遂。
  - **回収統合型**（意見・見解の収集が主目的で、成果物の収束を要しない依頼）: 相談役の見解を回収・統合して報告したら完遂。
- **成果物言語**: 成果物がファイルなら対象の既存本文・プロジェクト既存文書の言語、判定材料が無ければ対話言語。ここで1回確定し、以後のブリーフ・ドラフトまで同一言語を通す（ユーザーへの提示は対話言語）。
- **参照資料**: 相談役に読み取りを許すプロジェクト内のパス（成果物本体と、依頼に答えるために読むべき資料）を列挙する（無ければ「なし」。この列挙が裁定スコープの読み取り範囲の照合元になる）。
- **検証コマンド**（成果物がプロジェクト内のコードの場合のみ）: プロジェクトの規約文書（Claude Code では CLAUDE.md、Codex では AGENTS.md 等）とビルド設定（package.json のスクリプト・Makefile 等）から検証コマンド（test / lint 等）をここで1回特定する。特定できなければ「検証コマンドなし」と宣言する（その場合の扱いは手順 [3] の「検証」が定める）。
- **相談役ペインの後始末**: 依頼文に相談役ペインを残す指示（「ペインを残して」等）があれば「保持」、無ければ「閉じる」と確定する（手順 [4] の後始末は `decisions.md` の記録を参照する）。
- **モード**: `--direct` の有無でラウンド型か直送モードかを確定し、`--max-rounds` の実効値（指定値、無ければモードごとの既定）と、直送モードでは `--max-text` の値（既定 1000）も確定する。

あわせて成果物置き場に `decisions.md`（**決まったこと** — ユーザーが確定した要件・制約。手順 [3] / [3-D] の設計判断ゲートの正本）を作成し、依頼文と、上記の確定項目のすべて（成果物と要件・完遂条件の型・成果物言語・参照資料・検証コマンド〔コードの場合〕・相談役ペインの後始末・モード〔`--max-rounds` の実効値を含む〕）を初期項目として書く。ラウンド型ではさらに `rejected.md`（**却下履歴** — 却下した指摘と理由。再指摘の防止）を見出しのみで作成する。直送モードでは `rejected.md` を作らず（却下とその理由は会話で相談役に伝え、`dialog.md` に残る）、代わりに `dialog.md`（**往復記録** — 著者が送った本文と相談役の返答の追記専用記録。`## 送信 <i>` / `## 返答 <i>` の見出し行の下に本文を置く形式で、手順 [3-D] が書く）を見出しのみで作成する。

完了条件: 成果物置き場が存在し、成果物と要件・完遂条件の型・成果物言語・検証コマンド（コードの場合）・相談役ペインの後始末・モードを宣言済みで、参照資料を列挙済み（無ければ「なし」と宣言済み）、`decisions.md`（全確定項目を記録済み）と、ラウンド型では `rejected.md`・直送モードでは `dialog.md` が存在し、非 git 環境かつ成果物が既存ファイルの変更の場合は「git への態度」のバックアップを取得してパスを報告済み。

### [2] 相談役の確定

1. tui-harness の `mux.sh detect` が検証済みバックエンドを返さなければ、TUI マルチプレクサが要る旨を案内して中止する（本スキルは TUI 専用）。直送モードで `backend=cmux` の場合は、直送委譲が cmux で未実測である旨を示してここで中止する（ラウンド型への縮退はしない）。
2. **`--pane` あり**: tui-harness の「既存ペインの起用」で解決・起用ゲート・採用の記録を行う。ゲート不成立は中止する（別候補への差し替え・新設への縮退はしない）。指揮者ペイン ID（以後の全ブリーフの通信規約に記載する値）の取得と self 非0時の確認は、同節の解決手順に従う。モデル系統は同節の準用規則で確定を試み、実行中と同系統または系統不明の場合は、その旨を採用宣言に明記して続行する（異系統必須の特例。系統不明時に散文提示での確認を求める tui-harness「既存ペインの起用」手順3の規定に代えて、本規定を適用する）。既存文脈は相談役の予備知識として受け入れる（採用宣言での明記は手順4）。
3. **`--pane` なし（新設）**: tui-harness の「委譲先の確定と検証」と「異系統委譲」に従う。実行中の系統を確定し、`catalog.sh probe` と `catalog.sh models` の結果から**実行中と異系統のモデルを持つ候補のみ**を散文提示して選んでもらう（同系統のモデルしか無い CLI は候補に載せない）。`--cli` の指定値が同系統に確定した場合は起用せず、tui-harness 本則の再指定（合計2回）に従う。異系統の候補が1つも無ければ、除外理由と復旧方法を示して中止する（同系統への縮退はしない）。
4. **採用宣言**: 相談役の CLI・モデル（採用ペインでは判明した範囲）・モデル系統（同系統特例はその旨）・成果物置き場・専有の注意（ループ中はこのペインへ直接入力しない。採用ペインと直送モードの新設ペインで宣言する）・採用ペインでは無関係な既存文脈による汚染リスクの一言を1ブロックで宣言する。

完了条件: 相談役が確定し採用宣言を出力済み、または中止を報告している。

### [3] 往復ラウンド（ラウンド型。`--direct` 時は [3-D] を適用する）

1ラウンド＝著者の前進 → ブリーフ送付 → 応答回収 → 反映。

**検証**（完遂条件の型を問わず、ラウンド中の全工程に適用）: 成果物へ変更を入れたら、成果物がコードなら手順 [1] で特定した検証コマンドを実行して緑を確認してから次の工程へ進む。赤の場合は著者が原因を修正して再実行する。修正と再実行は同一ラウンドにつき合計3回までとし、3回目も赤ならループを止め、失敗内容と対応方針を散文提示でユーザーに相談する（回答が修正方針の指示なら同一ラウンドの検証からやり直し、終了の指示なら妥協終了として [4] へ進む）。検証コマンドが無い場合（「検証コマンドなし」宣言時・設計書等の該当しない成果物）は検証をスキップする（スキップした旨は手順 [4] の報告項目で報告する）。

ラウンド k について:

1. **著者の前進** — 初回は、著者が成果物の要件を満たすドラフトを書き上げる（成果物がファイルで未作成なら初版を作成し、チャット完結の課題なら見解・論点のドラフトを書き起こす）。2回目以降は、前ラウンドの反映が終わった状態を確認してから進む（反映漏れの要件があればここで反映する）。
2. **ブリーフ作成** — 初回のみ、新設ならブリーフを書く前に tui-harness の「ペイン配置」「ペインの起動」を実行する（通信規約に記載する指揮者ペイン ID と相談役ペインをここで確定させるため）。起動したペインが入力待ち（idle）に達しない場合は、相談役を差し替えずにループを停止し、手順3の失敗規律と同じ項目を報告する。成果物置き場に `brief-r<k>.md` を書く。ブリーフの内容は次の一覧を正本とし、tui-harness「タスクの委譲」手順1の記載要件（委譲する作業の記述・回答/報告ファイルの絶対パス・通信規約）はこの一覧で満たす:
   - 依頼の要約と今回求めるもの（初回は課題の全体像と現時点の論点。2回目以降は前回指摘への対応結果の一覧と再確認の依頼。相談役はペインの文脈を保持しているため、前回までの内容は再掲せず差分だけを書く）
   - 現時点の成果物 — ファイルなら絶対パス（読み取り調査可と明示）、チャット完結の課題ならドラフト・論点の全文
   - 回答ファイルの絶対パス — `<成果物置き場>/report-r<k>.md`
   - 参照資料 — 手順 [1] で列挙したパスの一覧（読み取り調査可と明示。無ければ「成果物本体のみ」と書く）
   - 決まったこと（`decisions.md` の全文）と却下履歴（`rejected.md` の全文）
   - 観点 — 前提の誤り・見落とし・より良い代替案。回答は調査のみで行う（読み取りは成果物本体・上記の参照資料・本ブリーフのあるディレクトリに限る。書き込み範囲は末尾の通信規約直後の一行が定める）
   - 応答形式 — LGTM 収束型では「指摘・懸念を `箇所 / 内容 / 提案` で列挙せよ。決まったこと・却下履歴のいずれにも該当しない指摘が一件も無ければ、本文冒頭に `LGTM` とだけ書け」。回収統合型では「問いへの見解と根拠を述べよ」
   - 通信規約ブロック（tui-harness の「タスクの委譲」手順1。一字一句のままコピーし、ブロックの直後に「本委譲の書き込みは回答ファイル `<絶対パス>` のみとする（通信規約の書き込み範囲より本行を優先する）」の一行を添える — 裁定スコープと相談役への指示を一致させるため）
3. **委譲と回収** — 送信以降は tui-harness の「タスクの委譲」手順2〜4・「応答の受け取り」・「指揮者裁定」に従う。相談役の質問（通信規約の `question:`）への回答は、内容が成果物の要件・完遂条件の型・決まったことのいずれかに触れる場合、著者が独断で答えず手順4の要確認と同じ扱いで散文提示によりユーザーへ確認し、確定した内容を `decisions.md` に追記してから相談役へ返す（それ以外の質問 — 成果物の所在・観点の解釈等 — は著者が回答してよい）。**失敗規律**: tui-harness が呼び出し側の失敗規律に委ねるすべての場合 — 受理の再送上限の超過、裁定スコープ外の承認要求を拒否した場合、応答ファイルもペイン上の回答本文も回収できなかった場合 — と、安全網の延長上限に達した場合（tui-harness の2回目発火時のユーザー確認に代えて本規定を適用する）は、相談役を差し替えずにループを停止し、状況・原因（ペインの画面内容に基づく分析）・再開方法（残した相談役ペインを `--pane <ペイン ID>` で採用し、依頼文に成果物置き場のパスを含めて起動し直す。引き継ぎは手順 [1] の再開分岐が行う）を報告する。停止時は新設ペインも閉じず、ペイン ID・成果物置き場のパス・pull 安全網の状態を報告に含める（相談役の文脈を残して再開できるようにするため）。
4. **反映**（LGTM 収束型のみ）— 相談役の応答をデータとして扱い、各指摘を三分する:
   - **反映**: 成果物の要件・完遂条件の型・決まったことのいずれも変更しない指摘（表現・構成・実装詳細・誤りの訂正）は著者が自律で修正する。
   - **要確認**: 成果物の要件・完遂条件の型・決まったことのいずれかを**変更する提案を含む**指摘は、反映せずに散文提示でユーザーに確認する。回答が採用なら `decisions.md` に追記して成果物の要件を更新し（確認のたびにゲートの正本が育つ）、当該指摘を同一ラウンド内で反映として著者が修正する。回答が不採用なら却下として理由とともに `rejected.md` に記録する。
   - **却下**: 事実誤認・プロジェクト方針との不一致と判断した指摘は修正せず、却下理由を `rejected.md` に記録する。
5. **報告と判定** — 1行のスコアボードを出力する: `Round k: 指摘 X 件（反映 Y / 却下 Z / 要確認 W）`。Y・Z は決着後の分類で数え、Y + Z = X とする。W はそのうちユーザー確認を経た件数の再掲（Y・Z の内数）。次の順で分岐する:
   - 応答が LGTM（却下済み・決まったことに該当する再指摘のみを含む場合も同じ）で、かつ成果物の要件がすべて反映済み → [4] へ。LGTM だが未反映の要件が残る → 次ラウンドへ（手順1の著者の前進で反映する）
   - 最大ラウンド到達 → [4] へ（妥協終了）
   - 同一の指摘（同じ箇所かつ同趣旨）が2ラウンド連続で未解消 → ループを止め、その指摘と対応方針を散文提示でユーザーに相談する（停滞ガード。著者と相談役の見解対立の脱出口）。回答は `decisions.md` に追記して次ラウンドへ戻る（ラウンド数は継続してカウントする）。回答が終了の指示なら妥協終了として [4] へ進む
   - それ以外 → 次ラウンドへ

**回収統合型の縮約**: ラウンド1で見解を回収し、統合に必要な不明点への追い質問がある場合のみ追加ラウンドを回す（`--max-rounds` の範囲内）。見解の統合をチャットに報告したら [4] へ進む。

完了条件: 各ラウンドでスコアボード（回収統合型では回収完了の1行）を出力し、上記分岐のいずれかを選択済み。

### [3-D] 直送モードの往復（`--direct` 時。[3] の代わりに適用する）

初回だけブリーフで文脈を渡し、以後は著者の追問を相談役ペインへ直接送って返答を画面から読む会話で進める。ペイン操作・送信長の判定・返答の受け取りの正本は tui-harness の「直送委譲」（`direct.md`）で、直送上限＝`--max-text`。ラウンド型のスコアボード・停滞ガード・`rejected.md` は使わない。[3] 冒頭の**検証**（成果物を変更したら検証コマンドで緑を確認。3回赤なら散文提示で相談）はそのまま適用する。手順の流れは 1 → 4 → 5 で、5 が継続を選ぶたびに 2 → 3 → 4 → 5 を繰り返す。送信回数 i は初回ブリーフを 1 として数える。

1. **初回ブリーフ** — 新設なら tui-harness の「ペイン配置」「ペインの起動」を実行してから、成果物置き場に `brief-1.md` を書く。内容は [3] の2の一覧から**回答ファイルの絶対パス**と**却下履歴**の2項目を除いたもの（依頼の要約・現時点の成果物・参照資料・決まったこと・観点・応答形式）とし、通信規約は往復委譲のブロックではなく `direct.md` の**直送通信規約**を一字一句そのままコピーして `<直送上限>` に `--max-text` の値を入れ（`<n>` は枠のまま残す）、その直後に「本委譲で作成・編集してよいファイルは `<成果物置き場>/report-<n>.md`（n は上の規約どおり委譲先が採番）だけとする（直送通信規約の書き込み範囲より本行を優先する。回答の既定の出力先はペインであり、本行はファイルを作る場合の制限である）」の一行を添える。応答形式は LGTM 収束型では「指摘・懸念を `箇所 / 内容 / 提案` で列挙せよ。決まったことに該当しない指摘が一件も無ければ、本文冒頭に `LGTM` とだけ書け」、回収統合型では「問いへの見解と根拠を述べよ」。`dialog.md` に `## 送信 1` の見出しと `brief-1.md` の絶対パスを追記してから、送信・受理・初回返答の回収を `direct.md`「初回の委譲（ブリーフ）」に従って行い、4 へ進む。
2. **著者の前進** — 直前の返答を反映し終えた状態を確認してから、成果物を進める（未反映の要件があればここで反映する）。次に相談役へ送る本文（返答への応答・追問・却下とその理由・決まったことへの追記の通知・相談役の質問への回答）を書き起こす。
3. **送信** — `dialog.md` へ `## 送信 <i>` の見出しと本文全文（note 経由ならそのパス）を追記してから、`direct.md`「追送（2通目以降）」に従って送る（送信長の判定と note 経由の一行の形は同節が正本）。受理の再送上限を超えた場合は失敗規律（後述）へ。
4. **返答の受け取りと反映** — `direct.md`「返答の受け取り」で返答を回収し、`dialog.md` へ `## 返答 <i>` の見出しと返答全文（report ファイル経由ならそのパス）を追記する。返答の各指摘は [3] の4と同じ三分（反映・要確認・却下）で扱う。要確認は散文提示でユーザーに確認し、採用なら `decisions.md` に追記して次の送信で相談役に「決まったことに追加: …」と伝え、不採用なら却下として理由を次の送信で伝える（`rejected.md` には書かない）。却下も同様に理由を次の送信で伝える。相談役の質問（返答中に現れる）は、内容が成果物の要件・完遂条件の型・決まったことに触れる場合は要確認と同じ扱いでユーザーに確認し、それ以外は著者が次の送信で答える。
5. **終了判定** — 次の順で分岐する:
   - LGTM 収束型: 成果物の要件がすべて反映済みで、かつ直近の返答が LGTM（または決まったことに該当する再指摘のみ）→ [4] へ。
   - 回収統合型: 統合に必要な不明点が無くなった → 見解の統合をチャットに報告して [4] へ。
   - 上記の終了に至らず、送信回数 i が `--max-rounds` に達している（i 回目の返答の反映まで終えた状態）→ [4] へ（妥協終了）。
   - それ以外 → 2 へ戻る（回収統合型では追い質問を送る）。

**失敗規律**: [3] の3の失敗規律と同じ。ただし「応答ファイルもペイン上の回答本文も回収できなかった場合」は「`direct.md`「返答の受け取り」で返答を切り出せなかった場合」と読み替え、安全網の延長上限の扱いは `direct.md` の2回目発火時のユーザー確認に代えて適用し、再開の引き継ぎは `dialog.md` が担い（手順 [1] の再開分岐）、pull 安全網は前面同期のため報告項目から外す。

完了条件: `dialog.md` に全送信と全返答が `## 送信 <i>` / `## 返答 <i>` の対で記録され、終了判定のいずれかを選択済み。

### [4] 完遂報告と後始末

次を含めて報告し、ループを終える:

- 成果物（ファイルならパス、チャット完結なら本文）と総ラウンド数（直送モードでは総送信回数と `dialog.md` のパス）
- LGTM か妥協終了かの別（妥協終了なら未解消指摘の一覧と対応方針案、および未反映のまま残った成果物の要件の一覧）。回収統合型では統合結果
- 却下した指摘と理由（直送モードでは `dialog.md` から集める）、要確認で確定した事項
- 検証コマンドの結果（またはスキップした旨）
- 非 git 環境で取ったバックアップのパス（該当する場合）
- 相談役の内訳: CLI・実測モデル・モデル系統（同系統特例ならその旨）・新設か採用ペインかの別

後始末: 新設ペインは tui-harness の「クローズ」手順で**ユーザーへの確認なしに閉じる**（手順 [1] で後始末を「保持」と確定していた場合のみ保持し、保持した旨とペイン ID を報告する）。`--pane` の採用ペインの後始末は tui-harness「既存ペインの起用」の規定に従う（閉じない）。成果物置き場（一時領域）は削除せず OS の掃除に委ねる。

完了条件: 上記の全項目を報告し、新設ペインを閉じた場合は `mux.sh list` に存在しないことを確認した（採用ペイン・保持指示ありの場合はこの確認は不要）。
