# tandem 代理実行型（`--invoke`）（正本）

SKILL.md 手順 [1] のポインタから読まれる規定の正本。`--invoke` 指定時に、手順 [1] の確定・手順 [3-I] の往復・手順 [4] の報告項目と新設ペインの後始末をここに従って行う。

**代理実行型**は、依頼文でユーザーが名指ししたスキル（明示起動専用のスキル＝モデル自身による起動を禁じたスキルを含む）を、相談役ペインの入力欄へ起動文を送って起動し（**代理起動**）、スキルが求める承認・回答に応じながら結果を回収して報告する型である。送受信は tui-harness の「直送委譲」（`direct.md`）の「追送（2通目以降）」と「返答の受け取り」を使い、初回ブリーフと直送通信規約は使わない（最初の送信は起動文そのもの。起動の前にスキルと無関係な文脈をペインに足さないため）。

原則は3つ（SKILL.md の「著者は一人」に代わる）。

- **起動するスキルはユーザーが名指しする** — 起動文にしてよいのは、依頼文で名指しされたスキルだけ。著者は依頼文の対象から起動文を組み立てて入力を代行し、どのスキルを使うかを選ばない。
- **書き込みは起動したスキルが行う** — ペインでの書き込み・外部操作は起動したスキルの規定に従って行われ、著者は承認ダイアログを裁定スコープで裁定する。
- **回答は方向性の指示に基づく** — スキルが求める承認・回答は、ユーザーが方向性を指示している場合（依頼文、または実行中の確認への回答に含まれた追加指示）に限り、著者がその指示に基づいて推論して答える。指示が無い・指示から判断できないものは散文提示でユーザーに確認する。

**送信回数**: 起動文1つあたりの送信回数は、その起動文自体と、それに続いて `mux.sh submit` で送った回答文を数える（承認ダイアログへのキー応答は数えない）。上限は `--max-rounds` の実効値（代理実行型の既定は 10。本項が正本）。

## 依頼の確定

1. SKILL.md 手順 [1] と同じ方法で成果物置き場を新規作成し、パスを控える（代理実行型は `resume.md` の再開を使わない。再開は失敗規律・報告の再開方法による）。
2. 依頼文から次を確定する:
   - **作業単位と起動の一覧**: 依頼文で名指しされたスキルと対象から、互いに独立した対象ごとのまとまり（例: PR 1件）を**作業単位**とし、各単位で起動するスキル名と引数を依頼文の順に並べる。引数は依頼文に書かれた対象と指定だけから組み立てる。同じ単位の起動は同じセッションで順に実行する（後の起動が前の出力を前提にしうるため）。起動文への組み立ては相談役の確定後に「代理実行」の1で行う。
   - **回答の方向性**: スキルが求める承認・回答について、依頼文が指示する方針（例:「投稿は BLOCKER と HIGH だけ」）。無ければ「指示なし」。
   - **裁定スコープ**: 著者が承認ダイアログを許可してよい書き込み先とコマンドの範囲。依頼文の指定に限り、指定が無ければ空とする（著者が推測で広げない）。
   - **相談役ペインの後始末**: 依頼文に保持の指示があれば「保持」、無ければ「完遂時に判断」。
   - **上限**: `--max-rounds` と `--max-text` の実効値。
3. 次のいずれかに当たる場合は、散文提示で確認してから確定する: 依頼文にスキル名が無い（著者はスキルを補わない）、起動の対象・引数が一意に読み取れない、作業単位の分け方が一意に決まらない。
4. 成果物置き場に `decisions.md`（「モード: 代理実行型」の一行と、依頼文と上記の確定項目のすべて。以後、確認の回答に含まれた方向性の追加指示を追記する）と `dialog.md`（見出しのみ）を作成し、作業単位と起動の一覧を宣言する。一意に読み取れた場合は返答を待たずに SKILL.md 手順 [2] へ進む。

完了条件: 成果物置き場が存在し、作業単位と起動の一覧・回答の方向性・裁定スコープ（空を含む）・ペインの後始末・上限を宣言済みで、`decisions.md` と `dialog.md` が存在する。

## 相談役の推奨

SKILL.md 手順 [2] の新設候補ごとに、名指しされた全スキルがそのハーネスのスキルディレクトリ（プロジェクト側 → グローバル側。Claude Code では `.claude/skills/` → `~/.claude/skills/`、Codex では `.agents/skills/` → `~/.agents/skills/`）に見つかるかを確認し（プロジェクト側は相談役ペインの作業ディレクトリ — 新設ではペインを起動する予定のディレクトリ — を起点にする。スキルディレクトリの場所が分からないハーネスは「確認できない」として推奨の対象から外し、その旨を示す）、全スキルが見つかる候補を推奨する（実行中と同じハーネスが該当すれば、それを第一の推奨とする）。該当する候補が無ければ「推奨なし」とし、見つからなかったスキル名を理由として示す（プラグイン経由など上記ディレクトリの外にあるスキルは、ユーザーの選択で起用できる）。

## 裁定スコープ

承認ダイアログは tui-harness の「指揮者裁定」で、上記で確定した裁定スコープと照合する。スコープ内は許可する。スコープ外は、ダイアログの内容（対象パス・コマンド）を示して散文提示で許可するか確認し、回答どおり許可または拒否を送る（tui-harness の範囲外＝拒否の規定に代えて本規定を適用する）。

## 代理実行

1. **スキルの確認とペインの準備** — `--cli` 指定・採用ペイン・推奨外の候補を選んだ場合は、ペインを立てる前に「相談役の推奨」と同じ方法で名指しされた全スキルを確認し、見つからない（または確認できない）スキルがあれば、そのスキル名を示して散文提示で起動してよいか確認する。起動しないと回答されたスキルの起動は未実行として `dialog.md` に記録し、残りの起動で続ける（全起動が未実行になる場合はペインを立てずに中止を報告する）。次に、新設なら tui-harness の「ペイン配置」「ペインの起動」を実行する。起動したペインが入力待ちに達しない場合は、そのペインを tui-harness の「クローズ」手順で閉じ、全起動文を未実行としてループを停止し、その旨を報告する（再開は `--pane` 無しの新規の起動で行う）。採用ペインは既存の文脈を保ったまま最初の単位を始め、採用宣言にその旨を含める（中止後の再開では、同じ単位の前の起動文の出力を後の起動文が前提にしうるため）。最後に、各起動を相談役ハーネスの明示起動の構文で起動文に組み立てる（Claude Code では `/<スキル名> <引数>`）。構文が分からない場合、または起動文が直送上限（`--max-text` の実効値）を超える場合は、散文提示で確認する（note 経由の一行に置き換えると起動文として解釈されないため）。
2. **起動文の送信** — 作業単位の順、単位内は起動文の順に、1つずつ処理する。`dialog.md` に `## 単位 <u> / 起動文 <k> / 送信 <i>` の見出しと本文を追記してから、`direct.md`「追送（2通目以降）」に従って送る（i は起動文ごとに 1 から数える）。
3. **画面の判別** — `direct.md`「返答の受け取り」で待って画面を読む（blocked は上記「裁定スコープ」で裁定する。working の2回目発火は、SKILL.md 手順 [3] の失敗規律ではなく tui-harness 本則どおり散文提示でユーザーに確認する — スキルの実行は相談より長くかかりうるため）。入力待ちの画面を、直前の送信のエコーより後ろの出力で次のいずれかに分類し（複数に当たる場合は上に書いたものを優先する）、`dialog.md` に `## 単位 <u> / 起動文 <k> / 返答 <i>` として分類と要旨を追記する:
   - **確認の要求**（スキルがユーザーに選択・承認・回答を求めて止まっている）→ 回答の方向性から答えが一意に決まり、かつテキストで答えられる問いなら、その答えを次の送信として 2 の形で送る（`dialog.md` に根拠とした方向性を併記する）。それ以外は、スキルの問いをそのまま示して散文提示でユーザーに確認し、回答を送る（キー操作で選ぶ UI なら `mux.sh answer` / `mux.sh key` で送る）。回答に方向性の追加指示が含まれていれば `decisions.md` に追記する。
   - **中止**（スキルが中止・失敗を報告している）→ 原因を `dialog.md` に記録し、その単位の残りの起動文を未実行として 4 へ進む。
   - **完了**（スキルが最終出力・完了報告を出している）→ 結果の要旨（出力の所在・主な結論・外部への書き込みがあればその URL 等）を `dialog.md` に記録し、単位内の次の起動文へ進む。
   - **継続中**（スキルがバックグラウンドの作業やペインからの通知を待っていると画面に示している）→ `mux.sh agent-wait "$PANE" --until working 1800000` でペインが作業を再開するまで待ってから、3 の待ちに戻る。この待ちが時間切れになったら判別不能として扱う。
   - **判別不能**（上のどれに当たるか決められない）→ 画面の要旨を示して散文提示でユーザーに確認し、回答に従う。
   送信回数が上限に達した起動文で、さらに送信が必要になった場合は、その起動文を中止として扱う。
4. **単位の区切り** — 単位内の全起動文が完了・中止・未実行のいずれかとして `dialog.md` に記録済みであることを確認する。次の単位があれば、ペインが入力待ちであることを確かめてから（採用ペインでは、最初の区切りの前に一度、既存の文脈が消えることを示して散文提示でリセットしてよいか確認し、その回答を以後の区切りに適用する。拒否された場合はリセットせずに次の単位へ進む）、相談役ハーネスの文脈リセットのコマンド（Claude Code では `/clear`）を `mux.sh submit` で送り、ペインが入力待ちに戻ったことを確かめてから次の単位の 2 へ進む（前の単位の出力が後の単位に混ざり、文脈が膨らむのを防ぐため）。入力待ちでない場合と、相談役ハーネスの文脈リセットのコマンドが分からない場合は、散文提示でユーザーに確認する。

**失敗規律**: 受理の再送上限の超過、または返答を画面から切り出せなかった場合は、ペイン自体が使えないため残りの単位も実行せずループを停止し、状況・原因（ペインの画面内容に基づく分析）・ペイン ID・成果物置き場と `dialog.md` のパス・未実行の起動文の一覧・再開方法（残したペインを `--pane <ペイン ID> --invoke` で採用し、未実行分だけを名指しした依頼文で起動し直す）を報告する。停止時はペインを閉じない。

完了条件: 全作業単位について、各起動文が完了・中止・未実行のいずれかとして `dialog.md` に記録されている、または失敗規律で停止を報告している。

## 完遂報告と後始末

次を含めて報告する:

- 作業単位ごとの結果: 各起動文の完了・中止・未実行の別、完了なら結果の要旨、中止なら原因と再開方法（再開方法は「失敗規律」の再開方法と同じ）
- 著者が回答の方向性に基づいて答えた回答の一覧（根拠とした方向性つき）と、ユーザーに確認して決めた事項
- `dialog.md` のパス

新設ペインの後始末: 後始末が「保持」なら保持する。「完遂時に判断」なら、全単位の結果を報告に収め終え、かつユーザーの確認が要る事項が残っていない場合に tui-harness の「クローズ」手順で閉じる。ユーザーがペインで確認すべき事項がある、または閉じるとペインのセッションにしか無い情報（後続の操作が前提にする出力等）が失われる場合は保持し、保持した理由とペイン ID を報告する。相談役の内訳・採用ペインと成果物置き場の後始末・完了条件は SKILL.md 手順 [4] を適用する。
