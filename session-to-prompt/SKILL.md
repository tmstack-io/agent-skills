# session-to-prompt — セッション内容から実装プロンプトを生成

現在のセッションで議論・決定した内容を整理し、コンテキストを持たない宛先（新規セッション / Workflow / Claude Code Goal / codex。Workflow と Goal は Claude Code 上で実行している場合のみ選択肢になる — Step 2 参照）がそれだけで実装を開始できる、自己完結した実装プロンプトを生成して保存する。

引数が与えられた場合はそのトピックに絞って抽出する。省略時はセッション全体から実装対象を特定する。

## 大原則

- **捏造禁止**: プロンプトに書いてよいのは、セッションで実際に議論・決定された内容、コードベースから検証できる事実、Step 3 でユーザーが回答した内容のみ。推測で仕様を補完しない。
- **fail fast**: セッションから実装対象が特定できない場合（雑談のみ、調査のみで実装方針が未定 等）は、プロンプトを生成せずその旨を明確に伝えて停止する。空虚な汎用プロンプトを出力しない。
- **自己完結性**: 新規セッションはこのセッションの記憶を一切持たない。「さっき話した通り」「例の件」のような参照は禁止。ファイルパス・シンボル名・コマンドは具体的に書く。

## 実行フロー

### Step 1: セッション分析

会話全体を振り返り、以下を抽出する:

1. **実装対象と目的** — 何を作る/直すのか、なぜか
2. **決定事項と理由** — 採用した設計・方針と、その根拠
3. **却下された代替案** — 検討したが採らなかった案と却下理由（新セッションでの蒸し返し・再発明を防ぐため必須）
4. **対象ファイル・シンボル** — 触るべきファイルパス、関数名、既存の類似実装
5. **制約・規約** — このセッションで明示されたプロジェクト固有ルール（グローバル CLAUDE.md 由来の一般則はテンプレートの「規律」定型ブロックで再掲するため、ここには固有・セッション固有の制約のみ）
6. **プロジェクト固有の罠** — プロジェクトの CLAUDE.md / `.claude/rules/` / docs から、実装時に踏みやすい落とし穴を収集（例: 「worker は dist 実行のため要 `npm run build`」）
7. **検証方法** — テスト・Lint・ビルドの実コマンド（package.json 等から実在を確認する）
8. **不足している判断点** — 実装指示として曖昧さが残る箇所のリスト（Step 3 の質問候補）

プロンプトに含めるファイルパスとコマンドは、可能な限りファイル探索・読み取り（Claude Code では Glob / Read）と package.json 等の参照で実在を確認する。

### Step 2: 実行手段と保存先の確認（1回で2問）

**必ずユーザーに選択式で確認する。** Claude Code では AskUserQuestion を使い、1回の呼び出しで以下の2問を聞く。同等ツールが無い環境では、散文で2問を選択肢の列挙つきで提示して回答を待つ（その場合も2問構成・選択肢・「（推奨）」の付与は維持する）。選択式を経ずに地の文の曖昧な質問で済ませない。

**問1: 実行手段** — 実行環境で成立する手段だけを提示する: **Workflow と Claude Code Goal は、Claude Code 上で実行している場合のみ選択肢に含める**。それ以外の環境（codex 等）では、新規セッション直実装と codex のみを提示する。セッション内容から最適な手段を推定し、その選択肢を先頭に置いて末尾に「（推奨）」を付ける。推定基準:

| 手段 | 向いているケース |
|---|---|
| 新規セッション直実装 | スコープが明確で、1セッションの対話的実装で完結する標準的なタスク（Claude Code / codex どちらの新規セッションも宛先にできる） |
| Workflow（マルチエージェント） | 独立したサブタスクに分割でき、並列実行や網羅性（多角レビュー・大規模移行）が効くタスク |
| Claude Code Goal | 長時間かかり、バックグラウンドで非対話に進めたいタスク |
| codex | 仕様が確定済みで、Codex が単体・非対話で実装完走できる粒度まで固まっているタスク |

**問2: 保存先** — 以下の選択肢を提示。リポジトリ内にプロンプト置き場の既存慣習（`docs/prompt/` 等）があればそれを先頭にして「（推奨）」を付ける。

- リポジトリ内（既存慣習のディレクトリ。なければ `docs/prompt/`）
- `/tmp` 直下
- セッションの一時領域

### Step 3: 不足情報の質問（必要時のみ）

Step 1 で挙げた不足判断点のうち、**選択された実行手段でプロンプトを書くうえで実際に必要なものだけ**をユーザーに選択式で質問する（Claude Code では AskUserQuestion。同等ツールが無い環境では散文で選択肢つきで質問し、回答を待つ）。手段確定後に行うのは、必要な質問が手段で変わるためである（例: Goal なら非対話前提なので判断保留を許さず全て確定させる必要があるが、直実装なら軽微な点は新セッションに委ねられる）。

- 1回の呼び出しに最大4問。原則1回、どうしても必要な場合のみ2回まで。
- 各質問に、コードベースやベストプラクティスから導ける推奨案があれば、その選択肢を先頭に置き「（推奨）」を付け、description に理由を書く。
- 不足がなければこのステップは丸ごとスキップする。
- 質問してもユーザーが保留した点は、繰り返し聞かずプロンプトの「未決事項」セクションに明記する。

### Step 4: プロンプト生成・保存

ファイル名: 保存先ディレクトリに既存のプロンプトファイルがあればその命名慣習に従う（例: `{number}-{description}.md` の連番なら次番号を採番）。慣習がなければ `YYYYMMDD-<内容を表す英語slug>-prompt.md`（日付は `date +%Y%m%d` で取得）。保存先ディレクトリが存在しなければ作成する。

以下のテンプレートに従って生成する（「未決事項」は該当がある場合のみ。それ以外のセクションは必須）:

```markdown
# <タスクタイトル>

<!-- 生成: YYYY-MM-DD / 元: <プロジェクト名> のセッション / 実行手段: <選択手段> -->

## 目的とゴール

<何を達成するか1〜3文。続けて、検証可能な完了条件を箇条書きで。
「〜を修正する」ではなく「`npx vitest run test/...` が通る」「`/cmd` 実行で〜が出力される」の形>

## 背景・経緯

<新セッションが前提を理解できる最小限の経緯。このファイル単体で完結させる>

## 決定事項と理由

<採用した設計・方針を「決定 / 理由」の対で列挙>

### 却下した代替案

<検討したが採らなかった案と却下理由。再提案・再検討は不要である旨を明記>

## スコープ外

<今回やらないことを明記（隣接リファクタ、関連機能の先回り実装 等）>

## 実装方針・手順

<「ステップ → そのステップの検証方法」の対で記述>

## 対象ファイル

<実在確認済みのパス・シンボル名。必要なら参照すべき既存実装や重要な snippet>

## 規律

<以下の定型を必ず含める。宛先が codex の場合はグローバルルールが読み込まれない前提のため一切省略しない>

- **fail fast**: 実行を安全に継続できない場合は曖昧に進めず、明示的なエラーで即停止する。明示的な指示なく後方互換・互換レイヤー・暗黙のフォールバックを実装しない。例外・エラーを握り潰さない。
- **検証ゲート**: typecheck / lint / test / build を全て緑にしてから完了とする（実コマンドは「検証方法」参照）。
- **完了報告**: 何を・なぜ・影響範囲・実施した検証・未対応/要確認事項を日本語で報告する。
- **コミット方針**: 指示があるまでコミットしない。コミットメッセージは日本語、Co-Authored-By 等の署名行は含めない。
- **プロジェクト固有の罠**: <Step 1 で収集した罠を列挙。なければこの行ごと省く>

## 制約・規約

<プロジェクト固有・タスク固有の制約のみ>

## 検証方法

<実在確認済みのテスト・Lint・ビルドコマンドと、期待される結果>

## 未決事項

<確定できなかった判断点と、判断を委ねる際の指針>

## 起動方法

<テンプレート直後の「手段別の『起動方法』セクション」を参照して記述>
```

**手段別の「起動方法」セクション:**

- **新規セッション直実装**: 「新規セッションで `このファイルを読んで実装してください: <パス>` と指示する」旨を記載。
- **Workflow**: Workflow は明示オプトインが必要なため、新セッションへの指示文に「ワークフローを使って」の文言を含めた起動指示を記載。加えて推奨フェーズ分割案（何を並列化し、何を検証フェーズにするか）を本文に含める。
- **Claude Code Goal**: バックグラウンド・非対話実行のため、途中でユーザーに質問できない前提を明記。未決事項が残っている場合はデフォルト判断の指針を必ず併記し、Goal への投入文（目的+完了条件の簡潔版）を冒頭に付ける。
- **codex**: Codex は Claude Code のグローバルルール（`~/.claude/CLAUDE.md` / `.claude/rules/`）を読まないため、「規律」定型ブロックを省略なしの全文で織り込む。単体で実装完走できる粒度まで手順を具体化し、判断保留を許さない（未決事項にはデフォルト判断の指針を必ず併記）。起動例 `codex "このファイルを読んで実装してください: <パス>"` を記載。

### Step 5: 報告

以下を最終メッセージで提示し、**自動では何も起動しない**:

1. 保存したファイルの絶対パス
2. 選択手段での起動手順（コピペ可能な形）
3. プロンプトの要点（目的・完了条件・未決事項の有無）を3行程度

## 品質チェック（保存前の自己検証）

- [ ] 新セッションがこのファイル**だけ**で作業を開始できるか（外部参照・暗黙の前提がないか）
- [ ] 完了条件は機械的または客観的に検証可能か
- [ ] ファイルパス・コマンドは実在を確認したか
- [ ] セッションにない情報を捏造していないか
- [ ] 却下案とスコープ外が書かれているか（新セッションの暴走・蒸し返し防止）
- [ ] 「規律」定型ブロックが含まれているか（codex 宛先は省略なしの全文か）
