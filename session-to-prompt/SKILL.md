# session-to-prompt — セッション内容から実装プロンプトを生成

現在のセッションで議論・決定した内容を整理し、コンテキストを持たない宛先（新規セッション / Workflow / Claude Code Goal / codex。Workflow と Goal は Claude Code 上で実行している場合のみ選択肢になる — Step 2 参照）がそれだけで実装を開始できる、自己完結した実装プロンプトを生成して保存する。

引数が与えられた場合はそのトピックに絞って抽出する。省略時はセッション全体から実装対象を特定する。

**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨する選択肢を理由一言つきで明示し（推奨できる選択肢が無い場合は「推奨なし」とその理由を明示する）、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。

## 大原則

- **捏造禁止**: プロンプトに書いてよいのは、セッションで実際に議論・決定された内容、コードベースから検証できる事実、Step 3 でユーザーが回答した内容のみ。推測で仕様を補完しない。
- **fail fast**: セッションから実装対象が特定できない場合（雑談のみ、調査のみで実装方針が未定 等）は、プロンプトを生成せずその旨を明確に伝えて停止する。空虚な汎用プロンプトを出力しない。
- **自己完結性**: 新規セッションはこのセッションの記憶を一切持たない。「さっき話した通り」「例の件」のような参照は禁止。ファイルパス・シンボル名・コマンドは具体的に書く。

## 実行フロー

### Step 1: セッション分析

会話全体を振り返り、以下を抽出する:

1. **実装対象と目的** — 何を作る/直すのか、なぜか
2. **決定事項と理由** — 採用した設計・方針と、その根拠
3. **却下された代替案** — 検討したが採らなかった案と却下理由
4. **対象ファイル・シンボル** — 触るべきファイルパス、関数名、既存の類似実装
5. **制約・規約** — このセッションで明示されたプロジェクト固有・セッション固有の制約（実行ハーネスのグローバル規約由来の一般則は、テンプレートの「規律」ブロックへ転記するためここには含めない）
6. **プロジェクト固有の罠** — 実行ハーネスのプロジェクト規約文書（Claude Code では CLAUDE.md と `.claude/rules/`、Codex では AGENTS.md）と docs から、実装時に踏みやすい落とし穴を収集（例: 「worker は dist 実行のため要 `npm run build`」）
7. **検証方法** — テスト・Lint・ビルドの実コマンド
8. **不足している判断点** — 実装指示として曖昧さが残る箇所のリスト（Step 3 の質問候補）

プロンプトに含めるファイルパスとコマンドは、可能な限りファイル探索・読み取り（Claude Code では Glob / Read）と package.json 等の参照で実在を確認する。

完了条件: 8項目すべてについて抽出結果または「該当なし」を確定し、パス・コマンドの実在確認を終えている。項目1（実装対象と目的）が確定できない場合は大原則の fail fast に従い、ここで停止してプロンプトを生成しない。

### Step 2: 実行手段と保存先の確認（1回で2問）

次の2問を1回の提示にまとめて散文提示で確認する。

**問1: 実行手段** — 実行環境で成立する手段だけを提示する: **Workflow と Claude Code Goal は、Claude Code 上で実行している場合のみ選択肢に含める**。それ以外の環境（codex 等）では、新規セッション直実装と codex のみを提示する。codex は、実行環境で codex CLI の存在を確認できた場合（POSIX シェルでは `command -v codex`）のみ選択肢に含める。推奨する手段はセッション内容から次の基準で推定する:

| 手段 | 向いているケース |
|---|---|
| 新規セッション直実装 | スコープが明確で、1セッションの対話的実装で完結する標準的なタスク（Claude Code / codex どちらの新規セッションも宛先にできる） |
| Workflow（マルチエージェント） | 独立したサブタスクに分割でき、並列実行や網羅性（多角レビュー・大規模移行）が効くタスク |
| Claude Code Goal | 長時間かかり、バックグラウンドで非対話に進めたいタスク |
| codex | 仕様が確定済みで、Codex が単体・非対話で実装完走できる粒度まで固まっているタスク |

**問2: 保存先** — 実行環境で成立する選択肢だけを提示する。リポジトリ内にプロンプト置き場の既存慣習（`docs/prompt/` 等）があればそれを推奨する。

- リポジトリ内（既存慣習のディレクトリ。なければ `docs/prompt/`。cwd がリポジトリ配下でない場合はこの選択肢を提示しない）
- OS の一時ディレクトリ（`$TMPDIR`、無ければ `/tmp`）直下
- 実行ハーネスが提供するセッション専用の一時ディレクトリ（Claude Code ではシステムプロンプトで案内される scratchpad ディレクトリ。提供が無い環境ではこの選択肢を提示しない）

完了条件: 実行手段と保存先ディレクトリが確定している。

### Step 3: 不足情報の質問（必要時のみ）

Step 1 で挙げた不足判断点のうち、**選択された実行手段でプロンプトを書くうえで実際に必要なものだけ**を散文提示で質問する。手段確定後に行うのは、必要な質問が手段で変わるためである（例: Goal なら非対話前提のため、保留された判断点にはデフォルト判断の指針を必ず付ける必要があるが、直実装なら軽微な点は新セッションに委ねられる）。

- 1回の提示に最大4問。原則1回、どうしても必要な場合のみ2回まで。
- 推奨案は、コードベースやベストプラクティスから導ける場合に限って示す。
- 不足がなければこのステップは丸ごとスキップする。
- 質問してもユーザーが保留した点は、繰り返し聞かずプロンプトの「未決事項」セクションに明記する。

完了条件: Step 1 項目8の不足判断点のすべてが、回答済み・選択手段では不要・未決事項に送る、のいずれかに振り分けられている（不足が無くスキップした場合はその旨を確定している）。

### Step 4: プロンプト生成・保存

**言語**: プロンプトの言語は、対象リポジトリの既存文書（規約文書・README 等）の言語に従い、判定材料が無ければ対話言語とする。テンプレートの見出しも同じ言語で書く。

**ファイル名**: 保存先ディレクトリに既存のプロンプトファイルがあればその命名慣習に従う（例: `{number}-{description}.md` の連番なら次番号を採番）。慣習がなければ `YYYYMMDD-<内容を表す英語slug>-prompt.md`（日付は実行環境で当日を YYYYMMDD 形式で取得する。POSIX シェルでは `date +%Y%m%d`）。保存先ディレクトリが存在しなければ作成する。算出したファイル名が既に存在する場合は上書きせず、slug の末尾に `-2` 等の連番を付けた別名で保存し、Step 5 の報告でその旨を伝える。

**「規律」ブロックの材料**: 実行ハーネスのグローバル規約文書（Claude Code では `~/.claude/CLAUDE.md` と `~/.claude/rules/`、Codex では `~/.codex/AGENTS.md`）を読み、宛先が読めない前提で再掲すべき一般則（実装の進め方・エラー処理・コミットの方針 等、プロジェクトを問わず適用される規則）を抜き出す。グローバル規約文書が無い環境では、テンプレートに固定で含まれる項目だけを書く。

以下のテンプレートに従って生成する（「未決事項」は該当がある場合のみ。それ以外のセクションは必須）。「起動方法」セクションは、本スキル同フォルダの `launch-methods.md` を Read し、Step 2 で選択された手段の項だけを適用して書く。

```markdown
# <タスクタイトル>

<!-- 生成: YYYY-MM-DD / 元: <プロジェクト名> のセッション / 実行手段: <選択手段> -->

## 目的とゴール

<何を達成するか1〜3文。続けて、検証可能な完了条件を箇条書きで。
「〜を修正する」ではなく「`npx vitest run test/...` が通る」「`/cmd` 実行で〜が出力される」の形>

## 背景・経緯

<新セッションが前提を理解できる最小限の経緯。このファイル単体で完結させる>

## 決定事項と理由

<採用した設計・方針を「決定 / 理由」の対で列挙>

### 却下した代替案

<検討したが採らなかった案と却下理由。再提案・再検討は不要である旨を明記>

## スコープ外

<今回やらないことを明記（隣接リファクタ、関連機能の先回り実装 等）>

## 実装方針・手順

<「ステップ → そのステップの検証方法」の対で記述>

## 対象ファイル

<実在確認済みのパス・シンボル名。必要なら参照すべき既存実装や重要な snippet>

## 規律

<宛先に関わらず、以下の固定項目と、Step 4 で抜き出したグローバル規約由来の一般則をすべて全文で含める（宛先はこのセッションの規約文書を読めない前提）>

- **検証ゲート**: typecheck / lint / test / build を全て緑にしてから完了とする（実コマンドは「検証方法」参照）。
- **完了報告**: 何を・なぜ・影響範囲・実施した検証・未対応/要確認事項を、依頼者との対話言語で報告する。
- **プロジェクト固有の罠**: <Step 1 で収集した罠を列挙。なければこの行ごと省く>
- <グローバル規約由来の一般則を1項目ずつ列挙>

## 制約・規約

<プロジェクト固有・タスク固有の制約のみ>

## 検証方法

<実在確認済みのテスト・Lint・ビルドコマンドと、期待される結果>

## 未決事項

<確定できなかった判断点と、判断を委ねる際の指針>

## 起動方法

<`launch-methods.md` の選択手段の項に従って記述>
```

完了条件（保存前に全項目を確認し、欠けていれば補ってから保存する）: 大原則の3項（捏造禁止・fail fast・自己完結性）を満たし、Step 1 の項目3（却下案）・4（実在確認済みの対象）・7（実在確認済みの検証コマンド）が反映され、テンプレートの必須セクション（「規律」の全項目を含む）がすべて埋まっている。

### Step 5: 報告

以下を最終メッセージで提示し、**自動では何も起動しない**:

1. 保存したファイルの絶対パス
2. 選択手段での起動手順（コピペ可能な形）
3. プロンプトの要点（目的・完了条件・未決事項の有無）を3行程度

完了条件: 上記3項目をすべて含む最終メッセージを提示し、いずれの手段も起動していない。
