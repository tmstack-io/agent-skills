# skill-feedback — 実走行の証跡によるスキル改善

このセッションでスキルを実際に使った結果を**証跡**として収集し、対象スキルの記述に対応付け、**汎化テスト**を通った修正だけを承認後に適用する。入力は、このセッションでしか得られない実走行の証跡である。Step 4 の承認まで、対象スキルを一切書き換えない。

<!-- BEGIN PROSE-PRESENTATION-CANONICAL -->
**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨する選択肢を理由一言つきで明示し（推奨できる選択肢が無い場合は「推奨なし」とその理由を明示する）、ツールを呼ばずターンを終了してテキスト回答を待つ。定型の選択肢でどれも一行で意味が通る場合に限り、空行区切りにせず一行に畳んでよい（推奨案と理由の明示は維持する）。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。
<!-- END PROSE-PRESENTATION-CANONICAL -->

## 適用範囲と汎化の地平

対象スキルの**適用範囲**（汎用／ハーネス専用／プロジェクト専用）が、修正が通用すべき軸——**汎化の地平**——を決める。軸は3つ:

- **案件軸** — 同一プロジェクトの別案件・別セッションでも通用する
- **プロジェクト軸** — 別プロジェクトでも通用する
- **ハーネス軸** — 別ハーネスでも通用する

| 適用範囲 | 引数 | 免除される軸 |
|---|---|---|
| 汎用（既定） | （無指定） | なし（全軸で通用が必要） |
| ハーネス専用 | `--myself` | ハーネス軸（実行ハーネスの固有ツール名・機構への言及は合格） |
| プロジェクト専用 | `--project` | プロジェクト軸（当該プロジェクトの固有名詞・固有知識は合格） |

案件軸はどの適用範囲でも免除されない（今回の案件限りの事情をスキルに焼き付けない）。引数が無い場合の適用範囲の確定手順は Step 0 の「適用範囲の確定」に従う。`--myself` と `--project` は排他で、同時に指定された場合は作業を始めず、どちらの適用範囲で進めるかを散文提示で確認する。

## Step 0: 前提の確認

1. **証跡ゲート**: このセッションのコンテキスト内に、スキルの実行（SKILL.md の読み込みと手順の遂行）の証跡が存在することを確認する（引数で対象が指定されている場合は、まず名前の一致で仮判定し、2 で対象の実体が確定した後に、証跡がその対象のものであることを再確認する）。存在しなければ何も作業せず中止し、「本スキルは実走行の証跡を入力とするため、対象スキルを使ったセッション内で起動する必要がある。テキストだけの静的な査読には skill-refine が使える（未導入なら `npx skills add tmstack-io/agent-skills` で導入できる）」と案内する。実行の存在は確認できるが、実行区間が要約・圧縮に置き換わっていて個々のやり取りを参照できない場合は、参照できる範囲を伝えたうえで「残っている範囲だけで進める」「中止する」の二択を散文提示で確認する。「残っている範囲だけで進める」を選んだ場合は、参照できなかった区間の範囲を Step 4 の提示と Step 5 の報告の冒頭に明記する。
2. **対象の特定**: 引数のスキル名またはパスから対象を特定する。引数が無い場合は、このセッションで直近に使ったスキルを対象候補とする。対象の実体は、まずこのセッションで実際に読み込まれた SKILL.md のパスとする（証跡ゲートで実行を確認済み）。それが特定できない場合は、自スキルの隣（`../<名前>/SKILL.md`）→ 実行ハーネス自身のスキルディレクトリのプロジェクト側 → グローバル側（例: Claude Code は `.claude/skills/` → `~/.claude/skills/`、Codex は `.agents/skills/` → `~/.agents/skills/`。その他のハーネスは、そのハーネス自身のプロジェクト側とグローバル側のスキルディレクトリを同じ順で見る）の順で探す。他ハーネス用のディレクトリは探さない。複数の場所に見つかった場合、および引数無しで候補を推定した場合は、どの絶対パスを対象にするかを散文提示で確認する。確定した対象の SKILL.md とフォルダ内の全参照ファイルを読む。
3. **適用範囲の確定**: 引数（`--myself` / `--project`）があればそれに従う。無指定の場合は候補を次の根拠で推定し、散文提示で確認する（推定のまま黙って確定しない）: プロジェクト側スキルディレクトリにあればプロジェクト専用、対象の手順が特定ハーネス固有のツール名・配置に依存していればハーネス専用、いずれにも当たらなければ汎用。`--myself` の場合は、実行中のハーネスの名称・固有ツール・スキル配置を本文で宣言する。対象の本文が別ハーネス専用を明示している場合（別ハーネスの専用宣言がある、実行ハーネスに無い機能が中核手順に据えられている等）は先へ進まず、その根拠を示して「このまま `--myself` で続行する」「中止する」の二択を散文提示で確認する。
4. **git への態度**: 本スキルが行うのは対象 SKILL.md（と同梱ファイル）の編集までで、コミット等の git 履歴操作は行わない（求められた場合もコミット案の提示まで）。git 管理の判定は、対象ファイルが git に追跡されているか（`git ls-files --error-unmatch <対象パス>` が成功するか）で行う。追跡されていない場合は、Step 5 の適用前に、書き換え対象になりうる全ファイル（SKILL.md と同梱参照ファイル）の複製を OS の一時ディレクトリ（`$TMPDIR`、無ければ `/tmp`）配下へ `<スキル名>-<元のファイル名>.<YYYYMMDD-HHMMSS>` の名前で保存する（複製を書き戻せば適用前に戻せる）。

完了条件: 対象の SKILL.md と全参照ファイルを読み終え、適用範囲が確定し、証跡ゲートを通過し、対象が git 管理下にあるか否かを判定済み。

## Step 1: 証跡の収集

セッションの先頭から現在までの対象スキルの実行区間を走査し、問題事象を次の4分類で列挙する:

1. **逸脱** — SKILL.md の指示が誤解・不履行のまま進んだ箇所
2. **補完** — 手順に規定が無く、ユーザーとの対話で方針を決めて埋めた箇所
3. **介入** — ユーザーが訂正・中断・やり直しを求めた箇所
4. **空振り** — 手順どおり実行したのに結果が期待とずれた箇所

各事象は、セッション内の発生箇所を指せる実際の出来事だけを記録する。スキル本文には入れないが報告には残す項目の置き場を**見送り枠**と呼ぶ（汎化テスト不合格・スキル外要因・出来事に紐づかない改善アイデアの三種が入る）。

完了条件: 4分類すべてについて該当の有無を判定済み（該当なしの分類も明記する）。

## Step 2: 原因の対応付け

各事象を次のいずれかに分類する:

- **原因記述あり** — 対象スキルの特定の記述（SKILL.md または同梱参照ファイルの規定）がその挙動を招いた。該当記述がどのファイルのどこにあるかを、引用とともに示す。
- **規定の不在** — SKILL.md に規定が無かったために起きた。不在の箇所（どの手順のどの分岐か）を特定する。
- **スキル外要因** — 対象の適用範囲では SKILL.md をどう書いても防げない要因（モデルの揺らぎや、免除されない軸の固有事情。例: 汎用スキルにおけるプロジェクト固有の事情）。修正候補にせず、見送り枠に回す。

完了条件: 全事象が3分類のいずれかに割り当て済み。

## Step 3: 汎化テスト

「原因記述あり」「規定の不在」の各事象に修正案を作り、それぞれに汎化テストを適用する。セッション駆動の修正は今回の案件に**過学習**しやすく、このテストが本スキルの品質の要である。判定は「適用範囲と汎化の地平」が定める対象軸（適用範囲が免除しない軸）に対して行う:

- **別場面の想定**: 対象軸ごとに、その軸が指す別の場面を最低1つ具体的に想定し、修正後の記述がその場面でも正しく働く（妨げにならない）と判定できるか。
- **固有事情の混入**: 修正文面が、対象軸の固有名詞・固有事情（今回の案件限りの事情は常に対象）を含まずに書けているか。

全対象軸で両方を満たした修正案だけが合格。不合格の修正案は本文に入れず、「今回限りの事情」として見送り枠に回す。汎化テストの過程で気づいた、特定の出来事に紐づかない改善アイデアは、その旨を明記して見送り枠に入れる（本文には入れない）。

完了条件: 全修正案に合否と判定理由が付いている。

## Step 4: 承認

合格した修正案がゼロ件の場合は承認を求めず、見送り枠と該当なしの分類を含む Step 5 の報告だけを行って終了する。

散文提示で次を提示する:

- 合格した修正案の一覧。各項目は、番号と一行要約の見出し行の下に、「事象（セッションで起きたこと）」「原因（原因記述または規定の不在）」「修正文面（書き換える箇所と、挿入・置換する具体的な文面）」の3つを下位箇条書きとして並べる。
- 見送り枠の一覧。
- 一覧の末尾に、推奨する適用対象を理由一言つきで添え、「適用対象の修正案を返信してください: `全件` / 番号指定（例: `1,3`） / `適用しない`」を提示する。

返信はこの三形のいずれかとして解釈し、解釈できない場合のみ選択肢を散文提示で再掲する。承認された項目だけが Step 5 で適用される。`適用しない` の場合は適用せず、Step 5 の報告のみ行う。

完了条件: 適用する修正案の番号の集合が確定し、その解釈を本文で復唱済み（合格した修正案がゼロ件の場合は、その旨を報告に明記していれば完了とする）。

## Step 5: 適用と報告

1. 承認された全項目について、Step 4 で提示した文面をそのまま対象 SKILL.md（必要なら同梱ファイル）へ適用する。Step 0 で git 追跡外と判定した場合は、書き換えの前に Step 0 の 4 の複製を保存する。ファイルの新設・削除・ディレクトリの改名を伴う修正は実施せず、実行手順として 2 の報告に載せる。
2. 報告を提示する: 適用した修正・承認されなかった修正案・見送り枠の全件。このうちプロジェクトに残す価値がある知見には、記録先候補（プロジェクトのエージェント向け規約文書（Claude Code では CLAUDE.md、Codex では AGENTS.md）・実行ハーネスの記憶機構・プロジェクトの docs 等）を一言添える（本スキルからは書き込まない）。
3. 適用後の文章品質・構成の磨き込みが必要そうなら、skill-refine の利用を一言案内する（導入手順の文言は Step 0 の 1 と同じものを使う。本スキルからは起動しない）。

適用後の整合確認で不整合を検出した場合は、承認済みの文面の範囲で直せるならその範囲で直し、直すために承認外の書き換えが要るなら適用を止めて Step 4 と同じ形で追加の修正案として提示する。

完了条件: 承認された全項目が適用済みで、適用した文面が Step 4 で提示した文面と一致しており、適用後の全文について frontmatter（name / argument-hint）とディレクトリ名・引数仕様が一致し、同じ意味の二箇所書きが無く、各ステップの完了条件が残り、参照先の記述が壊れていないことを確認済みで、報告を提示済み（git 追跡外の場合は全複製の絶対パスを報告に含む）。適用対象がゼロ件の場合は、その旨を報告に明記していれば完了とする。
